# Контракт

Владелец поручил ограничить высоту окна ввода сообщений (promptbox): весь блок — текст редактора, вложения и тулбар — занимает не более 1/3 рабочей области экрана, чтобы верхние ~2/3 оставались под диалог для чтения. Реализация в существующем compact-ui (плагин «места на экране»): сворачивание списков, скрытие навигации и прочие space-оптимизации уже живут там. Новый плагин не создавать; BB/core, тема и модели не меняются.

## Требования

1. **Кеп на всю карточку** `[data-app-composer]` (в 0.49 композер — div, не `<form>`): высота ≤ ⌊(innerHeight − 96px) / 3⌋, где 96px — штатный chrome вне рабочей области (page header + status bar). Не относительная высота всего экрана, а именно рабочей области чата.
2. **Переполнение поглощает скролл-зона редактора**: ей выставляется inline `max-height` = текущая высота − переполнение. Селектор — `div.overflow-y-auto:has(.ProseMirror)`, а в BB 0.49, где этой обёртки нет, — первый предок `.ProseMirror` с computed `overflow-y: auto|scroll` (fallback — сам ProseMirror). Тулбар, строка вложений и кнопки никогда не обрезаются и не уезжают за пределы формы.
3. **Развёрнутая очередь сообщений — ровно min(N, 3) строки.** Скролл-зоне очереди `[data-queued-messages-scroll]` и её flex-обёртке `[data-queued-messages-scroll-frame]` выставляется inline `max-height` = измеренная высота первых min(N,3) строк `[data-queued-message-row]` с зазорами (bottom последней видимой − top первой): 1 сообщение — 1 строка, 2 — 2, 3 — 3, 4+ — 3 строки и внутренний скролл. Фрейм клампится тоже — иначе flex-элемент держит карточку раздутой с мёртвым местом. Правило применяется всегда, не только при переполнении кепа. Свёрнутая панель остаётся смонтированной с нулевой высотой — её стиль не трогаем. Панель ищется внутри карточки и в её родителе (приоритет — кандидатам внутри карточки, отсоединённые копии отбрасываются). Логика очереди не зависит от селектора редактора: в BB 0.49 `div.overflow-y-auto:has(.ProseMirror)` внутри карточки отсутствует — скролл редактора определяется по computed `overflow-y` вверх от `.ProseMirror` (fallback — сам ProseMirror).
   **Рост панели:** фрейм очереди — `flex-1` и реальная высота ему отрезается бюджетом родителя, поэтому одного `max-height` на скролл мало: если до желаемой высоты не хватает места, каждому предку скролла до карточки выставляется `min-height` = целевая высота ребёнка + реальный слак предка на прочих детей (слак = высота предка − высота ребёнка). Дельта по цепочке не суммируется — расчёт идемпотентен, мёртвого зазора не возникает. `min-height` применяются reconcile-проходом (снимаются только лишние, переписываются только изменённые) — собственные записи не самовозбуждают наблюдатель; триггерами перемера служат childList и изменения `aria-hidden`/`inert`/`class`/`style` — переключение состояния хода (idle↔active) хост несёт именно классами, иначе протухший `min-height` оставлял мёртвый зазор до следующей порции мутаций. При N ≤ 3 высота берётся из `scrollHeight` скролла (точная, с паддингами); при N > 3 — измеренный спан первых трёх строк.
4. **Одно правило для desktop и mobile** без media-query: развёрнутый мобильный композер использует тот же DOM (`group/promptbox`), кеп считается от того же вьюпорта; свёрнутый мобильный инпут (~50px) под кеп не попадает и не трогается.
5. **Стабильность, без осцилляции**: решение о кепе принимается по `scrollHeight` (натуральной высоте контента), а не по текущей обрезанной высоте. Пока контент велик — кеп держится; когда текст удалён и форма вернулась бы под кеп сама — inline `max-height` снимается, редактор восстанавливает естественную высоту.
6. **Полы**: не бороться ниже штатного inline `min-height` редактора (~103px) — нижний предел 104px; у очереди нет пола — показывается ровно min(N,3) строк. Сверху остаётся штатный потолок BB 312px: наш кеп срабатывает только когда он меньше.
7. **CSS-фолбэк без `!important`**: статическое правило `max-height: min(312px, calc(33svh - 56px))` на `[data-app-composer]` в `lib/sidebar-controls.ts` убирает гонку до монтирования JS; inline-стиль JS-капа его корректно перекрывает.
8. Поведение BB не меняется: отправка, расписание, вложения, model picker, focus/keyboard, очередь сообщений. При отсутствии известной разметки — fail-open, интерфейс остаётся штатным.

## Проверка и выпуск

- Unit: полный набор тестов compact-ui, typecheck, `bb plugin build` — зелёные (134 теста). jsdom без ResizeObserver — монтирование деградирует без исключения.
- Chromium живьём: desktop 1440×1050 и mobile 390×844 (развёрнутый композер), длинный текст ~80 строк и симулированный блок вложений ~90px. Измеренная высота формы = ровно 0.33 рабочей области в обоих вариантах, редактор скроллится внутри, тулбар виден.
- Откат: удаление content script `composer-cap` и CSS-правила; настройки плагина не затрагиваются.
