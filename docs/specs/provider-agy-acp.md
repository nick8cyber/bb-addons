# provider-agy — миграция на ACP-транспорт

Мост `bb-plugin-provider-agy` пересаживается с нативного `agy --output-format stream-json` на `agy acp` поверх generic-моста `experimental_acpProviderBridge` (SDK `@get-bb/plugin-sdk`). Причина: stream-json не отдаёт ни мысли модели, ни аргументы/результаты тулов — в треде видны только пустые `agentMessage` и имя тула. По ACP generic-мост сам переводит `agent_thought_chunk` → `item/reasoning/textDelta`, `agent_message_chunk` → `item/agentMessage/delta`, `tool_call`/`tool_call_update` → `toolCall`/`commandExecution` с аргументами и выводом.

Живой прогон `acp-agy` (customAgents) подтвердил: мысли стримятся дельтами по ходу хода, тул-вызовы несут команду/путь/вывод/exitCode, существующий токен `~/.gemini/antigravity-cli` подходит без перелогина, `session/load` читает разговоры, созданные в stream-json.

Решение и отклонённые варианты — [ADR 0021](../adr/0021-provider-agy-acp-transport.md). Аудиты: дизайна — `thr_sjeifftbdr`, спеки — `thr_zr4e7sjrhv`; все находки учтены ниже.

## 1. Архитектура: обёртка + транспортный shim

Два слоя перехвата, потому что `handleLine` видит только границу «демон BB ↔ мост», а трафик `session/prompt`/`session/update` живёт на приватном stdio-пайпе между generic-мостом и процессом `agy acp`.

- **Обёртка** (`src/acp-wrapper.ts`, реэкспорт через `host.ts` — чистый фасад): объявляет `experimental_providerBridge`, оборачивает `experimental_acpProviderBridge`. Делегирует `handleLine` и `onClose` (метода `start` у generic-моста нет — `start(context)` реализует сама обёртка: инициализация `accountsDir`, леджера, пула). Перехватывает строки в обе стороны на границе демона.
- **stdio-shim** (`src/acp-shim`, подставляется в `acpLaunchSpec.command` вместо `agy`): прозрачный NDJSON-ретранслятор, спавнит реальный `agy acp`, пробрасывает stdin/stdout и параллельно снифит JSON-RPC — ответ `session/prompt` (`result.usage`, текст ошибки) и нотификации `session/update` (`tool_call_update` с текстом отказа) — и пишет события в side-channel (fd/файл), который читает обёртка. В обратную сторону shim правит запросы `session/new`/`session/load`: инъектит `params.disableBuiltInTools` (см. §9). Паттерн — `wrapper-script.ts` у rawizhere. Какой именно бинарник спавнит шим, решает реестр установок ([provider-agy-installs](provider-agy-installs.md), ADR-0033): путь бинарника установки аккаунта передаётся через `AGY_SHIM_REAL_BIN`; `resolveAgyCommand` остаётся только «неявной единственной установкой» при отсутствии `agy-installs.json`.

Generic-мост отвечает за: JSON-RPC, `session/new`/`load`/`prompt`/`cancel`/`set_mode`, перевод session/update → thread-дельты, permissions, steer. Обёртка отвечает за всё проприетарное ниже.

`server.ts` провайдера обновляется: `permissionModes: ["full","accept-edits"]` и `experimental_bridgeOptions` (`acpLaunchSpec`, `acpDialect: "generic"`) — сейчас заявлен только `"full"`, без правки демон не даст сменить режим. Из первоначального набора `["full","default","accept-edits","plan"]` оставлены два: generic-мост маппит режимы через `permissionCli.insertAfterArgs`, и доставляемы на этом диалекте только `full` и `accept-edits`; заявленный, но недоставляемый режим (проверено на `auto`) отклоняется демоном на `thread.start` («does not support permission mode») — декларируем только то, что реально доезжает.

## 2. Пул аккаунтов и изоляция

- Изоляция аккаунта — **только** флаг `--gemini-dir <account-home>/.gemini` с абсолютным путём в `acpLaunchSpec.args` при `thread/start`/`thread/resume`. Флаг `--app-data-dir` не передаётся: в agy 1.5.3 он резолвится относительно `--gemini-dir` и с абсолютным путём ломает стор. `HOME` не подменяется (остаются `~/.gitconfig`, `~/.ssh`; с оговоркой: служебная проба `agy models` (§2.3 п. 1) задаёт аккаунт через `HOME`, потому что `--gemini-dir` есть только у `agy acp`).
- Прокси аккаунта (`accounts/<label>/proxy`) — через `HTTP(S)_PROXY` в `acpLaunchSpec.env`.
- `src/accounts.ts` переезжает с одним дополнением: в него переносятся `isAccountIneligible` и `ineligibleBreaker` из `src/provider-bridge.ts` (~L484–509, ~L787–805) — парковка аккаунтов с капчей/регион-блоком и предохранитель от массовой парковки. Остальное без изменений: `listAccounts`, леджер `accounts-state.json`, `pickAccount` (тир по `priority`, LRU внутри тира, исключая сгоревший и `priority: 0` — см. §2.2), `markAccountCooldown`, `writeAccountHome`. Тесты пула обновляются под новые точки входа.
- Sticky: `providerThreadId` → аккаунт записывается на первом `thread/identity`; `thread/resume` берёт аккаунт-владельца из локальной мапы бесед (см. §2.1).

### 2.1 Локальное состояние инстанса (инцидент 11.11, тред `thr_vff52cr5vy`)

`accounts-state.json` — общий файл пула: инфраструктурный keeper синкает его односторонне владелец→спутник (~30 с + inotify; спутник — второй bb-инстанс на том же пуле). В нём смешаны два разных по природе вида данных: общие метки аккаунтов и per-instance данные — пины бесед и метки, которые спутник ставит по своим ошибкам. Любая запись спутника затирается следующей синхронизацией: его пин `providerThreadId→account` исчезает, `thread/resume` не находит владельца → запуск на дефолтном HOME («direct») → `not_found: trajectory not found` — хотя траектория жива в копии HOME нужного аккаунта на том же инстансе. Тем же механизмом стираются cooldown от 429, `lastUsedMs` и парковки (auth-dead/eligibility), выставленные спутником, — до истечения они не доживают.

Леджер разделяется по природе синка. Общий `accounts-state.json` хранит только `accounts` (метки пула — синкаются как раньше). Локальное состояние инстанса — файлы рядом в `bridge-data`, про которые keeper не знает и не трогает:

- `conversations-state.json` — `{ "conversations": { providerThreadId: accountLabel } }`. Пин пишется на `thread/identity` и живёт только на инстансе-создателе: resume всегда происходит там же, поэтому пин — локальное знание по построению. `loadLedger` возвращает `conversations` = union(legacy `accounts-state.json.conversations`, локальный файл; локальный побеждает) — одношаговая миграция, накопленные пины не теряются; `saveLedger` персистит мапу в локальный файл и больше не пишет `conversations` в общий (поле пропадает при первой записи). Миграция нетерпеливая (eager): если `loadLedger` видит в общем файле legacy-пины, а `conversations-state.json` ещё нет — он немедленно записывает их в локальный файл. Иначе сценарий «владелец обновился первым и сохранил очищенный общий, а спутник был idle» стирал бы пины спутника первым же синком keeper до его первой записи.
- `accounts-overlay.json` — `{ "accounts": { label: entry } }` + `writtenMs` на запись: тень меток, поставленных ЭТИМ инстансом (cooldown, lastUsed, ineligible, parkedReason). Каждая точка, где код мутирует метку аккаунта, дублирует её и в общий леджер (поведение одиночного инстанса не меняется), и в свой overlay — в overlay попадают только метки, выставленные локально, иначе снятие метки общей стороной никогда не доедет. `loadLedger` возвращает эффективные метки = merge(shared, overlay): `cooldownUntilMs`/`lastUsedMs`/`ineligibleAtMs` — max обеих сторон (breaker массовой парковки обязан видеть самый свежий штамп); `parkedReason`, `lastError` — со свежей стороны. Overlay-запись применяется, пока `overlay.writtenMs >= shared.lastUsedMs` по аккаунту; как только общая сторона видит более свежее использование или правку, тень снимается целиком — так и снятие парковки владельцем доезжает до спутника, а зазор между её 429-меткой и приездом общей метки самозаживляется (перегретый аккаунт сгорит и у владельца — его метка приедет синком).
- `accounts-models.json` — каталоги моделей аккаунтов (§2.3 п. 1).
- `threads-state.json` — соответствие threadId → { cwd, providerThreadId, atMs } для восстановления сессии после перезапуска обёртки (§12.6; поле `atMs` — ревизия 14, PLUG-306).

Размер overlay ограничен числом аккаунтов пула; истёкшие кулдауны умирают сравнением с `now` при чтении — сборки мусора не нужно. Запись — тот же temp+rename в том же каталоге, пофайлово (cross-file атомарности нет: потерянная при креше метка восполняется следующей записью). API `accounts.ts` для вызывающих не меняется: `loadLedger`/`saveLedger`/`conversationAccount`/`rememberConversation` и метки возвращают уже слитое состояние — stream-json мост (`provider-bridge.ts`) получает то же поведение бесплатно. Handoff треда на другой инстанс теряет пин — поведение как при промахе сегодня (запуск на дефолтном HOME, честный `trajectory not found`), новых деградаций нет.

Оба транспорта делят один леджер: `cliproxyRelayDataDir` в `provider-bridge.ts` — это тот же `context.dataDir` (`bridge-data`), имя осталось от cliproxy-релея; «отдельный релейный леджер» физически отсутствует и покрыт одной схемой. Keeper переносит **только** `accounts-state.json` (+ oauth-токен и `proxy` внутри `accounts/<label>/`): локальные файлы он не знает и не затирает. Инвентарь точек леджера:

- `acp-wrapper.ts`: pick ~L1090/L1527, проверки кулдауна ~L1515/L1641, парковка ~L1557–1593, `markAccountUse` ~L1727/L2376/L2490, кулдаун 429 ~L1748, `rememberConversation` на `thread/identity` ~L2039, `conversationAccount` на `thread/resume` ~L2452, причина ротации ~L2556.
- `provider-bridge.ts` (stream-json, тот же файл): pin-read ~L1037/L3126, cooldown+use ~L1115–1145, парковка+use, load ~L1652, `rememberConversation`+use ~L2110–2113, pick ~L2871, use ~L3030.

Merge в `loadLedger` стирает происхождение меток: по загруженному леджеру `saveLedger` не отличит «свою» метку от приехавшей общей, и слепое копирование в overlay вечно продлевало бы чужие метки. Поэтому мутации идут только через хелперы `accounts.ts`, которые попутно помечают метку в неперсистируемом `dirtyLabels` леджера: `markAccountUse`, `markAccountCooldown` и новый `markAccountIneligible(ledger, label, { parkedReason? })` — прямые записи полей (`ineligibleAtMs`/`parkedReason` в `acp-wrapper.ts` ~L1576–1578 и `ineligibleAtMs` в `provider-bridge.ts`) заменяются на него, без хелпера метки в overlay не ставятся. `rememberConversation` метку не трогает — он помечает `providerThreadId` в отдельном `dirtyPins` (pin-only save не должен бампить `writtenMs` overlay); `ledgerEntry` остаётся внутренним — будущий экспорт без пометки грязным запрещён. `saveLedger` пишет в overlay только записи из `dirtyLabels` (+`writtenMs`); при пустом `dirtyLabels` (например, вызов ради `rememberConversation`) файл overlay не перезаписывается — холостых `writtenMs`-бампов нет. Порядок файлов в одном вызове: сначала `conversations-state.json` и `accounts-overlay.json`, затем общий — при креше между ними общий файл ещё хранит старые данные, а локальные уже новые (union на чтении ничего не теряет).

Параллельные писатели одного инстанса (wrapper поднимается на каждый ход) пишут load-modify-save и могут стереть чужую свежую запись. Для `conversations-state.json` это закрывается merge-on-save по **грязным ключам**: перед rename `saveLedger` перечитывает файл с диска и поверх пишет только `dirtyPins` (не весь слепок — иначе stale-леджер вернул бы чужой перепин, воспроизведено аудитом). Для overlay — merge с диска **по полям** той же метки, иначе свежий `writtenMs` со stale-содержимым затирает соседний кулдаун (блокер аудита): `cooldownUntilMs`/`lastUsedMs`/`ineligibleAtMs` — max с дисковой записью; `parkedReason`/`lastError` — с более свежей записи, где «свежесть» считается от штампа overlay-записи **на момент нашего load** (`overlayStamp` в леджере): дисковая запись свежее нашей точки зрения побеждает — иначе stale-писатель стирает `parkedReason`/`lastError` соседа каждым `markAccountUse` (консёрн повторного аудита; проверка «дисковый `writtenMs` > now» мёртвая — на одной машине он всегда ≤ now). Строки выбираются по одному штампу на запись (per-record): мутация одной строки бампит «свежесть» обеих — принято, окно равно латентности save (зафиксировано в ADR-0025). **Дисковая запись участвует в merge только пока её тень применима** (`disk.writtenMs >= shared.lastUsedMs` по уже перечитанному дисковому общему файлу): снятая тень считается отсутствующей — иначе `max()` воскрешает мёртвый кулдаун под свежим `writtenMs` и каждый lift самоотменяется первым же dirty-save (блокер финального аудита). Отсутствующий `writtenMs` на диске считается 0; в overlay `lastError` сериализуется всегда, включая `null` — `null` свежей стороны это значение, а не «отсутствует». Остаточное окно read→rename (микросекунды) принимается — класс тот же, что у общего last-writer-wins.

Прочее состояние каталога: `accounts-parked/` — операторская книга (пустые маркеры ручной парковки/снятия по ADR-0002): код её не читает и не пишет, keeper не синкает — локальность бесплатно, в схему не входит. Внешние писатели общего файла — keeper (переносит как есть) и оператор. Ручное снятие парковки правится в протоколе и различается по стороне: **на владельце** «`cooldownUntilMs` = 0 **и** `lastUsedMs` = текущее время» в общем файле (либо прогон одного хода — `markAccountUse` сам поднимет `lastUsedMs`, и тень умрёт синком); **на спутнике** правка общего бесполезна (keeper вернёт версию владельца за ~30 с, и тень воскреснет) — путь оператора: удалить запись метки из `accounts-overlay.json` (или файл целиком). Внешние читатели: `bb-plugin-usage-pro` читает из общего файла только `accounts[label].cooldownUntilMs` — перенос `conversations` его не затрагивает.

Границы схемы (зафиксированы, не баги): тень снимается ЛЮБОЙ свежей shared-активностью на метке — спутник-специфичный кулдаун (свой egress/proxy) может умереть раньше `untilMs` от `markAccountUse` владельца; это цена одностороннего синка без метки «когда общая сторона писала» (ADR-0025). Overlay-записи на метку, которой нет ни в общем файле, ни в `accounts/` (аккаунт удалён), — «призраки»: `saveLedger` их вычищает, чтобы не утекали в общий файл и дальше синком. Детект призрака идёт по дисковому общему файлу + `accountsDir` и выполняется **безусловно перед записью общего файла** — не только при dirtyLabels: pin-only save тоже сливает в общий merged-view, иначе призрак уезжает синком и воскрешает удалённый аккаунт (консёрн аудита). `loadLedger` при применившейся тени берёт `parkedReason` = overlay ?? shared (fallback для диагностики — парк общей стороны виден, пока overlay своей причины не ставил). Откат версии до этой схемы теряет все пины (общий файл их больше не несёт) — принимается, откат идёт вместе с файлами. `*.pid.tmp` при креше копятся — тот же класс, что прежний temp+rename, GC не нужен. Eager-миграция срабатывает и при битом/пустом `conversations-state.json`, если legacy-пины им не покрыты — окно «load → wipe → креш до save» сокращается до микросекундного.

Проверка: харнесс `harness-pool.mjs` по умолчанию прогоняется на stream-json (явный `AGY_TRANSPORT ??= "stream-json"` в голове файла) — новая сессия стартует на выбранном аккаунте (HOME = дом аккаунта, `--conversation` на resume); выбор аккаунта на ACP и `--gemini-dir` покрыты `harness-acp.mjs`; `thread/resume` возвращается на аккаунт-владельца.

### 2.2 Приоритет аккаунта (ранжирование пула)

Порядок выбора в пуле задаётся числовым приоритетом — в дополнение к LRU, не вместо:

- `accounts[label].priority` в `accounts-state.json` — целое ≥ 0; отсутствует, не число, дробное или < 0 → дефолт `10`. Поле **общее** (shared-owned): живёт только в общем файле, задаётся оператором правкой на владельце (тот же атомарный temp+rename, что и прочие ручные правки) и доезжает до спутников обычным keeper-синком — overlay его не несёт и merge §2.1 не затрагивает. При записи общего файла `saveLedger` берёт `priority` из дискового `accounts-state.json`, если там есть запись метки (правка или удаление оператором не перетирается stale-леджером); если записи на диске нет — пишется значение из памяти.
- `priority: 0` — аккаунт не выбирается **никогда** (выключен из ротации без кулдаунов и парковки). Затронут только НОВЫЙ выбор: пины бесед, `thread/resume` на владельце и ручной возврат работают как раньше.
- `pickAccount`: из кандидатов (не `excludeLabel`, `priority > 0`) берётся высший `priority` среди **доступных** (кулдаун ≤ now); внутри одного приоритета — тот же LRU по `lastUsedMs`, тай-брейк `label`. Т.е. высший тир обслуживается кольцом LRU; более низкий тир вступает только когда ВСЕ аккаунты тиров выше охлаждены — это и есть «резервный» класс. Когда охлаждён весь пул, прежний фолбэк «окно откроется раньше всех» применяется внутри высшего присутствующего тира (не среди всех), `priority: 0` в фолбэк не входит.
- Если у всех кандидатов `priority: 0` — `pickAccount` возвращает `null` → сессия не закрепляется за аккаунтом пула и, как при пустом пуле, идёт через cliproxy-релей (если настроен) или direct-режим на дефолтном HOME.
- Ротации (квота/ineligible/auth-dead) выбирают сиблинга тем же `pickAccount` — резервный тир подхватывает выгоревший пул автоматически; `markAccountUse`/`markAccountCooldown`/парковки приоритет не трогают.
- Обратная совместимость: пул без единого поля `priority` ведёт себя как сегодня (все в тире 10, чистый LRU).

Проверка: кейсы в `harness-pool.mjs`/`harness-local-state.mjs` — высший тир выбирается первым; равные приоритеты идут по LRU; при охлаждённом высшем тире выбирается низший; `priority: 0` не выбирается даже будучи единственным свободным (фолбэк «весь пул охлаждён» его тоже пропускает); аккаунт без поля получает дефолт 10; выбор низшего тира пишет `markAccountUse` и участвует в LRU своего тира.

### 2.3 Возможности аккаунта и выбор по модели (ревизия 13.2, ADR-0030)

Аккаунты пула бывают разных тарифов, и набор моделей у них разный. До ревизии 11 аккаунт выбирался до того, как становилась известна модель, а каталог моделей снимался с одного аккаунта: модель, которой у закреплённого аккаунта нет, падала с `Unknown model ID`. Правила ниже это закрывают. Тарифы и имена моделей в коде не зашиваются — источник истины один: что отвечает родной `agy models` под каждым аккаунтом.

1. **Каталог аккаунта.** Для каждого аккаунта с `priority > 0` обёртка хранит список семейств моделей, полученный родной командой `agy models`, запущенной с окружением `HOME=<home>` аккаунта (флаг `--gemini-dir` есть только у подкоманды `agy acp`; `agy --gemini-dir … models` печатает справку и выходит с кодом 2 — так было до ревизии 13.2, и каталоги не заполнялись). Тот же способ — у прежнего пути §8 (`queryAgyModels`). Неуспех пробы (код выхода ≠ 0, пустой stdout, разбор не дал моделей) пишется в `acp-wrapper.log` одной строкой: аккаунт, код выхода, первые 200 символов stderr без токенов (семейство — id после снятия суффикса усилия, как в §8). Файл — `accounts-models.json` в каталоге данных плагина: `{ accounts: { <label>: { raw: [{id, displayName}], families: [..], unsupported: { <family>: <atMs> }, atMs } } }`. Файл локальный для инстанса (как файлы §2.1): keeper его не синхронизирует. Срок жизни записи — тот же, что у кэша моделей (6 ч). Обновление — лениво, не больше двух запусков `agy models` одновременно; пустой ответ или ошибка не затирают прежнюю запись. **Устаревшая запись остаётся пригодной для выбора, пока её не заменит успешный опрос: истечение TTL только ставит новый опрос в очередь, но не превращает аккаунт в «неизвестный».** **Не опрашиваются:** аккаунты с `priority = 0`; аккаунты с любым `parkedReason` (в т.ч. `tos-disabled`, `auth-dead`); аккаунты, чей кулдаун закончится позже срока жизни записи (`cooldownUntilMs − now > 6 ч`, например 24-часовая парковка eligibility): опрос до конца кулдауна устарел бы раньше, чем аккаунт вернётся. **Троттл:** на метку хранится в памяти время последней попытки опроса (`lastProbeAtMs`); повторная попытка не ставится раньше чем через 30 минут после прошлой (`MODEL_PROBE_MIN_INTERVAL_MS`), а успешная запись — раньше истечения TTL — упавший или пустой опрос не должен запускать `agy models` на каждый ход.
2. **Сводный каталог (`model/list`)** — объединение `raw` всех аккаунтов с `priority > 0` и **без `parkedReason`** (модель припаркованного аккаунта — tos-disabled/auth-dead — в пикер не попадает: она всё равно падала бы «not offered»), по id (первое встреченное `displayName`); выбор семейства по умолчанию и лестницы усилий — как в §8. Дисковый кэш `acp-models-cache.json` хранит уже объединённый результат. Пока нет ни одной записи каталога аккаунта, действует прежний путь §8 (один запрос `agy models`, затем холодный ACP).
3. **Подходит ли аккаунт для модели.** Модель сессии — семейство из `resolveModelSelection`. Аккаунт подходит, если семейство есть в его `families` и не отмечено в `unsupported` свежее срока жизни. Аккаунт без записи каталога (ещё не опрошен) считается подходящим, но выбирается только когда среди доступных нет аккаунта с известной поддержкой. Модель не задана (`acp-default`) — подходят все.
4. **Выбор с учётом модели — в четырёх точках.** `pickAccount` получает модель и каталог и оставляет в кандидатах только подходящие; дальше — прежние правила §2.2 (высший `priority` среди доступных, LRU, фолбэк «окно откроется раньше»), но уже внутри подходящих.
   - `thread/start`: модель разбирается из `options` **до** выбора аккаунта.
   - Ротация §3 (квота, ineligible, auth-dead, tos-disabled): сиблинг ищется только среди подходящих для модели сессии; ожидание и `resetsAt` для `provider.rateLimits` считаются по подходящим.
   - `turn/start` со сменой модели и `thread/resume`: если аккаунт сессии для новой модели не подходит — сначала автомат §3 пп. 2–3 на подходящем аккаунте (причина `model`, `sessionReplaced` с reason «the session's account does not offer the selected model»), затем ход. Кулдаун и парковка на прежний аккаунт при этом не ставятся.
   - Отказ в полёте: ответ `Unknown model ID` / `not available for the current authentication method` на `session/set_config_option` или `session/prompt` — причина `model`: семейство записывается в `unsupported` аккаунта, затем та же ротация на подходящего. Это не квота: кулдаун не ставится.
5. **Подходящих нет.** Ни один аккаунт пула модель не предлагает — ход падает честной ошибкой «model <family> is not offered by any pool account» без ротации, кулдаунов и ухода на аккаунт без модели. Подходящие есть, но все в кулдауне — прежняя ветка §3 «остыл весь пул» (rateLimits blocked до ближайшего `resetsAt` среди подходящих).
6. **Дорогие аккаунты — через `priority`, без отдельного механизма.** Аккаунту старшего тарифа оператор ставит `priority` ниже, чем у остальных (например 5 против 10). Тогда для модели, которую предлагают и обычные аккаунты, он вступает, только когда все обычные в кулдауне (§2.2), а для модели, которая есть только у него, он единственный кандидат и `priority` остальных роли не играет. Новые треды возвращаются на обычные аккаунты, как только хотя бы один освободился; уже закреплённый тред остаётся на своём аккаунте (sticky §2).
7. **`tos-disabled`.** Ответ Google «This service has been disabled in this account for violation of Terms of Service» — отдельная причина, не квота, не eligibility и не auth-dead. Аккаунт паркуется сразу и без срока (`cooldownUntilMs` — далёкое будущее, `ineligibleAtMs`, `parkedReason: "tos-disabled"`), автоповторов на нём нет. Предохранитель массовой парковки §2 к этой причине не применяется **в обе стороны: `tos-disabled` не считается в окне `checkIneligibleBreaker` и не удерживается открытым предохранителем** (бан аккаунта — не вина egress). Дальше — ротация на подходящего сиблинга (`sessionReplaced` с reason «the session's account was disabled by Google (Terms of Service)») или честный фейл, если подходящих нет. Снятие парковки — только ручной правкой оператора. Если **все** аккаунты пула припаркованы (любой `parkedReason`), даже запрос без модели (`acp-default`) падает честной ошибкой, а не уходит молча в direct-режим на дефолтный HOME. То же на `thread/resume`: если аккаунт сессии припаркован и подходящего сиблинга нет, resume падает той же честной ошибкой **без запуска `agy`** — припаркованный аккаунт не трогается ни одним путём. Пути компакции при отказе с причиной `tos-disabled` также паркуют аккаунт по ней и уходят на подходящего сиблинга или честную ошибку (см. п. 11, ревизия 14, PLUG-306).
8. **Что не меняется.** Кулдаун остаётся один на аккаунт, не по группе моделей; `priority`, sticky, overlay и синк §2.1–2.2; транспорт `AGY_TRANSPORT=stream-json`.
9. **Холодный старт: сначала каталоги, потом выбор (ревизия 13, по живому тесту 18.11).** Если ни у одного доступного аккаунта нет записи каталога, где семейство модели есть, а у части аккаунтов записи нет вовсе (первый запуск, сброс файла) — `pickAccount` для этой модели **ждёт** опроса каталогов этих аккаунтов (ждать нужно любой уже запущенной, стоящей в очереди или только что поставленной пробы такого аккаунта — независимо от их числа, хоть одна, хоть десять) родным `agy models` (не больше двух параллельно, общий предел ожидания 30 с; троттл и исключения п. 1 действуют) и только потом выбирает. Перебор аккаунтов «наугад» запрещён: живой тест показал, что без этого тред на модели старшего тарифа за 14 с открыл сессии на всех десяти обычных аккаунтах подряд — лишние обращения к Google и риск для аккаунтов. Истёк предел ожидания, а подходящего так и нет — честная ошибка п. 5, без ротации.
10. **Предел ротации по причине `model`.** Отказ `Unknown model ID` / `not available` в полёте (п. 4) переводит тред не больше чем на **один** следующий аккаунт и только если у него модель есть в свежем каталоге. Иначе — опрос каталога отказавшего аккаунта (если троттл позволяет) и честная ошибка п. 5. Цепочка «отказ → следующий наугад → отказ» запрещена.
11. **`validation-required`.** Ответ Google `403 PERMISSION_DENIED`, `reason: VALIDATION_REQUIRED` («Verify your account to continue») — отдельная причина, не квота и не ToS: аккаунту нужна ручная проверка владельцем в браузере. Аккаунт паркуется с `parkedReason: "validation-required"` (без срока, без автоповторов, вне предохранителя массовой парковки, вне сводного каталога и опросов — как `tos-disabled`); в лог обёртки пишется ссылка на справку Google без токенов из `validation_url`. Тред — на подходящего сиблинга (`sessionReplaced`, reason «the session's account needs Google account verification») или честная ошибка «account <label> needs Google account verification». Текст `⚠ Verification Required` не должен уходить пользователю как ответ модели. **Как распознаётся (ревизия 13.1, ревизия 18):** в ошибках (`provider.error`, ответ JSON-RPC, ошибка `thread/start` — в том числе внутреннего старта на сиблинге при ротации, `resume` и повторной сборке сессии) — по `reason: VALIDATION_REQUIRED` или «Verify your account to continue»; в тексте ответа модели — **только** точная форма agy: агентское сообщение, которое после обрезки ведущих и хвостовых пробелов и переводов строк начинается с `⚠ Verification Required` и ничем содержательным не продолжается (одна строка). Упоминание этих слов внутри обычного ответа модели (цитата, разбор ошибки) парковку не вызывает; проверяется только текущее сообщение текущего хода, без хвоста прошлых ходов. Буферизация префикса `⚠` (включая `"⚠ "`, `"⚠ V"`, `"⚠ Verification"`), удержание `item.textClose` и сброс состояния при отмене работают по общим правилам п. 13 (ревизия 18). Ответ eligibility с тем же текстом тоже означает ручную проверку и паркуется как `validation-required` (бессрочно), а не как 24-часовой `ineligible`. Снятие — ручной правкой оператора после проверки.
    - **Eligibility-отказ с просьбой или ссылкой проверки (ревизия 15, решение владельца 19.11, PLUG-332).** Любой отказ по допуску, в тексте которого есть просьба проверить аккаунт (`verify your account` — в том числе без «to continue») или ссылка `accounts.google.com`, приравнивается к `validation-required`: «это требует авторизовать через браузер», поэтому парковка бессрочная, автоповторов нет, снятие вручную. Метка — `parkedReason: "validation-required"` + `ineligibleAtMs` + `lastError` и **без `cooldownUntilMs`**: сам `parkedReason` выводит аккаунт из выбора навсегда, конечного срока у парковки нет. В лог обёртки — строка со ссылкой проверки владельцу без токенов. Разбор одинаков во всех путях, где причины различаются: отказ хода или старта, внутренние старты на сиблинге (ротация, `thread/start`, `resume`, повторная сборка), компакция, пробник моделей и stream-json мост. Предохранитель массовой парковки проверяется **до** такой метки — сработал, аккаунт не паркуется (массовый отказ не должен бессрочно класть пул); сама метка `validation-required`, как и все бессрочные парковки, в счётчик предохранителя не входит. Eligibility-отказ без просьбы/ссылки проверки (регион и общий отказ) — прежний короткий кулдаун 2 ч (`AGY_LOCATION_COOLDOWN_MS`), учитывается в предохранителе; суточного eligibility-кулдауна больше нет (24 ч `AGY_INELIGIBLE_COOLDOWN_MS` остаётся только у `auth-dead`). Уже стоящие суточные метки не мигрируются: дожидаются срока и уходят в бессрочную парковку при следующем отказе.
    - **Пути компакции (ревизия 14, PLUG-306; ревизия 18, PLUG-357):** внутренний старт `runCompactSeed` и внутренний `thread/resume` в `compactRestore` читают ошибку; если `parkedCauseOf` даёт причину (`validation-required` / `tos-disabled`) — аккаунт паркуется по ней, дальше единый порядок п. 13: перезапуск стадии seed на сиблинге (с мемо-промптом при отказе на стадии summary), а без сиблинга — сброс `compact = null`, `settledInternal = null` и `failOut` с ошибкой о необходимости проверки аккаунта (validation-required) либо ToS.
    - **Пробник `queryAcpSessionModels` (ревизия 14, PLUG-306):** JSON-RPC-ошибка `session/new` читается; при причине парковки (`parkedCauseOf`) аккаунт паркуется, пробник возвращает пустой список (фолбэк на кэш §8).
12. **Журнал переходов.** Каждый выбор и каждый переезд аккаунта (старт, ротация, resume на сиблинга, отказ по модели, парковка) — строка в `acp-wrapper.log`: тред, откуда → куда, причина. В журнал пишется и отказ `thread/start` без выбора аккаунта («model … is not offered», все припаркованы, нужна проверка): тред, модель, причина (ревизия 14, PLUG-306). Метки аккаунтов пишутся только в локальный лог; в репозиторий и публичные артефакты они не попадают.
13. **Квота текстом ответа (ревизия 16, ревизия 18 — PLUG-357).** agy сообщает об исчерпанной квоте не только ошибкой, но и обычным агентским сообщением: одна строка `⚠ Individual quota reached. Please upgrade your subscription to increase your limits. Resets in 127h43m16s.`, после которой ход закрывается как успешный. Такое сообщение — та же причина `quota`, что и `provider.error` с квотой: текст пользователю не уходит, граница хода не считается завершением (бюджет ретраев не сбрасывается), аккаунт охлаждается до названного сброса (без срока — 30 мин), дальше обычный план §2.3 — ротация на свободного подходящего сиблинга с handoff, ожидание в пределах `AGY_AUTO_RETRY_MAX_WAIT_MS` либо честная ошибка `rate-limit` с `errorInfo` 429 и `rateLimits blocked`.
    - **Точная форма маркера и распознавание:** только точная форма agy — текущее агентское сообщение текущего хода после обрезки ведущих и хвостовых пробелов/переводов строк начинается с `⚠ Individual quota reached` и остаётся одной строкой не длиннее ~300 символов (`/^⚠\s*Individual quota reached\b[^\n]{0,300}$/iu`). Настоящее сообщение agy (включая `fake-agy-acp`) может начинаться и заканчиваться переводом строки `\n` (`"\n⚠ Individual quota reached. … Resets in …\n"`). Маркер вторым текстовым сегментом хода (после прозы и вызова инструмента) распознаётся так же. Упоминание этих слов внутри обычного ответа модели (цитата, разбор ошибки) охлаждение не вызывает.
    - **Буферизация префикса и защита от утечки `⚠` (ревизия 18):** чанки текста сегмента удерживаются во внутреннем буфере обёртки до тех пор, пока:
      1) текст после `trimStart()` пуст (начальные чанки состоят только из пробелов и `\n`), либо
      2) текст после `trimStart()` является префиксом шаблона маркера квоты (`/^\s*⚠\s*(?:i(?:n(?:d(?:i(?:v(?:i(?:d(?:u(?:a(?:l(?:\s+(?:q(?:u(?:o(?:t(?:a(?:\s+(?:r(?:e(?:a(?:c(?:h(?:e(?:d)?)?)?)?)?)?)?)?)?)?)?)?)?)?)?)?)?)?)?)?)?)?)?)?$/iu`) или префиксом маркера валидации (`/^\s*⚠\s*(?:v(?:e(?:r(?:i(?:f(?:i(?:c(?:a(?:t(?:i(?:o(?:n(?:\s+(?:r(?:e(?:q(?:u(?:i(?:r(?:e(?:d)?)?)?)?)?)?)?)?)?)?)?)?)?)?)?)?)?)?)?)?)?$/iu`), либо
      3) текст после `trim()` уже совпадает с полным маркером квоты (`isAgentQuotaMessage`) или валидации (`isAgentValidationMessage`) и остаётся одиночной строкой до ~300 символов (хвостовой `\n` или замыкающие пробелы отдельным чанком расхождением не считаются).
      Расхождением (отклонением от маркера) считается ситуация, когда текст не подпадает ни под один из пп. 1–3 удержания, либо содержит `\n` после текста маркера с последующим непробельным символом (многострочная проза, например `"⚠ Note:\n..."`). При первом расхождении накопленный буфер немедленно и целиком сбрасывается (flush) в исходящий поток дельт клиенту (`item.textDelta`). Текст попадает в `summaryBuf` и `recentAssistantText` **только при реальном сбросе дельт клиенту** (никогда не пишется при удержании в буфере-кандидате, и подтверждённый маркер отказа в них не попадает).
    - **Удержание `item.textClose` и подтверждение маркера (ревизия 18):** событие `item.textClose` сегмента-кандидата, текст которого совпал с полным маркером квоты или валидации, удерживается вместе с буфером до следующей поступающей дельты:
      - Служебные дельты обёртки и SDK (`usage`, `contextWindow`, `provider.rateLimits`, `provider.warning`, `unhandled`, `item.progress`, дельты мыслей `item.textDelta` с каналом `reasoningText` и подобные мета-события) пропускаются наружу свободно и сброс буфера не вызывают. Правило по умолчанию: сброс буфера вызывают только открытие нового элемента (`item.open`), вызов инструмента (`toolCall`), содержательный текст модели (`item.textDelta` канала `agentMessage`) либо завершение хода (`turn.boundary`); `provider.error` обрабатывается штатным обработчиком ошибок.
      - Если следующая дельта — `turn.boundary` (ход завершается): маркер подтверждён, поглощается целиком (в тред клиенту не уходит ничего; если `item.open` уже успел уйти клиенту, он закрывается пустым `item.textClose`), и запускается ротационный автомат.
      - Если следующая дельта — содержательное продолжение хода (открытие нового элемента `item.open`, вызов инструмента `toolCall`, или новый текст `agentMessage`): маркер не является финальным отказом; обёртка сначала отдаёт клиенту задержанный буфер дельт текста, затем задержанный `item.textClose`, и только затем поступившую дельту — текст не теряется и структура потока не нарушается.
      - Если же сегмент закрывается (`item.textClose`), когда в буфере лежал лишь неполный префикс маркера (например, `"⚠"` или `"⚠ Individual"`): буфер немедленно сбрасывается клиенту вместе с `item.textClose`.
    - **Сброс при отмене prompt / steer (ревизия 18):**
      - При `turn/steer`: накопленный буфер неподтверждённого текста немедленно отдаётся клиенту (`item.textDelta` + `item.textClose`), а внутреннее состояние детектора (`agentMessageText`, `quotaRefusalText`, `validationRefusal`, флаги отказа) полностью сбрасывается в исходное. Отменённый prompt не влияет на следующий ввод, не поглощает ответ на steer и не вызывает ротацию.
      - При `thread/stop` и прерывании (abort/interrupt): неподтверждённый буфер выбрасывается, состояние детектора полностью сбрасывается.
    - **Квота при сжатии контекста (compact-summary / compact-seed) (ревизия 18):** отказ квоты текстом (`onQuotaRefusalBoundary`), квота ошибкой (`onProviderErrorDelta`) или отказ валидации (`onValidationRefusalBoundary`), настигшие внутренние ходы сжатия (`session.compact !== null`), обрабатываются детерминированно:
      - При отказе на стадии `compact-summary` (где `seedPromptText` ещё не сформирован колбэком `onSettled`): если частичный `summaryBuf` не пуст (модель до отказа успела выдать содержательный текст), тело seed формируется из него; если пуст — из `compactMemoPrompt(recentAssistantText...)`.
      - Исход `rotate` (есть свободный сиблинг): стадия seed перезапускается на новом сиблинге напрямую через `runCompactSeed` (по образцу `compactParked`: без `startRotation` и без handoff-хода `[quota-rotation-handoff]`).
      - Исход `wait` (сиблинга нет, ожидание кулдауна): объект `compact` сохраняется с подготовленным seed-телом (summaryBuf/memo), `settledInternal = null`, а очередь ходов демона удерживается до истечения таймера ожидания. По таймеру на остывшем аккаунте вызывается `runCompactSeed` с сохранённым seed-текстом (без `startRotation` и без handoff-повтора запроса пользователя, исключая появление фантомных ходов в треде).
      - Исход `fail` (сиблинга нет, бюджет исчерпан): стадия компакции сбрасывается (`session.compact = null`, `session.settledInternal = null`), и вызывается `failOut` с соответствующей причиной (429 для квоты, ошибка проверки аккаунта для validation-required).
      Это исключает зависание `session.compact` в активном состоянии и гарантирует штатное дренирование очереди `drainQueue`.
    - **Сессии без аккаунта после 429 (прямой режим и relay) (ревизия 18):** для любой сессии без аккаунта пула (`session.accountLabel === null` — как прямой режим, так и relay) при переходе в `rateLimitsBlocked`:
      - Все daemon-ходы, уже находящиеся в очереди `session.queue` на момент входа в блок, немедленно завершаются честным отказом `rate-limit` (HTTP 429, `errorInfo`, `settlesTurn: true`), исключая их многодневное зависание в очереди.
      - Срок локальной блокировки `resetsAt` в сессиях без аккаунта пула клампится сверху максимумом `DEFAULT_QUOTA_COOLDOWN_MS` (30 минут, `src/recovery.ts:187`): даже если в ответе назван далекий срок (например, `Resets in 127h`), наружу клиенту в `provider.rateLimits blocked` и локально отдаётся `resetsAt` не позднее чем через 30 минут от момента блокировки (или названный срок, если он меньше 30 минут), после чего блок снимается, позволяя пользователю, обновившему подписку, отправить новый запрос без ожидания 5 суток.
      - Обёртка заводит таймер разблокировки на рассчитанный срок; команда `thread/stop` немедленно отменяет (гасит) этот таймер.
      - По истечении таймера: блок снимается (`session.rateLimitsBlocked = false`), эмитится `provider.rateLimits` со статусом `allowed`, и вызывается `drainQueue(session)`.
      - Общее правило для всех режимов (включая пул): при поступлении любого входящего `turn/start`, если текущее время `now >= resetsAt`, блок снимается (`rateLimitsBlocked = false`), эмитится `provider.rateLimits` allowed, и очередь разблокируется.
      - Входящий `turn/start`, поступивший в прямом/relay режиме **до** истечения срока блокировки (`now < resetsAt`): немедленно и честно отвергается ошибкой `rate-limit` (HTTP 429, `errorInfo`, `settlesTurn: true`).
14. **Токен аккаунта пула — только в файле (ревизия 17, ревизия 18 — PLUG-357).** Системное хранилище ключей (macOS Keychain, Secret Service, Windows Credential Manager) — одна ячейка на пользователя машины, а agy читает её раньше файла `<дом аккаунта>/.gemini/antigravity-cli/antigravity-oauth-token`. Там, где хранилище доступно, любой аккаунт пула иначе работает под тем, кто вошёл последним, и ротация ничего не меняет. Поэтому каждый запуск agy на аккаунте пула — сессия ACP (`session/new`, `session/load`), опрос `agy models` (включая пробники каталога и stream-json `listAgyModels`), сессия stream-json и вход в `scripts/add-account.mjs` — получает в окружении `SSH_CONNECTION`: agy сам выбирает файловое хранение, когда видит SSH-сессию (в его логе — «Using file-based token storage because SSH session detected»), и к хранилищу ключей не обращается ни на чтение, ни на запись. Настоящий `SSH_CONNECTION` хоста сохраняется как есть; иначе ставится заглушка `127.0.0.1 0 127.0.0.1 0`.
    - **Абсолютный приоритет над пользовательскими и реестровыми env (ревизия 18):** маркер имеет последнее слово и защищён от переопределения на всех путях запуска аккаунтов пула:
      - Ключ `SSH_CONNECTION` из пользовательских `options.envVars` отбрасывается (любое переданное значение, включая пустую строку `""` или стороннее значение), если запуск выполняется для аккаунта пула, а `AGY_KEYRING` не равен `1`.
      - При запуске `agy models` (включая stream-json `listAgyModels` и пробники каталога) маркер накладывается строго ПОСЛЕ `install.env` реестра установок ([provider-agy-installs.md](provider-agy-installs.md) §2 п. 3: переменные плагина накладываются поверх переменных установки), защищая маркер от перекрытия значениями из `install.env`.
      - Защита маркера действует на всех путях запуска agy для аккаунтов пула: `session/new`, `session/load`, опрос `agy models` (включая пробники каталога), stream-json сессии, `add-account`.
    - **Не касается** прямого режима (без пула, свой `HOME` пользователя) и relay-дома с `GEMINI_API_KEY`: там вход остаётся там, где пользователь его сделал, и ключ `SSH_CONNECTION` из `envVars` проходит свободно без отбрасывания. Отключение — `AGY_KEYRING=1` в окружении bb. Побочный эффект: команды, которые agy запускает в треде, тоже видят `SSH_CONNECTION`. Синхронизация токена в хранилище ключей (`security add-generic-password` и подобное) не используется: общая ячейка даёт гонку между параллельными тредами и затирает личный вход владельца машины. Решение и отклонённые варианты — [ADR-0038](../adr/0038-provider-agy-pool-token-file-storage.md).
15. **Служебное сообщение прерывания потока при steer (ревизия 19 — PLUG-354).** При вклинивании сообщения в активный ход (`turn/steer`, например от плагина `automations` «страховка от простоя») бинарник agy может выдать в ответ модели служебное сообщение `⚠ The stream was interrupted. Please continue the task you were working on.`. Ход при этом не останавливается: модель сразу продолжает работу (рассуждения, вызовы инструментов, редактирование файлов), и граница хода закрывается в штатном режиме.
    - **Точная форма сообщения и распознавание:** только точная форма agy — текущее агентское сообщение текущего хода после обрезки ведущих и хвостовых пробелов/переводов строк совпадает со служебной строкой agy (`/^⚠\s*The stream was interrupted\.\s*Please continue the task you were working on\.?\s*$/iu`). Настоящее сообщение agy начинается и заканчивается переводом строки `\n` (`"\n⚠ The stream was interrupted. Please continue the task you were working on.\n"`). Упоминание этих слов внутри обычного ответа модели (цитата, разбор инцидента, многострочная проза) не подавляется и доставляется пользователю в полном объёме.
    - **Буферизация префикса и подавление (`processDeltaLine`):** префикс сообщения буферизуется во внутреннем буфере обёртки по общим правилам п. 13 (шаблон префикса `AGENT_INTERRUPTED_PREFIX_PATTERN` и `isAgentMarkerCandidate`). При совпадении с точной формой:
      - Дельты текста не передаются наружу клиенту (`item.textDelta` поглощаются).
      - Текст служебного сообщения **не попадает** в `recentAssistantText` и не загрязняет контекст при handoff/сжатии, а также исключается из `compact.summaryBuf`.
      - При закрытии сегмента (`item.textClose` / `item.close`) буфер кандидата очищается, а пустое закрытие клиенту не передаётся, не оставляя незакрытых элементов и не раскрывая служебную строку.
    - **Жизненный цикл хода:** появление строки **не считается ошибкой или отказом**:
      - Аккаунт не охлаждается и не паркуется, ротация и handoff не запускаются, бюджет ретраев не расходуется.
      - Граница хода (`turn.boundary`) не модифицируется: ход продолжается штатно до естественного завершения.
      - Если после строки ход всё-таки закрылся без продолжения — это отдельный непредвиденный сценарий, который не маскируется и возвращается архитектору.

Привязка аккаунта к установке (`accounts[label].install`, [provider-agy-installs](provider-agy-installs.md), ADR-0033) — отдельный фильтр выбора, не зависящий от модели: аккаунт, чья установка не объявлена в локальном реестре `agy-installs.json` или чей бинарник отсутствует/не исполняем, локально недоступен и исключается из кандидатов `pickAccount` на всех точках выбора (п. 4), из проб каталога и из сводного `model/list` — подмены бинарником другой установки нет (там же §5 п. 2). Строки журнала п. 12 несут суффикс `install=<имя>` (provider-agy-installs §9 п. 2).

Проверка (`harness-pool.mjs`, `harness-rotation.mjs`, fake-agy с каталогом, зависящим от `HOME`): модель есть только у аккаунта Б → `thread/start` закрепляет Б при любом `priority` и LRU; модель есть у А (priority 10) и Б (priority 5) → берётся А, при кулдауне А — Б, после снятия кулдауна новый тред снова на А; квота на Б при модели только-Б и свободном А → ожидание/rateLimits по Б, на А тред не уходит; смена модели в `turn/start` на отсутствующую у аккаунта → переезд с handoff без кулдауна прежнему; `Unknown model ID` в полёте → запись в `unsupported` и переезд; модель ни у кого → честная ошибка без ротации; `model/list` — объединение каталогов; аккаунт с `priority = 0` не опрашивается `agy models`; `tos-disabled` → парковка с `parkedReason`, переезд, повторного выбора аккаунта нет; пул без `accounts-models.json` ведёт себя как до ревизии 11; устаревшая запись каталога остаётся пригодной для выбора (старший тариф не всплывает раньше времени); упавший опрос не запускает `agy models` повторно до троттла; `tos-disabled`-аккаунт не опрашивается и не в сводном каталоге; причина `model` при остывших подходящих даёт rateLimits, а не ложное «not offered»; все аккаунты припаркованы → честный фейл даже для `acp-default`; отказ eligibility с просьбой/ссылкой проверки → `parkedReason: "validation-required"` без `cooldownUntilMs`, строка журнала со ссылкой, повторного выбора нет; отказ без просьбы/ссылки → кулдаун 2 ч; открытый предохранитель → парковки нет (ревизия 15).

## 3. Ротация аккаунтов и авторетрай по квоте

Штатный `provider-retry` сам не справляется: generic-мост шлёт `provider.error` без `errorInfo`, демон повтор не инициирует, а generic-мост отвергает параллельный `turn/start` («A turn is already active») и сбрасывает очередь вводов при ошибке хода (`dropQueuedTurnInputs`). Поэтому ротацию и повтор делает сама обёртка — по строгому автомату:

1. Ошибка квоты перехвачена (из shim/`provider.error`) → аккаунт помечается кулдауном, внешний `provider.error` **подавляется** — для демона ход остаётся активным.
2. Обёртка ждёт остановки/релиза текущей сессии, затем синтезирует `thread/start` на том же треде с `--gemini-dir` сиблинга → generic-мост релизит старую сессию и строит новую → обёртка эмитит `sessionReplaced` (contextLost).
3. Обёртка синтезирует `turn/start` с `input` = handoff-промпт (`[quota-rotation-handoff]` + recentAssistantText ≤4k + `git diff --stat`); идентификаторы хода маппятся на ожидаемый демоном turn, чтобы boundary/дельты закрыли исходный ход честно.
- Очередь ходов — **в самой обёртке** (generic очередь не держит): ходы, пришедшие во время ротации, выполняются по порядку на новой сессии.
- Если остыл весь пул: обёртка пропускает `provider.error` наружу с инжектированным `errorInfo{category:"rate-limit", httpStatusCode:429}` и эмитит `provider.rateLimits` (blocked, resetsAt = ближайший конец кулдауна) → штатный `provider-retry` ждёт resetsAt и перезапускает ход. Когда от `provider-retry` приходит повторный `turn/start`, обёртка проверяет кулдаун текущего аккаунта сессии: если мёртв/сменился — сначала автомат пп.2–3 (новая сессия + handoff), затем пропуск хода. Снятие blocked — `provider.rateLimits` allowed. Пока сессия в состоянии blocked, `drainQueue` **удерживает daemon-ходы** в очереди (internal-ходы автомата всегда дренируются; в прямом режиме и relay ходы очереди не удерживаются, а сразу получают 429 по п. 13); после `allowed`/settle очередь снимается `drainQueue` из `onSettled`.
- `AGY_AUTO_RETRY_MAX`, `AGY_AUTO_RETRY_MAX_WAIT_MS`, `AGY_INELIGIBLE_*` — те же env; смыслы кулдаунов по §2.3 п. 11 (ревизия 15): `AGY_LOCATION_COOLDOWN_MS` — весь eligibility-отказ без просьбы/ссылки проверки, `AGY_INELIGIBLE_COOLDOWN_MS` — только `auth-dead`; бюджет ретраев — на сессию, сбрасывается на честно завершённом ходе. Stop отменяет ожидание ретрая и висящий повтор.
- **auth-dead (инцидент 10.11):** слёт Google-входа пул-аккаунта — agy отвечает `auth_required`/`Authentication required` (в его логе «Silent sign-in failed», «not logged into Antigravity», «error getting token source»). Это НЕ квота и НЕ eligibility: классификатор (`isAuthDead`, единый список сигнатур в `accounts.ts`) заводит причину `auth-dead` → аккаунт паркуется как ineligible (длинный `cooldownUntilMs` + `ineligibleAtMs`, плюс `parkedReason:"auth-dead"` в accounts-state.json; тот же ineligible-breaker) → та же ротация пп.2–3 со свободного сиблинга, `sessionReplaced` с reason «the session's account lost its Google sign-in (auth_required)». `turn/start` и `resume` на припаркованном аккаунте попадают в ту же ветку по `cooldownUntilMs`. Пустой пул → честный `provider.error` (unauthorized) с текстом об исчерпании пула — без спама ротаций. `auth-dead` не трогает quota-поля и не считается toolError; наружу уходит `errorInfo{category:"unauthorized", httpStatusCode:401}` только когда ротация невозможна.

Проверка: харнесс `harness-rotation.mjs` на ACP — квота на А → переезд на Б с handoff за ~1с, демон видит один непрерывный ход; весь пул в кулдауне → rateLimits blocked + ретрай после resetsAt на ожившем сиблинге; ход, пришедший во время ротации, выполняется после неё; auth_required на живом ходу → парковка + переигровка на соседе; resume на мёртвом — ротация; все мертвы → честный фейл.

## 4. Классификация ошибок и rateLimits

`classifyError`/`quotaResetAtMs` переносятся дословно; парсинг «Resets in X» сохраняется. Форма квоты по ACP берётся из двух источников: JSON-RPC error `session/prompt` (видит shim) и `provider.error`/неуспешный boundary (видит обёртка на границе демона). `provider.rateLimits` эмитится обёрткой напрямую в поток дельт — generic-мост его не знает.

Проверка: фикстура fake-agy-acp (создаётся в рамках работ) с ответом квоты → классификатор даёт resetsAt, эмитится blocked-снапшот.

## 5. Usage за ход

`agy acp` возвращает `result.usage` (`inputTokens`, `outputTokens`, `cachedReadTokens`, `cachedWriteTokens`, `thoughtTokens`, `totalTokens`) в ответе `session/prompt`; generic-мост его игнорирует (схема читает только `stopReason`), и на границу `handleLine` он не попадает. Добыча — **stdio-shim** (§1): снифит ответ `session/prompt`, пишет usage в side-channel, обёртка эмитит usage-дельту в тред. SQLite-прокси не нужен. Лимиты аккаунтов по-прежнему собирает `bb-plugin-usage-pro` — не трогаем. С 11.11 рядом с usage-строкой эмитится и `contextWindow`-дельта (`size` = family-map, `estimated:true`, snapshot) — без неё метр окна контекста показывал «not available yet» (agy не шлёт `usage_update`, поэтому generic-мост сам её не синтезирует).

`used` — **нормализованная оценка**, не сырой агрегат: `result.usage` суммирует ВСЕ вызовы модели за ход, а каждый вызов перечитывает ~весь закешированный префикс, поэтому `input + cachedRead` на tool-heavy ходе в N раз больше реального окна (боевой случай: «3m / 1m»). Per-call usage в update-потоке нет — оценка только по агрегату. Шим считает `tool_call` за промпт (по request-id — следующий промпт может уйти на провод до результата предыдущего, artifact-nudge), кладёт `toolCalls` в `prompt-result`, обёртка считает `used ≈ (input + cachedRead)/(1 + toolCalls) + output + thought`. Точность — порядок одного вызова, остаётся `estimated:true`; вызовы модели без tool_call (суммаризация/steering) в `steps` не попадают, поэтому оценка дополнительно клампится в `size` — >100% окна невозможно.

Проверка: в треде после хода виден расход токенов; фикстура отдаёт usage → дельта проходит.

## 6. Восстановление: compaction fallback и ArtifactMetadata

- **Compact fallback** (`AGY_COMPACT_FALLBACK`): конечный автомат ADR-0003 переносится в обёртку — при отказе сжатия: `compactSummaryPrompt` в том же разговоре → новая сессия с `compactSeedPrompt`/`compactMemoPrompt` первым ходом. `/compact` у agy acp идёт обычным текстом промпта (проверено живым тестом); собственного `session/compact` у сервера нет.
- **ArtifactMetadata**: основной механизм — превентивный `WRITE_GUARDRAIL` в инструкциях сессии (перехват `tool_call_update` через `handleLine` невозможен). Дополнительно shim видит текст отказа `tool_call_update` («is not a valid artifact path») в side-channel → обёртка может однократно подать `writeRetryNudge` следующим вводом (`MAX_ARTIFACT_RETRIES=1` **на ход**: счётчик и флаг nudge сбрасываются на каждой границе хода — долгоживущая сессия не теряет nudge после первого использования).

Проверка: харнесс `harness-errors.mjs`/`harness-artifact.mjs` на ACP — компакт-фоллбэк проходит два шага, артефактный отказ встречает один повтор с nudge.

## 7. `thread/resume` при остывшем владельце и `turn/start` на остывшей сессии

Перехват `thread/resume` читает мапу бесед (§2.1): если аккаунт-владелец в кулдауне — запрос трансформируется в `thread/start` на свободном сиблинге, `needsHandoffPrompt` на первый ход (handoff-промпт подменяет `input`), клиенту шлётся `sessionReplaced`. Если владелец жив — делегируется как есть (session/load читает разговор, в т.ч. созданный в stream-json).

Та же проверка на каждом входящем `turn/start`: если аккаунт текущей сессии остыл (напр., повтор пришёл от provider-retry спустя часы) — сначала ротационный автомат §3 пп.2–3, затем пропуск хода.

**Подавление реплея `session/load`.** agy отвечает на `session/load` посреди потока реплея: вся история разговора (user/agent/thought-чанки, tool_call'ы) продолжает литься `session/update`-нотификациями после ответа — через `idle`-окно и внутрь следующего `session/prompt`, мимо гейта `session.loading` у generic-моста. Без фильтра реплеенные чанки рендерятся как вывод нового хода: ответ начинается с хвоста предыдущего ответа, мысли старого хода появляются после нового текста (инцидент 11.11, тред `thr_pi8u4n8ww4`). Shim на запросе `session/load`/`session/fork` поднимает `suppressReplay`: дальше дропаются все `session/update` реплеебельных видов (`agent_message_chunk`, `agent_thought_chunk`, `user_message_chunk`, `tool_call`, `tool_call_update`, `plan`; usage/info/config-нотификации проходят) до границы живого края — эха текущего `session/prompt`: на `session/prompt` запоминается нормализованный хвост (160 символов) текста промпта, `user_message_chunk`-чанки аккумулируются и сравниваются `endsWith` (короткая сторона ≥16 символов — старый «yes»/«ok» не притворится границей). Промпт короче 16 нормализованных символов («ok», «да») контентно неразличим со старым эхом — тогда граница позиционная: порядок в разговоре гарантирует, что всё после эха юзерского сообщения живое, поэтому первый не-user апдейт после user-чанков с момента промпта и есть живой край (в bb через мост недостижимо — промпт всегда с инструкциями; ветка для голых ACP-клиентов и текстлесс-промптов). Предохранители против съедения живого хода, если эхо не придёт: `reprompt` (второй `session/prompt` до границы → снять подавление), `boundary-quiet` (20 с тишины в потоке после промпта; каждый дропнутый апдейт перевзводит таймер — длинный реплей дожимается до конца), `boundary-deadline` (90 с от промпта — живые чанки тоже дропы, активность не может держать гейт вечно), `load-error` (ошибка `session/load` → реплея не будет, гейт снимается). `session/new` сбрасывает подавление. События `replay-end`/`replay-abort` с числом дропнутых уходят в side-channel.

Проверка: харнесс — resume с кулдаун-владельцем стартует сиблинга с handoff; resume с живым владельцем грузит ту же беседу; повторный turn/start на мёртвой сессии сначала ротирует; **фейковый `session/load` стримит историю после ответа — реплей не доходит до дельт нового хода**.

## 8. Модели, режимы, permissions

- `model/list`: быстрый путь — ответ из кэша (TTL 6 ч) или `agy models` (~100 мс); холодный прогон ACP-сервера только на промахе кэша (таймаут, при неудаче — последний кэш). Усилия — не отдельные модели: `gemini-3.8-flash` + `supportedReasoningEfforts` (low/medium/high) → `session/set_config_option` (`thought_level`), маппинг id вида `<model>-<effort>` по образцу `model-utils.ts` rawizhere; голый id без суффикса — стандартная лестница `thought_level` (low/medium/high), не «только medium».
- Permission mode треда → `session/set_mode` на живой сессии (`default`/`accept-edits`/`plan`; проверено: работает на лету). `--dangerously-skip-permissions` добавляется в args для `full` (`permissionCli`-маппинг). Декларация режимов в `server.ts` — см. §1.
- Канал смены режима на живой сессии — side-channel файл `acp-shim/ctl-<thread>-<nonce>.ndjson`: обёртка **создаёт его пустым при запуске сессии** (shim ставит `fs.watch` до первой записи; без файла watch молча не регистрируется). Shim дополнительно создаёт файл перед `watch` и дренирует его на каждой входящей строке — три независимых гарантии доставки `{"cmd":"set_mode","mode":...}` → `session/set_mode` в agy.
- Стиринг — `turn/steer` generic-моста (session/prompt на живой сессии); очередь стирингов старого моста не нужна — `session/cancel` отменяет mid-tool штатно (проверено).

Проверка: `bb provider models agy` отвечает <1с на горячем кэше; смена режима в треде не пересоздаёт сессию; стиринг доезжает в идущий ход.

- **Нативные субагенты agy отключены (11.11.2026)**: agy умеет запускать собственных субагентов (`invoke_subagent`, `manage_subagents`, `define_subagent`, `browser_subagent`, `native_swarm`/`manage_swarm`, `boost`) — они живут внутри процесса agy и в BB не видны; каждый субагент обязан быть тредом BB. Обёртка резолвит: `AGY_DISABLE_SUBAGENTS` env-override ("0" разрешает, прочее запрещает) > `providerSubagentsEnabled` > по умолчанию запрещено. Два слоя исполнения: (1) обёртка передаёт решение в env шима `AGY_DISABLE_SUBAGENTS`, shim инъектит `params.disableBuiltInTools` (список выше) в каждый `session/new`/`session/load` — поле штатного ACP `NewSessionParams`, агент фильтрует по своему реестру, лишние имена безвредны; (2) обёртка перед каждым запуском аддитивно мёржит в `<account-home>/.gemini/settings.json` `antigravityConfig.subagentsConfig.enabled=<resolved>` и `boostCommandDisabled=<!resolved>` (пишет и snake_case-вариант — схема парсера agy не подтверждена, protojson принимает оба) — re-enable тоже доезжает, страховка для путей без session-параметров.
- **Нативная память agy отключена (11.11.2026)**: та же категория невидимого состояния — тулы `memory`, `retrieve_memory`, `disable_memory` хранят заметки внутри account-home, в BB их не видно. Центральная настройка `memoryEnabled` (`bb plugin config provider-agy set memoryEnabled true`, по умолчанию **выключена** — осознанная инверсия контракта codex/claude-code, где память по умолчанию разрешена: у agy она скрыта от BB) → `options.providerOptions.providerMemoryEnabled`. Резолв: `AGY_DISABLE_MEMORY` env ("0" разрешает) > derived > default off. Два слоя, как у субагентов: shim добавляет memory-тулы в `params.disableBuiltInTools` на `session/new`/`load` (плюс спекулятивные `update_memory`/`save_memory`/`write_memory` — агент фильтрует неизвестные), обёртка стемпит `antigravityConfig.memoryConfig.enabled=<resolved>` (+snake_case) в settings.json на каждый запуск. У `devin acp` локального рычага памяти нет (Memory Drive/notes — облако) — см. `provider-devin.md` §4.
- Общий `conversation_summaries.db` мостом для чтения не используется — `SQLITE_BUSY` не возникает.
- Параллельные треды на одном аккаунте допустимы; кулдаун от 429 любого из них ставится на аккаунт целиком; покрывается тестом §11.

## 10. Что выкидывается

Парсер `step_update`/`handleResult` (заменён ACP-переводом), stale-quota-residue (в ACP ошибки не липнут), свипперы сессий/ходов (lifecycle ведёт generic-мост), очередь стирингов (штатный steer). Старый stream-json мост целиком остаётся за флагом `AGY_TRANSPORT=stream-json` на один релиз — откат без деплоя. Пока мост жив за флагом, аккаунт с любым `parkedReason` в нём не запускается ни одним путём: `rotateCooldownAccount`, resume, пересборка в `enqueueTurn`, `restoreCompactConversation` проверяют `parkedReason` и уходят на свободного сиблинга либо завершаются честной ошибкой (ревизия 14, PLUG-306).

## 11. Тест-план

1. Юнит: классификатор квоты под обе ACP-формы; маппинг `model/effort → session/set_config_option`; разбор usage из side-channel shim → usage-дельта; маппинг turn-идентификаторов при внутренней ротации.
2. Харнессы на **fake-agy-acp** (создаётся: NDJSON ACP по stdin/stdout, вкл. `result.usage` и отказы `tool_call_update`): пул+sticky; ротация по автомату §3 с handoff и подавленной ошибкой; весь пул в кулдауне → rateLimits+provider-retry → ретрай на ожившем сиблинге; resume на остылом; turn/start на мёртвой сессии; compact fallback 2 стадии; ArtifactMetadata (guardrail + nudge через shim); резолв висящего interaction при релизе сессии; **два параллельных треда на одном аккаунте** — кулдаун распространяется без сбоя соседнего треда; `disableBuiltInTools` во всех `session/new`/`session/load` транскрипта (субагент-тулзы + memory-тулы по env-флагу, re-enable через `providerSubagentsEnabled`/`providerMemoryEnabled`) и `settings.json` аккаунта со стемпами `subagentsConfig`/`memoryConfig`; реплей `session/load` после ответа подавляется shim до эха нового промпта (`replay/suppressed`); **локальное состояние §2.1**: пин беседы пишется в `conversations-state.json` и переживает перезапись `accounts-state.json` «сверху» (имитация keeper-синка — резюме всё равно находит владельца); cooldown/парковка, выставленные локально, переживают перезапись общего файла через overlay до истечения `untilMs`; overlay-тень снимается при более свежем `shared.lastUsedMs`; legacy `conversations` из общего файла доезжают в локальный при первой записи и из общего пропадают; метка, приехавшая общей стороной, в overlay НЕ копируется (dirtyLabels: прямая запись поля без хелпера overlay не делает); два враппера одного инстанса пишут одновременно — пины соседа не теряются (merge-on-save); те же сценарии на stream-json мосте (`provider-bridge.ts`, тот же `bridge-data`).
3. Живой прогон: тред на `agy` (ACP) — мысли стримом, аргументы/вывод тулов видны, usage после хода, стиринг, stop mid-tool, resume после рестарта bb; валидация обновлённого `server.ts` (режимы переключаются в UI).
4. Откат: `AGY_TRANSPORT=stream-json` — старое поведение без изменений; **регрессионный прогон существующего сьюта харнессов под флагом**.
5. Жизненный цикл шима (§12): чек «no orphan on parent death» — shim и его дерево мертвы ≤10 с после `kill -9` родителя; `SIGTERM` по живому shim → чистый выход с уборкой ≤10 с; реапер §12.3 убивает подставного сироту (`PPid=1`) и не трогает живого shim; `pgrep -cf 'acp-shi[m]'` после смерти треда → 0.

## 12. Жизненный цикл acp-shim: смерть вместе с хозяином (PLUG-274)

Инцидент 16.11 (постмортем «2026-11-16 orphan acp-shims»): 432 сироты `node <tmp>/acp-shim.mjs`, 6.1 GB RSS, возраст до 4.5 суток; `SIGTERM` игнорировали. Причины в коде: `fs.watch` на control-файле держит event-loop после `rlIn.on("close")` и `child.on("close")` (shim не выходит никогда); обработчики `SIGTERM/SIGINT/SIGHUP` форвардят сигнал ребёнку, но сам shim не завершается; внуки `agy acp` (8–16 node-процессов) сигнала не получают вообще.

Контракт: **shim умирает вместе с хозяином и убивает своих детей.**

### 12.1 Условия выхода shim
Shim входит в orderly shutdown при любом из:
1. **EOF на stdin** (`rlIn.on("close")`) — ACP-канал закрыт: родитель (bridge-worker) умер или отпустил сессию.
2. **Смерть родителя** — сторож: на старте запоминается `process.ppid`; unref-интервал ≤2 с сверяет `process.ppid` — сменился (пересадка на init/systemd) → shutdown. `PR_SET_PDEATHSIG` из чистого Node недоступен; ppid-поллинг — портируемый эквивалент.
3. **SIGTERM/SIGINT/SIGHUP** — сигнал = приказ завершиться, не только форвард ребёнку.
4. **`close` ребёнка** — `agy acp` умер сам: фиксируется код выхода (`childCloseExitCode`), затем тот же orderly shutdown (п. 12.2).
5. **EPIPE на stdout** — запись мосту упёрлась в закрытый пайп (родитель мёртв): тот же shutdown.

### 12.2 Порядок shutdown (≤10 с суммарно)
1. `acceptingClientInput=false`; закрыть `rlIn`, снять `fs.watch` control-файла, сбросить таймеры (replay fallback, set_mode settle) — event-loop обязан освобождаться.
2. `child.stdin.end()`; grace ~2 с → `SIGTERM` на **группу** ребёнка; ещё ~3–5 с → `SIGKILL` на группу. Ребёнок спавнится `detached: true` (своя process-группа), убийство — `kill(-child.pid, sig)`: гибнут `agy acp` и все его node-внуки. Вне Linux — fallback на прямой `child.kill` (деградация, не блокер).
3. Удалить свой файл `$AGY_SHIM_CONTROL` (покрывает и maintenance-шим `__models__` с `ctl-models.ndjson`); каталог данных не трогать — он общий.
4. Чистый путь завершается явным `process.exit()` — шим не ждёт опустошения loop. Дедлайн ~8 с от входа в shutdown (не unref) — только страховка: принудительный `exit`, если ребёнок/таймеры повисли; в норме не срабатывает.
5. **Идемпотентность**: вход в shutdown — одноразовый (флаг); при смерти worker'а могут сработать EOF+ppid-сторож+сигнал одновременно. Убийства терпят `ESRCH`, fs-операции — `ENOENT`, запись в закрытый `child.stdin` — `ERR_STREAM_DESTROYED`; ребёнок, мёртвый до входа в shutdown, не ломает путь.

### 12.3 Реапер на стороне обёртки (defense in depth)
`src/acp-wrapper.ts` — `reapOrphanShims()` в `start()` (при каждом поднятии worker) и в `onClose()`. Реапер — no-op вне Linux и никогда не роняет `start()`/`onClose()`: весь скан обёрнут, любая ошибка → log+skip.

- **Найти сироту.** Скан `/proc/[0-9]+/cmdline`: кандидат — `argv[0]` node-подобный И `basename(argv[1]) == "acp-shim.mjs"` (иначе `vim`/`grep acp-shim.mjs` получит kill). Из `/proc/<pid>/status` читается `PPid`. Сирота = `PPid` равен 1 или `/proc/<ppid>/comm == "systemd"` (покрывает PID1 и user-инстансы/subreaper'ов без резолва чужого PID).
- **Убить с деревом.** Лесенка, не голый KILL: `SIGTERM` шиму → grace ~8–10 с (новый shim сам добьёт detached-группу по §12.2; до-фиксный инстанс хотя бы форвардит TERM ребёнку) → `SIGKILL` шиму **и** явно его детям из `/proc/<pid>/task/*/children` (собрать до KILL, иначе дерево `agy` уйдёт в сироты — тот же класс утечки). Строка в `acp-wrapper.log`: pid, `AGY_SHIM_THREAD_ID` из `/proc/<pid>/environ`, возраст.
- **Maintenance-убийства probes** переведены на `killProcessTreeGracefully` — та же лесенка `SIGTERM` → grace ~9 с → сбор потомков `/proc/<pid>/task/*/children` → `SIGKILL` шиму и дереву. Раньше голый `child.kill("SIGKILL")` оставлял `agy acp` на EOF.
- **Каталоги `<os.tmpdir()>/agy-acp-*`** (остатки харнессов) — удалить только при ВСЕХ условиях: (a) каталог ≠ собственному `dataDir`/`shimDir` и не является его предком — реапер в `start()` крутится внутри процесса харнеса и увидит свежесозданный root «пустым»; (b) устаревание — ни одного файла с `mtime` моложе N мин (N=60): env харнеса выставляется после exec и в `/proc/<pid>/environ` его нет, значит единственный рабочий критерий «живости» — свежая запись; (c) ни один процесс **нашего uid** не ссылается внутрь каталога через `/proc/<pid>/cwd` или `/proc/<pid>/fd/*`. Скан ограничен процессами с uid == `getuid()` (uid — stat `/proc/<pid>`): mkdtemp-корни — `0700`, процессы чужого uid туда физически не входят, их fd/cwd не читаем и `EPERM` на них не считаем. `EPERM`/`EACCES` при чтении `cwd`/`fd` **живого** процесса своего uid разрешаем по сессии: читаем `/proc/<pid>/stat` (доступен всегда; поле `session` — 6-е поле `/proc/<pid>/stat` (4-е после `comm`: `state`, `ppid`, `pgrp`, `session`), `comm` парсится по последней `)` — в нём бывают пробелы и скобки, наивный `split(' ')` смещает индексы); процесс в **чужой** сессии — пропускаем (это сессионные/системные демоны с `dumpable=0` — `systemd --user`, `sd-pam`, `gpg-agent`, `sshd` и подобные; при демонизации они делают `setsid` и в пользовательские mkdtemp-корни не ходят). Same-uid процесс с `EPERM`/`EACCES` в **нашей** сессии = «ссылается», не удалять — демонов в нашей сессии нет, а скрывающий fd процесс рядом с нами повода для доверия не даёт. Это не граница безопасности против same-uid кода (тот может удалить каталог и напрямую), а защита от удаления каталога, занятого наблюдаемым процессом. Процесс, исчезнувший при скане (`ENOENT`/`ESRCH` при stat, `readlink`, `readdir` или чтении `/proc/<pid>/stat`), ссылкой не считается — завершившийся процесс каталог не держит. Ошибка `readlink` отдельного fd при уже прочитанном каталоге `fd/` классифицируется так же: `ENOENT`/`ESRCH` — fd пересоздан, пропуск; `EPERM`/`EACCES` — разрешение по сессии (процесс мог сбросить `dumpable` посреди скана); любой иной код или его отсутствие — «ссылается», не удалять. Переполнение бюджета скана — тот же отказ (не удалять).

### 12.5 Рантайм шима (настольный bb, 18.11.2026)
Шим — JS-файл, его запускает рантайм самого хоста: `process.execPath` в `buildLaunch()` (`launchSpec.command`) и в `queryAcpSessionModels()`. В серверном bb это `node`. В настольном bb (Electron, macOS/Linux/Windows) хост плагина — исполняемый файл `bb.app`, работающий как Node только при `ELECTRON_RUN_AS_NODE=1`; мост SDK вырезает эту переменную из окружения ребёнка (`withoutBridgeRuntimeEnv`), поэтому без неё бинарь bb стартует как приложение и сразу выходит (`exited (code 0)` до `initialize`).

- **Обёртка.** Если хост — Electron (`process.versions.electron` задан), в env шима в обоих местах запуска добавляется `ELECTRON_RUN_AS_NODE=1` (тот же приём, что у SDK для своего MCP-процесса). Отдельный Node на машине не нужен. В серверном bb env не меняется.
- **Шим.** Перед запуском настоящего `agy` удаляет `ELECTRON_RUN_AS_NODE` из env ребёнка — `agy` и его дочерние процессы не должны унаследовать режим.
- **Реапер §12.3.** Кандидат — `argv[0]` node-подобный **или** равен `process.execPath` хоста; остальные условия без изменений.

### 12.6 Шим всегда со своим окружением (PLUG-310, 18.11.2026)
Шим без `AGY_SHIM_REAL_BIN` выходит с кодом 2 (`acp-shim: AGY_SHIM_REAL_BIN is not set`). Инцидент 18.11: 13 раз за сутки на долгоживущем треде — после `turn/steer` (сообщение в идущий ход). Причина: обёртка пересылала опции steer как есть; демон кладёт туда статичный `acpLaunchSpec` с пустым `env`, мост SDK видел смену настроек и пересоздавал сессию командой шима без `AGY_SHIM_*`.

- **Каждый запрос с опциями** (`thread/start|resume`, `turn/start`, `turn/steer`, внутренние старты) для известной сессии проходит через `rewriteOptions` — `acpLaunchSpec` всегда тот, что собран `buildLaunch` для аккаунта сессии.
- **Страховка на выходе:** если до моста всё же доходит `acpLaunchSpec` с командой шима (`command = process.execPath` хоста) без `AGY_SHIM_*`, обёртка дополняет `env` из окружения запуска сессии (или собирает его заново); чужие спеки не трогаются. Страховка (`acpLaunchSpec` с командой шима без `AGY_SHIM_*`) сегодня по протоколу недостижима и оставлена как защита от будущих путей (ревизия 14, PLUG-306).
- **Неизвестный тред** (обёртка перезапустилась, сессии в памяти нет) на `turn/start|turn/steer`: обёртка восстанавливает сессию обычным внутренним `thread/resume` по локальной записи `threads-state.json` в каталоге данных (`threadId → cwd, providerThreadId, atMs`; атомарная запись, файл локальный, в репозиторий не попадает), исходный запрос ждёт окончания восстановления. Записи нет — явная ошибка `-32000`, без запуска шима. Синхронная ошибка внутреннего `thread/resume` превращается в ответ `-32000` исходному запросу, запись ожидания снимается, необработанного отказа промиса нет (ревизия 14, PLUG-306). `threads-state.json` ограничен: запись несёт `atMs` (время последней записи), хранится не больше 2000 записей, при превышении вытесняются самые давние; запись без `atMs` считается самой давней (ревизия 14, PLUG-306).
- Проверка: `harness-shim-env.mjs` — steer с пустым `env` в спеке, страховка, восстановление неизвестного треда; до исправления воспроизводит точный exit 2.

Не в scope: generic-мост bb (чужой код), stream-json мост (legacy за флагом), сторонний `google-antigravity-acp` (свой репозиторий rawizhere — та же болезнь, чинится отдельно).
