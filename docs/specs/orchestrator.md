# Orchestrator

Плагин переводит ручную раздачу работы координатором в код: правило маршрутизации становится данными, раздача — одним вызовом, сторож — частью плагина. Решения и их причины — [ADR-0015](../adr/0015-orchestrator.md).

Этапы: **MVP** (§1–§8), затем Fleet (§9), очередь и квоты (§10), профили (§11). Каждый этап выкладывается отдельно; старые механизмы (инструкции, внешний сторож, автоскрытие) работают рядом, пока владелец не отключит их отдельным словом.

## 1. Термины

| Термин | Значение |
|---|---|
| координатор | тред, который раздаёт работу (`BB_THREAD_ID` вызывающего агента) |
| исполнитель | тред, созданный раздачей; дочерний к координатору |
| уровень | класс задачи: `t1`, `t2`, `t3`, `review` (имена задаёт политика) |
| маршрут | пресет `bb tasks` + атрибуты для сторожа и квот (§2) |
| цепочка | упорядоченный список маршрутов уровня; следующий берётся при сбое предыдущего |
| делегирование | одна запись плагина: задача, исполнитель, маршрут, состояние (§7) |

## 2. Политика

Политика — JSON в настройке плагина `policy` (multiline). Пустая настройка — плагин работает с политикой по умолчанию из репозитория (`policy.default.json`, обезличенный профиль из гайда). Невалидная политика — плагин в статусе `needs-configuration` с текстом ошибки; раздача отклоняется, сторож продолжает следить за уже идущими делегированиями по сохранённым в них маршрутам.

```json
{
  "version": 1,
  "limits": { "maxActive": 5, "perLevel": { "t1": 3 } },
  "firstResponseSeconds": 90,
  "maxRunSeconds": 7200,
  "levels": {
    "t1": {
      "description": "архитектура, поиск причин, многофайловые фичи, миграции, рефакторинг",
      "chain": ["t1-complex", "t1-complex-alt"],
      "autoFallback": false
    },
    "t2": { "description": "обычные фичи и тесты по ясной спеке; задачи с картинками", "chain": ["t2-medium"], "autoFallback": true },
    "t3": { "description": "механические правки, документы, сбор данных", "chain": ["t3-simple", "t3-simple-alt"], "autoFallback": true },
    "review": { "description": "ревью спек до раздачи и результата после; только чтение", "chain": ["review"], "autoFallback": false }
  },
  "routes": {
    "t1-complex":     { "preset": "t1-complex",     "provider": "acp-devin" },
    "t1-complex-alt": { "preset": "t1-complex-alt", "provider": "agy" },
    "t2-medium":      { "preset": "t2-medium",      "provider": "agy" },
    "t3-simple":      { "preset": "t3-simple",      "provider": "acp-opencode", "quotaGroup": "opencode-zen" },
    "t3-simple-alt":  { "preset": "t3-simple-alt",  "provider": "acp-opencode" },
    "review":         { "preset": "review",         "provider": "acp-devin" }
  }
}
```

Правила валидации (каждое — отдельная ошибка с путём в JSON):
1. `version` = 1.
2. Каждый маршрут из `chain` есть в `routes`; каждый `routes.*.preset` существует в `bb tasks preset list` на момент загрузки политики. Отсутствующий пресет — предупреждение в статусе, маршрут помечается недоступным; уровень, у которого не осталось маршрутов, отклоняет раздачу.
3. `limits.maxActive` ≥ 1; `perLevel.*` ≤ `maxActive`.
4. `firstResponseSeconds` 30–600, `maxRunSeconds` ≥ 300.

Смысл `autoFallback: false`: сторож только снимает исполнителя и сообщает (§5.4), перевыпуск — решение координатора.

Модель, провайдер, усилие и права живут в пресете; политика их не дублирует. `provider` и `quotaGroup` нужны сторожу и квотам: какие ошибки считать исчерпанием (§5.2) и какие маршруты падают вместе. Маршрут без `quotaGroup` образует собственную группу с именем маршрута.

## 3. Инструкция для агентов

Плагин генерирует короткую инструкцию из политики: уровни с описаниями, правило «сложное не понижать», лимиты, как вызывать раздачу (§4) и что не ждать в форграунде. Текст ≤ 1500 символов, без ID тредов и путей.

- `bb orchestrator instructions` печатает текст.
- Настройка `injectInstructions` (по умолчанию `false`): `true` — текст подаётся через `bb.agents.configure` (динамические инструкции) только тредам-координаторам: треды без родителя (`thread.parentThreadId === null`). Исполнителям (дочерним тредам) ни инструкция, ни инструменты `orchestrator_*` не выдаются — рекурсивного делегирования нет. Выбор применяется при следующем построении сессии провайдера. В MVP выключено: действующие инструкции владельца не меняются без его слова.
- Инструменты агента (§6) выдаются по тому же правилу: только тредам без родителя, независимо от `injectInstructions`.

## 4. Раздача: `delegate`

Один вызов вместо «dispatch → thread update → options mode». Доступен как инструмент агента `orchestrator_delegate` и как CLI.

```
bb orchestrator delegate <TASK-KEY> --level <уровень> [--route <маршрут>] [--instructions <текст>] [--json]
```

Вход: ключ существующей задачи `bb tasks`, уровень из политики, необязательный маршрут (по умолчанию первый доступный в цепочке), необязательные доп. инструкции. Координатор — тред вызывающего агента: у инструмента — `PluginAgentToolContext.threadId`, у CLI — `PluginCliContext.threadId` (BB передаёт его из `BB_THREAD_ID`). Нет треда — вызов отклоняется.

Порядок, атомарный для вызывающего (все шаги или явная ошибка с тем, что успело выполниться). Вызовы `delegate` внутри плагина сериализуются (одна очередь на процесс); защиту на уровне базы даёт частичный уникальный индекс (§7).
1. Проверить политику, уровень, маршрут, лимиты (`maxActive`, `perLevel`) по делегированиям в статусах `dispatching`/`running`. Превышение — отказ с текущим счётчиком (очередь — этап §10).
2. Вставить запись делегирования со статусом `dispatching`. Если у задачи уже есть запись в `dispatching`/`running` — уникальный индекс отклоняет вставку → отказ «у задачи уже есть активный исполнитель» (защита от двойного запуска).
3. Выполнить `bb tasks dispatch <KEY> --preset <preset> [--instructions …] --json` (ответ `{task, preset, threadId}`) и взять `threadId`. У плагина `tasks` нет API привязки треда к задаче, поэтому раздача идёт через его CLI (ADR-0015 §1). Ошибка — запись удаляется, вызов возвращает ошибку.
4. Сразу привязать тред: `threads.update({threadId, parentThreadId: координатор, visibility: "hidden"})` и `bb thread update <threadId> --parent-notifications auto` через CLI — поля `parentNotifications` нет в типах `UpdateThreadRequest` SDK 0.4.87, сервер его принимает. Без него исполнитель не разбудит координатора, поэтому шаг обязателен.
5. Если пресет просит `permissionMode = full`, а провайдер сообщает опцию сессии `mode` со значением `bypass` и текущее значение другое — выставить `mode = bypass` (`bb thread options <id> --set mode=bypass`). Сразу после dispatch опции могут быть ещё пусты (сессия не построена) — шаг best-effort, повторяется при сверке (§7), пока сессия не сообщит опции или делегирование не закончится. Для `acp-devin` основное исправление — в провайдере ([provider-devin §1](provider-devin.md)); здесь — страховка.
6. Перевести запись в `running`, заполнить `thread_id`; комментарий в задачу через `bb tasks comment`: «Раздано: уровень, маршрут, тред».
7. Вернуть `{ delegationId, taskKey, threadId, level, route, status: "running" }`.

Ошибки шагов 4–6 не отменяют делегирование: запись в `running` с `setup_errors`, ответ содержит ошибку; сверка (§7) повторяет незавершённые шаги.

Инструмент агента возвращает ответ сразу и напоминает: закончить ход, отчёт придёт сообщением.

## 5. Сторож

Фоновый сервис плагина следит за каждым делегированием в статусе `running`. Заменяет внешний сторож и автоскрытие для делегирований этого плагина; треды, розданные вручную, не трогает.

### 5.1 Первый ответ (правило N секунд)

Окно открывается при старте хода исполнителя (`turn/started` или переход треда в `active`). Ответом считаются события: `item/started` (кроме `userMessage`), `item/completed`, дельты текста и размышлений, `item/toolCall/progress`, `item/commandExecution/outputDelta`. Если за `firstResponseSeconds` ответа нет — исполнитель **завис**: `threads.stop`, исход `stalled`.

Источник событий — подписка `experimental_thread.events` (не чаще раза в секунду) + чтение `threads.events.list` после последнего виденного номера. Таймер — на сервере, не зависит от опроса агентом.

Зависание до старта хода (подготовка рабочей копии, запуск провайдера) окно не ловит: оно открывается только с `turn/started`. В MVP такой случай виден лишь по `maxRunSeconds` (§5.3 `timeout`).

### 5.2 Исчерпание квоты

Первый сигнал — типизированный: `turn.failed` с `errorInfo.category` = `rate-limit` или `billing`. Запасной — текст события `provider/error`, `system/error` или ошибки хода совпадает с шаблоном квоты провайдера (`429`, `rate limit`, `quota`, `usage limit`, `Free usage limit reached`, `insufficient credits`; список — константа плагина, расширяемая в политике `routes.*.quotaPatterns`). Исход `quota`: запись → `quota`, затем `threads.stop`; все маршруты той же группы квоты (`quotaGroup`, а без неё — сам маршрут) помечаются недоступными на 15 минут.

### 5.3 Прочие исходы

Порядок для собственных остановок: **сначала статус в записи** (`stalled`, `quota`, `cancelled`), **потом** `threads.stop` — иначе свой стоп будет прочитан как внешний.

| Исход | Условие | Действие сторожа |
|---|---|---|
| `done` | `thread.idle` после начала хода, после `last_seq` нет `system/thread/interrupted`, `thread.archived`, `thread.deleted`, и очередь сообщений исполнителя пуста (`threads.queuedMessages.list`) | статус `done`; ничего не перевыпускать (отчёт координатору доставляет сам BB как дочернему треду). Очередь не пуста — делегирование остаётся `running`: начнётся новый ход |
| `cancelled` | `thread.idle` вместе с `system/thread/interrupted`, либо `thread.archived` / `thread.deleted`, и запись не была переведена сторожем в `stalled`/`quota` | статус `cancelled`, без перевыпуска, комментарий в задачу |
| `failed` | `thread.failed` / `turn.failed` без признаков квоты | статус `failed`, сообщение координатору с текстом ошибки |
| `approval` | `interaction.pending` у исполнителя | статус не меняется; сообщение координатору: какой запрос и команда для решения (`bb thread interactions approve\|grant\|answer\|respond`). Не чаще раза в 10 минут — по `last_approval_notified_at` |
| `stalled` | §5.1 | статус, стоп, затем §5.4 |
| `quota` | §5.2 | статус, стоп, затем §5.4 |
| `timeout` | дольше `maxRunSeconds` | одно сообщение координатору (`timeout_notified_at`); не останавливать |

### 5.4 Перевыпуск

Для `stalled` и `quota`:
- `autoFallback: true` и в цепочке есть следующий доступный маршрут → в одной транзакции старое делегирование переводится в `reissued`, а новое вставляется в `dispatching` с `reissue_of`; затем §4 шаги 3–7. Так перезапуск сервиса посреди перевыпуска не даёт дубля. Не больше одного автоперевыпуска на маршрут для задачи.
- иначе → статус `stalled`/`quota`, перевыпуска нет.

В обоих случаях: сообщение координатору (`threads.send` с `mode: "queue-if-active"`, текст начинается с `[orchestrator]`) и комментарий в задачу: исход, маршрут, новый тред или «перевыпуск за координатором». Сообщение не должно обрывать ход координатора: у Claude оно читается на границе шага, у `acp-devin` — ждёт конца хода ([provider-devin §2](provider-devin.md)).

## 6. CLI

```
bb orchestrator delegate <KEY> --level <уровень> [--route <r>] [--instructions <t>] [--json]
bb orchestrator status [--coordinator <thr>] [--all] [--json]   # делегирования и счётчики
bb orchestrator show <delegationId|threadId> [--json]
bb orchestrator cancel <delegationId|threadId>                   # стоп исполнителя, статус cancelled
bb orchestrator policy [show|validate] [--json]                  # действующая политика и ошибки
bb orchestrator instructions                                     # текст §3
bb orchestrator reconcile                                        # принудительная сверка §7
```

Инструменты агента: `orchestrator_delegate`, `orchestrator_status`, `orchestrator_cancel` (те же контракты). Ошибки CLI — по контракту `PluginCliRegistration`: `exitCode ≠ 0` и текст в `stderr`; с `--json` — `stdout` `{ok:false,error:{code,message,hint}}`. Инструменты агента возвращают ту же структуру ошибки.

## 7. Хранилище и сверка

SQLite плагина, миграции только добавлением.

`delegations`: `id`, `task_key`, `task_id`, `coordinator_thread_id`, `thread_id`, `level`, `route`, `preset`, `provider`, `status` (`dispatching|running|done|failed|stalled|quota|reissued|cancelled`), `reissue_of`, `turn_started_at`, `first_response_at`, `last_seq`, `setup_errors`, `last_approval_notified_at`, `timeout_notified_at`, `created_at`, `updated_at`. Частичный уникальный индекс `delegations(task_key) WHERE status IN ('dispatching','running')`.

`route_holds`: `quota_group` (группа квоты или имя маршрута без группы), `until`, `reason`.

Сверка — при старте сервиса и каждые 60 с: для каждого `running` перечитать тред и события после `last_seq`, применить §5; повторить незавершённые шаги §4.4–4.6. Тред не найден, удалён или в архиве → `cancelled`, повторы прекращаются. Запись в `dispatching` старше 5 минут без `thread_id` (сбой между шагами 2 и 3) — удаляется с комментарием в задачу. Перезапуск или перезагрузка плагина не теряет делегирования и не создаёт дубликаты перевыпуска (§5.4).

## 8. Совместимость и приёмка MVP

Рядом со старыми механизмами:
- делегирования плагина не трогают внешний сторож; внешний сторож не нужно запускать на треды плагина (иначе возможен двойной перевыпуск) — инструкция §3 об этом говорит;
- автоскрытие tasks-тредов и cron остаются; повторное скрытие безвредно;
- действующие инструкции агентов не меняются (`injectInstructions=false`).

Приёмку проводит координатор после слияния задач в main и установки плагина (отдельный шаг, не задача исполнителя; исполнители проверяют только тесты и сборку). Смоук гайда через плагин, в тестовом проекте трекера:
1. `delegate SMK-1 --level t3` → тред скрыт, дочерний к координатору, `parentNotifications=auto`, привязан к задаче (`bb tasks threads SMK-1`), комментарий «Раздано».
2. Отчёт исполнителя приходит координатору сообщением без опроса; `status` показывает `done`.
3. Повтор `delegate SMK-1` при активном исполнителе — отказ.
4. Зависание: политика с `firstResponseSeconds=30` и маршрутом, который не отвечает (тестовый пресет на заведомо молчащую модель или остановка хода сразу после старта) → `stalled`, стоп, перевыпуск на следующий маршрут цепочки, комментарий, сообщение координатору; новый тред скрыт и дочерний.
5. Перезагрузка плагина посреди работы исполнителя → после сверки статус верный, дубликатов нет.
6. `npm test`, `npm run typecheck` зелёные; тесты на политику, состояние, сторож (фальшивые события), CLI.

## 9. Этап 2: Fleet

Панель в треде координатора: список исполнителей (задача, уровень, маршрут, статус, время), выбор — чат исполнителя (`ThreadChat`) прямо в панели; действия «пауза» (стоп с сохранением треда), «продолжить» (сообщение исполнителю), «отменить». Индикатор в заголовке треда — только если есть делегирования. Пауза записывает статус до остановки, чтобы стоп не прочитался как `done`.

## 10. Этап 3: очередь и квоты

- Превышение лимитов — делегирование в статусе `queued` вместо отказа; запуск по освобождению слота, FIFO внутри уровня.
- Перед раздачей — `system.usageLimits()`: маршрут, у провайдера которого квота ниже порога политики, пропускается в пользу следующего.
- Обязательный шаг ревью: настройка уровня `requiresReview` — после `done` исполнителя плагин сам ставит задачу ревью на уровне `review` и сообщает координатору только после ревью.

## 11. Этап 4: профили

Набор политик (`profiles`) и выбор профиля в настройках: «как у нас», «Claude + ChatGPT», «только бесплатное» из гайда. Генерация пресетов из профиля (`bb orchestrator presets apply --profile <p> --dry-run`).
