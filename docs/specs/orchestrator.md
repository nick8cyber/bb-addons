# Orchestrator

Универсальный плагин оркестрации для BB. Любой пользователь ставит его и получает готовую логику: координатор декомпозирует работу в задачи `bb tasks`, раскладывает их по уровням сложности и раздаёт исполнителям на любых провайдерах (Claude Code, Codex, ACP-агенты вроде Devin и OpenCode, agy и другие), сторож следит за зависаниями и квотами. Плагин — единственный источник правил раздачи: навык координатора и правило маршрутизации идут из него, а не из ручных инструкций. Какие модели стоят на уровнях, решает пользователь: настраивает агент по инструкции плагина (§2.1), готовых наборов моделей плагин не навязывает.

Плагин не содержит логики конкретных провайдеров: он работает с тредами, задачами и событиями BB. Что плагин требует от провайдера и известные пробелы провайдеров — §12. Решения и их причины — [ADR-0015](../adr/0015-orchestrator.md).

Этапы: **MVP** (§1–§8, §2.1 инструкция настройки, §12, §13 роли), затем Fleet (§9), очередь и квоты (§10). Каждый этап выкладывается отдельно. На установке, где уже есть ручные механизмы (инструкции раздачи, внешний сторож, автоскрытие), они работают рядом до приёмки; переход — §8.

## 1. Термины

| Термин | Значение |
|---|---|
| координатор | тред, который раздаёт работу (`BB_THREAD_ID` вызывающего агента) |
| исполнитель | тред, созданный раздачей; дочерний к координатору |
| уровень | сложность задачи для исполнителя: `complex` (сложная), `medium` (средняя), `simple` (простая), `review` (проверка); имена задаёт политика |
| маршрут | пресет `bb tasks` + атрибуты для сторожа и квот (§2) |
| цепочка | упорядоченный список маршрутов уровня; следующий берётся при сбое предыдущего |
| делегирование | одна запись плагина: задача, исполнитель, маршрут, состояние (§7) |

## 2. Политика

Политика — JSON в настройке плагина `policy` (multiline). Пустая настройка — плагин в статусе `needs-configuration` с подсказкой «настройте через навык `orchestrator-setup`» (§2.1); раздача отклоняется. Пример ниже — образец формата, не значение по умолчанию. Невалидная политика — плагин в статусе `needs-configuration` с текстом ошибки; раздача отклоняется, сторож продолжает следить за уже идущими делегированиями по сохранённым в них маршрутам.

```json
{
  "version": 1,
  "limits": { "maxActive": 5, "perLevel": { "complex": 3 } },
  "firstResponseSeconds": 90,
  "maxRunSeconds": 7200,
  "levels": {
    "complex": {
      "description": "архитектура, поиск причин, многофайловые фичи, миграции, рефакторинг",
      "chain": ["complex", "complex-alt"],
      "autoFallback": false
    },
    "medium": { "description": "обычные фичи и тесты по ясной спеке; задачи с картинками", "chain": ["medium"], "autoFallback": true },
    "simple": { "description": "механические правки, документы, сбор данных", "chain": ["simple", "simple-alt"], "autoFallback": true },
    "review": { "description": "ревью спек до раздачи и результата после; только чтение", "chain": ["review"], "autoFallback": false }
  },
  "routes": {
    "complex":     { "preset": "complex",     "provider": "acp-devin" },
    "complex-alt": { "preset": "complex-alt", "provider": "agy" },
    "medium":      { "preset": "medium",      "provider": "agy" },
    "simple":      { "preset": "simple",      "provider": "acp-opencode", "quotaGroup": "opencode-zen", "quotaPatterns": ["Free usage limit reached"] },
    "simple-alt":  { "preset": "simple-alt",  "provider": "acp-opencode" },
    "review":         { "preset": "review",         "provider": "claude-code" }
  }
}
```

Проверка существования пресетов (`bb tasks preset list`) не выполняется синхронно при загрузке плагина — только при `policy validate`, при раздаче и в фоне не чаще раза в 10 минут (и только при изменении политики или наличии активных делегирований), с таймаутом вызова CLI 15 с, вне очереди `delegate`; предупреждения видны в `bb orchestrator policy show` и в журнале плагина (SDK не даёт плагину статус-предупреждений).

Правила валидации (каждое — отдельная ошибка с путём в JSON):
1. `version` = 1.
2. Каждый маршрут из `chain` есть в `routes`; каждый `routes.*.preset` существует в `bb tasks preset list` на момент загрузки политики. Отсутствующий пресет — предупреждение в статусе, маршрут помечается недоступным; уровень, у которого не осталось маршрутов, отклоняет раздачу.
3. `limits.maxActive` ≥ 1; `perLevel.*` ≤ `maxActive`.
4. `firstResponseSeconds` 30–600, `maxRunSeconds` ≥ 300.
5. Необязательное `routes.*.quotaPatterns` — массив непустых строк (подстроки без учёта регистра), не больше 20; дополняет встроенный список шаблонов квоты §5.2.
6. Необязательное `routes.*.unavailablePatterns` — то же для шаблонов снятой модели (§5.3 `unavailable`).

Смысл `autoFallback: false`: сторож только снимает исполнителя и сообщает (§5.4), перевыпуск — решение координатора.

Уровень `release-audit` — проверяющий агент выкладки (спека [release](orchestrator-release.md) §3): цепочка любой длины, рекомендуется `autoFallback: true`. Уровень нужен, только если включена команда `release`; без него `release` отказывает с подсказкой настроить. Координатор на этот уровень не раздаёт — его запускает только конвейер `release`.

Модель, провайдер, усилие и права живут в пресете; политика их не дублирует. `provider` и `quotaGroup` нужны сторожу и квотам: какие ошибки считать исчерпанием (§5.2) и какие маршруты падают вместе. Маршрут без `quotaGroup` образует собственную группу с именем маршрута.

### 2.1 Настройка: инструкция для агента

Плагин не содержит готовых наборов моделей. Настройку делает агент пользователя по навыку `orchestrator-setup` (поставляется в плагине):
1. Спросить пользователя, какие подписки и провайдеры у него есть и что жалко тратить.
2. Посмотреть, что реально доступно: `bb provider list`, `bb provider models <id>` (модели и уровни рассуждений — только из этого вывода).
3. Предложить, какой пресет на каком уровне (`complex` — сложное, `medium` — среднее, `simple` — простое, `review` — проверка) и цепочку резерва; показать таблицу пользователю и получить согласие.
4. Создать недостающие пресеты (`bb tasks preset create … --permission full --environment worktree` с контрактом исполнителя; ревьюеру — контракт «только чтение») или использовать уже существующие пресеты пользователя.
5. Записать политику (`bb plugin config orchestrator set policy …`), проверить `bb orchestrator policy validate`.

Навык выдаётся тредам с ролью, у которой можно раздавать (`delegates = true`, §13), всегда — настройка нужна до первой раздачи, даже если `injectInstructions = false`.

### 2.2 Правила работы с git

Отдельная настройка плагина `gitInstructions` (multiline, ≤ 1500 символов) — правила работы с git для исполнителей. Плагин добавляет её текст в начало `--instructions` при каждой раздаче (`delegate` и перевыпуск), отдельным разделом «Работа с git», перед доп. инструкциями вызова. Значение по умолчанию (обезличенное):

```text
Работа с git:
- Первым шагом: git fetch origin и перенос базовой ветки (git merge --ff-only origin/<база>); не вышло — вопрос координатору.
- Работай только в своей рабочей копии и своей ветке; не переключай чужие ветки и не трогай основной чекаут.
- Коммить под автором из конфига репозитория: без --author и git -c user.*; автор не задан — не коммить, напиши в отчёте.
- Без push и PR: локальный коммит, в отчёте ветка и SHA.
- Не запускай git reset --hard, git clean, git checkout -- и другие команды, теряющие чужую работу.
- Обход гейтов запрещён: никаких --no-verify, -c core.hooksPath=…, --author и записи core.hooksPath через git config (в любой области).
```

Пользователь меняет текст под свой репозиторий (база, именование веток, подпись); навык `orchestrator-setup` спрашивает об этом при настройке. Пустая строка — раздел не добавляется.

## 3. Правила для агентов: навык и правило маршрутизации

Плагин — единственный источник правил раздачи. Два слоя:

1. **Навык `orchestrator-coordinator`** (скилл в манифесте плагина, полный порядок работы): план — не команда; спека до раздачи; шаблон описания задачи; выбор уровня («сомневаешься — выше», «сложное не понижать»); раздача только через `delegate`; не ждать в форграунде — отчёт придёт сообщением; что делать по исходам сторожа; ревью до и после — на уровне `review`; проверка результата координатором; push и PR — только координатор. Текст навыка не содержит имён моделей и провайдеров — уровни и маршруты он берёт из `bb orchestrator instructions`.
2. **Короткое правило** (генерируется из политики, ≤ 1500 символов, без ID тредов и путей): уровни с описаниями, лимиты, команда `delegate`, отсылка к навыку. `bb orchestrator instructions` печатает его.

Подача:
- **Тред-координатор** — тред, чья роль разрешает раздавать (`delegates = true`; из коробки — `orchestrator`, §13). Роль берётся из таблицы `thread_roles` (§13.2). Если строки ещё нет — запасной критерий: нет родителя (`parentThreadId === null`) и нет признаков исполнителя:
  1. тред создан раздачей задач: `origin.pluginId === "tasks"` в контексте `configure` / `originPluginId === "tasks"` в хуке и DTO (основной признак, есть с рождения треда; заполненность в контексте `configure` проверяется живым тредом в PLUG-129);
  2. тред записан исполнителем в `delegations.thread_id`;
  3. запасные: заголовок в формате раздачи `bb tasks` — `<KEY> · …`; в том же bb-проекте (`delegations.project_id` = проект треда) есть запись `dispatching` без `thread_id` моложе 2 минут, созданная не этим тредом.
  Даже при утечке правила исполнителю раздать работу он не сможет: `delegate` проверяет вызывающего в момент вызова (§4).
- **Что выдаёт `bb.agents.configure`** (обработчик у плагина один — SDK допускает ровно один; выбор выдачи — отдельный модуль, который расширяют задачи этапов): тредам-координаторам — инструменты `orchestrator_*` всегда; если `injectInstructions = true` (по умолчанию) — ещё правило маршрутизации, навык `orchestrator-coordinator` и инструкция роли. Координатор по запасному критерию (строки в `thread_roles` нет) получает то же, что роль `orchestrator`, включая её инструкцию; строку при этом не записывает. Остальным ролям — их инструкция роли (если `injectInstructions = true`) и их инструменты/навыки. `injectInstructions = false` гасит **все** тексты плагина (правило, навыки координатора, инструкции ролей); остаются инструменты и навык `orchestrator-setup`.
- **Бюджет текста.** SDK отдаёт агенту одно поле `instructions` на плагин, обрезанное до 4096 символов. Плагин собирает его так: инструкция роли ≤ 2500 + правило маршрутизации ≤ 1500 + разделители; валидация длины при загрузке настроек и тест на самую длинную роль.
- **Устойчивость.** Ошибка внутри `configure` (база недоступна и т.п.) выключила бы выдачу плагина целиком (SDK fail-closed) — поэтому выбор роли обёрнут в обработку ошибок: при сбое роль по запасному критерию без записи, предупреждение в журнал.
- Выбор применяется при следующем построении сессии провайдера: живая сессия держит инструкции, с которыми построена.
- Дойдёт ли текст до агента, зависит от провайдера (§12): у провайдера, который не передаёт агенту инструкции BB, роль и правило недоступны — координатором такой провайдер в MVP не поддерживается, исполнителем — поддерживается (задача приходит в тексте раздачи).

## 4. Раздача: `delegate`

Один вызов вместо «dispatch → thread update → options mode». Доступен как инструмент агента `orchestrator_delegate` и как CLI.

```
bb orchestrator delegate <TASK-KEY> --level <уровень> [--route <маршрут>] [--instructions <текст>] [--json]
```

Вход: ключ существующей задачи `bb tasks` (ULID задачи приводится к ключу до проверок, чтобы защита от повтора работала по ключу), уровень из политики, необязательный маршрут (по умолчанию первый доступный в цепочке), необязательные доп. инструкции. Координатор — тред вызывающего агента: у инструмента — `PluginAgentToolContext.threadId`, у CLI — `PluginCliContext.threadId` (BB передаёт его из `BB_THREAD_ID`). Нет треда — вызов отклоняется. Тред не координатор по критерию §3 (роль без `delegates`, а без роли — родитель или признаки исполнителя) — вызов отклоняется с кодом `not-a-coordinator`: так исполнитель или аудитор не раздаст работу ни инструментом, ни через CLI из своей оболочки, даже если пользователь сам открыл его корневым чатом.

Порядок, атомарный для вызывающего (все шаги или явная ошибка с тем, что успело выполниться). Вызовы `delegate` внутри плагина сериализуются (одна очередь на процесс); защиту на уровне базы даёт частичный уникальный индекс (§7).
1. Проверить политику, уровень, маршрут, лимиты (`maxActive`, `perLevel`) по делегированиям в статусах `dispatching`/`running`. Превышение — отказ с текущим счётчиком (очередь — этап §10).
2. Вставить запись делегирования со статусом `dispatching`. Если у задачи уже есть запись в `dispatching`/`running` — уникальный индекс отклоняет вставку → отказ «у задачи уже есть активный исполнитель» (защита от двойного запуска).
3. Выполнить `bb tasks dispatch <KEY> --preset <preset> [--instructions …] --json` (ответ `{task, preset, threadId}`) и сразу записать `threadId` в `thread_id` записи (до следующих шагов). У плагина `tasks` нет API привязки треда к задаче, поэтому раздача идёт через его CLI (ADR-0015 §1). Явный отказ dispatch (CLI вернул ошибку с кодом) — запись удаляется, вызов возвращает ошибку. Таймаут или непонятный ответ (тред мог уже создаться) — запись остаётся `dispatching` без `thread_id`, вызов возвращает ошибку «результат раздачи неизвестен»; её разбирает сверка §7 (поиск треда через `bb tasks threads`).
4. Сразу привязать тред: `threads.update({threadId, parentThreadId: координатор, visibility: "hidden"})` и `bb thread update <threadId> --parent-notifications auto` через CLI — поля `parentNotifications` нет в типах `UpdateThreadRequest` SDK 0.4.87, сервер его принимает. Без него исполнитель не разбудит координатора, поэтому шаг обязателен. Там же — запись роли исполнителя в `thread_roles` (upsert, `source = delegate`): уровень `review` → `auditor`, остальные → `executor`. Если первая сессия исполнителя построилась раньше, исправленная роль вступит в силу со следующего построения.
5. Если пресет просит `permissionMode = full` (`bb tasks preset show <preset> --json` → `permissionMode`), а провайдер сообщает опцию сессии `mode` со значением `bypass` и текущее значение другое (`bb thread options <id> --json` → опция `mode`, её `values` и `value`) — выставить `mode = bypass` (`bb thread options <id> --set mode=bypass`). Сразу после dispatch опции могут быть ещё пусты (сессия не построена) — шаг best-effort, повторяется при сверке (§7), пока сессия не сообщит опции или делегирование не закончится. Для `acp-devin` основное исправление — в провайдере ([provider-devin §1](provider-devin.md)); здесь — страховка.
6. Перевести запись в `running` **только из `dispatching`** (условие в том же UPDATE); если запись уже `cancelled` (отменили во время раздачи) — остановить созданный тред и вернуть «отменено»; комментарий в задачу через `bb tasks comment`: «Раздано: уровень, маршрут, тред».
7. Вернуть `{ delegationId, taskKey, threadId, level, route, status: "running" }`.

Ошибки шагов 4–6 не отменяют делегирование: запись в `running` с `setup_errors`, ответ содержит ошибку; сверка (§7) повторяет незавершённые шаги.

Инструмент агента возвращает ответ сразу и напоминает: закончить ход, отчёт придёт сообщением.

## 5. Сторож

Фоновый сервис плагина следит за каждым делегированием в статусе `running`. Заменяет внешний сторож и автоскрытие для делегирований этого плагина; треды, розданные вручную, не трогает.

### 5.1 Первый ответ (правило N секунд)

Окно открывается при старте хода исполнителя (`turn/started` или переход треда в `active`). Ответом считаются события: `item/started` (кроме `userMessage`), `item/completed`, дельты текста и размышлений, `item/toolCall/progress`, `item/commandExecution/outputDelta`. Если за `firstResponseSeconds` ответа нет — исполнитель **завис**: `threads.stop`, исход `stalled`. Перед решением «завис» сторож обязательно дочитывает события треда после `last_seq` (`threads.events.list`): ответ, пришедший, но ещё не обработанный, отменяет решение. Если дочитать события не удалось (ошибка `threads.events.list`), решения «завис» нет — оно откладывается до следующей проверки; непрочитанный журнал не равен молчанию. Чтение — страницами не больше 100 событий (предел сервера BB).

Источник событий — подписка `experimental_thread.events` (не чаще раза в секунду) + чтение `threads.events.list` после последнего виденного номера. Таймер — на сервере, не зависит от опроса агентом.

Зависание до старта хода (подготовка рабочей копии, запуск провайдера) окно не ловит: оно открывается только с `turn/started`. В MVP такой случай виден лишь по `maxRunSeconds` (§5.3 `timeout`).

### 5.2 Исчерпание квоты

Первый сигнал — типизированный: `turn.failed` с `errorInfo.category` = `rate-limit` или `billing`; ответ провайдера «повторю сам» (`willRetry = true`) квотой не считается, пока провайдер не сдался. Решение по `thread.failed` принимается только после чтения событий хода: если среди них есть `turn.failed` с категорией квоты — исход `quota`, а не `failed`. Запасной — текст события `provider/error`, `system/error` или ошибки хода совпадает с шаблоном квоты провайдера (`429`, `rate limit`, `quota`, `usage limit`, `Free usage limit reached`, `insufficient credits`; список — константа плагина, расширяемая в политике `routes.*.quotaPatterns`). Исход `quota`: запись → `quota`, затем `threads.stop`; все маршруты той же группы квоты (`quotaGroup`, а без неё — сам маршрут) помечаются недоступными на 15 минут.

### 5.3 Прочие исходы

Порядок для собственных остановок: **сначала статус в записи** (`stalled`, `quota`, `cancelled`), **потом** `threads.stop` — иначе свой стоп будет прочитан как внешний.

| Исход | Условие | Действие сторожа |
|---|---|---|
| `done` | `thread.idle` после начала хода, после `last_seq` нет события потока `system/thread/interrupted`, тред не архивирован и не удалён (события `bb.events.on` `thread.archived`/`thread.deleted`, поля DTO `archivedAt`/`deletedAt`), и очередь сообщений исполнителя пуста (`threads.queuedMessages.list`) | статус `done`; ничего не перевыпускать (отчёт координатору доставляет сам BB как дочернему треду). Очередь не пуста — делегирование остаётся `running`: начнётся новый ход |
| `cancelled` | `thread.idle` вместе с событием потока `system/thread/interrupted` с причиной `manual-stop` (остановил пользователь или агент), либо тред архивирован или удалён (`bb.events.on` `thread.archived`/`thread.deleted`, поля DTO), и запись не была переведена сторожем в `stalled`/`quota` | статус `cancelled`, без перевыпуска, комментарий в задачу |
| `interrupted` | `system/thread/interrupted` с любой причиной, кроме `manual-stop` (перезапуск демона `host-daemon-restarted`, простой провайдера `provider-turn-idle` и т.п.) | не отмена. Первый раз: исполнителю одно сообщение `[orchestrator] ход прерван (<причина>), продолжай задачу`, статус остаётся `running` (`resume_count += 1`), координатору — уведомление. После «продолжай» новый ход должен начаться за `firstResponseSeconds`: не начался (сообщение не доставлено, тред в `idle` без нового хода и с пустой очередью) — как повторное прерывание. Повторно — как `stalled` (§5.4) |
| `failed` | `thread.failed` / `turn.failed` без признаков квоты | статус `failed`, сообщение координатору с текстом ошибки |
| `unavailable` | исполнитель не запустился, потому что провайдер не принял модель или маршрут: ошибка старта до первого хода (`thread.start failed`) или текст ошибки совпадает с шаблоном снятой модели (`model not found`, `model_not_found`, `unknown model`; список — константа плагина, расширяемая в политике `routes.*.unavailablePatterns`) | проверяется раньше `failed`. Статус `stalled` с причиной «маршрут недоступен», маршрут (не группа квоты) помечается недоступным на 15 минут (`route_holds`), затем §5.4; остановка считается подтверждённой — исполнитель не работает |
| `approval` | `interaction.pending` у исполнителя | статус не меняется; сообщение координатору: какой запрос и команда для решения (`bb thread interactions approve\|deny\|grant\|answer\|respond`). Не чаще раза в 10 минут — по `last_approval_notified_at` |
| `stalled` | §5.1 | статус, стоп, затем §5.4 |
| `quota` | §5.2 | статус, стоп, затем §5.4 |
| `timeout` | дольше `maxRunSeconds` | одно сообщение координатору (`timeout_notified_at`); не останавливать |

### 5.4 Перевыпуск

Для `stalled` и `quota`:
- Остановка старого исполнителя должна подтвердиться (`threads.stop` без ошибки и тред не `active`); не подтвердилась — перевыпуска нет: статус остаётся, координатору сообщение «не удалось остановить исполнителя», сверка повторит.
- `autoFallback: true` и в цепочке есть следующий доступный маршрут **после текущего** (лимит — только автоперевыпуски этой задачи, ручные делегирования маршрут не исключают) → в одной транзакции старое делегирование переводится в `reissued`, а новое вставляется в `dispatching` с `reissue_of`; затем §4 шаги 3–7. Так перезапуск сервиса посреди перевыпуска не даёт дубля. Сверка доводит новую запись `dispatching` с `reissue_of` до раздачи (не удаляет её); если раздача невозможна (явный отказ — и сразу, и в сверке) — новая запись `failed`, координатору сообщение о потере перевыпуска. Не больше одного автоперевыпуска на маршрут для задачи.
- Вставка новой записи невозможна, потому что у задачи уже есть активное делегирование (координатор раздал вручную, пока сторож останавливал старого) → перевыпуска нет: старая запись остаётся `stalled`/`quota`, координатору одно сообщение «перевыпуск за координатором: у задачи уже есть активное делегирование», повторов нет.
- иначе → статус `stalled`/`quota`, перевыпуска нет.

В обоих случаях: сообщение координатору (`threads.send` с `mode: "queue-if-active"`, текст начинается с `[orchestrator]`) и комментарий в задачу: исход, маршрут, новый тред или «перевыпуск за координатором». Сообщение не должно обрывать ход координатора: у Claude оно читается на границе шага, у `acp-devin` — ждёт конца хода ([provider-devin §2](provider-devin.md)).

## 7. Хранилище и сверка

SQLite плагина, миграции только добавлением.

`delegations`: `id`, `task_key`, `task_id`, `project_id` (bb-проект координатора), `coordinator_thread_id`, `thread_id`, `level`, `route`, `preset`, `provider`, `status` (`dispatching|running|done|failed|stalled|quota|reissued|cancelled`), `reissue_of`, `turn_started_at`, `first_response_at`, `last_seq`, `setup_errors`, `last_approval_notified_at`, `timeout_notified_at`, `resume_count`, `retry_count`, `created_at`, `updated_at`. Частичный уникальный индекс `delegations(task_key) WHERE status IN ('dispatching','running')`.

`route_holds`: `quota_group` (группа квоты или имя маршрута без группы), `until`, `reason`.

`pending_roles`: `project_id` (ключ), `role`, `updated_at` — текущий выбор в окне нового чата. `thread_roles`: `thread_id` (ключ), `role`, `decided_at`, `source` (`hook|delegate`) — §13.2. Обе таблицы и их миграции добавляет PLUG-141 (после миграций PLUG-129).

Сверка — при старте сервиса и каждые 60 с: для каждого `running` перечитать тред и события после `last_seq`, применить §5; повторить незавершённые шаги §4.4–4.6. Тред не найден, удалён или в архиве → `cancelled`, повторы прекращаются.

Предел повторов: сверка повторяет одно и то же действие по записи (неподтверждённая остановка §5.4, доведение `dispatching` с `reissue_of` при неизвестном исходе раздачи) не больше 10 раз подряд (`retry_count`, сброс при успехе). Предел исчерпан — повторы прекращаются, ошибка `retry-exhausted` в `setup_errors`, координатору одно сообщение с последней ошибкой и командой для ручного решения. Запись в `dispatching` старше 5 минут: с `thread_id` — довести шаги 4–6; без `thread_id` — найти тред задачи через `bb tasks threads <KEY> --json`, созданный после `created_at` записи: нашёлся — записать и довести шаги 4–6, нет — удалить запись с комментарием в задачу. Перезапуск или перезагрузка плагина не теряет делегирования и не создаёт дубликаты перевыпуска (§5.4).

## 8. Совместимость и приёмка MVP

Рядом со старыми механизмами:
- делегирования плагина не трогают внешний сторож; внешний сторож не нужно запускать на треды плагина (иначе возможен двойной перевыпуск) — инструкция §3 об этом говорит;
- автоскрытие tasks-тредов и cron остаются; повторное скрытие безвредно;
- до перехода на установке с ручными инструкциями раздачи держать `injectInstructions = false` (по умолчанию `true`, §3), чтобы правило плагина не дублировало ручное.

Переход на установке с ручными механизмами — после приёмки и отдельным шагом координатора: своя политика, записанная по навыку `orchestrator-setup`, `injectInstructions=true`, ручные инструкции раздачи отключаются (у нас — плагин `orchestration-notes`), внешний сторож и автоскрытие остаются страховкой, пока владелец не отключит их отдельным словом. Провайдерные «костыли» раздачи (хуки, дописывающие флаги к `bb thread spawn` и привязку после `bb tasks dispatch`) удаляются: раздача идёт через `delegate`.

Приёмку проводит координатор после слияния задач в main и установки плагина (отдельный шаг, не задача исполнителя; исполнители проверяют только тесты и сборку). Смоук гайда через плагин, в тестовом проекте трекера:
1. `delegate SMK-1 --level simple` → тред скрыт, дочерний к координатору, `parentNotifications=auto`, привязан к задаче (`bb tasks threads SMK-1`), комментарий «Раздано».
2. Отчёт исполнителя приходит координатору сообщением без опроса; `status` показывает `done`.
3. Повтор `delegate SMK-1` при активном исполнителе — отказ.
4. Зависание: политика с `firstResponseSeconds=30` и маршрутом, который не отвечает (тестовый пресет на заведомо молчащую модель или остановка хода сразу после старта) → `stalled`, стоп, перевыпуск на следующий маршрут цепочки, комментарий, сообщение координатору; новый тред скрыт и дочерний.
5. Перезагрузка плагина посреди работы исполнителя → после сверки статус верный, дубликатов нет.
6. Роли: новый чат с выбранной в окне ролью `auditor` → `thread_roles` = `auditor` записан хуком раньше первого построения сессии, агент цитирует инструкцию роли; `delegate --level review` → исполнитель `auditor`, агент ревьюера цитирует инструкцию `auditor` уже в первом ходе; тред с ролью `executor` получает `not-a-coordinator` и через CLI; тред из `bb tasks dispatch` без `delegate` → `executor`.
7. Сжатие: Claude Code — после сжатия контекста инструкция роли на месте (агент цитирует её); Codex — то же, отдельный пункт (не проверялось).
8. `npm test`, `npm run typecheck` зелёные; тесты на политику, состояние, сторож (фальшивые события), роли, CLI.

## 9. Этап 2: Fleet

Панель в треде координатора: список исполнителей (задача, уровень, маршрут, статус, время), выбор — чат исполнителя (`ThreadChat`) прямо в панели; действия «пауза» (стоп с сохранением треда), «продолжить» (сообщение исполнителю), «отменить». Индикатор в заголовке треда — только если есть делегирования. Пауза записывает статус до остановки, чтобы стоп не прочитался как `done`.

## 10. Этап 3: очередь и квоты

- Превышение лимитов — делегирование в статусе `queued` вместо отказа; запуск по освобождению слота, FIFO внутри уровня.
- Перед раздачей — `system.usageLimits()`: маршрут, у провайдера которого квота ниже порога политики, пропускается в пользу следующего.
- Обязательный шаг ревью: настройка уровня `requiresReview` — после `done` исполнителя плагин сам ставит задачу ревью на уровне `review` и сообщает координатору только после ревью.

## 11. Этап 4: обмен политикой

Экспорт и импорт политики (`bb orchestrator policy export|import`) для передачи своей схемы другому пользователю; без секретов и ID тредов. Пресеты по именам из политики пользователь заводит у себя сам (навык `orchestrator-setup`).

## 12. Что плагин требует от провайдера

| Требование | Зачем | Где проверено |
|---|---|---|
| События треда BB (`turn/started`, `item/*`, `turn.failed`, idle/failed) | сторож §5 | общие для всех провайдеров — их пишет BB |
| `permissionMode = full` доходит до агента | исполнитель не висит на подтверждении | Claude Code, Codex — да; Devin — после [provider-devin §1](provider-devin.md); agy — работает только в `full`; другие ACP-агенты — не проверено |
| Динамические инструкции BB доходят до агента | правило и навык координатора §3 | Claude Code — в системной части каждого запроса; Codex — не проверено (§8 п.7); ACP-агенты — один раз текстом в начале сессии (Devin — с возвратом после сжатия); agy — **не доходят** (мост не передаёт `instructions`) |
| Сообщение посреди хода не обрывает команду | сообщения сторожа §5.4 | Claude Code — да; Devin — после [provider-devin §2](provider-devin.md); прочие ACP-агенты — вероятно обрывает (общий код моста), не проверено |

## 13. Роли агента

Роль — инструкция и принцип работы агента в треде плюс набор инструментов плагина, доступных ему. Роль выбирается при старте треда; по умолчанию — оркестратор. MVP — три встроенные роли и выбор в окне нового чата; свои роли пользователя и роль исследователя — следующий этап (§13.4).

### 13.1 Роли MVP

| Роль | Принцип | `delegates` | Инструменты и навыки плагина |
|---|---|---|---|
| `orchestrator` (по умолчанию) | сам задачу не выполняет: декомпозирует в задачи `bb tasks`, раздаёт исполнителям через `delegate` по уровням, проверяет и сводит результат | да | `orchestrator_delegate`, `orchestrator_status`, `orchestrator_cancel`; навыки `orchestrator-coordinator`, `orchestrator-setup` |
| `executor` | выполняет задачу сам, субагентов не запускает, отчитывается по контракту задачи | нет | нет |
| `auditor` | только читает и проверяет: находки «место → проблема → исправление», вердикт; ничего не правит и не коммитит | нет | нет |
| `release-auditor` | проверяющий агент конвейера выкладки: только чтение, строгий JSON-вердикт APPROVE/REJECT по актуальности документов и утечкам ([release](orchestrator-release.md) §3) | нет | нет |

Инструкции ролей — константы плагина, каждая ≤ 2500 символов (§3, бюджет).

Роль `release-auditor` в окне нового чата не предлагается: её получает только тред аудита, запущенный `release` (запись в `thread_roles` с `source = delegate`).

### 13.2 Выбор роли и привязка к треду

1. **Окно нового чата.** Плагин добавляет в строку действий окна нового чата выпадающий список «Роль» (`composer.customize`, область `new-thread`; точное место — по SDK, «рядом с выбором модели» не гарантируется). При монтировании и при каждой смене список вызывает RPC `setPendingRole({projectId, role})` → таблица `pending_roles(project_id, role, updated_at)` хранит **текущий выбор** проекта (не удаляется при использовании). `projectId = null` (чат без проекта) → роль по умолчанию. Известное ограничение MVP: выбор хранится на проект, поэтому окно нового чата того же проекта, открытое на другом устройстве, перезапишет выбор — побеждает последнее открытое или изменённое окно.
2. **Решение роли — хук `message.dispatch`.** Хук срабатывает до подготовки окружения и построения сессии. Поля: `thread.status`, `thread.originPluginId` (источник треда; корневой `originPluginId` контекста — источник конкретной отправки, им не пользоваться), `thread.parentThreadId`, `thread.sourceThreadId`, `thread.title`, `origin`, `attempt`. Роль решается только на первом сообщении треда: `attempt = start-turn`, `thread.status = "pending"`, треда нет в `thread_roles`. Правило по порядку:
   - `thread.originPluginId = "tasks"` → исполнитель: ключ задачи из заголовка `<KEY> · …` (он есть с рождения треда) → запись делегирования этой задачи в `dispatching`/`running` → уровень `review` → `auditor`, иначе `executor`; записи нет → `executor`;
   - есть `thread.sourceThreadId` (боковой чат, передача сессии) → роль источника из `thread_roles`; нет строки — дальше по правилу;
   - есть `thread.parentThreadId` → `executor`;
   - `origin = "app"` (новый чат из окна) → текущий выбор проекта (`pending_roles.role`); выбора нет → `orchestrator`;
   - иначе (`cli`, `plugin`, `sdk`, автоматизации) → `orchestrator`.
   Результат — в `thread_roles(thread_id, role, decided_at, source)`, `source ∈ {hook, delegate}` (запасной критерий §3 ничего не записывает).
   **Хук fail-closed по SDK:** исключение или ответ дольше 10 с не дают сообщению уйти, а хуки выполняются под общей блокировкой сервера. Поэтому весь обработчик — в `try/catch` с ответом «пропустить» при любой ошибке, внутри только синхронный SQLite плагина: без CLI, сети и `await`. Тесты: исключение внутри → «пропустить»; время обработчика в тестах < 50 мс.
3. **`configure` только читает `thread_roles`;** нет строки — запасной критерий §3. Тест на порядок «хук раньше первого `configure`» — в PLUG-141, живая проверка — в приёмке §8 п.6.
4. **`pluginMetadata.role`** пишется после решения — только для показа и других плагинов. Источник правды — `thread_roles`: метаданные плагина может переписать сам агент треда.
5. **Ограничение.** Плагин выдаёт и отнимает только свои инструменты; встроенные инструменты провайдера (правка файлов, оболочка) он отключить не может. «Оркестратор сам не делает» и «аудитор только читает» держатся на инструкции роли и на правах пресета.

### 13.3 Подача инструкции роли

По §3: инструкция роли идёт в общем поле `instructions` (бюджет 2500), при `injectInstructions = false` не подаётся. У Claude Code инструкции плагинов BB — в системной части запроса; Codex — проверяется приёмкой §8. У ACP-агентов — по возможностям провайдера (§12): у Devin инструкции возвращаются после сжатия плагином `provider-devin`; у agy инструкции пока не доходят (PLUG-139) — роль у него до исправления не работает.

### 13.4 Следующий этап: свои роли

Роли — JSON в настройке `roles`: `id`, `name`, `instructions` (≤ 2500), `tools`, `skills`, `delegates`. Валидация при загрузке настроек: `tools` и `skills` — только из списка плагина (неизвестное имя в `configure` выключило бы выдачу плагина всем тредам), ошибка → `needs-configuration`. Шаблон `researcher` (собирает и анализирует сведения, цитирует источники, выводы отделяет от фактов). Роль работает и в одиночном режиме (пользователь сам открыл чат исполнителя или аудитора), и в мультиагентном.
