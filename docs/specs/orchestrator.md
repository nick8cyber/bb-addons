# Orchestrator

Универсальный плагин оркестрации для BB. Любой пользователь ставит его и получает готовую логику: координатор декомпозирует работу в задачи `bb tasks`, раскладывает их по уровням сложности и раздаёт исполнителям на любых провайдерах (Claude Code, Codex, ACP-агенты вроде Devin и OpenCode, agy и другие), сторож следит за зависаниями и квотами. Плагин — единственный источник правил раздачи: навык координатора и правило маршрутизации идут из него, а не из ручных инструкций. Какие модели стоят на уровнях, решает пользователь: настраивает агент по инструкции плагина (§2.1), готовых наборов моделей плагин не навязывает.

Плагин не содержит логики конкретных провайдеров: он работает с тредами, задачами и событиями BB. Что плагин требует от провайдера и известные пробелы провайдеров — §12. Решения и их причины — [ADR-0015](../adr/0015-orchestrator.md).

Текущее состояние — ревизия 26: разделы §16 (решения по аудиту архитектуры) и §17 (по аудиту реализации и e2e) **перекрывают** ранние разделы там, где расходятся.

Этапы: **MVP** (§1–§8, §2.1 инструкция настройки, §12, §13 роли), **ветки и уборка** (§4.1 заходы, §14 вливание, §15 уборщик; ревизия 23, [ADR-0024](../adr/0024-orchestrator-branches-janitor.md)), затем Fleet (§9), очередь и квоты (§10). Каждый этап выкладывается отдельно. На установке, где уже есть ручные механизмы (инструкции раздачи, внешний сторож, автоскрытие), они работают рядом до приёмки; переход — §8.

## 1. Термины

| Термин | Значение |
|---|---|
| координатор | тред, который раздаёт работу (`BB_THREAD_ID` вызывающего агента) |
| исполнитель | тред, созданный раздачей; дочерний к координатору |
| уровень | сложность задачи для исполнителя: `complex` (сложная), `medium` (средняя), `simple` (простая), `review` (проверка); имена задаёт политика |
| маршрут | пресет `bb tasks` + атрибуты для сторожа и квот (§2) |
| цепочка | упорядоченный список маршрутов уровня; следующий берётся при сбое предыдущего |
| делегирование | одна запись плагина: задача, исполнитель, маршрут, состояние (§7) |

## 2. Политика

Политика — JSON в настройке плагина `policy` (multiline). Пустая настройка — плагин в статусе `needs-configuration` с подсказкой «настройте через навык `orchestrator-setup`» (§2.1); раздача отклоняется. Пример ниже — образец формата, не значение по умолчанию. Невалидная политика — плагин в статусе `needs-configuration` с текстом ошибки; раздача отклоняется, сторож продолжает следить за уже идущими делегированиями по сохранённым в них маршрутам.

```json
{
  "version": 1,
  "limits": { "maxActive": 5, "perLevel": { "complex": 3 } },
  "firstResponseSeconds": 90,
  "maxRunSeconds": 7200,
  "levels": {
    "complex": {
      "description": "архитектура, поиск причин, многофайловые фичи, миграции, рефакторинг",
      "chain": ["complex", "complex-alt"],
      "autoFallback": false
    },
    "medium": { "description": "обычные фичи и тесты по ясной спеке; задачи с картинками", "chain": ["medium"], "autoFallback": true },
    "simple": { "description": "механические правки, документы, сбор данных", "chain": ["simple", "simple-alt"], "autoFallback": true },
    "review": { "description": "ревью спек до раздачи и результата после; только чтение", "chain": ["review"], "autoFallback": false }
  },
  "routes": {
    "complex":     { "preset": "complex",     "provider": "acp-devin" },
    "complex-alt": { "preset": "complex-alt", "provider": "agy" },
    "medium":      { "preset": "medium",      "provider": "agy", "firstResponseSeconds": 300 },
    "simple":      { "preset": "simple",      "provider": "acp-opencode", "quotaGroup": "opencode-zen", "quotaPatterns": ["Free usage limit reached"] },
    "simple-alt":  { "preset": "simple-alt",  "provider": "acp-opencode" },
    "review":         { "preset": "review",         "provider": "claude-code" }
  }
}
```

Проверка существования пресетов (`bb tasks preset list`) не выполняется синхронно при загрузке плагина — только при `policy validate`, при раздаче и в фоне не чаще раза в 10 минут (и только при изменении политики или наличии активных делегирований), с таймаутом вызова CLI 15 с, вне очереди `delegate`; предупреждения видны в `bb orchestrator policy show` и в журнале плагина (SDK не даёт плагину статус-предупреждений).

Правила валидации (каждое — отдельная ошибка с путём в JSON):
1. `version` = 1.
2. Каждый маршрут из `chain` есть в `routes`; каждый `routes.*.preset` существует в `bb tasks preset list` на момент загрузки политики. Отсутствующий пресет — предупреждение в статусе, маршрут помечается недоступным; уровень, у которого не осталось маршрутов, отклоняет раздачу.
3. `limits.maxActive` ≥ 1; `perLevel.*` ≤ `maxActive`.
4. `firstResponseSeconds` 30–600 (общий и необязательный `routes.*.firstResponseSeconds` — перекрывает общий для маршрута; нужен провайдерам с долгим холодным стартом, например agy — 1,5–3 мин, §12), `maxRunSeconds` ≥ 300.
5. Необязательное `routes.*.quotaPatterns` — массив непустых строк (подстроки без учёта регистра), не больше 20; дополняет встроенный список шаблонов квоты §5.2.
6. Необязательное `routes.*.unavailablePatterns` — то же для шаблонов снятой модели (§5.3 `unavailable`).

Смысл `autoFallback: false`: сторож только снимает исполнителя и сообщает (§5.4), перевыпуск — решение координатора.

Уровень `release-audit` — проверяющий агент выкладки (спека [release](orchestrator-release.md) §3): цепочка любой длины, рекомендуется `autoFallback: true`. Уровень нужен, только если включена команда `release`; без него `release` отказывает с подсказкой настроить. Координатор на этот уровень не раздаёт — его запускает только конвейер `release`.

Модель, провайдер, усилие и права живут в пресете; политика их не дублирует. `provider` и `quotaGroup` нужны сторожу и квотам: какие ошибки считать исчерпанием (§5.2) и какие маршруты падают вместе. Маршрут без `quotaGroup` образует собственную группу с именем маршрута.

### 2.1 Настройка: инструкция для агента

Плагин не содержит готовых наборов моделей. Настройку делает агент пользователя по навыку `orchestrator-setup` (поставляется в плагине):
1. Спросить пользователя, какие подписки и провайдеры у него есть и что жалко тратить.
2. Посмотреть, что реально доступно: `bb provider list`, `bb provider models <id>` (модели и уровни рассуждений — только из этого вывода).
3. Предложить, какой пресет на каком уровне (`complex` — сложное, `medium` — среднее, `simple` — простое, `review` — проверка) и цепочку резерва; показать таблицу пользователю и получить согласие.
4. Создать недостающие пресеты (`bb tasks preset create … --permission full --environment worktree` с контрактом исполнителя; ревьюеру — контракт «только чтение») или использовать уже существующие пресеты пользователя.
5. Записать политику (`bb plugin config orchestrator set policy …`), проверить `bb orchestrator policy validate`.

Навык выдаётся тредам с ролью, у которой можно раздавать (`delegates = true`, §13), всегда — настройка нужна до первой раздачи, даже если `injectInstructions = false`.

### 2.3 Ревью по сложности и модель по просьбе (ревизия 24)

**Роль уровня.** Необязательное поле уровня `role`: `"auditor"` или `"executor"` (по умолчанию `executor`; уровень с именем `review` без поля — `auditor`, как раньше). Делегирования уровня с ролью `auditor` получают роль `auditor` (§4 шаг 4, §13), не проверяются итогом захода (§4.1) и считаются ревью в `release` ([release](orchestrator-release.md) §2 шаг 1). Уровней-ревью может быть несколько.

**Модели ревью — настройка пользователя**, как и у исполнителей: уровни ревью — обычные уровни политики со своими цепочками маршрутов и пресетов, пользователь меняет модели правкой политики (навык `orchestrator-setup` спрашивает модель для каждого уровня ревью так же, как для уровней исполнителей); плагин моделей не навязывает. Пример владельца: сложное — Opus 5.5 High, среднее — Gemini 3.8 High, простое — SWE-2.

**Ревью по сложности.** Необязательное поле политики `reviewByLevel` — какой уровень ревью брать по сложности проверяемой работы:

```json
"reviewByLevel": { "complex": "review", "medium": "review-medium", "simple": "review-simple" }
```

`delegate <KEY> --level review` при заданном `reviewByLevel`: плагин берёт уровень **последнего по времени** делегирования задачи с ролью `executor` (любого уровня, есть он в карте или нет) и раздаёт на уровень `reviewByLevel[<он>]`; в ответе и комментарии — «review → review-medium по сложности исполнения medium». Нет делегирований исполнителя (ревью спеки, плана) или уровня нет в карте — остаётся `review`. Явный уровень ревью (`--level review-simple`) карту не применяет. Валидация: каждое значение карты — уровень политики с ролью `auditor`.

**Модель по просьбе пользователя.** Пользователь в треде координатора может попросить другую модель для конкретной раздачи:
- `--route <маршрут>` — любой маршрут из `routes` политики, не только из цепочки уровня;
- `--preset <пресет>` — разовый пресет вне политики (например, разовый аудит на другой модели); пресет должен существовать (`bb tasks preset show`), провайдер берётся из пресета, маршрут записывается как `preset:<имя>`, квота разового пресета — по модели: исчерпание закрывает (`route_holds`, 15 минут) все маршруты политики с тем же провайдером **и той же моделью** (по `bb tasks preset show` их пресетов; модели сравниваются без суффикса варианта в квадратных скобках — `claude-opus-5-5[1m]` и `claude-opus-5-5` одна квота), перевыпуск их пропускает; маршруты того же провайдера с другими моделями (например, разные бесплатные модели OpenCode) открыты.

`--route` и `--preset` взаимоисключающие; с любым из них карта `reviewByLevel` не применяется — цепочка перевыпуска берётся у уровня из `--level` как есть. Сторож следит за такой раздачей как за любой другой. Перевыпуск (§5.4) при `autoFallback: true` продолжает **цепочку уровня с её начала**, пропуская маршруты, уже использованные этой задачей. Без `autoFallback` — только сообщение координатору. Разовые модели в политику не вносятся. Инструмент `orchestrator_delegate` принимает те же поля `route` и `preset`.

Правило §3 и навык координатора: уровень ревью — `review`, плагин сам подберёт модель по сложности; просьба пользователя «проверь на <модели>» — `--route` или `--preset`, не правка политики.

### 2.2 Правила работы с git

Отдельная настройка плагина `gitInstructions` (multiline, ≤ 1500 символов) — правила работы с git для исполнителей. Плагин добавляет её текст в начало `--instructions` при каждой раздаче (`delegate` и перевыпуск), отдельным разделом «Работа с git», перед доп. инструкциями вызова. Значение по умолчанию (обезличенное):

```text
Работа с git:
- Первым шагом: git fetch origin и перенос базовой ветки (git merge --ff-only origin/<база>); не вышло — вопрос координатору.
- Работай только в своей рабочей копии и своей ветке; не переключай чужие ветки и не трогай основной чекаут.
- Коммить под автором из конфига репозитория: без --author и git -c user.*; автор не задан — не коммить, напиши в отчёте.
- Без push и PR: локальный коммит, в отчёте ветка и SHA.
- Не запускай git reset --hard, git clean, git checkout -- и другие команды, теряющие чужую работу.
- Обход гейтов запрещён: никаких --no-verify, -c core.hooksPath=…, --author и записи core.hooksPath через git config (в любой области).
```

Пользователь меняет текст под свой репозиторий (база, именование веток, подпись); навык `orchestrator-setup` спрашивает об этом при настройке. Пустая строка — раздел не добавляется.

## 3. Правила для агентов: навык и правило маршрутизации

Плагин — единственный источник правил раздачи. Два слоя:

1. **Навык `orchestrator-coordinator`** (скилл в манифесте плагина, полный порядок работы): план — не команда; спека до раздачи; шаблон описания задачи; выбор уровня («сомневаешься — выше», «сложное не понижать»); раздача только через `delegate`; не ждать в форграунде — отчёт придёт сообщением; что делать по исходам сторожа; ревью до и после — на уровне `review`; проверка результата координатором; push и PR — только координатор. Текст навыка не содержит имён моделей и провайдеров — уровни и маршруты он берёт из `bb orchestrator instructions`.
2. **Короткое правило** (генерируется из политики, ≤ 1500 символов, без ID тредов и путей): уровни с описаниями, лимиты, команда `delegate`, отсылка к навыку. `bb orchestrator instructions` печатает его.

Подача:
- **Тред-координатор** — тред, чья роль разрешает раздавать (`delegates = true`; из коробки — `orchestrator`, §13). Роль берётся из таблицы `thread_roles` (§13.2). Если строки ещё нет — запасной критерий: нет родителя (`parentThreadId === null`) и нет признаков исполнителя:
  1. тред создан раздачей задач: `origin.pluginId === "tasks"` в контексте `configure` / `originPluginId === "tasks"` в хуке и DTO (основной признак, есть с рождения треда; заполненность в контексте `configure` проверяется живым тредом в PLUG-129);
  2. тред записан исполнителем в `delegations.thread_id`;
  3. запасные: заголовок в формате раздачи `bb tasks` — `<KEY> · …`; в том же bb-проекте (`delegations.project_id` = проект треда) есть запись `dispatching` без `thread_id` моложе 2 минут, созданная не этим тредом.
  Даже при утечке правила исполнителю раздать работу он не сможет: `delegate` проверяет вызывающего в момент вызова (§4).
- **Что выдаёт `bb.agents.configure`** (обработчик у плагина один — SDK допускает ровно один; выбор выдачи — отдельный модуль, который расширяют задачи этапов): тредам-координаторам — инструменты `orchestrator_*` всегда; если `injectInstructions = true` (по умолчанию) — ещё правило маршрутизации, навык `orchestrator-coordinator` и инструкция роли. Координатор по запасному критерию (строки в `thread_roles` нет) получает то же, что роль `orchestrator`, включая её инструкцию; строку при этом не записывает. Остальным ролям — их инструкция роли (если `injectInstructions = true`) и их инструменты/навыки. `injectInstructions = false` гасит **все** тексты плагина (правило, навыки координатора, инструкции ролей); остаются инструменты и навык `orchestrator-setup`.
- **Бюджет текста.** SDK отдаёт агенту одно поле `instructions` на плагин, обрезанное до 4096 символов. Плагин собирает его так: инструкция роли ≤ 2500 + правило маршрутизации ≤ 1500 + разделители; валидация длины при загрузке настроек и тест на самую длинную роль.
- **Устойчивость.** Ошибка внутри `configure` (база недоступна и т.п.) выключила бы выдачу плагина целиком (SDK fail-closed) — поэтому выбор роли обёрнут в обработку ошибок: при сбое роль по запасному критерию без записи, предупреждение в журнал.
- Выбор применяется при следующем построении сессии провайдера: живая сессия держит инструкции, с которыми построена.
- Дойдёт ли текст до агента, зависит от провайдера (§12): у провайдера, который не передаёт агенту инструкции BB, роль и правило недоступны — координатором такой провайдер в MVP не поддерживается, исполнителем — поддерживается (задача приходит в тексте раздачи).

## 4. Раздача: `delegate`

Один вызов вместо «dispatch → thread update → options mode». Доступен как инструмент агента `orchestrator_delegate` и как CLI.

```
bb orchestrator delegate <TASK-KEY> --level <уровень> [--route <маршрут>] [--instructions <текст>] [--json]
```

Вход: ключ существующей задачи `bb tasks` (ULID задачи приводится к ключу до проверок, чтобы защита от повтора работала по ключу), уровень из политики, необязательный маршрут (по умолчанию первый доступный в цепочке), необязательные доп. инструкции. Координатор — тред вызывающего агента: у инструмента — `PluginAgentToolContext.threadId`, у CLI — `PluginCliContext.threadId` (BB передаёт его из `BB_THREAD_ID`). Нет треда — вызов отклоняется. Тред не координатор по критерию §3 (роль без `delegates`, а без роли — родитель или признаки исполнителя) — вызов отклоняется с кодом `not-a-coordinator`: так исполнитель или аудитор не раздаст работу ни инструментом, ни через CLI из своей оболочки, даже если пользователь сам открыл его корневым чатом.

Порядок, атомарный для вызывающего (все шаги или явная ошибка с тем, что успело выполниться). Вызовы `delegate` внутри плагина сериализуются (одна очередь на процесс); защиту на уровне базы даёт частичный уникальный индекс (§7).
1. Проверить политику, уровень, маршрут, лимиты (`maxActive`, `perLevel`) по делегированиям в статусах `dispatching`/`running`. Превышение — отказ с текущим счётчиком (очередь — этап §10).
2. Вставить запись делегирования со статусом `dispatching`. Если у задачи уже есть запись в `dispatching`/`running` — уникальный индекс отклоняет вставку → отказ «у задачи уже есть активный исполнитель» (защита от двойного запуска).
3. (r30: вместо dispatch — «Свой запуск исполнителя» ниже, шаги а–е; dispatch — только запасной путь.) Выполнить `bb tasks dispatch <KEY> --preset <preset> [--instructions …] --json` (ответ `{task, preset, threadId}`) и сразу записать `threadId` в `thread_id` записи (до следующих шагов). У плагина `tasks` нет API привязки треда к задаче, поэтому раздача идёт через его CLI (ADR-0015 §1). Явный отказ dispatch (CLI вернул ошибку с кодом) — запись удаляется, вызов возвращает ошибку. Таймаут или непонятный ответ (тред мог уже создаться) — запись остаётся `dispatching` без `thread_id`, вызов возвращает ошибку «результат раздачи неизвестен»; её разбирает сверка §7 (поиск треда через `bb tasks threads`).
4. (r30: родитель, уведомления и скрытие задаются при создании; шаг сводится к сверке и роли: `threads.update` с `parentThreadId` — ТОЛЬКО если сверка показала расхождение, иначе не вызывать — он шлёт `ownership-assigned`. Ошибка чтения треда — повтор следующим проходом, без `update`. `parentNotifications` проверяется по `bb thread show --json` или ответу `spawn` (в DTO SDK поля нет). Текст ниже — для запасного пути через dispatch.) Сразу привязать тред: `threads.update({threadId, parentThreadId: координатор, visibility: "hidden"})` и `bb thread update <threadId> --parent-notifications auto` через CLI — поля `parentNotifications` нет в типах `UpdateThreadRequest` SDK 0.4.87, сервер его принимает. Без него исполнитель не разбудит координатора, поэтому шаг обязателен. Там же — запись роли исполнителя в `thread_roles` (upsert, `source = delegate`): уровень с ролью `auditor` (§2.3; по умолчанию — уровень `review`) → `auditor`, остальные → `executor`. Если первая сессия исполнителя построилась раньше, исправленная роль вступит в силу со следующего построения.
5. Если пресет просит `permissionMode = full` (`bb tasks preset show <preset> --json` → `permissionMode`), а провайдер сообщает опцию сессии `mode` со значением `bypass` и текущее значение другое (`bb thread options <id> --json` → опция `mode`, её `values` и `value`) — выставить `mode = bypass` (`bb thread options <id> --set mode=bypass`). Сразу после dispatch опции могут быть ещё пусты (сессия не построена) — шаг best-effort, повторяется при сверке (§7), пока сессия не сообщит опции или делегирование не закончится. Для `acp-devin` основное исправление — в провайдере ([provider-devin §1](provider-devin.md)); здесь — страховка.
6. Перевести запись в `running` **только из `dispatching`** (условие в том же UPDATE); если запись уже `cancelled` (отменили во время раздачи) — остановить созданный тред и вернуть «отменено»; комментарий в задачу через `bb tasks comment`: «Раздано: уровень, маршрут, пресет, тред» (r30).
7. Вернуть `{ delegationId, taskKey, threadId, level, route, status: "running" }`.

Ошибки шагов 4–6 не отменяют делегирование: запись в `running` с `setup_errors`, ответ содержит ошибку; сверка (§7) повторяет незавершённые шаги.

Инструмент агента возвращает ответ сразу и напоминает: закончить ход, отчёт придёт сообщением.

### 4.1 Заходы: каждый — своя копия и своя ветка

Каждая раздача (первая, доработка, перевыпуск) получает **новую** рабочую копию и **новую** ветку — их создаёт пресет с `--environment worktree` (ветка вида `bb/<key>-…-thr_…`, уникальна по треду). Одна ветка в двух копиях запрещена: копия, оставшаяся на ушедшей вперёд ветке, показывает «откат» чужих правок, и сведение по такой копии теряет работу.

**Итог захода.** Когда делегирование уходит в `done` (§5.3), сторож снимает итог из рабочей копии треда исполнителя (путь — из среды треда: SDK или `bb environment show <id> --json`, поля `path`, `branchName`, `mergeBaseBranch`): `result_branch` (текущая ветка, `git symbolic-ref --short HEAD`), `result_sha` (`git rev-parse HEAD`), `result_commits` (`git rev-list --count <mergeBaseBranch>..HEAD`), `result_dirty` (`git status --porcelain` не пуст). Для уровня `review` и роли `auditor` итог не проверяется (они не коммитят). У исполнителя одно сообщение координатору `[orchestrator] <KEY>: …`, если: копия грязная, коммитов нет или ветка не совпадает с `branchName` среды (исполнитель ушёл в чужую ветку). Снять итог не удалось (среды нет, git ошибся) — пометка в `setup_errors`, `done` не отменяется.

**Задача без кода (r28, 12.11, слово владельца).** Координатор помечает раздачу как не требующую коммитов: `delegate <KEY> --no-code` (инструмент `orchestrator_delegate`: `noCode: true`) — проверки, сбор данных, разбор, smoke. Пометка хранится в делегировании (`no_code`) и наследуется автоперевыпуском сторожа (§5.4). Новый заход — это новый `delegate`: пометку он не наследует, нужен явный `--no-code`, без флага раздача обычная (r28.1, ревью PLUG-237). Для такого делегирования сторож не пишет «коммитов нет»; «копия грязная» и «чужая ветка» остаются (исполнитель задачи без кода не должен менять файлы). Если коммиты всё же есть — строка координатору «задача без кода, но есть коммиты: N». В инструкции исполнителю при `--no-code` добавляется строка «задача без кода: файлы репозитория не менять, не коммитить; итог — отчёт», а требования памятки git о коммите, ветке и SHA в итоге (§2.2) не выводятся — чтобы инструкции не противоречили друг другу (r28.1). `merge` и `release` по задаче, чей последний заход — без кода и без коммитов, отказывают: «задача без кода: вливать нечего» (r28.1); если коммиты есть — работают как обычно. В `status`/`show` — пометка `no-code`.

**Доработка — новый заход.** Повторный `delegate` той же задачи, у которой есть прошлое делегирование с `result_sha`, — заход `round = прошлый + 1`. Плагин добавляет в `--instructions` после раздела «Работа с git» раздел «Заход N»:

```text
Заход <N>: продолжение работы с коммита <sha> (ветка <branch> прошлого захода).
- Первым шагом: git merge --ff-only <sha>; не fast-forward — git merge --no-edit <sha>; конфликт — вопрос координатору.
- Ветку прошлого захода не открывай и в её рабочую копию не заходи: работай только в своей ветке.
```

Флаги `delegate`: `--from <sha|ветка>` — продолжить с указанного коммита вместо последнего итога; `--fresh` — без продолжения (раздел не добавляется); оба сразу — отказ `incompatible-flags`. Перевыпуск (§5.4) — тот же заход: наследует `round` и `continue_from` своего делегирования. Уровни с ролью `auditor` (§2.3) раздела «Заход N» не получают — вместо него строка «Проверяемый итог: коммит <sha> (ветка <branch>, заход <N>)» без команд git. В записи: `round`, `continue_from`.

## 5. Сторож

Фоновый сервис плагина следит за каждым делегированием в статусе `running`. Заменяет внешний сторож и автоскрытие для делегирований этого плагина; треды, розданные вручную, не трогает.

### 5.1 Первый ответ (правило N секунд)

Окно открывается при старте хода исполнителя (`turn/started` или переход треда в `active`). Ответом считаются события: `item/started` (кроме `userMessage`), `item/completed`, дельты текста и размышлений, `item/toolCall/progress`, `item/commandExecution/outputDelta`. Если за `firstResponseSeconds` ответа нет — исполнитель **завис**: `threads.stop`, исход `stalled`. Перед решением «завис» сторож обязательно дочитывает события треда после `last_seq` (`threads.events.list`): ответ, пришедший, но ещё не обработанный, отменяет решение. Если дочитать события не удалось (ошибка `threads.events.list`), решения «завис» нет — оно откладывается до следующей проверки; непрочитанный журнал не равен молчанию. Чтение — страницами не больше 100 событий (предел сервера BB).

Источник событий — подписка `experimental_thread.events` (не чаще раза в секунду) + чтение `threads.events.list` после последнего виденного номера. Таймер — на сервере, не зависит от опроса агентом.

Зависание до старта хода (подготовка рабочей копии, запуск провайдера) окно не ловит: оно открывается только с `turn/started`. В MVP такой случай виден лишь по `maxRunSeconds` (§5.3 `timeout`).

### 5.2 Исчерпание квоты

Первый сигнал — типизированный: `turn.failed` с `errorInfo.category` = `rate-limit` или `billing`; ответ провайдера «повторю сам» (`willRetry = true`) квотой не считается, пока провайдер не сдался. Решение по `thread.failed` принимается только после чтения событий хода: если среди них есть `turn.failed` с категорией квоты — исход `quota`, а не `failed`. Запасной — текст события `provider/error`, `system/error` или ошибки хода совпадает с шаблоном квоты провайдера (`429`, `rate limit`, `quota`, `usage limit`, `Free usage limit reached`, `insufficient credits`; список — константа плагина, расширяемая в политике `routes.*.quotaPatterns`). Исход `quota`: запись → `quota`, затем `threads.stop`; все маршруты той же группы квоты (`quotaGroup`, а без неё — сам маршрут) помечаются недоступными на 15 минут.

### 5.3 Прочие исходы

Порядок для собственных остановок: **сначала статус в записи** (`stalled`, `quota`, `cancelled`), **потом** `threads.stop` — иначе свой стоп будет прочитан как внешний.

| Исход | Условие | Действие сторожа |
|---|---|---|
| `done` | `thread.idle` после начала хода, после `last_seq` нет события потока `system/thread/interrupted`, тред не архивирован и не удалён (события `bb.events.on` `thread.archived`/`thread.deleted`, поля DTO `archivedAt`/`deletedAt`), очередь сообщений исполнителя пуста (`threads.queuedMessages.list`) и **последний ход закончился без ошибки** (не `errored`, см. ниже) | статус `done`, итог захода (§4.1); ничего не перевыпускать (отчёт координатору доставляет сам BB как дочернему треду). Очередь не пуста — делегирование остаётся `running`: начнётся новый ход |
| `cancelled` | `thread.idle` вместе с событием потока `system/thread/interrupted` с причиной `manual-stop` (остановил пользователь или агент), либо тред архивирован или удалён (`bb.events.on` `thread.archived`/`thread.deleted`, поля DTO), и запись не была переведена сторожем в `stalled`/`quota` | статус `cancelled`, без перевыпуска, комментарий в задачу |
| `interrupted` | `system/thread/interrupted` с любой причиной, кроме `manual-stop` (перезапуск демона `host-daemon-restarted`, простой провайдера `provider-turn-idle` и т.п.) | не отмена. Первый раз: исполнителю одно сообщение `[orchestrator] ход прерван (<причина>), продолжай задачу`, статус остаётся `running` (`resume_count += 1`), координатору — уведомление. После «продолжай» новый ход должен начаться за `firstResponseSeconds`: не начался (сообщение не доставлено, тред в `idle` без нового хода и с пустой очередью) — как повторное прерывание. Повторно — как `stalled` (§5.4) |
| `errored` | тред `idle` (не `error`), но последний ход закончился ошибкой: `turn/completed` со `status = "failed"` или с полем `error`, либо событие `turn.failed`; если `turn/completed` хода нет — последнее событие хода перед простоем `provider/error`/`system/error` без `willRetry = true` (после него нет ни одного события ответа §5.1). Есть `turn/completed` — исход решает только он: ошибки после него (например, выход процесса агента после хода) не учитываются. `turn/completed` со `status = "interrupted"` — не ошибка (ход прерван новым сообщением или остановкой; это `interrupted`/`cancelled`). Ошибка инструмента посреди хода, после которой агент продолжил работу, — не исход: ход не закончен. **Страховка:** вживую не наблюдалось — проверка 112 делегирований 11.11: все ходы, закончившиеся ошибкой, переводили тред в `error` (→ `failed`) | сначала квота (§5.2) и снятая модель (`unavailable`) по тексту. Иначе первый раз: исполнителю одно сообщение `[orchestrator] ход оборвался ошибкой: <текст до 300 символов>. Продолжай задачу`, статус остаётся `running` (`resume_count += 1`), координатору — одна строка с текстом ошибки. Новый ход не начался за `firstResponseSeconds` или ход снова закончился ошибкой — `failed`. Повтор `errored` и повтор `interrupted` считаются раздельно (свои метки), общий `resume_count` — только статистика |
| `failed` | `thread.failed` / `turn.failed` без признаков квоты; повторный `errored` | статус `failed`, сообщение координатору с текстом ошибки; при `autoFallback: true` — перевыпуск §5.4 (случай 11.11: ревьюер на agy упал с `503 UNAVAILABLE: No capacity available`, и делегирование осталось `failed` без перевыпуска при включённом `autoFallback`) |
| `unavailable` | исполнитель не запустился, потому что провайдер не принял модель или маршрут: ошибка старта до первого хода (`thread.start failed`) или текст ошибки совпадает с шаблоном снятой модели (`model not found`, `model_not_found`, `unknown model`; список — константа плагина, расширяемая в политике `routes.*.unavailablePatterns`) | проверяется раньше `failed`. Статус `stalled` с причиной «маршрут недоступен», маршрут (не группа квоты) помечается недоступным на 15 минут (`route_holds`), затем §5.4; остановка считается подтверждённой — исполнитель не работает |
| `approval` | `interaction.pending` у исполнителя | статус не меняется; сообщение координатору: какой запрос и команда для решения (`bb thread interactions approve\|deny\|grant\|answer\|respond`). Не чаще раза в 10 минут — по `last_approval_notified_at` |
| `stalled` | §5.1 | статус, стоп, затем §5.4 |
| `quota` | §5.2 | статус, стоп, затем §5.4 |
| `timeout` | дольше `maxRunSeconds` | одно сообщение координатору (`timeout_notified_at`); не останавливать |

### 5.4 Перевыпуск

Для `stalled`, `quota` и `failed` (у `failed` — только при `autoFallback: true`; без него сторож лишь сообщает):
- Остановка старого исполнителя должна подтвердиться (`threads.stop` без ошибки и тред не `active`); не подтвердилась — перевыпуска нет: статус остаётся, координатору сообщение «не удалось остановить исполнителя», сверка повторит.
- `autoFallback: true` и в цепочке есть следующий доступный маршрут **после текущего** (лимит — только автоперевыпуски этой задачи, ручные делегирования маршрут не исключают) → в одной транзакции старое делегирование переводится в `reissued`, а новое вставляется в `dispatching` с `reissue_of`; затем §4 шаги 3–7. Так перезапуск сервиса посреди перевыпуска не даёт дубля. Сверка доводит новую запись `dispatching` с `reissue_of` до раздачи (не удаляет её); если раздача невозможна (явный отказ — и сразу, и в сверке) — новая запись `failed`, координатору сообщение о потере перевыпуска. Не больше одного автоперевыпуска на маршрут для задачи.
- Вставка новой записи невозможна, потому что у задачи уже есть активное делегирование (координатор раздал вручную, пока сторож останавливал старого) → перевыпуска нет: старая запись остаётся `stalled`/`quota`, координатору одно сообщение «перевыпуск за координатором: у задачи уже есть активное делегирование», повторов нет.
- иначе → статус `stalled`/`quota`, перевыпуска нет.

В обоих случаях: сообщение координатору (`threads.send` с `mode: "queue-if-active"`, текст начинается с `[orchestrator]`) и комментарий в задачу: исход, маршрут, новый тред или «перевыпуск за координатором». Сообщение не должно обрывать ход координатора: у Claude оно читается на границе шага, у `acp-devin` — ждёт конца хода ([provider-devin §2](provider-devin.md)).

### 5.5 Гарантия доставки итога координатору (ревизия 24; заменено §16.5)

Координатор должен узнать о каждом исходе своего исполнителя, даже на слабой модели и даже если уведомление BB не дошло. Исходы со своим сообщением сторожа (`stalled`, `quota`, `unavailable`, `failed`, `errored`, `interrupted`, `approval`, `timeout`, перевыпуск) уже доставляет плагин. Для `done` и `cancelled` основной путь — уведомление BB дочернего треда (`parentNotifications = auto`, §4 шаг 4): в журнале координатора `client/turn/requested` с `systemMessageKind = "child-completed"` и `systemMessageSubject.threadId` = тред исполнителя.

Правило: через 120 с после перехода делегирования в `done`/`cancelled` (и при каждой сверке §7, пока не подтверждено) сторож ищет в журнале координатора такое уведомление, пришедшее после `turn_started_at` последнего хода исполнителя. Нашлось — `result_notified_at`, `result_notice = bb`. Не нашлось — плагин сам отправляет координатору (`threads.send`, `queue-if-active`):

```text
[orchestrator] <KEY> (<уровень>, тред <thr>) закончил: <done|cancelled>.
<итог исполнителя — `threads` output, до 3000 символов; пусто — «исполнитель закончил без отчёта: проверь тред или раздай заход заново»>
```

и пишет `result_notice = plugin`. Ошибка отправки — повтор при сверке (предел §7). Координатор в архиве или удалён — только журнал плагина. Пустой итог исполнителя (`done` без текста ответа) — всегда сообщение плагина, даже если уведомление BB было.

**Привязка без холостого уведомления (r27, 12.11, слово владельца).** BB шлёт родителю системное сообщение «… is now a child of this thread» (`ownership-assigned`) при каждой **смене** родителя треда (`thread update --parent-thread`); каждое такое сообщение будит координатора на целый ход без пользы (вживую 20 из 61 хода координатора за вечер). Поэтому родитель задаётся **при создании** треда — `bb tasks dispatch … --parent-thread <координатор>` (и `--parent-notifications auto`, если флаг принимается), а `thread update --parent-thread` остаётся только запасным путём, если при создании родитель не встал (проверка шага 4 ниже). Приёмка — вживую: раздача не порождает у координатора сообщения `ownership-assigned`; итог исполнителя (`child-completed`) приходит как прежде. Если BB всё равно шлёт уведомление при создании — это записывается здесь как ограничение BB, плагин не обходит его. **Итог r27 (разведка PLUG-235):** у `bb tasks dispatch` в BB 0.49.0 нет `--parent-thread` (RPC `delegate` плагина tasks принимает только `taskId`, `presetId`, `extraInstructions`), поэтому r27 заменён r30.

**Свой запуск исполнителя (r30, 12.11, слово владельца — вариант «свой запуск»; разведка PLUG-235).** Плагин сам создаёт тред исполнителя с родителем и сам привязывает задачу, без `bb tasks dispatch`. Живая проверка: тред, созданный с `parentThreadId`, не порождает у родителя `ownership-assigned` (его шлёт только смена родителя). Шаги вместо §4 п.3–4:
- а) **Данные.** `bb tasks show <KEY> --json` (задача, проект, подзадачи, вложения, комментарии) и `bb tasks preset show <preset> --json` (провайдер, модель, reasoning, serviceTier, permissionMode, environmentKind, baseBranch, machineId, instructions). Проект задачи без связанного bb-проекта — отказ, как у dispatch. `projectId` для `spawn` — `project.linkedBbProjectId` из `bb tasks show --json`, а не `project_id` записи (там проект координатора).
- б) **Стартовый промпт.** Одна функция плагина повторяет шаблон BB `buildSeedPrompt`: `# KEY · title`, затем разделы Description, Project context, Sub-tasks, Attachments (только список `- имя · id` и строка `Fetch with: bb tasks attachment get <id> --out <path>`, без скачивания), Recent comments (последние 5), Report-back contract (текст скопирован из BB 0.49.0), Preset instructions, Additional instructions (доп. инструкции `delegate` и инструкции плагина, как сейчас). Заголовок треда — `KEY · title`, обрезка по ширине отображения до 120, как у BB (`truncateToWidth`). Дрейф шаблона при обновлении BB — принятый риск: шаблон в одном месте, тест на его разделы.
- в) **Создание.** `sdk.threads.spawn({projectId, environment, providerId, model, reasoningLevel, serviceTier?, permissionMode, title, prompt, parentThreadId: координатор, parentNotifications: "auto", visibility: "hidden"})`. `primaryHostId` берётся из `system.config()`: сбой вызова — неизвестный исход (`dispatch-unknown`, как п.(1) е), пустой `primaryHostId` — явный отказ `spawn_target_invalid`. Если запись вышла из `dispatching` не через отмену (удалена или иная) — созданный тред останавливается и раздача отклоняется (`dispatch-failed`, без комментария «Раздано»). `model` и `reasoningLevel` передаются, только если заданы в пресете непустыми (иначе BB берёт дефолт, как builtin dispatch). Среда по пресету: `project-default` → `{type:"project-default"}`; `new-worktree` → `{type:"host", hostId: machineId ?? primaryHostId, workspace:{type:"managed-worktree", baseBranch: preset.baseBranch ? {kind:"named", name: preset.baseBranch} : {kind:"default"}}}` — `baseBranch` объект, не строка. `primaryHostId` — из `system.config()`; в зависимости раздачи (`DispatchStepsDeps`) добавляется `primaryHostId(): Promise<string>`. Плюс `pluginMetadata: {delegationId}` — метка, по которой сверка находит тред без `thread_id`. В типах SDK 0.4.87 нет только `parentNotifications` (приведение типа, сервер принимает); `parentThreadId`, `visibility`, `pluginMetadata` есть. `lifecycleOwnerThreadId` не задаётся (как у dispatch). Сразу после ответа `spawn` записать `thread_id` в делегирование. В зависимости раздачи (`DispatchStepsDeps.threads`) нужны `spawn` и `list`.
- г) **Привязка задачи** — первый подшаг `finishDispatchSteps` (§4 п.4), чтобы её выполняли и раздача, и сверка записи `dispatching` с `thread_id` (падение между записью `thread_id` и привязкой → сверка привяжет). Привязка идемпотентна (`ON CONFLICT … DO UPDATE` в tasks); у записей запасного пути повторный attach лишь перепишет имя пресета на «Attached» — принято. `bb tasks attach <KEY> --thread <id>`; если статус задачи `backlog` или `todo` — `bb tasks update <KEY> --status in_progress`. Сбой любого из двух — не отказ раздачи: запись в `running` с `setup_errors` шага `tasks-attach`, сверка (§7, `retrySetupSteps`) повторяет шаг до успеха (предел повторов §7). Сверка, ищущая тред раздачи, берёт его из `thread_id` записи, а не только из `bb tasks threads` (привязки может ещё не быть). Комментарий «Раздано: уровень, маршрут, пресет, тред» (§4 п.6) заменяет системный «Dispatched to»: его и имя пресета в списке тредов задачи (там будет «Attached») публично не записать — принятая косметика.
- д) **Происхождение.** У треда `originPluginId = "orchestrator"` (не подделывать `tasks`). Все места плагина, где «тред создан плагином tasks» означает «исполнитель» (роли, уборщик, координатор/не координатор), признают и `orchestrator`; поведение для старых тредов (`tasks`) не меняется.
- е) **Ошибки `spawn` и запасной путь.** (1) **Исход неизвестен** — таймаут (SDK ждёт 75 с), обрыв, 5xx, нечитаемый ответ: тред мог создаться, поэтому как §4 п.3 «таймаут или непонятный ответ» — запись остаётся `dispatching` без `thread_id`, ошибка `dispatch-unknown`; сверка ищет тред (ниже). (2) **Явный отказ** — ответ 4xx с кодом (`spawn_target_invalid`, `parent_thread_invalid` с `details.reason`, ошибки среды, провайдера, модели): вызывающему отдаются `code` и `details.reason`, без отката на dispatch: как явный отказ dispatch с соблюдением `onDispatchFailure` (новая раздача — запись удаляется; автоперевыпуск сторожа, `reissue_of` задан — запись в `failed`, §5.4), ошибка вызывающему. Если `spawn` уже вернул тред, а раздача потом признана несостоявшейся (отмена во время раздачи, фатальная ошибка до `running`) — `threads.stop` этого треда до удаления или `failed` записи, чтобы не остался исполнитель без надзора. (3) **Запасной путь** на `bb tasks dispatch` + `thread update` (с уведомлением, строка `setup_errors` «свой запуск недоступен: <ошибка>») — только при явном отказе схемы по полям `parentThreadId`, `parentNotifications`, `visibility`. В BB 0.49.0 схема создания треда не строгая (незнакомые ключи молча отбрасываются), так что этот путь на деле недостижим; реальная страховка — сверка п.4: родитель или скрытие не встали — `thread update`. Тесты запасного пути — модульные, не проверка живого поведения. (4) **Поиск треда без `thread_id`** (сверка §7 и `cancel`): сначала `threads.list({parentThreadId: координатор, includeHidden: true})` с фильтром по метке `pluginMetadata.delegationId` (запасной фильтр — `createdAt ≥ created_at` записи и заголовок с префиксом `KEY · `); кандидат с читаемой меткой `delegationId` **другой** записи пропускается; нашёлся — записать `thread_id` и довести шаги, включая привязку; ничего не нашлось — в конце всегда `bb tasks threads <KEY>` (записи запасного пути и записи, созданные до r30 без метки). Не нашёлся — прежние правила §7 (повтор раздачи для перевыпуска, удаление для прочих) по истечении окна. Шаг 4 сводится к проверке: родитель, уведомления и скрытие на месте — ничего не делать; расходятся — `thread update` (запасной путь, уведомление допустимо).
- Остальное без изменений: перевыпуск сторожа и `release-audit` идут тем же путём раздачи, жизненный цикл задачи (статусы треда, комментарии) BB ведёт по привязке. Приёмка вживую: раздача не порождает у координатора `ownership-assigned`; задача показывает тред и `In Progress`; итог `child-completed` приходит как прежде; тесты — шаблон промпта, среда из пресета (оба вида, `baseBranch` named/default), таймаут `spawn` → `dispatching` с `dispatch-unknown`, сверка находит непривязанный тред по метке и не раздаёт повторно, падение между записью `thread_id` и привязкой → сверка привязывает, ошибка чтения при сверке → без `update`, запасной путь только по полям родителя/видимости (модульный), фатальная ошибка среды без отката, автоперевыпуск при отказе `spawn` → `failed`, сбой attach → `setup_errors` и повтор сверкой, остановка треда при отмене после `spawn`, отсутствие `threads.update` при совпадении родителя, происхождение `orchestrator` в ролях и уборщике.

Проверка привязки (§4 шаг 4) повторяется сверкой до подтверждения: у треда исполнителя `parentThreadId` = координатор и `parentNotifications = auto`; иначе — повторить шаг и одна строка координатору при неудаче.

Правило §3 и навык координатора: итоги исполнителей приходят сами — сообщением `[bb system] … completed` или `[orchestrator] …`; не ждать в форграунде и не опрашивать в цикле; раздавать только через `delegate` (ручные `bb tasks dispatch` и `bb thread spawn` под сторож и гарантию доставки не попадают); сомневаешься — `bb orchestrator status`.

Перезапуск или перезагрузка плагина не теряет делегирования и не создаёт дубликаты перевыпуска (§5.4).

## 8. Совместимость и приёмка MVP

Рядом со старыми механизмами:
- делегирования плагина не трогают внешний сторож; внешний сторож не нужно запускать на треды плагина (иначе возможен двойной перевыпуск) — инструкция §3 об этом говорит;
- автоскрытие tasks-тредов и cron остаются; повторное скрытие безвредно;
- до перехода на установке с ручными инструкциями раздачи держать `injectInstructions = false` (по умолчанию `true`, §3), чтобы правило плагина не дублировало ручное.

Переход на установке с ручными механизмами — после приёмки и отдельным шагом координатора: своя политика, записанная по навыку `orchestrator-setup`, `injectInstructions=true`, ручные инструкции раздачи отключаются (у нас — плагин `orchestration-notes`), внешний сторож и автоскрытие остаются страховкой, пока владелец не отключит их отдельным словом. Провайдерные «костыли» раздачи (хуки, дописывающие флаги к `bb thread spawn` и привязку после `bb tasks dispatch`) удаляются: раздача идёт через `delegate`.

Приёмку проводит координатор после слияния задач в main и установки плагина (отдельный шаг, не задача исполнителя; исполнители проверяют только тесты и сборку). Смоук гайда через плагин, в тестовом проекте трекера:
1. `delegate SMK-1 --level simple` → тред скрыт, дочерний к координатору, `parentNotifications=auto`, привязан к задаче (`bb tasks threads SMK-1`), комментарий «Раздано».
2. Отчёт исполнителя приходит координатору сообщением без опроса; `status` показывает `done`.
3. Повтор `delegate SMK-1` при активном исполнителе — отказ.
4. Зависание: политика с `firstResponseSeconds=30` и маршрутом, который не отвечает (тестовый пресет на заведомо молчащую модель или остановка хода сразу после старта) → `stalled`, стоп, перевыпуск на следующий маршрут цепочки, комментарий, сообщение координатору; новый тред скрыт и дочерний.
5. Перезагрузка плагина посреди работы исполнителя → после сверки статус верный, дубликатов нет.
6. Роли: новый чат с выбранной в окне ролью `auditor` → `thread_roles` = `auditor` записан хуком раньше первого построения сессии, агент цитирует инструкцию роли; `delegate --level review` → исполнитель `auditor`, агент ревьюера цитирует инструкцию `auditor` уже в первом ходе; тред с ролью `executor` получает `not-a-coordinator` и через CLI; тред из `bb tasks dispatch` без `delegate` → `executor`.
7. Сжатие: Claude Code — после сжатия контекста инструкция роли на месте (агент цитирует её); Codex — то же, отдельный пункт (не проверялось).
8. `npm test`, `npm run typecheck` зелёные; тесты на политику, состояние, сторож (фальшивые события), роли, CLI.

### 8.1 Итог живой приёмки (09.11)

- П. 1–5 пройдены вживую: раздача одной командой (скрытый дочерний тред, уведомления, привязка, комментарий), отчёт исполнителя сообщением и `done`, отказ повторной раздачи, зависание → остановка и перевыпуск по цепочке, перезагрузка плагина посреди работы исполнителя без потери надзора и дублей.
- П. 6: роли из `delegate` (`executor`, `auditor`), роль из хука для дочернего треда, `not-a-coordinator` — пройдены; список «Роль» в окне нового чата — не проверен вживую.
- П. 7 (инструкции после сжатия) — не проверен.
- Найдено приёмкой и исправлено: страницы событий больше 100 отклоняются сервером (§5.1, ревизия 18); снятая у провайдера модель (§5.3 `unavailable`, ревизия 19).
- Известные пробелы следующего этапа: доработка исполнителю, чьё делегирование уже `done`, не под надзором сторожа; плагин вызывает CLI `bb` без адреса своего сервера (на инстансе с нестандартным портом вызовы уходят на порт по умолчанию).
- Лимиты `limits` поддерживаются кодом, но в рабочей политике владельца не заданы — решение о них отложено.

## 9. Этап 2: Fleet

Панель в треде координатора: список исполнителей (задача, уровень, маршрут, статус, время), выбор — чат исполнителя (`ThreadChat`) прямо в панели; действия «пауза» (стоп с сохранением треда), «продолжить» (сообщение исполнителю), «отменить». Индикатор в заголовке треда — только если есть делегирования. Пауза записывает статус до остановки, чтобы стоп не прочитался как `done`.

## 10. Этап 3: очередь и квоты

- Превышение лимитов — делегирование в статусе `queued` вместо отказа; запуск по освобождению слота, FIFO внутри уровня.
- Перед раздачей — `system.usageLimits()`: маршрут, у провайдера которого квота ниже порога политики, пропускается в пользу следующего.
- Обязательный шаг ревью: настройка уровня `requiresReview` — после `done` исполнителя плагин сам ставит задачу ревью на уровне `review` и сообщает координатору только после ревью.

## 11. Этап 4: обмен политикой

Экспорт и импорт политики (`bb orchestrator policy export|import`) для передачи своей схемы другому пользователю; без секретов и ID тредов. Пресеты по именам из политики пользователь заводит у себя сам (навык `orchestrator-setup`).

## 13. Роли агента

Роль — инструкция и принцип работы агента в треде плюс набор инструментов плагина, доступных ему. Роль выбирается при старте треда; по умолчанию — оркестратор. MVP — три встроенные роли и выбор в окне нового чата; свои роли пользователя и роль исследователя — следующий этап (§13.4).

### 13.1 Роли MVP

| Роль | Принцип | `delegates` | Инструменты и навыки плагина |
|---|---|---|---|
| `orchestrator` (по умолчанию) | сам задачу не выполняет: декомпозирует в задачи `bb tasks`, раздаёт исполнителям через `delegate` по уровням, проверяет и сводит результат | да | `orchestrator_delegate`, `orchestrator_status`, `orchestrator_cancel`; навыки `orchestrator-coordinator`, `orchestrator-setup` |
| `executor` | выполняет задачу сам, субагентов не запускает, отчитывается по контракту задачи | нет | нет |
| `auditor` | только читает и проверяет: находки «место → проблема → исправление», вердикт; ничего не правит и не коммитит | нет | нет |
| `release-auditor` | проверяющий агент конвейера выкладки: только чтение, строгий JSON-вердикт APPROVE/REJECT по актуальности документов и утечкам ([release](orchestrator-release.md) §3) | нет | нет |

Инструкции ролей — константы плагина, каждая ≤ 2500 символов (§3, бюджет).

**Хендофф (ревизия 24, слово владельца 11.11).** Инструкции ролей `orchestrator` и `executor` обязательно содержат правило хендоффа — слабые модели с малым контекстом сами о нём не помнят, а после сжатия теряют состояние:

```text
Хендофф: веди файл HANDOFF.md в хранилище своего треда ($BB_THREAD_STORAGE/HANDOFF.md) — цель, решения пользователя, что сделано (ветки, SHA, задачи), что в работе и что дальше. Обновляй после каждого значимого шага и до того, как контекст заполнится; после сжатия контекста или перезапуска первым делом прочитай его.
```

Координатору — дополнительно: ссылки на треды исполнителей и их задачи. Роли `auditor`/`release-auditor` (короткие проверки) хендофф не ведут. Если у провайдера нет `$BB_THREAD_STORAGE` — `~/.cache/bb-handoff/<id треда>.md`, не внутри рабочей копии (неотслеживаемый файл делает копию «грязной», и уборщик §15 её не уберёт).

Роль `release-auditor` в окне нового чата не предлагается: её получает только тред аудита, запущенный `release` (запись в `thread_roles` с `source = delegate`).

### 13.2 Выбор роли и привязка к треду

1. **Окно нового чата.** Плагин добавляет в строку действий окна нового чата выпадающий список «Роль» (`composer.customize`, область `new-thread`; точное место — по SDK, «рядом с выбором модели» не гарантируется). При монтировании и при каждой смене список вызывает RPC `setPendingRole({projectId, role})` → таблица `pending_roles(project_id, role, updated_at)` хранит **текущий выбор** проекта (не удаляется при использовании). `projectId = null` (чат без проекта) → роль по умолчанию. Известное ограничение MVP: выбор хранится на проект, поэтому окно нового чата того же проекта, открытое на другом устройстве, перезапишет выбор — побеждает последнее открытое или изменённое окно.
2. **Решение роли — хук `message.dispatch`.** Хук срабатывает до подготовки окружения и построения сессии. Поля: `thread.status`, `thread.originPluginId` (источник треда; корневой `originPluginId` контекста — источник конкретной отправки, им не пользоваться), `thread.parentThreadId`, `thread.sourceThreadId`, `thread.title`, `origin`, `attempt`. Роль решается только на первом сообщении треда: `attempt = start-turn`, `thread.status = "pending"`, треда нет в `thread_roles`. Правило по порядку:
   - `thread.originPluginId = "tasks"` → исполнитель: ключ задачи из заголовка `<KEY> · …` (он есть с рождения треда) → запись делегирования этой задачи в `dispatching`/`running` → уровень `review` → `auditor`, иначе `executor`; записи нет → `executor`;
   - есть `thread.sourceThreadId` (боковой чат, передача сессии) → роль источника из `thread_roles`; нет строки — дальше по правилу;
   - есть `thread.parentThreadId` → `executor`;
   - `origin = "app"` (новый чат из окна) → текущий выбор проекта (`pending_roles.role`); выбора нет → `orchestrator`;
   - иначе (`cli`, `plugin`, `sdk`, автоматизации) → `orchestrator`.
   Результат — в `thread_roles(thread_id, role, decided_at, source)`, `source ∈ {hook, delegate}` (запасной критерий §3 ничего не записывает).
   **Хук fail-closed по SDK:** исключение или ответ дольше 10 с не дают сообщению уйти, а хуки выполняются под общей блокировкой сервера. Поэтому весь обработчик — в `try/catch` с ответом «пропустить» при любой ошибке, внутри только синхронный SQLite плагина: без CLI, сети и `await`. Тесты: исключение внутри → «пропустить»; время обработчика в тестах < 50 мс.
3. **`configure` только читает `thread_roles`;** нет строки — запасной критерий §3. Тест на порядок «хук раньше первого `configure`» — в PLUG-141, живая проверка — в приёмке §8 п.6.
4. **`pluginMetadata.role`** пишется после решения — только для показа и других плагинов. Источник правды — `thread_roles`: метаданные плагина может переписать сам агент треда.
5. **Ограничение.** Плагин выдаёт и отнимает только свои инструменты; встроенные инструменты провайдера (правка файлов, оболочка) он отключить не может. «Оркестратор сам не делает» и «аудитор только читает» держатся на инструкции роли и на правах пресета.

### 13.3 Подача инструкции роли

По §3: инструкция роли идёт в общем поле `instructions` (бюджет 2500), при `injectInstructions = false` не подаётся. У Claude Code инструкции плагинов BB — в системной части запроса; Codex — проверяется приёмкой §8. У ACP-агентов — по возможностям провайдера (§12): у Devin инструкции возвращаются после сжатия плагином `provider-devin`; у agy на ACP-мосту (ADR-0021) инструкции доходят — подтверждено сквозной проверкой 12.11 (координатор на agy вёл хендофф и раздавал по правилу).

### 13.4 Следующий этап: свои роли

Роли — JSON в настройке `roles`: `id`, `name`, `instructions` (≤ 2500), `tools`, `skills`, `delegates`. Валидация при загрузке настроек: `tools` и `skills` — только из списка плагина (неизвестное имя в `configure` выключило бы выдачу плагина всем тредам), ошибка → `needs-configuration`. Шаблон `researcher` (собирает и анализирует сведения, цитирует источники, выводы отделяет от фактов). Роль работает и в одиночном режиме (пользователь сам открыл чат исполнителя или аудитора), и в мультиагентном.

## 14. Вливание итога захода: `merge`

```
bb orchestrator merge <KEY|delegationId> [--into <ветка>] [--no-autofix] [--dry-run] [--json]
```

Вливает итог захода (§4.1) в рабочую копию координатора. Вызывает только координатор этого делегирования (тред вызова = `coordinator_thread_id`); рабочая копия — среда треда координатора. `<KEY>` — последнее `done`-делегирование задачи с `result_sha`.

Проверки до вливания (каждая — отказ с кодом и подсказкой):
0. (r28.1) Делегирование без кода (`no_code`) без коммитов (`result_commits` 0 или NULL) — отказ `nothing-to-merge` «задача без кода: вливать нечего»; проверяется раньше проверки итога (`no-result`).
1. Делегирование `done`, есть `result_sha`, `result_dirty = false` (`dirty-result`: исполнитель не закоммитил — доработка новым заходом).
2. Копия координатора чистая (`git status --porcelain` пуст) и стоит на ветке (не отсоединённый HEAD).
3. Ветка-приёмник: `--into` или текущая ветка копии; она не из списка защищённых `janitor.protectedBranches` (по умолчанию `main`, `master`, `dev`) — `protected-branch`: в защищённые ветки код уходит только через `release` ([release](orchestrator-release.md)).
4. Одно вливание на копию одновременно (блокировка в плагине).

Порядок: (без `git fetch`: копии одного репозитория делят хранилище объектов; наличие `result_sha` — `git cat-file -e`) → `git merge --no-ff --no-edit -m "merge <KEY> r<N> (<sha7>)" <result_sha>` под автором из конфига репозитория (без `--author`, `-c user.*`, `--no-verify`). Успех → `merge_status = merged`, `merged_into`, `merged_sha`, `merged_at`; комментарий в задачу «Влито в <ветка> (<sha7>)». Тесты `merge` не гоняет: проверка — шаг координатора, выкладка — `release`.

Конфликт → `git merge --abort` (копия возвращается к исходному состоянию), `merge_status = conflict`. Слияние не завершилось без конфликтных файлов (отказ хука, таймаут; таймаут вливания ~10 мин) — `--abort`, `merge_status = failed`, ошибка `merge-hook-failed`, разбор не раздаётся. При любом неуспехе копия координатора обязана вернуться к исходной ветке и HEAD с чистым `git status`, иначе ошибка `copy-not-restored`. `--into` — только локальная ветка (`git check-ref-format --branch`, `show-ref --verify refs/heads/<имя>`), защищённость проверяется по нормализованному имени. Повторный `merge`: делегирование в `fix-delegated` — отказ `fix-delegated`, в `merged` — `already-merged`. Не удалось прочитать копию исполнителя для проверки §16.2 — отказ `stale-check-failed`; копии уже нет (среда удалена, 404) — проверка пропускается: итог больше не может измениться. У копии координатора незавершённое слияние, cherry-pick, revert или rebase — отказ до вливания (`copy-busy`). В файл блокировки пишутся исходные ветка и HEAD; блокировка умершего процесса снимается только после восстановления копии к ним. Блокировка — файлом в каталоге git копии (видна всем процессам), не в памяти. Без `--no-autofix` плагин сам раздаёт **заход разбора конфликта**: та же задача и уровень, `continue_from = result_sha`, доп. инструкция «Влей <ветка-приёмник>@<sha7 её вершины> в свою ветку: git merge --no-edit <sha>; разреши конфликты по смыслу обеих сторон, прогони тесты, закоммить; в отчёте — какие файлы и как сведены», `merge_status = fix-delegated`, координатору одна строка. Когда заход разбора `done` — координатор снова вызывает `merge` (его итог уже содержит вершину приёмника, вливание пройдёт без конфликта). `--dry-run` — только проверки и `git merge-tree --write-tree` (есть ли конфликт), копия не меняется.

## 15. Уборщик: копии, ветки и треды после вливания

Фоновая служба плагина (`bb.background.service`) вместо разрозненных скриптов: следит, чтобы не копились влитые рабочие копии, ветки и треды исполнителей, и сообщает о брошенных. Удаляет только влитое и чистое; невлитое и грязное — только в отчёт.

Настройка `janitor` (JSON, multiline). По умолчанию `{"enabled": false}` — для нового пользователя уборщик выключен, навык `orchestrator-setup` предлагает включить.

```json
{
  "enabled": true,
  "mode": "apply",
  "afterMerge": "10h",
  "abandonedAfter": "10d",
  "intervalMinutes": 60,
  "excludeProjects": [],
  "protectedBranches": ["main", "master", "dev"],
  "deleteBranches": true
}
```

- `mode`: `apply` — удалять; `report` — только отчёт (сухой прогон). Поле не задано или с ошибкой — `report`; неизвестные ключи настройки — ошибка валидации, уборщик выключен.
- `afterMerge`: срок после вливания до уборки — `<число>m|h|d`, от `15m` (например `1h`, `10h`, `24h`).
- `abandonedAfter`: через сколько простоя невлитое попадает в отчёт «брошено» (от `1d`).
- `intervalMinutes` ≥ 15. `excludeProjects` — id проектов BB, которые убирает кто-то другой. У владельца — пусто: уборщик ведёт все проекты, включая growthhack; его cron-скрипт уборки снимается после приёмки §8.2 п.5 (решение владельца 11.11).

**Что смотрит.** Среды BB `managed = true`, провайдер `git-worktree`, статус `ready`, проекта не из `excludeProjects`. Для каждого репозитория — один `git fetch --prune origin` за прогон.

**Влитая копия** (решение владельца 11.11: удалять, только когда система точно уверена, что ничего не потеряется) — HEAD копии **и ветка копии** (`branchName` среды, если она существует и отличается от текущей ветки HEAD) — предки одной из **удалённых** веток: `origin/<защищённая ветка>` или `mergeBaseBranch` среды, взятая только как удалённая ветка (`origin/<имя>`; значение-SHA, локальная ветка без пары на `origin` — не учитываются), (локальные ветки общие на весь репозиторий и копии не принадлежат: невлитые чужие ветки уборке копии не мешают, их работа после удаления копии не теряется) проверено сразу после успешного `git fetch` этого прогона (fetch не удался — репозиторий в этом прогоне пропускается целиком). Вливание в локальную ветку координатора (`merge`, §14) влитым **не считается**, пока результат не на `origin`: копию координатора тоже могут убрать. Момент вливания — первое время прогона, когда уборщик увидел копию влитой (`janitor_items.first_seen_at` для состояния «влита»); отсчёт `afterMerge` — от него, не от времени коммита.

**Удаляется, только если всё верно одновременно:**
1. Копия влита (выше) и остаётся влитой на каждом прогоне, и с момента, когда её впервые увидели влитой, прошло `afterMerge` (по умолчанию `10h`).
2. В копии есть свои коммиты — коммиты ветки копии после точки её создания (первая запись reflog ветки «Created from <sha>», а без неё — `createdAt` среды против времени коммитов; данных нет — своих коммитов нет), а не «HEAD отстаёт от базы» — либо тред простаивает дольше `abandonedAfter` (свежий тред без коммитов выглядит «влитым»: такую копию нельзя убирать посреди работы).
3. `git status --porcelain --untracked-files=all --ignore-submodules=none` пуст (настройки репозитория вроде `status.showUntrackedFiles=no` не скрывают файлы); ошибка или таймаут `git status` — копия остаётся (`status-failed`), в копии нет незавершённого слияния, перебазирования или cherry-pick. Файлы из `.gitignore` (сборка, зависимости) считаются восстановимыми и удаляются вместе с копией — **кроме вложенных хранилищ** (грубое правило, ревью PLUG-203): копия остаётся, если внутри неё (обход файловой системы, без опоры на `git status`, включая игнорируемые и неотслеживаемые каталоги; кроме собственного `.git`-файла копии) есть хоть одно из: путь записи `git worktree list --porcelain` (`nested-worktree`), запись `.git` (файл или каталог) или каталог с признаками bare-хранилища — `HEAD` + `objects/` + `refs/` (`nested-repo`), запись индекса с режимом `160000` (gitlink, `git ls-files -s`) или `.gitmodules`/`$GIT_DIR/modules` (`has-submodules`). Обход не удался или слишком глубок — «не доказано», копия остаётся (`nested-unknown`). Файлы с флагами `skip-worktree`/`assume-unchanged` (`git ls-files -v`), чьё содержимое на диске (`git hash-object`) отличается от индекса, — копия остаётся (`hidden-changes`); спасение §16.4 их тоже забирает.
4. **Все** треды среды и **все** неархивные треды каскада (включая детей без своей среды) в статусе `idle` или `error` (не `active`, `pending`, `starting`, `stopping`), очередь сообщений каждого пуста (`queuedWork = none`, включая строки автоповтора `provider-retry`), нет ожидающих запросов (`interactions`), среда не принадлежит делегированию в `dispatching`/`running`.
5. Нет живого процесса с текущим каталогом внутри копии: `/proc/<pid>/cwd` процессов своего пользователя (владелец — по `/proc/<pid>`), пути сравниваются после `realpath`. Нет `/proc` (macOS и др.) — копия остаётся (`process-unknown`).

**Действие:** непосредственно перед архивом — перечитать треды каскада, повторить `git status` и сверить HEAD копии со снимком начала прогона (изменился — архив отменяется) (снимок начала прогона устаревает); затем заархивировать треды среды (ошибка архива любого треда — разархивировать уже заархивированные, копию не трогать, `kept`) → `bb environment cleanup <env>` → отказ уборки: разархивировать треды, запись `kept` с причиной. `--dry-run` ничего не пишет и ничего не отправляет (только вывод команды). `mode: report` не ставит `first_seen_at` и не меняет состояние копий; служебные отметки отчёта (`janitor_meta`: время суточного сообщения, список объявленных брошенных) пишутся — иначе после перезапуска сообщение повторится. Копия, переставшая быть брошенной, из списка объявленных удаляется — но не при временных сбоях прогона (fetch, чтение тредов): тогда список не трогается. `git worktree prune` плагин **не вызывает никогда**: он стирает reflog HEAD копий, удалённых вручную, — единственную ссылку на их коммиты; метаданные удалённых копий убирает сам BB или git по своему сроку. Затем, если `deleteBranches`, удалить локальную ветку копии (`git branch -D` — только после проверки предка из п.1, ветка не защищённая и не открыта ни в одной копии по `git worktree list --porcelain`). Удалённые ветки (`origin/…`) уборщик не трогает. Возврат: `bb thread unarchive` + `bb thread restore-environment`.

**Ветки без копий.** Невлитые ветки `bb/` без копии при простое попадают в отчёт «брошено» (в суточном сообщении — только число и первые 10, полный список — `janitor report`). Локальные ветки с префиксом `bb/`, влитые в `origin/<защищённую>`, не открытые ни в одной копии, — удаляются, только если правило «ничего не теряется» (§16.3) выполняется и для **reflog самой ветки** (`git log -g refs/heads/<b>`: `branch -D` стирает его, а там может быть единственный след коммита после `reset`); иначе ветка остаётся (`branch-unpushed`), при простое дольше `abandonedAfter` — в отчёт «брошено». Прочие ветки людей не трогаются.

**Отчёт, без удаления:** невлитое с простоем дольше `abandonedAfter`; грязное с тем же простоем; среда, чьи треды уже в архиве, а ветка не влита. Раз в сутки — одно сообщение координатору по средам его делегирований (`[orchestrator] уборщик: брошено N копий …` со списком и командой разбора); остальное — в `bb orchestrator janitor report` и журнале плагина. Другим тредам уборщик не пишет.

**Итог прогона** — одна строка в журнале плагина: удалено копий/веток/тредов, освобождено МБ, оставлено по причинам. `bb orchestrator janitor run` — внеочередной прогон, `report` — последнее состояние и список брошенного.

## 16. Ревизия 25: решения по аудиту архитектуры (11.11)

Раздел **перекрывает** указанные места §2–§15; при расхождении действует он. Найдено независимым аудитом спек ревизии 24.

### 16.1 Один владелец повтора хода: `provider-retry` раньше сторожа (Б2; подтверждено владельцем 11.11)
BB сам ставит повтор упавшего хода в очередь треда (`bb provider-retry`: перегрузка, 5xx, окно подписки). Случай 11.11: ход ревьюера упал с 503, сторож поставил `failed`, через 14 с BB продолжил тред «Please continue.», исполнитель работал ещё больше часа без надзора.
- На `turn.failed`/`thread.failed`/`errored` сторож сначала читает очередь треда (`threads.queuedMessages.list`, `bb provider-retry status`): есть строка автоповтора — делегирование остаётся `running`, отметка `provider-retry-pending` в `setup_errors`, координатору ничего; исход решается после повтора.
- Решили перевыпускать или останавливать (`quota` с закрытием группы, `stalled`, повторный `failed`) — сначала `bb provider-retry cancel` строки автоповтора этого треда, потом статус и стоп. Не удалось отменить — перевыпуска нет, сообщение координатору.
- Квота по тексту (§5.2) — только когда ход закончился ошибкой; посреди хода — только типизированный `errorInfo.category`.

### 16.2 Оживший тред и устаревший итог (Б3)
- `turn/started` у треда делегирования в `done`/`failed`/`cancelled` (координатор ответил исполнителю после отчёта) — делегирование возвращается в `running` (`revived_count += 1`), если у задачи нет другого активного делегирования; есть — тред останавливается, координатору строка.
- Пробуждение уведомлением трекера о комментарии (сообщение треду начинается с `New comment on task <KEY> from` — плагин `tasks` шлёт его всем тредам задачи, включая прошлые заходы) — **не** оживление. Правило по журналу: смотрятся **все** `client/turn/requested` треда после `last_seq` (BB пишет запрос при постановке в очередь, не при старте хода — запрос может лежать посреди чужого хода). Все они — уведомления трекера → не оживление: ход терминального делегирования молча останавливается (сначала отмена автоповтора §16.1, потом `threads.stop`, без сообщения координатору — только журнал плагина), статус не меняется, `last_seq` сдвигается. Хоть один другой (координатор, пользователь, автоповтор) → оживление по общему правилу (только последнее делегирование задачи; прошлый заход — стоп и строка координатору). Сверка (§7) применяет то же правило к терминальным строкам, у которых в журнале есть ходы после `last_seq` (перезапуск плагина посреди хода). Случай 11.11: отчёт третьего захода комментарием разбудил тред второго захода.
- Итог захода (§4.1) пересчитывается при каждом `done`.
- `merge` (§14) перед вливанием сверяет `result_sha` с HEAD копии исполнителя: расходится — отказ `stale-result` с подсказкой дождаться `done`.

### 16.3 Уборщик: каскад архива и область (Б1)
`bb thread archive` архивирует тред **вместе с детьми и скрытыми форками**; после архива последнего треда BB сам удаляет копию через 5 минут.
- Область по умолчанию `scope: "workers"` (решение владельца 11.11) — среды тредов-исполнителей: тред создан раздачей (`originPluginId = "tasks"`) или имеет родителя. Корневые чаты пользователя и координаторов — только при `scope: "all"`.
- Перед архивом уборщик строит **весь каскад** (тред, его дети и скрытые форки рекурсивно) и применяет условия 1–5 §15 к каждой среде каскада; тред с неархивными детьми, незакрытыми делегированиями (`dispatching`/`running`) или ожидающими запросами не трогается.
- Удаление — **только архив** (`bb environment cleanup` не вызывается: BB удаляет копию сам). Ветка удаляется следующим прогоном, когда копии уже нет.
- Влитость при rebase (Сущ. ветки 2): второй признак — `git cherry origin/<база> <ветка>` без строк «+» (каждый коммит копии по patch-id уже на origin). Признак влитости задаёт только отсчёт `afterMerge` и отчёт; удалить копию разрешает лишь условие «ничего не теряется» ниже. Squash-слияние нескольких коммитов этим не распознаётся — такие копии уходят в отчёт, не удаляются.
- Свои коммиты (§15 п.2, §4.1 `result_commits`) — только **достижимые**: `git rev-list --count <старт>..<вершина ветки копии>`, где старт — первая запись reflog ветки «Created from <sha>» (нет reflog — своих коммитов нет). Перемотки и rebase без своих коммитов дают 0.
- **Ничего не теряется (главное условие удаления, ревизия 25; окончательно упрощено 11.11 по ревью PLUG-201).** Каждый коммит, на который когда-либо указывали HEAD или ветка копии (весь reflog HEAD и `refs/heads/<ветка копии>`, плюс текущие вершины), **и каждый его предок, которого нет на origin** (`git rev-list <все эти позиции> --not <удалённые ветки>`, без фильтра по reflog), обязан быть либо предком удалённой ветки (`origin/<защищённая>` или базовой), либо совпадать по `git patch-id --verbatim` с коммитом на ней (точное сравнение, включая пробелы и отступы — `--stable` их не различает; сверяется для самого коммита, `rev-list --no-walk`; пустой коммит — только предком). Позиции кроме HEAD и ветки копии — также `refs/worktree/*` и `refs/bisect/*` этой копии. **Признак «содержимое уже на origin» (`merge-tree`) для удаления не используется**: его обманывают драйверы слияния (`ours` из настроек, встроенный `union` из `.gitattributes`, имена с `=`) — три подтверждённые потери подряд. Хоть один коммит не прошёл — копия остаётся (`unpushed-commits`), при простое дольше `abandonedAfter` — в отчёт «брошено». Копия, чья ветка по `merge-tree` (с отключёнными атрибутами) совпадает с origin, но коммиты не прошли, — в отчёт с пометкой «похоже, влито squash — проверьте и удалите вручную», не удаляется. Подмодули (`.gitmodules` или `$GIT_DIR/modules`) — копия не удаляется (`has-submodules`). Проверка повторяется непосредственно перед архивом вместе с проверкой незавершённых merge/rebase/cherry-pick. Свои коммиты считаются строго `git rev-list --count <старт>..<вершина ветки копии>` (старт — «Created from»).
- Удаление ветки — `git update-ref -d refs/heads/<b> <проверенная вершина>` (атомарно против перестановки ветки между проверкой и удалением); непосредственно перед ним — заново `git worktree list --porcelain` (ветка не открыта ни в одной копии). Для `refs/worktree/*` и `refs/bisect/*` читается и их reflog, как у HEAD.
- Суточное сообщение координатору — только когда в списке брошенного появились новые копии.

### 16.4 Спасение незакоммиченного при архиве (Сущ. ветки 4)
На `thread.archived` треда-исполнителя с грязной копией плагин **всегда** (независимо от `janitor.enabled`) в окне 5 минут сохраняет состояние (неотслеживаемые файлы — через `--pathspec-from-file`; неполное спасение — строка координатору): `git stash create` (с неотслеживаемыми — через временный индекс) → `git update-ref refs/orchestrator/rescue/<id треда> <sha>`; координатору строка с командой восстановления в **новый** каталог (`git worktree add <каталог> <ref>^1` → `git stash apply <ref>` в нём), не в основную копию. Ref не удаляется уборщиком.

**Удаление треда (r29, разведка PLUG-238; правка после ревью спеки).** То же спасение — и на событие `thread.deleted`. При удалении треда BB снимает копию так же, как при архиве: `git worktree remove --force` через 5 минут (`retireGraceMs` 300000) после первого из событий «архив» или «удаление» — если тред сначала заархивировали, окно отсчитывается от архива. Ветка остаётся, незакоммиченное пропадает. Событие приходит сразу после мягкого удаления — по каждому треду каскада. Данные события такие же, как у `thread.archived`, проверка «тред — исполнитель плагина» та же.
1. Плагин подписывается на `thread.deleted` и вызывает ту же функцию спасения с причиной «удалён» (у архива — «заархивирован»); причина — единственное отличие в строках координатору.
2. **Когда спасать.** Фазу среды НЕ проверять: в момент события тред может ещё работать (ход останавливают через 30 с после архива), и у среды `phase=active`, хотя BB её потом снимет. Молчать только если у среды есть другой живой тред — не в архиве, не удалён и не тот, что пришёл в событии (тот же список тредов среды, что у уборщика); общую среду BB не снимает. Поля нет или ответ непонятен — спасать. Копии или среды уже нет (давно заархивированный тред, BB её снёс) — тишина, только журнал плагина; так же и при архиве (тест `thr_gone` не меняется).
3. **Повторный снимок.** Перед снимком сравнить новое состояние с уже сохранённым: деревья `<ref>^{tree}`, `<ref>^2^{tree}` и (если есть) `<ref>^3^{tree}`. Сравнивать с последним снимком (наибольший N). Совпадают — снимок не делать, строку не слать. Отличаются (архив → разархивировали → правили → удалили) — новый ref `refs/orchestrator/rescue/<id треда>-<N>` (N = 2, 3, …), прежние не трогаются; строка координатору с новым ref и каталогом восстановления `<repo>-rescue-<id>-<N>` (у первого снимка — прежний `<repo>-rescue-<id>`), чтобы не столкнуться с уже восстановленным.
4. **Гонки.** Ref создаётся атомарно: `git update-ref <ref> <sha> ""` (запишется, только если ref ещё нет). Отказ «ref уже есть» — не сбой: сравнить по п.3 с ref, который занят; отличается — пробовать N+1. Вызовы спасения для одного треда идут по очереди (очередь на id треда внутри плагина). Временный индекс — уникальный каталог (`mkdtemp`), а не имя из pid и времени.
5. **Сбой.** Копия есть и грязная, но снимок не удался (`HEAD` нет, `stash create` упал, `update-ref` упал не из-за «ref уже есть») — строка координатору, единая для обеих причин: «тред <id> <заархивирован|удалён> с несохранённой работой, снимок НЕ удался (<шаг>: <ошибка>) — копия <путь> уходит под уборку BB через ≤5 минут, проверь вручную». Слово «НЕ удался» остаётся (тест на архив не ломается). Функция снимка возвращает шаг и ошибку.
6. **Координатор удалён тем же каскадом** (по r27 исполнитель — дочерний тред координатора, удаление координатора удаляет и их). Если тред-координатор удалён или отправка строки не удалась — запись в журнал плагина (`warn`) с ref и путём; каждое спасение (и сбой) пишется строкой в хранилище плагина: тред, ref (у сбоя — пусто), корень репозитория, причина (заархивирован/удалён), ошибка сбоя (`<шаг>: <ошибка>`), время, дошла ли строка координатору (таблица `janitor_rescues`, §7); `janitor report` читает эту таблицу (не обходит репозитории — путь снесённой среды неизвестен), так спасённое не теряется без адресата.
7. Удаление треда плагин не задерживает: вето-хука у плагинов в BB нет.
8. Не покрыто (известное ограничение): удаление проекта или машины, `bb environment cleanup/delete` — BB снимает копию сразу, без окна; удаление, пока плагин не запущен, — события не переигрываются. Снимок делается в момент события, пока ход исполнителя ещё может идти (до 30 с после архива): правки, сделанные после снимка и до остановки, не попадут. Периодический снимок грязных копий — только если такие промахи появятся на деле.
9. Тесты: удаление грязного исполнителя → ref и строка «удалён»; архив и удаление без правок между ними → один ref, одна строка; архив → правка → удаление → два ref (`<id>` и `<id>-2`), две строки; архив и удаление параллельно → один ref, одна строка; копии нет при удалении → тишина; архив активного треда (`phase=active` в момент события) → ref и строка; у среды есть другой живой тред → тишина; поля нет → спасать; `<id>-2` → каталог `<repo>-rescue-<id>-2`; запись в таблице спасений и вывод в `janitor report`; сбой снимка при удалении → строка «НЕ удался» с шагом; координатор удалён → журнал и `janitor report`; удаление чужого треда → ничего; чистая копия → ничего. Тесты `thr_gone` и «НЕ удался» (архив) не ломать.

### 16.5 Доставка итога: BB основной канал, плагин — проверка и досылка (Сущ. доставка 3, заменяет §5.5; пересмотрено 11.11 после живой проверки)
Живая проверка 11.11: при `parentNotifications = stuck` справка BB велит исполнителю самому слать итог родителю через `bb thread tell` — итог приходил дважды (от исполнителя и от плагина). Поэтому:
- `delegate` ставит исполнителю `parentNotifications = auto` (как в §4 шаг 4): итог приносит BB уведомлением `child-completed` (`child-interrupted` для прерванного), исполнитель сам ничего не шлёт.
- Через 120 с после `done`/`cancelled` (и сверкой, пока не подтверждено) плагин ищет в журнале координатора после старта последнего хода исполнителя уведомление BB о нём: `systemMessageKind` `child-completed`/`child-interrupted` с `systemMessageSubject.threadId` = тред исполнителя, либо `child-outcome-batch`, в `outcomes` которого он есть; пачка без перечня тредов, пришедшая после конца хода исполнителя, тоже засчитывается. Нашлось — `result_notice = bb`, сообщения нет. Не нашлось — плагин досылает `[orchestrator] <KEY> (<уровень>, тред <thr>): <done|cancelled>, ветка <branch>, коммит <sha7>, копия <чистая|грязная>` + итог исполнителя (`threads.output`, до 3000 символов), `result_notice = plugin`. Пустой итог исполнителя — сообщение плагина всегда («закончил без отчёта»), ветка/SHA/чистота — всегда одной строкой плагина, если итог захода сомнителен (§4.1).
- Захват отправки, повтор сверкой, отметка `legacy` при выкатке — без изменений.
- Подтверждение остановки (§5.4): только статус `idle` или `error` (`stopping`/`starting` — не остановлен).
- Зависание после первого ответа: `routes.*.idleSeconds` (по умолчанию 1800) — нет ни одного события ответа дольше — одно сообщение координатору, без остановки. `startSeconds` (по умолчанию 600) — нет `turn/started` после раздачи — одно сообщение.
- Памятка после сжатия: если в журнале координатора есть событие сжатия контекста, плагин шлёт ему одно сообщение: правило §3 коротко, путь хендоффа, сводка `bb orchestrator status`. Нет такого события у провайдера — пункт приёмки.

### 16.6 merge и release (Сущ. ветки 1, выкладка 2, 5)
- `release <KEY>` публикует ветку, где лежит итог задачи: `merge_status = merged` — ветку `merged_into` из копии координатора, иначе ветку исполнителя. Переключение копии координатора на `merged_into` — под той же блокировкой копии, что у `merge` §14 (один `merge`/`release` на копию одновременно), с проверкой чистоты до переключения и тем же восстановлением; аудитор выкладки привязан к SHA, а не к ветке в копии: после выкладки (успех или отказ) копия возвращается к исходной ветке и HEAD с чистым `git status`, иначе ошибка `copy-not-restored`; грязная копия координатора — отказ до переключения.
- Все `git merge` плагина и инструкций (§4.1, §14, release sync) — с явным `-m` без имён веток и id тредов.
- Авторазбор конфликта — настройка `mergeAutofix` (по умолчанию `false`: только отчёт координатору). У владельца — `true`.
- Скан категорий 2–4 release — по патчу каждого коммита диапазона, не только по итоговому диффу. Номера тредов — настройка проекта release `threadIds` (по умолчанию `true`; решение владельца 11.11: номера тредов обезличены и нужны пайплайну, чтобы писать агентам-авторам). `true` — строка «Источник: bb тред thr_…» в теле PR, `thr_…` в коммитах и диффе не считается утечкой (категория `bbIds` для них отключена). `false` — строки «Источник» нет, `thr_…` **и ключи задач трекера** в сообщениях коммитов и диффе — находка по `leaks` проекта; `merge` (§14) в таком проекте пишет сообщение без ключа задачи (`merge r<N> (<sha7>)`). Настройка управляет всеми идентификаторами bb (треды и ключи задач): при `true` правила находок для `thr_…` **и** ключей задач выключены; при `false` оба включены, а плагин сам их не публикует — сообщение `merge` без ключа, в теле PR нет ни «Источник», ни «Задача: <KEY>», ветка на удалённом сервере для `target: pr` называется `release/<sha7 первого выпуска задачи>` — имя записывается при первом `release` и переиспользуется повторными (одна ветка и один PR на задачу; локальное имя ветки исполнителя `bb/<key>-…-thr_…` не публикуется); заголовок PR — тема HEAD-коммита, если в ней нет идентификаторов bb (`thr_…`, ключ задачи); иначе или без темы — `release <sha7>`; никогда не название задачи. Имя ветки публикации записывается и переиспользуется только вида `release/…` (после переключения `threadIds` с `true` на `false` ветка исполнителя не публикуется). Итог, влитый `merge` (§14), синхронизируется с целевой веткой только слиянием (`sync: rebase` для него не применяется — rebase потерял бы правки разрешения конфликта в merge-коммите). Уже опубликованную историю не переписывать (force-push запрещён).
- Гейт выкладки (общий хук) — **защита от забывчивости**, не от умысла: агент того же пользователя может записать токен сам. Жёсткий гейт — защита ветки на стороне хостинга (обязательные проверки); решение пользователя, навык `orchestrator-setup` предлагает. Владелец 11.11: мягкий гейт достаточен; где важно — защита ветки на хостинге (переезд проекта на GitLab с закрытым push в main). Токен — на ветку и SHA, файл на запуск `release`.

### 16.7 Вердикт ревьюера и роль по умолчанию (выкладка 3, 4)
- Ревьюер (роль `auditor`) заканчивает отчёт строкой JSON `{"verdict":"OK"|"CHANGES","blockers":<n>}`; `release` шаг 1 читает её, а не прозу; нет строки — не ОК.
- **Вердикт обязателен (r31, 12.11, слово владельца; правки после двух ревью спеки).** Касается тредов-ревьюеров (роль `auditor`) и аудитора выкладки (`release-auditor`). Проверка — до перевода делегирования в `done`, когда ход такого треда закончился и у треда нет незавершённых фоновых задач (`item/backgroundTask` без завершения — провайдер сам поднимет ход, ждём его). **Где искать вердикт:** у ревьюера — строка JSON `{"verdict":…}` в последнем комментарии агента в задаче, а если там её нет — в последнем сообщении треда; «вердикта нет» — только если строки нет ни там, ни там (комментарий «тесты идут» без JSON — не «не ОК», а «нет вердикта»); у аудитора — только последнее сообщение треда (как читает конвейер). Гейт шага 1 выкладки (`reviewVerdict`) ищет вердикт ревьюера **в том же порядке** (комментарий без JSON → последнее сообщение; нет нигде — «нет вердикта», а не «не ОК»), чтобы сторож и гейт не расходились. Вердикт есть — обычный путь. Нет — делегирование остаётся `running`, плагин записывает `verdict_nudged_at` и seq/время отправки и шлёт в тред одно напоминание «заверши вердиктом: дождись проверок в этом же ходе (не фоном) и закончи строкой JSON …»; своя досылка итога §16.5 по этому концу хода не делается. Уведомление BB `child-completed` (у ревьюеров `parentNotifications=auto`) плагин отменить не может — оно придёт; навык координатора: «ревьюер закончил без вердикта — плагин уже напомнил, сам не буди». Второй промах засчитывается только по ходу, начавшемуся после напоминания (`turn/started` позже записанного seq); пока такой ход не начался, работают обычные таймеры сторожа §5 (зависание, квота). Снова без вердикта — `done` без ОК и **одна** строка координатору «ревью <KEY> без вердикта: <тред>» (вместо досылки итога, не вдобавок); у аудитора — отказ выкладки «аудит без вердикта», выкладка `rejected`. Напоминание — одно на делегирование. 12.11: Gemini трижды и Opus один раз заканчивали ход, оставив тесты в фоне; координатор будил их вручную. Тесты: без вердикта → `running` + одно напоминание без досылки; затем вердикт → обычный путь; снова без вердикта (ход после напоминания) → одна строка / отказ; старый `turn/completed` до нового хода → не второй промах; фоновая задача не завершена → ждём без напоминания; комментарий без JSON и вердикт в сообщении → без напоминания; аудитор с JSON только в комментарии → напоминание.
- Пока политика не валидна (`needs-configuration`), роль по умолчанию корневого чата (согласовано владельцем 11.11) — без роли (только навык `orchestrator-setup`); `orchestrator` — после валидной политики. Это действует и на выбор `orchestrator` в окне нового чата (окно записывает его само при открытии) и на запасную выдачу при ошибке: без валидной политики роль `orchestrator` получает только навык настройки — ни инструментов, ни инструкции координатора.

## 17. Ревизия 26: решения по финальному аудиту реализации и e2e (12.11)

Раздел **перекрывает** §2–§16 там, где расходится. Источники: аудит реализации (PLUG-206) и живая сквозная проверка на провайдерах (PLUG-205).

### 17.1 Роли (Б3 аудита)
Роль по умолчанию `orchestrator` — только корневым тредам, созданным человеком или агентом: `origin` `app` (окно нового чата, по `pending_roles`) или `cli` (`bb thread spawn`). Треды, созданные плагинами, SDK и автоматизациями (`origin` `plugin`/`sdk`/автоматизация — advisor, live-call, perspectives и т. п.), роли не получают: ни инструментов раздачи, ни инструкции координатора. Вживую 84 из 101 решения хука были такими тредами. Исключение — плагины, продолжающие чат человека (передача сессии другому агенту): настройка `userThreadPlugins` (по умолчанию `["handoff", "external-compact"]` — передача сессии и сжатие чата в новый тред) — их тред наследует роль источника, а без известного источника получает `orchestrator`, как чат из окна. Правило про родителя важнее: тред с родителем — исполнитель, даже если его создал такой плагин. Известное ограничение (12.11): BB не отдаёт тредам `handoff` источник (`sourceThreadId` пуст у всех 17 живых), поэтому корневой тред передачи без родителя получает `orchestrator`, даже если владелец передал в другого агента тред исполнителя; вживую таких нет (18 тредов с ролью `orchestrator` — корневые чаты владельца и тестовые координаторы, ни один не исполнитель). Если понадобится — роль меняется вручную, BB-источник появится — наследование заработает без правок плагина.

Уже записанные роли (по ревью PLUG-211): строки `thread_roles` с `orchestrator` у тредов плагинов вне `userThreadPlugins` переписываются на «без роли» — разово миграцией и лениво в `configure` (у треда есть `originPluginId` не из списка). Ленивая правка двусторонняя: тред плагина из `userThreadPlugins` без родителя с «без роли» получает `orchestrator` обратно.

Инструкции ролей `orchestrator` и `executor` дополнительно содержат запрет: не выполнять `sudo`, не ставить пакеты и не менять машину вне своей рабочей копии — только сообщить координатору (e2e 12.11: тестовый координатор выполнил `sudo apt-get install`).

### 17.2 Сторож и доставка
- `done` только при прочитанном `turn/completed` последнего хода и треде, перечитанном непосредственно перед записью статуса (новый ход уже начался — не `done`) (С2).
- Смена `result_sha` (оживление, новый ход) сбрасывает `merge_status`, `merged_*` этого делегирования (С3).
- `merge`, вызванный по уведомлению BB раньше, чем сторож записал `done` (уведомление приходит за секунды до сверки): `merge` сам запускает сверку **новейшего** делегирования исполнителя задачи (любого захода) и только потом выбирает итог — иначе после захода 2 он вольёт итог захода 1 или ответит `already-merged` по нему (e2e 1). Новейший заход в `failed`/`stalled`/`quota`/`dispatching`/`running` — отказ с подсказкой `merge <id>` для прошлого захода; прошлый берётся сам только если новейший отменён (`cancelled`). Поиск события сжатия для памятки — по типу событий, а не среди последних 50 любых. Нет точки начала ветки (`continue_from`, «Created from») — проверка «коммитов нет» пропускается, а не даёт 0. Заход аудита выкладки считается отдельно от заходов исполнителя (свой резерв). Причина недиспатчабельного маршрута пишется в задачу один раз. Отмена делегирования самим координатором (`orchestrator cancel`) не порождает сообщения «закончил без отчёта» — только шапку `cancelled`, если уведомления BB о прерывании не было.
- Номер захода (`round`) считается только по делегированиям с ролью `executor` (ревью и аудит выкладки номер не сдвигают) (e2e 2).
- Тихая остановка прошлого захода (§16.2): перед `threads.stop` плагин ставит треду `parentNotifications = off`, после подтверждённой остановки возвращает `auto` — иначе BB шлёт координатору уведомление о прерванном ходе (e2e 4). Перед `off` записывается отметка; сверка (§7) возвращает `auto` любому треду с отметкой, если остановка завершена или не подтвердилась (перезапуск, сбой между шагами) — уведомления не остаются выключенными.
- Сжатие контекста координатора распознаётся также по `item/completed` с типом `contextCompaction` (Codex не шлёт `thread/compacted`) (e2e 7). Памятка — только по делегированиям этого координатора; опрос только координаторов с активными делегированиями (мелко 6).
- Окно первого ответа для `--preset`: `routes.*.firstResponseSeconds` любого маршрута политики с тем же провайдером, иначе необязательное поле политики `firstResponseSecondsByProvider` (`{"codex": 300}`), иначе общее (e2e 8).
- Маршрут, который нельзя раздать (отказ dispatch: неверный уровень рассуждений, снятая модель), — причина комментарием в задачу и строкой координатору (e2e 6).
- Автоперевыпуск «один на маршрут» — в пределах захода, не всей жизни задачи (мелко 4).
- `result_commits` и «коммитов нет» — от `continue_from` (заходы 2+) или «Created from», не от `mergeBaseBranch` (мелко 1).
- Ограничение BB, вне плагина: назначение родителя шлёт координатору «is now a child» (вживую 95 из 383 запросов) — плагин его не подавляет (§12).
- Уведомления трекера о комментариях доставляет плагин `tasks` по своим правилам (вживую — автору последнего комментария агента, с `--notify`); правило §16.2 применяется к любому такому пробуждению.

### 17.3 merge и release
- `release` выполняется **вне** очереди `delegate` (в очереди — только раздача аудитора выкладки) (С1).
- Гейт ревью привязан к публикуемым коммитам и проверяется **на шаге 1** (приёмка), до любых действий конвейера (Б4; по ревью PLUG-210):
  - публикуемая вершина = ветка исполнителя → она обязана совпадать с `result_sha`, и на `result_sha` есть ОК-ревью; иначе `unreviewed-commits` со списком лишних коммитов (уже опубликованное — предки `origin/<цель>` и прошлого `published_sha` — лишним не считается); вершина для аудита и публикации — ровно та, что сверена, без повторного чтения `HEAD`;
  - публикуемая вершина = ветка `merged_into` → проходит, если есть ОК-ревью **на самой вершине** (покрывает всё под ней, включая коммиты координатора — например документы, которые по release §1 правит координатор), либо у каждого влитого делегирования, ещё не опубликованного (после последнего `published_sha` / вне `origin/<цель>`), есть ОК-ревью на его `merged_sha` и сверх влитого нет коммитов, кроме созданных самим конвейером; иначе `unreviewed-commits`;
  - коммиты, которые создал сам конвейер (синк-слияние, правка трейлера `--no-docs`), записываются в `releases` и в гейте не считаются чужими, в том числе на повторном запуске после отказа;
  - коммит слияния, которого нет в копии, — понятный отказ, не ошибка git;
  - вершина, проверенная гейтом (после синк-слияния), запоминается; после проверок проекта и перед аудитом/публикацией `HEAD` обязан с ней совпадать, иначе `unreviewed-commits`; на пути ветки исполнителя — отказ на шаге 1, если у его треда идёт ход (по ревью PLUG-214);
  - ОК-ревью на коммите **ниже** вершины засчитывается, если все коммиты между ним и вершиной создал сам конвейер (`pipeline_shas`) — повтор после отказа;
  - влитые делегирования отбираются по ветке **и** проекту; проверка fast-forward от прошлой опубликованной вершины — на шаге 1;
  - ход исполнителя «идёт», если статус треда не `idle`/`error`; запрос `client/turn/requested` на остановленном треде считается ходом не дольше 2 минут;
  - при rebase пустые коммиты сопоставляются с исходными по автору и сообщению.
- `target: pr`: URL PR читается из stdout `gh pr create` текстом (Б1).
- Повторный `release` после нового захода — продолжает ту же ветку публикации от `published_sha` (fast-forward), в тот же PR (С4).
- Пост-проверка `push`: `git rev-list <новые> --not <pushedSha>` (С5).
- Настройки проекта release `allowedTrailers` (например `Co-Authored-By`, `Signed-off-by`) и `allowedEmails` (адреса и домены, не считающиеся утечкой) (С6). Элемент `allowedTrailers` — имя трейлера (разрешены все значения) или «имя: начало значения» (`Co-Authored-By: Claude` разрешает `Co-Authored-By: Claude Opus …`, но не `Co-Authored-By: Devin …`); сравнение без учёта регистра (по согласованию с куратором проекта 12.11). Слово владельца 12.11: трейлеры `Co-Authored-By` (ни Claude, ни Devin) не разрешены ни в одном проекте — `allowedTrailers` с ними из настройки убраны.
- Позиционные аргументы CLI `release` не захватывают значения `--no-docs`, `--kb`, `--no-kb` (мелко 7). Вердикт ревью — из комментария задачи, а без него из итога треда ревьюера (мелко 5).
- `merge` читает `janitor.protectedBranches` (мелко 2). `--level release-audit` координатору запрещён; `--preset` сверяет уровень с политикой (мелко 3).
- **Общий хук:** установщик ставит обёртки для **всех** имён хуков из `githooks(5)`, включая `reference-transaction` и серверные (`pre-receive`, `update`, `proc-receive`, `post-receive`, `post-update`), **кроме `push-to-checkout`** — само наличие этого хука отключает встроенное обновление рабочего дерева при `receive.denyCurrentBranch=updateInstead` (по ревью PLUG-214); установщик берёт каталог токенов только у плагина (`bb orchestrator hooks-dir`), недоступен — отказ с подсказкой; проверка «`core.hooksPath` уже задан другим» — до копирования файлов; каждая вызывает локальный `$GIT_DIR/hooks/<имя>` **только если он исполняемый** (как сам git; неисполняемый — пропуск), передаёт аргументы, stdin и код выхода — иначе глобальный `core.hooksPath` отключает остальные хуки (Б2). Проверка свежести установки отказывает и при **отсутствии** любой обёртки (старая установка только с `pre-push`). Каталог токенов установщик берёт у плагина (`bb orchestrator hooks-dir`), а не вычисляет сам. Каталог токенов — единый путь, который знают и плагин, и установщик (каталог данных плагина; запасной `/tmp` убрать) (мелко 9).

### 17.4 Уборщик
- Список тредов — через SDK постранично, не одним выводом CLI (С7).
- Обход файловой системы копии — асинхронно или отдельным процессом (`find`), не блокируя процесс сервера (С8).
- `mode: report` пишет строки журнала уборщика для всех состояний (без `first_seen_at` — отсчёт `afterMerge` не начинается) и показывает строки «готова к удалению» — только то, что `apply` действительно удалит (с учётом `deleteBranches` и живых тредов); `--dry-run` ничего не пишет, только показывает; `janitor report` выводит строки последнего прогона (С9). Список тредов читается постранично **дважды** подряд, наборы id сравниваются (дубли внутри прохода убираются; треды, созданные после начала первого прохода, в сравнении не участвуют, но входят в итоговый список — объединение проходов); наборы различаются — один повтор пары проходов, затем «список не доказан» (`threads-unknown`) с записью в журнал плагина (размеры наборов, разница). **Восстановимость (по ревью PLUG-218):** перед каждым удалением уборщик записывает SHA — вершину ветки (`janitor_items.tip_sha`) и HEAD копии с вершиной её ветки при архиве — и строки в журнал плагина: `removing <что> <репозиторий>:<ветка> at <sha>` до удаления (строка уборщика в состоянии «удаляется») и `removed …` после; `report --json` показывает SHA у строк «удалено» и «удаляется»; копия, которой уже нет, со строкой «удаляется» закрывается как удалённая; если прогон в итоге оставил копию, к строке `removing` пишется парная `kept … (removal cancelled: <причина>)`; `janitor run/report --json` выводит их; README — команда восстановления `git branch <ветка> <sha>` (работает, пока `gc` не убрал объекты, ≈2 недели). Сверка по `threads.count` не используется: обёртка SDK не передаёт серверу флаги `includeArchived`/`includeHidden` (живой замер 12.11: 504 против 2400) и одно сочетание «удалили на прочитанной странице + создали на непрочитанной» она не ловит. Отказ из-за версии git — записанный прогон с ошибкой и ненулевой код выхода `janitor run`.
- Среды со статусом `ready`, чей каталог отсутствует (вживую 307), — отдельная причина `missing-dir` с учётом `lifecycle`; тред такой среды без детей и активных делегирований — в отчёт (удалять нечего, решает пользователь) (мелко 8).
- Минимальная версия git — 2.39 (`patch-id --verbatim`; `merge-tree --write-tree` — 2.38); ниже — уборщик и `merge --dry-run` отказывают с подсказкой. Пути из git — с `-c core.quotePath=false -c diff.mnemonicPrefix=false` (мелко 11).
- Ограничения (документировать в README): исполнители на другой машине не поддержаны (итог захода, `merge`, спасение читают копию локальным git); без `/proc` уборщик ничего не удаляет.

## 18. Ревизия 32: универсальность и свои сценарии (12.11, слово владельца «делай все 5»; переписано после аудита Fable 5.2)

Цель: плагин ставят люди на своих стендах с другими языком, раскладкой репозиториев, хостингом кода и процессами. Всё, что заточено под стенд автора, становится настройкой; прежнее поведение установки автора сохраняется её явными значениями. Правило для будущих правок: ни одного буквального предположения о проекте, раскладке, языке, хостинге или процессе в коде — только настройка с документированным значением по умолчанию. **Главный контракт выкладки — [release](orchestrator-release.md) §2 п.0–5; здесь — схема настроек и общие механизмы; при расхождении главная — release-спека.**

### 18.1 Язык (`language`)
- Настройка плагина `language`: `en` | `ru`, по умолчанию `en`. Все тексты, которые плагин порождает для людей и агентов, — из каталога строк `src/i18n/<язык>.ts` по ключам: строки координатору, итоговые строки выкладки и отказы, комментарии в задачи, инструкции исполнителю (строка «задача без кода», «Заход N», напоминание о вердикте), правило координатора, тексты ролей, памятка git по умолчанию, ответы CLI и инструментов, тексты сторожа и уборщика, тексты UI (`app.tsx`), тексты git-хука `pre-push`.
- **Не переводятся** (машинные контракты): JSON вердикта, коды ошибок (`release-refused`, `dispatch-unknown` …), имена полей и настроек, маркеры тела PR, которые плагин разбирает (§18.6 `prBody`), метки в журналах, которые ищут тесты, — тесты проверяют тексты через ключи каталога.
- Нет ключа в выбранном языке — `en` и предупреждение в журнал.
- Формулировки, которые спеки требуют «ровно такими» (release §2 п.2 и др.), — это значения каталога `ru`; у `en` — их перевод в каталоге, тесты сверяют по ключу.
- **Памятка git (§2.2):** значение настройки `gitInstructions`, совпадающее со встроенным текстом любого языка, считается «по умолчанию» (пустая строка по-прежнему значит «раздел не добавляется», §2.2) и выводится на текущем языке; изменённое владельцем — как есть.
- **Навыки:** два набора с разными именами — `orchestrator-coordinator`/`orchestrator-setup` (английские) и `orchestrator-coordinator-ru`/`orchestrator-setup-ru`; плагин объявляет (`configure`) только набор текущего языка.
- **Git-хук `pre-push`:** его тексты версионированы вместе с языком; смена языка переустанавливает хук (иначе `hook-stale`).
- **Подписи настроек в схеме BB** — английские (схема одна на все языки); README — английский, `README.ru.md` — русский.
- Окно при выкладке задачи о языке: координатор задаёт `language: "ru"` у себя до публикации, если BB принимает неизвестный ключ настройки; иначе окно (английские тексты до задания ключа) принимается.

### 18.2 Шаги после выкладки — схема (поведение — release §2 п.2)
```
"postPublish": {
  "on": "published" | "merged",          // по умолчанию: push → published, pr → merged
  "checkout": "<путь>",                  // необязателен; нет — без ff и перезагрузок
  "branch": "<ветка копии>",             // по умолчанию цель
  "reloadPlugins": false,                // по умолчанию false (как сейчас в коде); установка автора — true явно
  "commands": [ { "name": "deploy", "run": ["argv", "..."], "cwd": "checkout" | "<путь>",
                  "timeoutSec": 300, "when": ["<шаблон>", ...], "stopOnFail": false,
                  "installsDeps": false } ]
}
```
- `when` — по диапазону выкладки (`remote_base_sha..published_sha`), вычисляемому в **основном каталоге репозитория** (копию исполнителя к `merged` мог убрать уборщик); шаблон сопоставляется с полным путём от корня репозитория; диапазон не вычислился (нет базы — первая выкладка в новую ветку; git упал) — команда выполняется. Диалект шаблонов: `*` (без `/`), `**` (любые каталоги), `?`; своя реализация без новых зависимостей.
- Окружение команды: `ORCH_EVENT` (`release.published` или `pr.merged`), `ORCH_TASK`, `ORCH_SHA` (опубликованный коммит; для `merged` — коммит слияния, если провайдер его вернул, иначе опубликованный), `ORCH_BRANCH`, `ORCH_TARGET`, `ORCH_REPO_DIR` (основной каталог репозитория — путь, не URL); аргументы — только из настройки, данные задачи в аргументы не подставляются.
- `cwd` по умолчанию — `checkout`, если он задан, иначе основной каталог репозитория; `cwd: "checkout"` без `checkout` — ошибка настройки (предупреждение при чтении, команда не выполняется: «<name>: нет checkout»).
- `name` уникален в списке (дубль — ошибка настройки при чтении, вторая команда не выполняется).
- `stopOnFail: true` и исход не `ok` — остальные команды получают «<name>: пропущена — не прошла <имя>», перезагрузок нет.
- `on: "merged"` при `push` — ошибка настройки (предупреждение, считается `published`); `on: "merged"` при `prProvider: none` — ошибка настройки (предупреждение: шаги не выполнятся никогда — слежения нет).
- Команды и хуки (§18.5) — один запускатель с одним журналом.

### 18.3 Провайдер PR (`prProvider`)
- `{ "type": "github" }` — по умолчанию, `gh`; `{ "type": "command", "create": [...], "view": [...], "find": [...]? }`; `{ "type": "none" }`.
- Контракт `command`: каталог запуска — основной каталог репозитория, таймаут `timing.prCommandTimeoutSec` (60). `create`: окружение `ORCH_BRANCH`, `ORCH_TARGET`, `ORCH_TITLE`, тело PR в stdin, печатает URL (`https?://\S+` — первая такая строка); ненулевой код выхода — отказ, даже если URL напечатан; нет URL — отказ «PR не открыт: <вывод>» (ветка уже запушена, повтор `release` откроет PR). Весь вывод провайдера в строках («PR не открыт», «слежение невозможно») — через ту же очистку, что вывод команд (§18.5). `view`: окружение `ORCH_PR_URL`, печатает JSON `{"state":"OPEN"|"MERGED"|"CLOSED","mergeCommit":"<sha>"|null}`; иное — ошибка провайдера (идёт в `timing.prErrorLimit`). `find` (необязателен): окружение `ORCH_BRANCH`, `ORCH_TARGET`, печатает URL открытого PR ветки или пусто. Без `find` повторная выкладка задачи переиспользует `pr_url` прошлой выкладки этой задачи и ветки, если `view` = `OPEN`; иначе `create`.
- **Чей PR.** Если в теле PR есть маркер (`prBody` с `{thread}`) — проверка §16.6 по маркеру (узнаются и прежний «Источник: bb тред», и `BB-Thread:`). Маркера нет (`threadIds: false`, шаблон без `{thread}`, провайдер `command`) — «свой PR» определяется по своим записям: `pr_url` прошлых выкладок этой задачи этим координатором; иначе PR считается чужим и `release` в него не пишет.
- `none` — ветка выпуска публикуется, PR не открывается: строка «ветка опубликована: <ветка>; PR открой вручную», задача `in_review`, слежения нет.
- Доступность провайдера проверяется на шаге 1 выкладки, до аудита (release §2 п.0).

### 18.4 Сроки (`timing`)
- Поле `timing` настройки выкладки (`defaults` и проект; слияние **по ключам**, а не заменой объекта): `auditTimeoutMinutes` 30, `checksMinutes` 10, `prepareMinutes` 20, `prPollMinutes` 5, `prStaleHours` 72, `prReopenWatchHours` 72, `prErrorLimit` 3, `prCommandTimeoutSec` 60, `commandTimeoutSec` 300 (по умолчанию для команд `postPublish`); у хуков свой срок — `timeoutSec` хука, по умолчанию 120 (хуки не привязаны к проекту выкладки).
- Сроки сторожа — в политике: уже есть `firstResponseSeconds` и др.; в `policy.timing` переносятся: `quotaHoldMinutes` 15 (удержание маршрута при квоте), `approvalRepeatMinutes` 10 (повтор «ждёт решения»), `postDispatchGraceMinutes` 5 (отсрочка после раздачи), `bbNotifyWaitSeconds` 120 (ожидание уведомления BB). Такты 5 с и 60 с остаются константами.
- Пределы: минуты 1…1440, часы 1…720, секунды 5…3600, счётчики 1…100; вне пределов или не число — предупреждение в журнал и `status`, значение по умолчанию.
- Числа в текстах строк подставляются из `timing`.

### 18.5 Запускатель команд и хуки событий (`eventHooks`)
**Один запускатель** для `postPublish.commands` и хуков:
- Журнал `command_runs`: `id`, `source` (`postPublish`|`hook`), `run_key` (для команды — id выкладки + имя; для хука — id события + имя хука), `name`, `status` (`queued`|`running`|`ok`|`failed`|`timeout`|`interrupted`|`skipped`), `pid`, `pgid`, `proc_start` (время старта процесса из `/proc/<pid>/stat` — защита от переиспользования pid), `exit_code`, `output_tail`, `queued_at`, `started_at`, `finished_at`. `queued` — запланирован, процесс не стартовал (повтор после рестарта безопасен); `running` пишется **до** запуска процесса, итог — после. `run_key` уникален: один ключ — не больше одного процесса.
- **Процесс команды:** запускается в своей группе процессов (`setsid`/`detached`). Таймаут и остановка плагина шлют SIGTERM **группе**, через 10 с — SIGKILL; итог — `timeout` или `interrupted`.
- **После рестарта** плагина: записи `queued` запускаются; записи `running` — если процесс с `pid` и тем же `proc_start` жив, группа завершается (SIGTERM → 10 с → SIGKILL), затем запись `interrupted`; **не повторяются**; в итоговой строке — «<name>: прервана перезапуском». Завершение записи — условным переходом из `running` (если старый экземпляр плагина допишет итог позже — проиграет переходу и не перезапишет).
- **Самоперезагрузка orchestrator не выполняется**, пока в журнале есть `running`: «orchestrator: идут команды — перезагрузи позже» (как у провайдеров с ходами). После постановки самоперезагрузки новые команды и хуки остаются `queued` (запустятся новым процессом) — окно до перезагрузки их не убьёт.
- Живость после рестарта проверяется по **группе** процессов (`pgid`: есть ли живые члены группы), а не только по `pid` лидера.
- `stopOnFail` и рестарт: команда, прерванная рестартом, считается не `ok` — следующие команды этой выкладки получают «пропущена — не прошла <имя>», а не запускаются.
- Выполнение — вне такта сторожа. Порядок: команды одной выкладки — по очереди; разные копии и хуки — параллельно, не больше `maxConcurrentCommands` (настройка плагина, по умолчанию 4); команды с `cwd: checkout` держат замок на копию (тот же, что у ff и перезагрузок). Срок хранения `command_runs` и `events` — 30 дней (`retentionDays`).
- Вывод: последние 300 символов, одной строкой, без управляющих символов, через маскировку секретов: правила категории утечек release §4 плюс для вывода команд — логин/пароль в URL (`scheme://user:pass@`), `glpat-…`, `Authorization: Bearer …`/`Bearer <токен>`, пары `token=`, `password=`, `secret=`, `apikey=` (значение маскируется). README: маскировка — не гарантия, команды не должны печатать секреты. Все значения, подставляемые в скрипт самоперезагрузки (текст строки, путь `rootDir`, SHA), — файлом или base64, не интерполяцией в shell.
- Команды запускаются списком аргументов без shell; `sh -c` — только если владелец сам так написал.

**Хуки событий** — настройка `eventHooks` (имя `hooks` занято git-хуками): `[{ "name", "on": ["<событие>"...], "run": [...], "projects": ["proj_…"]?, "timeoutSec": 120, "notifyOnFail": false }]`.
- События пишутся в таблицу `events` (`id`, `kind`, `payload` JSON, `created_at`) **в той же транзакции**, что и переход, который их порождает, и **в той же транзакции** событие сопоставляется с хуками, действующими в этот момент: для каждого подходящего — запись `command_runs` со статусом `queued` (ключ — `event_id` + имя хука). Позже событие с хуками больше не сопоставляется: хук, добавленный или переименованный после события, по нему не запускается. Таблица `events` начинается пустой: история до миграции событий не порождает.
- **Переход → событие** (версия 1):

| Переход | Событие | Примечание |
|---|---|---|
| делегирование → `done` | `delegation.done` | все уровни, включая ревью; кроме `release-audit` (его исход — события выкладки) |
| → `failed` | `delegation.failed` | |
| → `stalled` или `quota` | `delegation.stalled` | `reason`: `stalled`/`quota` |
| делегирование ревью → `done` с прочитанным вердиктом (r31) | `review.verdict` | `verdict`, `blockers`; один раз на делегирование (отметка в записи), чтение вердикта на шаге 1 выкладки события не порождает |
| выкладка → `published` | `release.published` | |
| → `rejected` | `release.rejected` | |
| → `failed` | `release.failed` | |
| PR → `merged` / `closed` | `pr.merged` / `pr.closed` | |
| `cancelled`, `reissued`, промежуточные | — | внутренние, событий нет |
| оживший тред (§16.2): `done` → `running` → снова `done` | `delegation.done` повторно | норма: это новый итог, у события новый `id`; хуки должны быть идемпотентны по `delegationId`, если им это важно |

- **JSON события** (stdin хука; версия 1): `{ "version": 1, "event", "at", "task", "project", "coordinatorThreadId", "delegationId"?, "level"?, "route"?, "threadId"?, "reason"?, "verdict"?, "blockers"?, "releaseId"?, "sha"?, "branch"?, "target"?, "prUrl"? }`; окружение: `ORCH_EVENT`, `ORCH_TASK`, `ORCH_PROJECT`. Новые поля добавляются, существующие не меняются без новой версии. `project` — у событий делегирования проект делегирования, у событий выкладки и PR — проект настройки выкладки (`settings_project_id`); `projects` хука сравнивается с ним же.
- `notifyOnFail` по умолчанию `false`; при `true` — одна строка координатору на **серию** сбоев хука («хук <name> на <событие> упал: <итог>»), следующая — только после успешного запуска этого хука.
- **Доверие.** Настройки плагина может изменить любой тред с доступом к `bb` CLI (агенты с shell), поэтому изменения **исполняемых настроек** отслеживаются: это `eventHooks`, `postPublish.commands`, `prProvider` с `command`, `checks` (выполняются через `sh -c`). Плагин хранит в своей базе снимок — хеш каждой исполняемой записи по имени (проект + поле + имя) — и сверяет его при старте и при смене настроек; так изменение видно и после `bb plugin reload`. Первый снимок (после установки или миграции) записывается **молча**. Расхождение — запись в журнал плагина и в `status` (только **имена** изменённых записей и хеши, без значений — в аргументах бывают секреты) и одна строка координаторам, у которых есть делегирование или выкладка не в конечном статусе: «изменены исполняемые настройки: <имена>»; таких нет — только журнал и `status`. Журнал изменений появляется в PLUG-245 вместе с `postPublish.commands` (окна без журнала нет). README предупреждает: хуки и команды выполняются от пользователя BB; давать агентам shell = доверять им это.

### 18.6 Процесс автора — тоже настройки
- **Тексты ролей** — настройка `roleTexts` с ключами только `orchestrator`, `executor`, `auditor` (дополнение к тексту роли, а не замена; предел BB 2500 символов на итог); `release-auditor` не переопределяется. Обязательные части плагин добавляет сам и пользователь их не убирает: запрет `sudo`, установки пакетов и изменений хоста (§17.1), строка JSON-вердикта у `auditor` (r31). Изменения текстов по умолчанию — только эти: запасной путь хендоффа — настройка `handoffPath` (по умолчанию `$BB_THREAD_STORAGE/HANDOFF.md`, без путей автора); «спека и ADR» → «документация проекта»; имя уровня ревью — из политики, а не буквальное `review`. Установка автора получает прежний смысл без `roleTexts` (тексты по смыслу не меняются).
- **Тело PR** — шаблон `prBody` настройки выкладки с подстановками `{thread}`, `{task}`, `{title}`; по умолчанию: `BB-Thread: {thread}` и `BB-Task: {task}`. При `threadIds: false` шаблон не применяется — тело пустое, как сейчас (§16.6: id треда и ключ задачи не публикуются). Разбор «чей PR» — §18.3. Установка автора задаёт прежний шаблон явно (`Источник: bb тред {thread}` / `Задача: {task}` — на него завязан CI/CD growthhack). release-спека §2 шаг 6 и §6 переписаны под `prBody` и `prProvider`.
- **Заметка в базу знаний** (`--kb`/`--no-kb`) — флаги остаются необязательными, как сейчас; опция `requireNote` (по умолчанию `false`) при `true` делает отказ шага 1 без одного из флагов: «нужна заметка: --kb <заметка> или --no-kb <причина>». Установка автора — `false` (поведение не меняется). Строка «KB-заметка» в итоговой строке — ключ каталога.
- **Умолчания скана утечек**: нет `commitIdentity` — проверка автора не блокирует, а предупреждает (строка в `status` «автор коммитов не задан»). Трейлеры — новая настройка `leaks.trailers`: `block` | `warn`, по умолчанию `warn` для новых установок; `leaks` проекта сливается с `defaults.leaks` **по ключам** (как `timing`), а не заменяет его целиком; release §4 (категории 1–2 «отказ всегда») уточняется: трейлеры — по `leaks.trailers`, секреты — отказ всегда. Установка автора — `leaks.trailers: "block"` и `commitIdentity` (уже задан) **явно, до выкладки PLUG-249** (слово владельца 12.11: подписи `Co-Authored-By` запрещены). Навык настройки ведёт пользователя по `commitIdentity`, `allowedTrailers`, `leaks`.
- `userThreadPlugins` по умолчанию пуст.
- Платформа: Linux (используются `sh`, `/proc`, группы процессов); macOS и Windows не поддерживаются. Внешние программы: `git` ≥ 2.39, `gitleaks` (без него выкладка отказывает), `gh` — только для `prProvider: github`. Всё записано в README.
- Реестр провайдеров не прочитан — перезагрузка пропускается для **всех** плагинов (а не по слову `provider` в id — это было соглашение автора об именах).

### 18.7 Что остаётся завязанным и почему
- Стартовый промпт исполнителя — копия шаблона BB (§4 r30 б): дрейф при обновлении BB принят, тест разделов ловит расхождение, запасной путь — `bb tasks dispatch`.
- Протокол с BB (события, `threads.spawn`, `bb automation`) — платформа плагина.
- Инструменты стенда автора (синхронизация второго пользователя, `safe-push.sh`) — вне плагина.

### 18.8 Порядок работ и приёмка
Строго последовательно (миграции только добавлением в конец, перестановка относительно применённых ломает загрузку; общий запускатель):
1. **PLUG-245** — запускатель и журнал `command_runs` (§18.5 первая часть: группы процессов, `queued`, завершение после рестарта, очередь и пределы, срок хранения, маскировка), журнал изменений исполняемых настроек (§18.5 «Доверие»), `postPublish` r11 (любая раскладка, `commands`, `on`, `installsDeps`, без `checkout`), `timing` (release + политика), строки п.2–4 из `timing`.
2. **PLUG-248** — `prProvider` (github/command/none, `find`, проверка на шаге 1), `prBody`, `requireNote`.
3. **PLUG-246** — `eventHooks`, `events`, таблица переходов, доверие (журнал и строка об изменении исполняемых настроек); запускатель — из PLUG-245.
4. **PLUG-249** — `roleTexts`/`handoffPath`, умолчания скана, `userThreadPlugins`, README «Платформа».
5. **PLUG-247** — язык, двумя раздачами: 247a — каталог строк, `language`, навыки двумя наборами, `pre-push`, перенос строк задач 1–4; 247b — перенос остальных модулей по одному (сторож, уборщик, merge, роли, UI).
Каждая следующая — от коммита предыдущей после её выкладки. Задача 247 — две отдельные раздачи (247a, 247b), каждая — один коммит; 247b — один заход на все оставшиеся модули. В задаче 249 нейтральные тексты — константы в коде (каталог строк появится в 247a и заберёт их). Приёмка: новая установка (`language: en`, без `postPublish`, `eventHooks`, `prProvider`) ведёт себя как сейчас, но по-английски и с нейтральными умолчаниями; установка автора после явных `language: "ru"`, `prBody` (прежний), `leaks.trailers: "block"`, `postPublish.reloadPlugins: true` — без изменений поведения; тесты на каждый пункт 18.1–18.6; README — раздел «Настройка под свой процесс» с примерами: плагин в корне репозитория, команда деплоя, GitLab через `command`, хук в чат; в примерах только `/home/example/…` и `example.com`.
