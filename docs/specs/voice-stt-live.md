# voice-stt-live — живой голосовой ввод (стриминг) через плагин-UI

Статус: draft → review. База: `bb-plugin-voice-stt` (файловый путь, в main).
Связано: `docs/specs/voice-stt.md` — остаётся контрактом файлового пайплайна;
настоящая спека добавляет второй режим и перекрывает §12 («UI не трогаем»)
только для элементов, описанных здесь.

## 1. Цель и контекст

Файловый контракт `ai.voice.transcribe` отдаёт запись плагину только после
окончания — задержка «отпустил кнопку → текст» 10–15 с (connect+setup+генерация
+settle). Цель — UX уровня OmniFlow: транскрипт идёт **во время речи**, финал
~1–2 с после отпускания, вставка в черновик композера автоматически.

Живой режим — **дополнение**, не замена: нативная кнопка и файловая цепочка
остаются (iOS-нативный ввод, `bb voice transcribe`, фоллбэк-путь live-режима).

## 2. Объём

- `app.tsx` + `app.css` в `bb-plugin-voice-stt`: кнопка в композере, оверлей
  записи (единственное место показа интеримов), composer-команда с шорткатом.
- `server.ts`: WS-эндпоинт стриминга + RPC выдачи одноразового токена.
- Потоковая Gemini-сессия в server entry (`open`/`push`/`end`), буфер до
  `setupComplete`, живые константы финиша OmniFlow.
- Фоллбэк: накопленный PCM → WAV → внутренний host-RPC с `skipStages
  ["gemini-live"]` → codex → groq. ffmpeg на live-пути не вызывается
  (он нужен только Gemini-стадии файловой цепочки).
- Размещение: тот же плагин `voice-stt`, не новый.

Вне объёма: правки bb core, нативной кнопки, `provider-codex`,
`bb-plugin-live-call`, iOS-специфичный нативный код.

## 3. UI: точки входа и жизненный цикл

### 3.1. Точки входа (все ведут в один recording singleton)

1. `composer.actions` — кнопка микрофона плагина в композере (scope: все
   `thread`, `queued-message`, `new-thread`). Известное ограничение: в свёрнутом
   (compact) композере плагинные actions хост не рисует — покрыто п. 2–4.
2. `app.composer.experimental_registerCommand` — команда «Voice STT Live:
   диктовка» с шорткатом (Mod+Shift+V). Composer-команда получает bound
   `composer` в `run({composer})` — привязка бесплатная; обычный
   `app.commands.register` для этого НЕ подходит (его контекст даёт только
   threadId/projectId, без composer handle).
3. `experimental_sidebarFooter` action «Диктовка» — запасной вход; целевой
   композер резолвится через `useComposers()` (primary/focused pane); если
   композера нет — запись идёт в «no-target» режиме и финал остаётся в
   оверлее с кнопкой «копировать».
4. Плавающая кнопка (FAB) в `experimental_appOverlay` — основной видимый
   вход: оверлей смонтирован постоянно, кнопка видна без открытого
   композера, включая мобильный клиент. Позиция — середина правого края
   экрана: в стороне от композера, кнопки отправки и нижних панелей
   (размещение внизу справа перекрывало отправку на мобильной раскладке —
   регрессия, зафиксировано). Тот же жест (hold/toggle), цель — через
   резолвер `useComposers()`; во время записи FAB — кнопка стоп.

Нативную кнопку микрофона **не скрываем**: официального способа нет, CSS по
`aria-label` ломается локализацией (bb-plugin-ru). Две кнопки сосуществуют;
наша отличается иконкой/подсказкой «Живой ввод».

### 3.2. Оверлей записи (`experimental_appOverlay`)

Показывается при активной записи независимо от точки входа и состояния
композера: индикатор записи (пульс + секундомер), живой интерим-текст,
«Отпустите/Enter — вставить», «Esc — отмена»; во время записи в карточке
явные кнопки «Вставить»/«Отмена» (мобильный клиент — без клавиатуры).
Оверлей — единственное место
показа интеримов (в черновик они не пишутся).

### 3.3. Жизненный цикл записи

- Состояние записи — **одиночный объект уровня приложения** (не состояние
  компонента): компоненты кнопки перемонтируются при смене раскладки и
  навигации, запись не должна прерываться.
- Привязка к композеру: `useComposer().key` на старте; при финишe —
  `insert(..., {at:"end"})` по сохранённому handle. Композер ушёл с экрана —
  текст остаётся в оверлее с кнопкой «копировать» (best-effort вставка, без
  тихих потерь).
- `pointerdown` на кнопке → старт сессии немедленно (прогрев сокета,
  §5): разрешение микрофона и AudioContext будим прямо в обработчике
  указателя (требование iOS — как в live-call `engine`).
- **Модель нажатия — гибридная, явно:** hold >400 мс = «держи и говори»,
  отпускание → `end`; быстрый тап <400 мс = toggle, повторное нажатие или
  Enter в оверлее → `end`. Двух смыслов у одного жеста нет: длительность
  удержания выбирает режим в первые 400 мс.
- Esc/уход со страницы → `cancel` (без вставки и без отправки на движки).
  Enter в оверлее → `end` + вставка (submit черновика НЕ делаем никогда).
- Повторные/быстрые нажатия во время открытой сессии — игнор с визуалом;
  одновременных сессий нет.

## 4. Протокол: клиент (app) ↔ server entry

### 4.1. Токен и подключение

- RPC `liveToken` (server entry): выдаёт одноразовый токен, TTL 30 с,
  одноразовый (погашается при первом hello). Ответ `{token}`.
- WS `GET /api/v1/plugins/voice-stt/http/live-voice` через
  `bb.http.experimental_websocket("/live-voice", …, {auth:"local"})`:
  `local` гарантирует запрос со страницы bb; токен — второй фактор.
- Первый кадр клиента — JSON `{"type":"hello","token":"<t>"}`. Неверный/
  просроченный/повторный токен → close 4401; нет hello за 3 с → close 4009
  (конвенция кодов как у live-call: 44xx — отказ, 40xx — busy/timeout).
- Второй hello/второе подключение при живой сессии → close 4009 «busy».

### 4.2. Кадры

Клиент → сервер:
- `{"type":"hello","token":…}` — первый кадр, обязателен.
- Бинарные кадры — PCM16 s16le mono 16 кГц, чанками ~100 мс (как их даёт
  AudioWorklet; ScriptProcessor — запасной путь, оба в live-call engine).
  **Клиент шлёт PCM сразу после hello, не дожидаясь `ready`** — сервер сам
  буферит до `setupComplete` (§4.3); иначе буфер — мёртвый код.
- Серверный cap накопленного PCM — 10 МБ; превышение → `end` принудительно.
- `{"type":"end"}` — пользователь отпустил: сервер досылает накопленное,
  шлёт `audioStreamEnd` **строго после последнего аудио-кадра** (иначе
  сервер Gemini отбрасывает хвост — подтверждено живьём, voice-stt.md §6.6).
  `end` до `ready` легален: сервер дожидается setupComplete, добивает буфер
  и шлёт streamEnd.
- `{"type":"cancel"}` — отмена: сессия закрывается, ничего не транскрибируем.

Сервер → клиент:
- `{"type":"ready"}` — информационный: сессия Gemini поднята (setupComplete);
  оверлей показывает «слушаю». НЕ гейт отправки.
- `{"type":"interim","text":…}` — живой интерим для оверлея.
- `{"type":"final","text":…,"engine":"gemini-live"|"codex"|"groq"|"silence",
  "degraded"?:true}` — `degraded` при фоллбэке (оверлей помечает).
- `{"type":"error","code":…,"message":…}` + close.

### 4.3. Серверная сторона сессии

1. hello+токен → открыть Gemini-сессию (сразу, до полного hello-финала можно
   не ждать аудио — прогрев §5). **Прогрев опционален**: если сокет уже был
   открыт заранее на pointerdown, reconnect при dead/expire.
2. Бинарные кадры → `session.push()`; до `setupComplete` сервер буферит
   (семантика буфера как у OmniFlow — §6.3 voice-stt.md). Сервер также
   аккумулирует весь PCM (нужен для WAV-фоллбэка §4.5 и RMS-тишины §4.4).
3. `end` → drain буфера → `audioStreamEnd` → ждать финал по §4.4 →
   `{"type":"final"}`. Таймаут/провал → фоллбэк §4.5.
4. `cancel`/закрытие сокета → Gemini-сессия завершается, буфер выбрасывается.

### 4.3а. Обрыв сокета у клиента (политика одна, явно)

Клиент держит **свою копию всего записанного PCM** (она же идёт в WAV-
фоллбэк). Обрыв посреди записи: клиент продолжает захват локально, оверлей
«переподключение»; серверная сессия при разрыве умирает — резюма нет.
На отпускании: сокет жив → обычный `end`; мёртв → новый токен + новая
сессия, реплей всего PCM (эквивалент файлового blast через живую сессию);
реконнект не удался за 5 с → WAV → файловая цепочка через host-RPC
(`skipStages` не нужен — Gemini не трогали).

### 4.4. Финиш живого стрима (отличается от файлового §6.6!)

В стриме сервер **не отстаёт**: аудио шло реальным темпом, интеримы уже шли.
Поэтому константы исходные OmniFlow для живого потока:

- settle: `sinceEnd ≥ 0.8 c И sinceLastActivity ≥ 1.0 c` → resolve (финал).
- cap: `sinceEnd ≥ 6.0 c` → **провал стадии** → фоллбэк §4.5. Файловые
  константы (3.0 c settle, масштабируемый cap) здесь не применяются.
- `turnComplete` после нашего `audioStreamEnd` — тоже resolve (OmniFlow).
- **Пустой финал — два случая, явно:** (а) RMS накопленного PCM ≈ тишина
  (порог калибруется как в live-call VAD; честной речи не было) →
  `{"type":"final","text":"","engine":"silence"}`, БЕЗ фоллбэка — оверлей
  показывает «тишина»; (б) звук был, а транскрипт пуст → мягкий провал →
  фоллбэк §4.5 (как файловый путь).

### 4.5. Фоллбэк из живого режима

Провал Gemini-сессии (ошибка, cap, квота после ротации ключей §6.4
voice-stt.md) → накопленный PCM оборачивается в WAV-заголовок (функция
`pcmToWav`, 44-байт header) → **внутренний host-RPC `voiceStt.transcribe`
с `skipStages:["gemini-live"]`** → codex → groq напрямую.

Почему не `ai.voice.transcribe`: файловая цепочка всегда начинает с
ffmpeg→Gemini — повторный прогон сожжёт бюджет на той же сдохшей Gemini
(до ~55 с/ключ при квоте) и лишний ffmpeg. Поэтому в host entry
добавляется второй контракт — наш собственный `voiceSttHostContract`
(метод `transcribe` = та же цепочка, но с опциональным `skipStages:
EngineId[]`; по умолчанию полный порядок — им и отвечает ai-сервис).
ffmpeg при пропуске gemini-стадии не вызывается — WAV и так годится для
codex/groq multipart.

Клиенту уходит `final` с фактическим `engine` и `degraded:true` — оверлей
помечает «фоллбэк».

### 4.6. Лимиты и квоты

- Ключи Gemini общие с live-call (те же значения настроек, свой secret-
  ключ плагина): звонок и диктовка делят квоту сессий — конфликт
  невозможен технически (отдельные сокеты), но квота проектная — зафиксировать
  риск, ротация 2 ключей как в §6.4.
- Максимум записи 5 минут: по достижении — автоматический `end` + заметка
  в оверлее. Лимит сессии Gemini Live ~10 мин — запас ×2.
- Одновременных live-сессий нет (один singleton); повторный вход во время
  записи — фокус на оверлей, не новая сессия.

## 5. Бюджеты времени

| Этап | Бюджет |
|---|---|
| pointerdown → WS open + hello + setupComplete (прогретая сессия) | ≤ 3 с |
| то же, холодная (connect+setup) | ≤ 5 с |
| запись | ≤ 5 мин (auto-end) |
| `end` → final (settle/cap §4.4) | ≤ 6 c |
| фоллбэк codex → groq | ≤ 15 c + ≤ 15 c |

Накопленная задержка «отпустил → текст в черновике»: Gemini ~1–2 с
(догон потока + settle), фоллбэк — как файловый путь.

## 7. Настройки

Секреты те же: `geminiKeys`, `groqApiKey`, `groqModel`, `geminiLiveModel`.
`language` (существующая) действует и на live-путь (`languageCodes`).

Новые настройки:
- `liveInput` (boolean, default `true`) — выключает кнопку/команду/оверлей
  live-режима, не трогая файловый сервис.
- `vocabularyTerms` (string, multiline, optional) — термины для
  `custom_vocabulary` Gemini. На файловом пути словарь строится из
  `prompt`-hint'а транскрибации; на live-пути hint'а нет → словарь берётся
  из этой настройки (тот же парсер: split по newline/`,`/`;`, trim, dedup
  case-insensitive, cap 1000).

Манифест `package.json`: добавить `"app": "./app.tsx"` в `bb`, `engines:
{"bb": ">=0.46.1", "bbPluginSdk": ">=0.6.49"}` (по live-call). Плюс
`STATUS.md` плагина — состояние live-режима рядом с файловым.

## 8. Безопасность

- WS только `{auth:"local"}` + одноразовый токен; hello-гейт 3 с.
- Ключи — только server-side (как сейчас); в кадрах/логах маскировка §10
  voice-stt.md.
- Микрофон только по жесту пользователя; индикатор записи всегда виден;
  запись не стартует без `ready` дольше 5 с → error + отмена.
- Текст вставляется только в черновик (`insert`), не отправляется
  автоматически — `submit()` не вызываем никогда.

## 9. Тесты

Юнит (mock WS в обе стороны, без сети):
- `live-token`: выпуск, TTL, одноразовость, отказ повторного/невалидного.
- `live-ws`: hello-гейт (4001/4009), порядок кадров, cancel сбрасывает
  сессию, end шлёт streamEnd ПОСЛЕ последнего аудио-чанка (антиррегрессия
  потери хвоста).
- `live-session`: буфер до setupComplete сохраняет порядок; push после end
  игнор; settle 1.0 c/cap 6 c → resolve/fail; turnComplete-after-end →
  resolve; пустой финал → мягкий провал.
- `wav`: корректный 44-байт header (RIFF/fmt/data, длины).
- singleton записи: повторный вход не плодит сессии; composer key binding;
  unmount не рвёт запись (логика, не DOM).
- Цепочка: `degraded:true` при фоллбэке, engine пробрасывается.
- Маскировка: ни один кадр/лог не содержит ключей и токенов.

## 10. Ручная проверка (acceptance)

1. Desktop/web (localhost или HTTPS): кнопка в expanded-композере →
   диктовка → интеримы в оверлее → отпустил → текст в черновике ≤ ~2 с.
2. Compact-композер: кнопки нет → команда/шорткат запускает оверлей →
   вставка работает.
3. Отмена Esc — ничего не вставляется, сессия закрыта.
4. Битый ключ Gemini → `final` с `engine:"codex"`, `degraded:true`.
5. iOS (ручная проверка на устройстве): видимость плагинной кнопки в
   композере и работа микрофона; при отсутствии кнопки — вход через
   sidebar/команду. Зафиксировать результат в STATUS.
6. Запись >5 мин → auto-end, текст вставлен.
7. Уход со страницы во время записи → cancel, сессий в логе не висит.

## 11. Публичный репозиторий

Те же правила, что в voice-stt.md §11: без реальных id, путей `/home/…`,
ключей, адресов; синтетика в тестах; коммиты без приватных фактов стенда.
