# Выкладка через `release`

Расширение [спеки оркестратора](orchestrator.md). Задача: координатор не может забыть шаг выкладки, а утечки личных и чувствительных данных ловятся до push — машиной и отдельным проверяющим агентом, а не памятью координатора.


> Ревизия 6: гейт ревью по SHA на шаге 1 (ревью вершины покрывает коммиты координатора), коммиты конвейера не считаются чужими, вершина не перечитывается, release вне очереди `delegate`, URL PR из stdout `gh`, повтор — та же ветка и PR, `allowedTrailers`/`allowedEmails`, обёртки для всех хуков кроме `push-to-checkout` — [orchestrator §17.3](orchestrator.md).
>
> Ревизия 5: публикуемая ветка, `-m` без имён веток, скан по каждому коммиту, настройка проекта `threadIds`, гейт как защита от забывчивости, токен на ветку и SHA, JSON-вердикт ревьюера — [orchestrator §16.6–16.7](orchestrator.md); при расхождении действует он.

## 1. Принцип

- Выложить в удалённый репозиторий можно **только** командой `bb orchestrator release <KEY>`. Обычный `git push` из треда отклоняет общий git-хук (§5).
- `release` — конвейер: шаги идут по порядку, любой провал останавливает выкладку и возвращает задачу координатору с причиной.
- Документы (спеки, ADR, документацию, заметки базы знаний) правит **координатор** — у него контекст. Конвейер проверяет, что он это сделал.
- Правило одно на все проекты (`defaults`), отдельные проекты его переопределяют (`projects`, §6). Проект со своим процессом вливания (например, свой CI/CD с дежурным куратором) проходит те же шаги проверки, а конечное действие у него — PR в свою ветку; дальше работает его процесс. Полное исключение проекта (`excluded: true`) — только по явной настройке.

## 2. Конвейер `release`

```
bb orchestrator release <KEY> [--no-docs <причина>] [--kb <заметка>|--no-kb <причина>]
```

| Шаг | Что проверяется | Кто | Провал |
|---|---|---|---|
| 1. Приёмка | у задачи есть делегирование `done`; последнее ревью по задаче (делегирование уровня с ролью `auditor`, [orchestrator §2.3](orchestrator.md)) — «ОК»; координатор — вызывающий тред; последний заход исполнителя — без кода (`no_code`) и без коммитов — отказ `release-refused` «задача без кода: вливать нечего» (orchestrator §4.1 r28.1, r9) | скрипт | отказ с перечнем, чего не хватает |
| 2. Ветка | свежая целевая ветка вносится в ветку исполнителя по режиму проекта `sync`: `merge` (по умолчанию: `git merge origin/<цель>`, история запушенной ветки не переписывается) или `rebase` (только для ещё не запушенных веток); конфликт — отказ. Force-push запрещён всегда | скрипт | «конфликт, сведи вручную» |
| 3. Проверки проекта | команды проверок из настройки проекта (тесты, типы, сборка); строгий разбор результата | скрипт | вывод упавшей проверки |
| 4. Машинный скан | §4 категории 1–4 по диффу выкладки и по метаданным коммитов диапазона `merge-base(origin/<цель>, HEAD)..HEAD` (после `merge` в ветку попадают чужие коммиты цели — их автор не проверяется) — `gitleaks` + шаблоны плагина; строгость по категориям — из настройки проекта | скрипт | список находок «файл:строка → категория» |
| 5. Аудит проверяющего агента | §3 | агент | `REJECT` с находками → задача возвращается координатору |
| 6. Публикация | целевое действие проекта `target` (§6). `push` — push в указанную ветку, задача → `done`. `pr` — push ветки выпуска и PR в указанную ветку; в теле PR обязательна строка `Источник: bb тред thr_…` (по ней CI/CD проекта находит автора и шлёт ему отказы гейтов); задача → `in_review`; плагин её не закрывает — в `done` переводит координатор или куратор проекта вручную по факту выкладки (роботы CI/CD задачи bb не закрывают). Повторный `release` по той же задаче добавляет новые коммиты в ту же ветку PR, без force-push; в ветку PR с другим «Источником» `release` не пишет. Комментарий в задачу «выложено: коммит, ветка / PR» | скрипт | ошибка push — отказ, ничего не помечается |
| 7. Пост-проверка | повторный скан того, что реально легло в удалённый репозиторий (или в ветку PR), — по тем же правилам проекта, что шаг 4 (`commitIdentity`, `leaks`, `allowedTrailers`, `allowedEmails`, `threadIds`; r7: без них каждый коммит ложно попадал в «подпись не задана»), проект настройки — из записи выкладки (§6 п.6). Если повторный скан невозможен (нет базы удалённого диапазона — первая выкладка в новую ветку), это строка координатору «пост-проверка: скан пропущен, причина», а не молчание (r8). Сверка «выложено в обход»: для `push` — коммит в целевой ветке без записи `release` в задаче; для `pr` — только PR, открытые `release` (merge-коммиты очередей, резолверов, PR людей и других сессий законны). Статусы процесса проекта у PR (ожидание подписи, парковка, отказ гейта) провалом не считаются | скрипт | сообщение координатору (`[orchestrator]`) |

**Детерминированный исход выкладки (r10, 12.11, слово владельца; заменяет черновик r10 «пересинхронизация без нового аудита» — отклонён после ревью спеки: дыры в гейте при переименованиях и правках спек, сложность не окупается).** Принцип: на одну выкладку координатор получает **ровно одно** сообщение на конечный исход — опубликовано или отказ с причиной; промежуточные состояния (аудит идёт, APPROVE, публикация идёт) не будят. Если цель ушла вперёд во время аудита (non-fast-forward на шаге 6) — это обычный отказ публикации «цель ушла вперёд — повтори `release`»; координатор не пушит в цель, пока идёт его выкладка.
0. **Одна выкладка в цель за раз.** Шаг 1 отказывает, если в ту же цель того же репозитория уже идёт выкладка (`auditing`/`publishing`): «в <цель> уже идёт выкладка <KEY> — повтори после неё». Документы координатора в цель во время выкладки — его дисциплина (safe-push вне плагина).
1. **Строка об успехе.** После публикации и пост-проверки — одна строка координатору `[orchestrator]`: `push` — «выложено <KEY>: <sha7> в <ветка>; задача done» плюс итог шагов после публикации (п.2); `pr` — «PR открыт <KEY>: <url>; слежу до влития» (итог — по п.3). Находки пост-проверки и её сбой (в т.ч. неудачный `fetch`) входят в эту же строку, отдельной не идут. Сейчас (до r10) при успехе был только комментарий в задаче — координатор о публикации не узнавал (12.11: 20 минут ожидания).
2. **Шаги после публикации (`push`).** Настройка проекта `postPublish` (§6): `{ "checkout": "<путь локальной копии, из которой установлены плагины>", "branch": "<ветка копии, по умолчанию цель>", "reloadPlugins": true }`. Порядок, каждый провал — пропуск остатка с причиной в строке п.1, копия не трогается:
   - копия на ветке `branch` (12.11 копию владельца переключил на свою ветку другой тред — плагины работали с чужой ветки) и чистая по отслеживаемым файлам; иначе «копия не на <ветка> / с правками — не обновлена»;
   - `base` = HEAD копии до обновления; `git fetch` и `git merge --ff-only origin/<цель>`; ff невозможен — без перезагрузки (12.11: перезагрузка из необновлённой копии);
   - изменённые каталоги — `git diff --name-only <base>..HEAD` (от HEAD копии, а не от базы выкладки: отставшая копия догоняет и прошлые выкладки) → `plugins/<dir>/` → id по `rootDir` из `bb plugin list --json`;
   - каталог с изменённым `package.json` или lock-файлом не перезагружается: «<id>: изменены зависимости — нужен npm ci, перезагрузи вручную»;
   - плагин-провайдер (`provider-*`) с идущими ходами исполнителей на нём (делегирования `running` с этим провайдером) не перезагружается: «<id>: идут ходы — перезагрузи позже» (перезагрузка оборвала бы их);
   - остальные — `bb plugin reload <id>`; ошибка — в строку п.1.
   **Самоперезагрузка orchestrator** — последней и только когда в процессе нет других операций (такт конвейера и сторожа свободен; иначе ждёт следующего такта). Перед ней плагин (а) пишет в хранилище отметку «ждёт подтверждения» (ключ выкладки, ожидаемый SHA = `git -C <rootDir> rev-parse HEAD` после ff), (б) ставит разовую скриптовую автоматизацию BB через 3 минуты, без модели: если отметка не снята — `bb thread tell <координатор> "выложено <KEY> <sha7>; orchestrator после перезагрузки не поднялся — проверь bb plugin list"`. Новый процесс при старте сверяет `git -C <rootDir> rev-parse HEAD` с ожидаемым SHA, снимает отметку и автоматизацию и шлёт строку п.1 «выложено …; перезагружено: <id…>» (SHA не совпал — «перезагружено, но копия на <sha>, ожидался <sha>»). Ровно одна строка: от нового процесса либо от автоматизации. Перезагрузка не удалась сразу (старый процесс жив) — строка п.1 с ошибкой, автоматизация снимается.
3. **Слежение за PR (`pr`).** Такт сторожа раз в 5 минут, без модели: `gh pr view <url> --json state,mergedAt,mergeCommit,comments` (по URL, вне копии выкладки — её может убрать уборщик). Следит **одна** запись на `pr_url` — последняя выкладка этого PR; более ранние с тем же `pr_url` не следят. Конечные: `MERGED` → задача `done`, строка «PR влит <KEY>: <url> → <sha7>»; `CLOSED` → строка «PR закрыт без влития <KEY>: <url>» и последний комментарий робота CI/CD одной цитатой ≤ 300 символов. Переоткрытый PR (снова `OPEN`) — слежение продолжается молча. Нет конечного состояния через 72 часа от публикации PR — одна строка «PR висит 72 ч <KEY>: <url>», дальше молча до конечного. Ошибка `gh` (нет `gh`, токена, доступа) три такта подряд — одна строка «слежение за PR невозможно: <ошибка>», слежение останавливается. Промежуточные статусы (очередь, ожидание подписи, парковка) — молча. Статус выкладки остаётся `published`; состояние PR — в новых полях `pr_state`, `pr_checked_at`, `pr_stale_notified`, `pr_error_count` (`pr_url` уже есть). Если CI/CD проекта сам сообщает автору PR конечный исход (GHS, GH-670) — слежение плагина всё равно идёт: автор PR — тред исполнителя, а не координатор.
4. **Без дублей от аудитора.** Режим уведомлений BB задаётся по уровню: у `release-audit` — `parentNotifications: "off"` во всех местах, где плагин его ставит или чинит (свой запуск §4 в, проверка привязки §4 п.4, сверка §7, запасной путь через dispatch, перевыпуск по цепочке); досылка итога §16.5 для `release-audit` не выполняется. Строки сторожа об аудиторе остаются: «ждёт решения» (запрос разрешения), зависание, квота — иначе зависшего аудитора никто не увидит. Аудит, не завершившийся за 30 минут, — отказ выкладки «аудит не завершился за 30 мин» и остановка треда. О вердикте координатор узнаёт только из итоговой строки: `REJECT` — строка с находками (как сейчас), `APPROVE` — ничего, затем строка п.1 или отказ публикации. Аудитор без вердикта — orchestrator §17 «Вердикт обязателен» (одно напоминание, затем отказ «аудит без вердикта», статус выкладки `rejected`).
5. **Ровно один раз.** Каждая итоговая строка (п.1, п.3, отказы) — с отметкой в записи выкладки: отметка ставится до отправки (захват), сбой отправки снимает захват для повтора в следующем такте. Конвейер досматривает и записи `published` без отметки о строке п.1 (падение после публикации, до строки), не только `auditing`/`publishing`.
6. Тесты: вторая выкладка в ту же цель → отказ п.0; `push` → одна строка с SHA и итогом п.2; копия не на ветке / грязная / ff невозможен → строка с причиной, без перезагрузки; изменённый `package.json` и провайдер с ходами → пропуск с причиной; перезагрузка только изменённых по диффу от HEAD копии; самоперезагрузка → строку шлёт новый процесс, автоматизация снята; новый процесс не поднялся → строку шлёт автоматизация; SHA не совпал → строка с расхождением; PR влит / закрыт / переоткрыт / 72 ч / ошибка `gh` ×3 → по одной строке или тишина по п.3; две выкладки одного PR → одна следящая запись; аудитор с уведомлениями `off` во всех местах и без досылки; аудит дольше 30 мин → отказ; падение между публикацией и строкой → строка в следующем такте, ровно одна.

Шаги 1–4 и 6–7 не тратят токены модели. Шаг 5 идёт в фоне: `release` возвращает ответ сразу («аудит запущен»), координатор заканчивает ход, итог приходит сообщением `[orchestrator]`. После `APPROVE` шаги 6–7 выполняет сам плагин.

## 3. Проверяющий агент (шаг 5)

- Маршрут — уровень политики `release-audit` с цепочкой резерва любой длины и `autoFallback: true`: недоступен первый проверяющий (молчит, квота, снятая модель — исходы §5 основной спеки) — сторож перевыпускает аудит на следующий маршрут цепочки. Пользователь задаёт цепочку в политике. Все маршруты цепочки исчерпаны — `release` останавливается и сообщает координатору, выкладки нет.
- Роль — встроенная `release-auditor` (только чтение, как `auditor`) с постоянной инструкцией плагина.
- Вход: дифф выкладки, сообщения и метаданные коммитов, список документов проекта из карты (§6), находки шага 4.
- Проверяет:
  1. **Документация актуальна.** Каждое изменение поведения в коде отражено в связанных спеках, ADR, документации; нет противоречий «код ↔ спека»; ревизии и даты спек обновлены. Если координатор указал `--no-docs <причина>` — оценивает, обоснована ли причина.
  2. **Утечки** — все категории §4, включая то, что не ловится шаблонами (смысловые: имена людей, описания внутренней инфраструктуры, ссылки на приватные треды и задачи).
- Находки не содержат значения секретов: значение маскируется (иначе находка сама становится утечкой) — и в выходе агента, и в логах, и в комментариях.
- Явный отказ от правки документов (`--no-docs <причина>`) записывается в сообщение коммита трейлером `Docs-not-needed: <причина>` — его же понимают гейты проектов; агент оценивает обоснованность.
- Выход — строгий JSON: `{"verdict":"APPROVE"|"REJECT","findings":[{"category","file","line","problem","fix"}]}`. Непарсящийся ответ после напоминания (orchestrator §17 «Вердикт обязателен», r31) = `REJECT`.
- Проверяющий агент читает файлы и дифф; защитные хуки провайдера не должны ложно блокировать чтение (у `acp-devin` — исправить ложное срабатывание защиты конфигов на слово `install` в командах чтения до включения `release`).
- Сторож §5 основной спеки следит за ним как за обычным исполнителем (зависание, квота, перевыпуск по цепочке `release-audit`).

## 4. Категории утечек

| № | Категория | Примеры | Шаг 4 (машина) | Шаг 5 (агент) |
|---|---|---|---|---|
| 1 | Секреты | токены, API-ключи, пароли, приватные ключи (`*.pem`, `*.key`, `id_*`), `.env`, VPN-конфиги с `PrivateKey`, ссылки `vless://` | да (`gitleaks` + шаблоны) | да |
| 2 | Личность автора | личная почта в авторе/коммитере/тексте; подпись не та, что задана в настройке; трейлеры чужих ботов | да (сверка с разрешённой подписью) | да |
| 3 | Привязка к машине | абсолютные пути (`/home/…`, `/Users/…`, `/opt/…`), имена хостов, внутренние IP и порты, пути к хранилищам тредов | да (шаблоны) | да |
| 4 | Идентификаторы bb | `thr_…`, `proj_…`, `env_…`, ключи задач приватного трекера, адреса `*.getbb.app` — **в коде и документах**. В сообщении коммита строка-трейлер `BB-Thread: thr_…` разрешена (не находка); контракт с CI/CD проекта — строка `Источник: bb тред thr_…` в теле PR (§2, шаг 6) | да (шаблоны; трейлер в сообщении коммита пропускается) | да |
| 5 | Смысловые | имена людей, описание личной инфраструктуры, содержимое приватных переписок | нет | да |

**Синтетические пути в тестах (r8, 12.11).** Тестам сканера и выкладки нужны пути вида `/home/…` как данные. Два законных места:
- **Отрицательные образцы** (сканер должен промолчать) — пути с префиксами-фикстурами `/home/example/` и `/Users/example/`: сканер категории 3 их не считает находкой.
- **Положительные образцы** (сканер должен найти) — только в файлах фикстур утечек, перечисленных **поштучно** в `leaks.allow` проекта (не каталогом `tests/`). Тесты импортируют образцы оттуда. Для bb-addons — `plugins/bb-plugin-orchestrator/tests/fixtures/leak-samples.ts`.
- Исключение префиксов-фикстур проверяется **по каждому вхождению пути**, а не по строке целиком (строка с `/home/example/a` и настоящим путём рядом — находка), и в добавленных строках, и в тексте коммитов. В коде сканера префиксы записываются регулярным выражением, не строкой пути.
- Переходное правило: пока установлен сканер без исключения префиксов (до выкладки r8), отрицательные образцы тоже держатся в файле фикстур; так же — все прежние буквальные пути в тестах (их перенос безопасен: удалённые строки не сканируются).
- Фиктивные id в тестах — `proj_` плюс не больше 5 символов (`proj_repo`), иначе это категория 4.

Собирать путь из частей, чтобы сканер его не увидел, запрещено — это обход гейта (§5), даже для выдуманного пути (r7 разрешала с комментарием — отменено: машиной не отличить выдуманное от настоящего). Ревьюер публичного репозитория смотрит историю ветки целиком (`git log -p`), а не только итог.

Строгость категорий 3–4 задаёт проект (`leaks`, §6): по умолчанию для приватных — предупреждение, для публичных — отказ; плюс разрешённые места (`allow`: пути и шаблоны), где такие упоминания — норма проекта (например, журнал планов с ID тредов, документы выкладки с путями стенда). Категории 1–2 — отказ всегда.

Разрешённая подпись коммитов — настройка `commitIdentity`. Рекомендация: имя аккаунта GitHub и его noreply-адрес вида `<id>+<логин>@users.noreply.github.com` — GitHub показывает коммит от аккаунта, почта регистрации нигде не видна. Подпись с любой другой почтой — категория 2. `commitIdentity` можно переопределить в проекте (§6); значение `"repo"` — разрешённая подпись берётся из конфига репозитория (для проектов со своим роботом CI/CD, который сам требует определённого автора).

## 5. Запрет обхода

- Общий хук `pre-push` (глобальный `core.hooksPath` на машине) пропускает push только с одноразовым маркером, который выставляет `release` на время шага 6: случайный токен для конкретного коммита в файле, доступном на запись только процессу плагина (не переменная окружения агента); хук сверяет токен и SHA и гасит токен после push. Без маркера — отказ «выкладка только через `bb orchestrator release`».
- Глобальный `core.hooksPath` отключает хуки из `.git/hooks` репозитория, поэтому каждый общий хук сначала проверяет свои условия, а затем **вызывает локальный хук репозитория** `$GIT_DIR/hooks/<имя>`, если он есть, и возвращает его код. Репозиторий с собственным локальным `core.hooksPath` (локальная настройка сильнее глобальной) общие хуки не получает вовсе — так свой процесс проекта остаётся нетронутым; такие репозитории перечисляются при установке, чтобы это было видно.
- Перед установкой на машину: опись всех репозиториев — где хуки в `.git/hooks`, где свой `core.hooksPath`; тест «локальный хук по-прежнему срабатывает» на каждом виде.
- Флаги `--no-verify`, `-c user.*`, `-c core.hooksPath=…`, `--author` и запись `core.hooksPath` командой `git config` (в любой области) в командах агентов отклоняет хук провайдера (как защита конфигов у Devin) и инструкция ролей.
- Исключённые проекты (§1) хук не трогает.
- Push от других системных пользователей (роботы CI/CD, резолверы) хук не касается — он стоит только у пользователя разработки.

## 6. Настройка

Настройка плагина `release` (JSON): правило по умолчанию и переопределения по bb-проектам.

```json
{
  "commitIdentity": "Имя <id+логин@users.noreply.github.com>",
  "defaults": {
    "target": { "action": "push", "branch": "main" },
    "checks": [],
    "public": false
  },
  "projects": {
    "proj_a": { "checks": ["npm test", "npm run typecheck"], "docsMap": { "plugins/foo/": ["docs/specs/foo.md"] }, "public": true },
    "proj_b": {
      "target": { "action": "pr", "branch": "dev" }, "sync": "merge", "commitIdentity": "repo",
      "checks": ["make lint", "make test-changed"],
      "leaks": { "machine": "warn", "bbIds": "warn", "allow": ["docs/PLAN.md", "docs/DEPLOY.md"] }
    },
    "proj_c": { "excluded": true }
  }
}
```

- `target.action`: `push` — push в `target.branch` (например `main`, `dev` или другая ветка); `pr` — ветка выпуска и PR в `target.branch`.
- Поля проекта перекрывают `defaults` и верхний `commitIdentity` по ключам. `docsMap` — какие документы связаны с какими путями кода (для проверяющего агента и подсказки координатору); без него агент проверяет все документы репозитория (`docs/`, `README*`, ADR).
- `sync`: `merge` (по умолчанию) | `rebase`.
- `checks` — быстрые проверки до выкладки (линтеры, типы, тесты по затронутому); полные наборы, smoke и миграции оставлять CI проекта, чтобы не дублировать и не грузить общую машину.
- `leaks`: строгость категорий 3 (`machine`) и 4 (`bbIds`) — `block` | `warn`, и `allow` — пути, где они допустимы.
- `excluded: true` — `release` для проекта отказывает, общий git-хук его не трогает.
- `postPublish` (r10, §2 «Детерминированный исход» п.2): `{ "checkout": "<путь>", "branch": "<ветка, по умолчанию цель>", "reloadPlugins": true|false }` — после публикации `push` ff локальной копии, из которой установлены плагины, и перезагрузка изменённых плагинов. Нет ключа — шаг не выполняется (строка об успехе всё равно идёт).
- **Какой проект настройки (r7, уточнено r8).** Ключ `projects` — bb-проект **репозитория**, а не проект делегирования (задачи по вложенному репозиторию часто раздаются из родительского bb-проекта: вживую 149 делегирований, `release` брал чужую настройку `excluded`). Правило r8:
  1. Основной каталог репозитория копии — путь первой записи `git worktree list --porcelain` (для обычного клона — его корень; запись с пометкой `bare` — совпадением не считается). Сравнение по `realpath`.
  2. Кандидаты — bb-проекты (`bb project list --json`), чей **основной** путь (`realpath`) на **этом хосте** (`hostId` пути = текущий хост) равен основному каталогу; второстепенные пути проектов не учитываются. Путь проекта, которого нет на этой машине (удалён, чужая ОС), — не кандидат и не ошибка.
  3. Нет кандидатов по пути — только тогда читается `origin` копии; кандидаты — проекты с совпадающим `gitRemoteUrl` после нормализации (схема и `git@host:` → `host/path`; без userinfo `user:token@`, без порта, без `.git` и завершающего `/`; хост в нижнем регистре). Такой кандидат годится, только если у него есть **явная запись** в `projects` настройки и его путь существует на машине; иначе он отбрасывается. URL в выводе и отказах не печатается (в нём может быть токен).
  4. Один кандидат — он. Несколько — проект делегирования, если он среди них, иначе отказ `release-settings-ambiguous`. Ни одного — отказ `release-settings-unknown`.
  5. Ошибка — это сбой `git` в копии, `realpath` основного каталога копии, `bb project list` (ненулевой выход, таймаут, JSON неожиданной формы): отказ `release-settings-unknown`, а не подмена проекта — гейт падает закрыто.
  6. Проект настройки определяется **один раз на шаге 1** и записывается в запись выкладки (`settings_project_id`); шаги 6–7 и повторный заход той же выкладки берут его оттуда и заново не ищут. Старые записи без него — определяются заново по этому правилу (с отказом при ошибке).
  7. `merge` (подстановка ключа задачи по `threadIds`) при ошибке или неоднозначности считает `threadIds: false` — строже.
  В выводе `release` и в отказах указываются оба проекта: проект настройки и проект делегирования. Записи `project_id` делегирований не меняются.

## 7. Установка

Общий git-хук (§5) ставится только пользователю машины, который ведёт разработку (настройка `core.hooksPath` в его глобальном git-конфиге), а не всем пользователям bb. Инстансы без разработки его не получают.

До установки — опись всех репозиториев пользователя: служебные репозитории с автоматическим push (например, база знаний с автосинхронизацией) вносятся в исключения установщика, иначе их автопуш сломается; репозитории со своим `core.hooksPath` перечисляются как «свой процесс».

## 8. Решения владельца (09.11)

1. Подпись по умолчанию — noreply-адрес аккаунта GitHub владельца; почта регистрации не показывается. Проект может задать свою (`commitIdentity`, в том числе `"repo"`).
2. Сигнал о проскочившей утечке и о выкладке в обход — только координатору.
3. Общий git-хук — только пользователю машины, который ведёт разработку.
4. Целевое действие задаётся на проект: push в любую ветку или PR в любую ветку; одно правило по умолчанию и переопределения.
5. Проверяющий агент — с цепочкой резервных моделей любой длины.
6. Трейлер `BB-Thread:` в сообщении коммита разрешён; ID bb в коде и документах — находка.
