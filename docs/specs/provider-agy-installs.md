# provider-agy — параллельные установки agy и привязка аккаунтов

## 1. Контекст и цели

На инстансе с пулом аккаунтов Antigravity возникает необходимость использовать несколько параллельных установок исполняемого бинарника `agy` (как минимум два бинарника из разных каталогов файловой системы).

**Цели:**
1. **Разнесение нагрузки между бинарниками.** Основная цель — распределить нагрузку процессов и локального состояния по двум независимым бинарным установкам, а не поддержка разных версий. По умолчанию версии установок совпадают; разные версии допустимы, но не являются основным сценарием.
2. **Строгая привязка аккаунтов к установкам.** Каждый аккаунт пула привязывается к конкретной установке; все действия от имени аккаунта выполняются строго бинарником назначенной установки без неявных подмен.
3. **Единый пул планирования.** Логика пула (ранжирование `priority`, LRU, учет доступности моделей по §2.3, квотные кулдауны и парковки) остается сквозной и установку не учитывает: аккаунты одного тарифа взаимозаменяемы независимо от того, к какой установке они привязаны.
4. **Изоляция и предотвращение смешивания.** Исключить конфликты при самообновлении, разделении кэшей и временных файлов между установками.

Решение и отклонённые варианты зафиксированы в [ADR-0033](../adr/0033-provider-agy-installs.md).

## 2. Архитектура реестра установок (`agy-installs.json`)

Информация об установках хранится в локальном файле конфигурации инстанса в каталоге данных плагина: `<dataDir>/agy-installs.json`.

1. **Локальность инстанса.** Файл `agy-installs.json` является строго машинным (instance-local): пути к бинарникам и системные пути различаются на разных хостах. Инфраструктурный keeper его **не синхронизирует** (по аналогии с `conversations-state.json` и `accounts-overlay.json` из §2.1). На каждой машине пула, включая спутники, оператор создает собственный реестр с **теми же именами установок**, что фигурируют в поле `install` общего `accounts-state.json`; пути под именами локальны для машины, а в пределах одного реестра разные имена могут указывать и на один и тот же бинарник (§3 п. 3).
2. **Формат реестра:**
   ```json
   {
     "installs": {
       "main": {
         "bin": "/opt/google/antigravity/bin/agy",
         "env": {
           "XDG_CACHE_HOME": "/var/cache/agy-main"
         }
       },
       "secondary": {
         "bin": "/opt/google/antigravity-alt/bin/agy",
         "env": {
           "XDG_CACHE_HOME": "/var/cache/agy-alt"
         }
       }
     },
     "default": "main"
   }
   ```
3. **Схема и валидация:**
   - `installs`: словарь именованных записей.
   - Имя установки: строка по шаблону `^[a-z0-9-]{1,32}$`.
   - `bin`: абсолютный путь к файлу бинарника (непустая строка с ведущим `/`). Существование файла и флаг исполняемости в схему **не входят**: это локальная доступность установки, проверяемая перед каждым выбором аккаунта и каждым запуском (§5 п. 2), а не условие валидности реестра. Иначе отсутствующий бинарник одной дополнительной установки делал бы «битым» весь реестр и ронял весь пул и `direct`/`relay`.
   - `env` (опционально): объект строковых переменных окружения, добавляемых в дочерние процессы данной установки (для разведения путей кэша, логов и каталогов обновления). Значения `env` входят в `session.launchEnv`, поэтому страховка §12.6 (`completeShimLaunchEnv`) восстанавливает их вместе с остальным окружением запуска. Порядок слияния окружения запуска: `env` установки кладётся **первым слоем** (поверх `process.env` обёртки), а ключи плагина, шима и аккаунта — **поверх него** и при совпадении побеждают, как в существующих сборках `{...process.env, ...<нижний слой>, ...<ключи запуска>}`. Ключи, которыми управляют плагин, шим и аккаунт, — `HOME`, `ELECTRON_RUN_AS_NODE`, `GEMINI_API_KEY`, `GOOGLE_GEMINI_BASE_URL`, прокси-ключи `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY` в обоих регистрах и **весь префикс `AGY_*`** — переопределить через `env` нельзя: **присутствие любого из этих ключей делает реестр невалидным** — ошибка схемы по п. 4, ни один запуск не выполняется. Под префиксный запрет попадают семейства, которые плагин сам выставляет дочерним процессам, — `AGY_SHIM_*` (окружение шима, `shimEnvFor`) и `AGY_DISABLE_*` (`AGY_DISABLE_SUBAGENTS`, `AGY_DISABLE_MEMORY`: `buildLaunch` записывает их в `launchEnv` на каждую сессию, `acp-wrapper.ts`), — и ручки уровня процесса обёртки, читаемые из `process.env`: `AGY_PATH`, `AGY_TRANSPORT`, `AGY_ACCOUNTS`, `AGY_CLIPROXY*`, `AGY_AUTO_RETRY_*`, `AGY_IDLE_KILL_MS`, `AGY_STALL_KILL_MS`, `AGY_TOOL_STALL_MS`, `AGY_INELIGIBLE_*`, `AGY_LOCATION_COOLDOWN_MS`, `AGY_COMPACT_FALLBACK`, `AGY_NOISE_STEP_TYPES` — чужое их значение в дочернем окружении сменило бы поведение вложенных запусков и шима. Прокси, relay-учётка и каталог аккаунта следуют за аккаунтом, а не за установкой; `ELECTRON_RUN_AS_NODE` обёртка выставляет для шима (`shimRuntimeEnv`), а шим снимает его у дочернего `agy` (`acp-shim.mjs`) — чужое значение ломает режим интерпретатора.
   - `default`: обязательное имя установки, выполняющей роль **основной** (все остальные записи считаются **дополнительными**). Значение `default` обязано присутствовать в словаре `installs`.
4. **Битый реестр — громкая ошибка.** Если файл `agy-installs.json` существует, но не разбирается как JSON, не проходит схему п. 3 (включая запретный ключ в `env`) или `default` не указывает на запись в `installs`:
   - Пул аккаунтов не запускается: ни один аккаунт не считается доступным.
   - Сессии без аккаунта (`direct`, `relay`) тоже не запускаются: бинарник основной установки определить нельзя.
   - `thread/start` и `thread/resume` завершаются честной ошибкой с причиной (файл реестра и конкретное нарушение схемы).
   - Тихого отката к неявной установке (`resolveAgyCommand`) **нет** — наличие файла реестра означает, что оператор перешел на режим реестра, и молча игнорировать его нельзя.
   - Граница «битости» — только валидность самого файла: отсутствующий или неисполняемый бинарник реестр не ломает (п. 3) и обрабатывается как локальная недоступность конкретной установки (§5 п. 2).
5. **Перечитывание по mtime.** Реестр перечитывается с диска при смене mtime файла `agy-installs.json` (stat выполняется при выборе аккаунта и перед запуском процесса). Перезагрузка плагина для применения изменений реестра **не требуется**. Если оператор всё же перезагружает плагин — только при отсутствии активных тредов на agy.
6. **Обратная совместимость (байт в байт):**
   - Если файл `agy-installs.json` отсутствует, плагин работает в режиме единой неявной установки, где путь к бинарнику определяется существующей функцией `resolveAgyCommand(process.env)` (`AGY_PATH` → `~/.local/bin/agy` → `PATH`). Для пулов, в которых ни у одного аккаунта нет поля `install`, отличий от прежнего поведения нет.
   - Исключение: если у аккаунта задано поле `install` (приехало синком с другой машины), а локального реестра нет — аккаунт **недоступен на этой машине** (см. §5 п. 2): привязку не к чему применить.

## 3. Привязка аккаунтов (`accounts-state.json`)

Привязка аккаунта к установке хранится в общем файле пула `accounts-state.json` в поле `accounts[label].install`.

1. **Правила владения и синхронизации (shared-owned):**
   - Поле `install` подчиняется ровно тем же правилам, что и числовой приоритет `priority` (спека `provider-agy-acp.md` §2.2):
     - Поле является **общим** (shared-owned) и хранится только в `accounts-state.json`.
     - Задается оператором (командой добавления аккаунта, импортом или перепривязкой — §4) **только на инстансе-владельце пула**, как и прочие правки общего файла: keeper синкает `accounts-state.json` односторонне владелец→спутник, и локальная запись спутника стирается за ~30 с (§2.1 `provider-agy-acp.md`).
     - При записи общего файла `saveLedger` перечитывает существующее дисковое значение `install` для метки аккаунта, предотвращая затирание ручной правки stale-слепком из памяти.
     - Записи меток, которые есть на диске, но отсутствуют в памяти (аккаунт добавлен конкурентно между `loadLedger` и `saveLedger` — §4.1), `saveLedger` **переносит в записываемый файл целиком**: stale-слепок памяти не вправе уронить чужую запись вместе с её привязкой.
     - **Блокировка записей общего файла.** Все записи `accounts-state.json` — и `saveLedger` обёртки, и команды оператора §4 (`add-account.mjs`, `import-accounts.mjs --install`, `--rebind`) — выполняются под общим advisory lock-файлом `<dataDir>/accounts-state.lock`: захват созданием файла с флагом `O_EXCL`, повторные попытки захвата с таймаутом, снятие в `finally`. Взаимоисключение делает цикл «чтение слепка → слияние → запись» атомарным относительно других писателей: слепок, снятый до записи `install`, не может быть записан поверх неё (§4.1 шаг 5). Блокировку берут только писатели; читатели (`loadLedger`, `listAccounts`) её не захватывают — записи общего файла атомарны (`temp + rename`), и читатель всегда видит одну из двух целых версий.
       - **Содержимое lock-файла:** pid процесса-держателя, время захвата и случайный nonce захвата (`{"pid": <pid>, "atMs": <epoch-мс>, "nonce": "<случайная строка>"}`). Lock считается зависшим, если записанный pid не существует на этой машине (держатель умер, не сняв lock) **или** файл старше 60 с — возраст считается по `atMs` внутри файла, при нечитаемом содержимом — по mtime файла; удержание длится одну запись `temp + rename`, и минута многократно превышает штатное время. Снятие lock'а в `finally` удаляет файл, только если `pid`, `atMs` и `nonce` в нём совпадают с собственными значениями захвата — завершившийся бывший держатель не стирает чужой свежий lock (остаточное окно протокола записано в следующем пункте).
       - **Снятие зависшего lock'а — под отдельным break-lock'ом, не прямым удалением.** Прямое удаление нарушало бы взаимоисключение: два захватчика, оба увидевшие один зависший lock, — первый удалил файл и захватил lock, второй удаляет уже его свежий lock и тоже захватывает — на машине два писателя одновременно; а окно «lock удалён → собственный `O_EXCL`-захват» внутри одного снимающего впускает третьего захватчика. Поэтому снятие сериализуется отдельным файлом `<dataDir>/accounts-state.lock.break`, захватываемым тем же созданием с `O_EXCL` и с тем же содержимым `{"pid", "atMs", "nonce"}`. Break считается зависшим, только если записанный в нём pid держателя **не существует** на этой машине **и** mtime файла старше короткого порога (30 с; операция под break'ом — одно чтение и один `unlink`, порог многократно превышает штатное удержание): живой, пусть и медленный, держатель break'а по возрасту не теряется. Зависший break снимается прямым `unlink` после повторного stat — файл всё ещё стар и pid всё ещё отсутствует; вложенный сериализатор для break'а не вводится — рекурсия бы не завершалась. Под захваченным break'ом захватчик **перечитывает** `accounts-state.lock` и удаляет его, только если `pid` и `atMs` совпали с прочитанными до захвата break'а — lock всё ещё тот же зависший; несовпадение — lock уже снят или подменён свежим: break отпускается, цикл захвата повторяется с начала. После успешного `unlink` зависшего lock'а снимающий отпускает break и возвращается к обычному захвату `O_EXCL`. Удаление зависшего lock'а возможно только под break'ом, поэтому увидевший пустой путь третий захватчик легально берёт `O_EXCL`, а чужой свежий lock снимающий не трогает: удалить его можно было бы лишь под break'ом и лишь при совпадении содержимого с зависшим слепком (остаточное окно — в следующем пункте). Сам break-файл снимается в `finally` по тому же контракту владельца, что и основной lock.
       - **Остаточное окно (известное ограничение v1).** Гарантия «не тронуть чужой свежий lock» действует при соблюдении протокола, но два узких случая честно остаются: (1) держатель break'а умер внутри break-секции **и** два снимающих пришли одновременно — «повторный stat → `unlink`» имеет TOCTOU-окно на уровне самого break'а: пока первый снимающий стоит между stat и `unlink`, второй успевает снять тот же зависший break, создать свой свежий и войти в break-секцию — `unlink` первого сносит уже свежий break, и в break-секции оказываются двое; (2) живой держатель lock'а удерживает его дольше 60 с (SIGSTOP, своп) — lock снимается по возрасту, а пришедший в себя держатель продолжит писать как владелец. Ущерб ограничен: `saveLedger` перечитывает `install`/`priority` с диска при каждой записи, у `add-account.mjs` есть повторная проверка и откат (§4.1 шаг 5); у `--rebind` потерянное обновление теоретически возможно, но вероятность окна микроскопична. Ядерная блокировка (`flock`) эти окна закрыла бы, но в v1 не вводится — нативная зависимость вне объёма.
       - **Область lock'а — вся операция сохранения.** `saveLedger` пишет три файла — `conversations-state.json`, `accounts-overlay.json` и `accounts-state.json` (`accounts.ts`) — и читает дисковое состояние для слияния (общий файл для переноса меток, `priority` и `install`; файл pins): lock берётся до начала операции `saveLedger` и покрывает её целиком — чтения и записи всех трёх файлов, порядок шагов внутри операции значения не имеет. По таймауту пропускается **вся** запись, а не только общий файл.
       - **Граница ожидания.** `saveLedger` исполняется синхронно в event-loop обёртки (`accounts.ts`), и блокировать цикл нельзя: суммарное ожидание захвата — десятки миллисекунд (`O_EXCL` + несколько коротких повторов), длинного ожидания в синхронном пути нет. Команды §4 — отдельные процессы вне event-loop и ждут дольше: повторы до таймаута порядка 10 с.
       - **Исчерпание повторов (таймаут lock'а).** `saveLedger` **пропускает** запись: изменения остаются в памяти леджера до следующего сохранения, а в `acp-wrapper.log` пишется предупреждение с троттлингом не чаще раза в 5 минут (образец — §5 п. 2). Пропущенная запись могла бы потеряться при завершении обёртки до следующего сохранения (парковка аккаунта не дошла бы до общего файла): при **штатном завершении** обёртка выполняет одну попытку `saveLedger` под тем же lock'ом и с тем же таймаутом. Триггер — хуки жизненного цикла моста `experimental_providerBridge` (`acp-wrapper.ts`): `onClose` — выгрузка моста при остановке/перезагрузке демона — сейчас очищает таймеры ожидания сессий и запускает реапер сирот (`reapOrphanShims`), после чего передаёт вызов мосту; `onSigterm` и `onSigint` — только передают вызов мосту. Все три хука ведут в `shutdown` моста (`provider-bridge.ts`), который останавливает дочерние процессы сессий; итоговая попытка `saveLedger` выполняется в каждом из них **до** передачи в `shutdown` (после него дочерние процессы уже убиты) — вызов `saveLedger` в хуках — **новый код**. Команды §4 **отказывают**: ничего не пишется — ни привязка, ни каталог аккаунта.
       - Писатель вне блокировки файл перезаписать может — advisory lock этого не запрещает: keeper-синк перезаписывает общий файл на спутнике, а на владельце, где выполняются команды §4.1, keeper общий файл не пишет (синк односторонний владелец→спутник) — писателями вне блокировки для §4.1 остаются только ручная правка оператора и сторонний процесс, для них служат повторная проверка и откат.
     - Локальный файл `accounts-overlay.json` поле `install` **не содержит** и в merge-on-save оверлея оно не участвует.
2. **Значение по умолчанию и недопустимые значения:**
   - Если у аккаунта поле `install` **отсутствует**, аккаунт считается привязанным к **основной установке** (`default` из реестра). При добавлении аккаунта в основную установку поле `install` явно на диск не записывается.
   - Любое **присутствующее** значение `install`, не проходящее шаблон имени `^[a-z0-9-]{1,32}$`, — включая не-строковые значения и пустую строку — трактуется как **неизвестная установка**: аккаунт недоступен на этой машине (§5 п. 2). Тихого отката к основной установке нет: опечатка в поле не должна молча переводить аккаунт на чужой бинарник.
3. **Поведение на спутнике (satellite instance):**
   - Инфраструктурный keeper синхронизирует `accounts-state.json` с владельца на спутник.
   - Имя установки (`install: "secondary"`) приезжает на спутник через синк.
   - Спутник сопоставляет это имя со своим локальным реестром `agy-installs.json` и запускает бинарник по локальному пути, прописанному на этой машине.
   - На каждом спутнике оператор создает реестр с **теми же именами установок**, что на владельце; на спутнике оба имени могут указывать и на один и тот же бинарник (путь локален).
   - Поле `default` реестра спутника — локальное значение и **не обязано совпадать** с `default` владельца: аккаунты без поля `install` запускаются бинарником основной установки **данной машины**.
   - Если на спутнике установка с таким именем не объявлена в локальном реестре (или реестра нет вовсе), аккаунт на спутнике признается локально недоступным (см. §5).
   - Команды записи привязки (§4) на спутнике **не выполняются**: локальная запись общего файла будет стёрта следующим keeper-синком, и аккаунт молча уйдёт в основную установку — то есть начнёт запускаться чужим бинарником.

## 4. Добавление и перепривязка аккаунтов оператором

### 4.1 Единая команда добавления — `scripts/add-account.mjs`

Путь добавления аккаунта **один** для основной и дополнительной установки — одна и та же команда оператора; установки отличаются **только** флагом `--install`:

```bash
node scripts/add-account.mjs --label <метка>               # аккаунт в основную установку
node scripts/add-account.mjs --label <метка> --install <имя>  # аккаунт в дополнительную установку
```

Команда выполняется оператором в интерактивном терминале **на инстансе-владельце пула**. Она пишет в общий файл `accounts-state.json`, а keeper синкает его односторонне владелец→спутник (§2.1 `provider-agy-acp.md`): запись, сделанная на спутнике, стирается за ~30 с — аккаунт молча ушёл бы в основную установку и запускался бы чужим бинарником. Сторону скрипт проверяет по пустому файлу-маркеру `<dataDir>/pool-satellite` (по образцу операторских маркеров `accounts-parked/`): маркер есть → отказ, ничего не пишется; маркера нет → владелец (одноинстансные пулы маркер не создают, спутнику его выставляет оператор — §12 п. 2).

Команда делает пять шагов. Порядок шагов закрывает гонку «пул увидел аккаунт без привязки»: `listAccounts` (`accounts.ts`) находит аккаунт по файлу токена `accounts/<метка>/.gemini/antigravity-cli/antigravity-oauth-token`, который `agy` пишет **уже во время входа**, — поэтому до записи и проверки `install` аккаунт не должен появляться в `accounts/`:

1. Проверяет входные условия: метка свободна (нет ни каталога `accounts/<метка>`, ни записи с такой меткой в `accounts-state.json`); при `--install <имя>` — имя проходит шаблон и присутствует в реестре `agy-installs.json`.
2. Создает **staging-каталог вне `accounts/`** — `<dataDir>/.add-account-<метка>`: аккаунт в нём невидим для `listAccounts` и недоступен пулу.
3. Берет бинарник установки из реестра `agy-installs.json`: без флага `--install` — бинарник **основной** установки (`default`); с флагом — бинарник записи `<имя>`. Если реестра нет — используется `resolveAgyCommand(process.env)` (сегодняшнее поведение). Запускает **родной вход** этим бинарником (§4.2) с `HOME=<staging>` в интерактивном терминале.
4. После успешного входа, **пока каталог ещё в staging** и аккаунт невидим пулу, записывает привязку и проверяет её: при `--install <имя>` с именем, отличным от `default`, под общим lock-файлом `accounts-state.lock` (§3 п. 1) атомарно (temp + rename) пишет `accounts[<метка>].install = <имя>` в `accounts-state.json` и перечитывает файл с диска, сверяя записанное значение; без флага или при имени `default` поле не пишется и проверка не нужна. Затем атомарным `rename` переносит staging-каталог в `<dataDir>/accounts/<метка>` — с этого момента аккаунт виден пулу уже с привязкой на диске.
5. Сразу после rename **повторно** перечитывает `accounts-state.json` с диска: привязка на месте — команда завершается успехом. Привязка не читается (общий файл перезаписан слепком без новой метки писателем вне блокировки §3 п. 1 — ручной правкой оператора или сторонним процессом) — каталог **немедленно переносится обратно в staging** (убирается из `accounts/`), после чего цикл «запись `install` → проверка в staging → rename → проверка» повторяется (несколько попыток). Исчерпание попыток — **ошибка с откатом**: staging-каталог удаляется, как при прерванном входе. Окно «аккаунт в `accounts/` без `install` на диске» ограничено интервалом между rename и повторной проверкой и закрывается немедленным возвратом в staging: на время повторов каталога в `accounts/` нет — оставленный там аккаунт без `install` был бы виден пулу как привязанный к основной установке и запустился бы чужим бинарником, именно этот исход и закрывает откат. Тем же откатом команда под тем же lock-файлом `accounts-state.lock` наилучшим усилием удаляет запись `accounts[<метка>]` из общего файла; если запись осталась, она относится к несуществующей метке и на выбор не влияет (пул находит аккаунты по каталогам — `listAccounts` по файлу токена), а при повторном добавлении шаг 1 откажет на занятой метке и оператор удалит её ручной правкой. Это страховка от записей общего файла вне блокировки: `saveLedger` и команды §4 пишут `accounts-state.json` под общим lock-файлом `accounts-state.lock` (§3 п. 1), поэтому слепок леджера, снятый до шага 4, не может быть записан поверх привязки; потерять `install` в этом окне может только писатель вне блокировки (ручная правка оператора, сторонний процесс) — для такого случая и служат повторная проверка и откат. В штатном случае после rename метка присутствует и в общем файле, и в `accounts/` — следующий `loadLedger` её видит, и привязка дальше переживает сохранения по правилам §3 п. 1. **Известное ограничение v1:** если `install` уже потерян писателем вне блокировки, выбор аккаунта пулом внутри окна «rename → повторная проверка» запустит сессию бинарником `default` (метка в `accounts/` видна без привязки), а возврат каталога в staging эту сессию оборвёт; окно длится один rename и одно чтение файла, вероятность мала — устранение не входит в v1.

Отказы команды:
- Запуск на спутнике (есть маркер `<dataDir>/pool-satellite`) — отказ с указанием запускать команду на владельце: записи общего файла на спутнике затираются keeper-синком.
- `--install <имя>` при **отсутствующем реестре** или **неизвестном имени** — команда завершается ошибкой, **ничего не пишется** (ни каталог, ни привязка).
- Имя, не проходящее шаблон `^[a-z0-9-]{1,32}$`, — отказ по той же схеме.
- Метка занята (каталог `accounts/<метка>` или запись в `accounts-state.json` уже есть) — отказ.
- Вход прерван или завершился неудачей — staging-каталог удаляется; в `accounts/` и в `accounts-state.json` ничего не попадает.
- Исчерпание попыток записи привязки (шаг 5, перезапись общего файла писателем вне блокировки §3 п. 1) — отказ с откатом: каталог аккаунта уже возвращён из `accounts/` в staging на первом провале проверки и удаляется вместе с ним; повторное добавление выполняется той же командой сначала — но если после отката в общем файле осталась запись метки, шаг 1 откажет на занятой метке: сначала удалить её ручной правкой (см. шаг 5).

Без реестра и без флага результат совпадает с сегодняшним порядком заведения аккаунта (README «Adding an account»): тот же родной вход тем же бинарником, привязка при этом не пишется вовсе; staging лишь делает появление аккаунта в `accounts/` атомарным.

### 4.2 Родной вход (Native Sign-in) — через `HOME`

Вход выполняется бинарником **той установки, к которой привязывается аккаунт**, с домашним каталогом аккаунта. Под `add-account.mjs` это staging-каталог (§4.1 шаг 3); при ручном входе по README — каталог аккаунта:

```bash
HOME=<dataDir>/.add-account-<метка> <бинарник установки>   # под add-account.mjs
HOME=<dataDir>/accounts/<метка> <бинарник>                # ручной путь из README
```

- Флаг `--gemini-dir` для входа **не используется**: он существует только у подкоманды `agy acp` (`provider-agy-acp.md` §2.3 п. 1); у `agy` без подкоманды такого флага нет. Изоляция аккаунта при входе достигается подменой `HOME`, как описано в README плагина («Adding an account»).
- Обычный и дополнительный аккаунт входят **одинаково**: отличается только путь бинарника, взятый из реестра.
- Вход интерактивный: оператор выбирает Google OAuth, открывает ссылку, возвращает код; сразу после экрана входа `agy` закрывается, промпт из него не отправляется.

### 4.3 Вторичные пути

**Импорт готовых токенов** — `scripts/import-accounts.mjs` расширяется флагом `--install <имя>`:

```bash
node scripts/import-accounts.mjs --file <path> --label <label> [--install <имя>]
node scripts/import-accounts.mjs --cliproxy [dir] [--install <имя>]
node scripts/import-accounts.mjs --opencode [--install <имя>]
```

- Без `--install`: поле `install` в `accounts-state.json` не пишется, аккаунт привязывается к основной установке (`default`).
- С `--install <имя>`: имя проверяется по реестру `agy-installs.json`; при отсутствующем реестре или неизвестном имени — **отказ, ничего не пишется**; при имени `default` поле не пишется, иначе записывается `accounts[label].install`.
- Как и `add-account.mjs`, импорт выполняется **только на владельце**: на спутнике (маркер `<dataDir>/pool-satellite`, §4.1) — отказ, ничего не пишется. Локальная запись спутника стёрлась бы keeper-синком за ~30 с, и привязанный аккаунт молча ушёл бы в основную установку.
- Гонка §4.1 закрывается тем же приёмом: импорт кладёт файлы токена в staging-каталог вне `accounts/`, записывает `install` под общим lock-файлом `accounts-state.lock` (§3 п. 1) и только затем `rename`-ом делает аккаунт видимым пулу; проверка привязки чтением с диска до и после rename и откат при её провале или исчерпании попыток — те же, что в §4.1 шагах 4–5.

**Перепривязка существующего аккаунта** — атомарная операция:

```bash
node scripts/import-accounts.mjs --rebind --label <label> --install <имя>
```

- Перепривязка — правка общего файла, поэтому выполняется **только на владельце** (как ручные правки `priority`, §2.2 `provider-agy-acp.md`): на спутнике (маркер `<dataDir>/pool-satellite`) — отказ, файл не меняется, иначе привязка стёрлась бы синком за ~30 с.
- Проверяет существование имени `<имя>` в `agy-installs.json`; при отсутствующем реестре или неизвестном имени — отказ, файл не меняется.
- Под общим lock-файлом `accounts-state.lock` (§3 п. 1) атомарно через временный файл (temp + rename) обновляет запись `accounts[label].install` в `accounts-state.json`. Если указано имя основной установки (`default`), свойство `install` удаляется из записи аккаунта.
- Локальные оверлеи не затрагиваются.
- Перепривязка действует на **новые запуски** процессов: идущие сессии не перезапускаются и продолжают работать на бинарнике, с которым были подняты; следующий запуск аккаунта (новый тред, пересборка сессии, resume) пойдет уже бинарником новой установки.

## 5. Выбор аккаунта и сквозная логика пула

1. **Независимость выбора от установки:**
   - Алгоритм `pickAccount` (§2.2, §2.3) распределяет запросы по сквозным правилам для всего пула:
     1. Фильтрация по исключению (`excludeLabel`), положительному приоритету (`priority > 0`), отсутствию постоянной парковки (`parkedReason === undefined`), и пригодности по модели (§2.3).
     2. Проверка локальной доступности установки на текущей машине (см. п. 2 ниже) — единственный шаг, где установка учитывается.
     3. Выбор высшего тира приоритета среди доступных (кулдаун ≤ now).
     4. Внутри тира — строгий LRU по `lastUsedMs` (с тай-брейком по `label`).
     5. При охлаждении всех кандидатов — выбор аккаунта с наиболее ранним открытием окна внутри высшего присутствующего тира.
   - Аккаунты одного тарифа и приоритета, привязанные к разным установкам, чередуются в едином цикле LRU.
   - Установка определяет **только то, каким бинарником запустить уже выбранный аккаунт** — и больше ничего.
2. **Строго, без подмены (Strict Execution Contract):**
   - Если аккаунт привязан к установке, имя которой отсутствует в `agy-installs.json` (включая значения, не проходящие шаблон имени — §3 п. 2, и отсутствие реестра при заданном `install` — §2 п. 6), либо файл бинарника по указанному пути не существует / не исполняем:
     - Аккаунт признается **локально недоступным** на данном хосте и исключается из кандидатов в `pickAccount`.
     - Это локальное состояние хоста: оно **не записывается** в общий файл `accounts-state.json` и не является `parkedReason`.
     - Запуск аккаунта бинарником другой установки **категорически запрещен**.
     - Предупреждение пишется в локальный лог обёртки (`acp-wrapper.log`) с троттлингом (не чаще одного раза в 5 минут на аккаунт), чтобы не засорять диск при частых опросах.
   - Если закрепленный за таким аккаунтом тред пытается возобновиться (`thread/resume`):
     - Обёртка пытается выполнить переключение на подходящего свободного сиблинга (автомат ротации).
     - Если сиблингов нет — операция немедленно завершается честной ошибкой с указанием имени недоступной установки и пути к бинарнику.
   - Проверка существования и исполняемости бинарника (`accessSync(bin, X_OK)`) выполняется **при каждом выборе аккаунта и каждом запуске**, а не один раз при загрузке реестра: файл может появиться или исчезнуть между перечитываниями (§2 п. 5). Появившийся бинарник возвращает аккаунт в строй без правок файлов.
   - Недоступный бинарник **основной** установки делает недоступными аккаунты без `install`; `direct`/`relay` при этом завершаются честной ошибкой с именем `default`-установки и путём — подмена на `resolveAgyCommand` не выполняется.
3. **Пробы и сводный каталог моделей:**
   - Аккаунт с недоступной установкой не запускается нигде — включая пробы: `runModelProbe` для него не стартует, а `maintenanceEnvAndArgs` его не выбирает, т.к. выбор идёт через `pickAccount` (п. 2).
   - В сводном каталоге моделей (§2.3 п. 2) остаётся последний известный каталог такого аккаунта из `accounts-models.json` — как у любого давно не опрошенного аккаунта; на выбор это не влияет, т.к. аккаунт исключён из кандидатов ещё до проверки пригодности по модели.

| 13 | `plugins/bb-plugin-usage-pro` (бандл `provider-usage-base`) | `fetchAgyAccountsUsage` → `runAgySingleAccount(baseDir, label, agyBin, statePath)` (путь бинарника — `getAgyPath`) | Сбор квот конкретного аккаунта пула (`agy --output-format json -p /usage`, `HOME` = каталог аккаунта) | Бинарник установки данного аккаунта по `accounts[label].install` и локальному реестру (иначе `default`; недоступная установка — §9 п. 3) |

## 7. Ротация между установками

1. **Свободная ротация:**
   - Если сессия на аккаунте установки `main` исчерпала квоту (или встретила `auth-dead`, либо смену модели), ротационный автомат (§3) вызывает `pickAccount`.
   - Если наилучшим доступным кандидатом по приоритету и LRU оказывается аккаунт установки `secondary`, ротация переводит сессию на него.
   - Новая сессия синтезируется через `synthThreadStart` → `thread/start` с окружением и бинарником установки `secondary`.
   - Демон BB видит непрерывный ход; в тред отправляется `sessionReplaced`.
2. **Сквозная поддержка каталогов моделей (§2.3):**
   - Начиная с ревизии 11 спеки `provider-agy-acp.md`, каталоги моделей хранятся раздельно по каждому аккаунту в `accounts-models.json` и формируются на основе ответа `agy models` под окружением этого аккаунта.
   - Если установки имеют разные версии бинарников и поддерживают разный набор моделей, это учитывается автоматически: каталог каждого аккаунта отражает возможности именно того бинарника, которым он опрашивается.
   - Фильтр пригодности аккаунта в `pickAccount` исключает назначение аккаунта на модель, отсутствующую в его каталоге. Никаких дополнительных правок в механизм каталогов моделей не требуется.

## 8. Изоляция и предотвращение взаимного влияния

Чтобы процессы разных установок не мешали друг другу, определены границы изоляции:

1. **Файлы бинарников и самообновление:**
   - Каждая установка ссылается на собственный путь `bin`.
   - На машине, где установки реально разведены, оператор размещает бинарники в непересекающихся каталогах — иначе изоляции нет. На спутнике оба имени реестра могут указывать на один и тот же бинарник (§3 п. 3): тогда установка вырождается в единую и требования к разнесению снимаются.
   - Секция `env` в `agy-installs.json` позволяет изолировать пути загрузки обновлений и временных файлов (например, `TMPDIR`, `XDG_CACHE_HOME`).
2. **Состояние под настоящим `$HOME` вне папки аккаунта:**
   - Для `agy acp` изоляция аккаунта выполняется через `--gemini-dir <account-home>/.gemini`, при этом `$HOME` процесса намеренно не подменяется (для сохранения доступа к `~/.gitconfig` и `~/.ssh`).
   - Если бинарник `agy` сохраняет глобальное состояние вне `--gemini-dir` (например, в `~/.cache` или `~/.local/share`), для дополнительной установки в реестре задаются изолирующие переменные `XDG_CACHE_HOME`, `XDG_DATA_HOME` и `XDG_STATE_HOME`.
3. **Шим и файлы управления (`acp-shim`):**
   - Файлы управления шима именуются с использованием идентификатора треда и уникального нонса: `ctl-<thread>-<nonce>.ndjson`; у maintenance-шима проб моделей (`__models__`) — `ctl-models.ndjson` (как в `provider-agy-acp.md` §8). Каталог `acp-shim/` общий для всех установок, имена control-файлов не пересекаются — конфликты между параллельными процессами разных установок исключены.
   - Сам скрипт `acp-shim.mjs` универсален: он считывает путь к реальному бинарнику из переменной окружения `AGY_SHIM_REAL_BIN`, передаваемой индивидуально для каждого запуска.
4. **Реапер процессов-сирот (§12.3):**
   - Механизм `reapOrphanShims()` идентифицирует сиротские процессы по наличию интерпретатора Node/Electron и имени аргумента `acp-shim.mjs`.
   - Завершение дерева процессов (`procDescendants(pid)`) выполняется строго вниз по дереву PID конкретного сиротского шима.
   - Реапер не ищет процессы по имени `agy` вслепую по всей системе, поэтому он:
     - Гарантированно находит и завершает дочерние процессы `agy` любой установки, если их родительский шим осиротел;
     - Никогда не трогает живые процессы других установок или чужих инстансов.
   - Очистка временных каталогов `sweepStaleShimTmpDirs` удаляет только каталоги `agy-acp-*` старше 1 часа, на которые нет открытых файловых дескрипторов от живых процессов.

## 9. Видимость и журнал

1. **Фиксация установок при старте:**
   - Регистрация реестра выполняется в **обеих** точках инициализации плагина — они стартуют независимо друг от друга:
     - `start(context)` обёртки в `src/acp-wrapper.ts` (рядом со строкой `acp wrapper started`) → журнал `acp-wrapper.log`;
     - `start(context)` stream-json моста в `src/provider-bridge.ts` (рядом со строкой `bridge started …`) → журнал `bridge.log`.
   - В каждый из журналов пишется строка вида:
     `installs registry loaded: default=main; main: /path/to/bin; secondary: /path/to/alt-bin`
   - **Версии установок:** обёртка ведет кэш версии по ключу (путь, mtime, размер) файла бинарника; бинарник ради опроса версии запускается **только при изменении файла** (новая mtime/размер), а не при каждом старте. Пока способ узнать версию не подтвержден (§13 п. 1), в журнал пишутся только имя установки и путь.
   - Когда способ опроса версии подтвержден: расхождение версий между установками — предупреждение в журнале, **не ошибка**:
     `warning: install version mismatch: main is v1.5.3, secondary is v1.5.0`
     Предупреждение носит информационный характер и не блокирует запуск.
2. **Журнал переходов пула (§2.3 п. 12):**
   - Новых форматов строк не вводится. Существующие строки журнала `acp-wrapper.log` дополняются суффиксом `install=<имя>`:
     - `thread <id>: pinned to account <label> (model <m>, proxy <…>, install=secondary)`
     - `thread <id>: move <label1> → <label2> (<cause>, install=<label2-install>)`
     - `thread <id>: resuming <providerThreadId> on account <label> (install=secondary)`
   - Журнал ACP-обёртки — `acp-wrapper.log` (не `bridge.log`).
3. **Отображение в Usage Pro (дополнения к §6 `usage-account-display.md`):**
   - usage-pro читает реестр `agy-installs.json` и поле `accounts[label].install` **из каталога данных provider-agy** (`<dataDir>` плагина provider-agy, тот же, где лежит `accounts-state.json`); собственной копии реестра у usage-pro нет.
   - Реализация сборщика живёт в `plugins/bb-plugin-usage-pro/dist/provider-usage-base.js` (`fetchAgyAccountsUsage` → `runAgySingleAccount` ← `getAgyPath`). Файл отслеживается git и **правится на месте** — отдельных `.ts`-исходников сборщика в репозитории нет; `server.ts` и тесты плагина импортируют его напрямую (`import … from "./dist/provider-usage-base.js"`), README плагина называет его исходным backend-артефактом. Так сделаны PLUG-300 (`1da99a00`) и PLUG-301 (`5f9239d5`) — тот же порядок и здесь.
   - Проверка правки: `vitest run` плагина usage-pro (`npm test` в `plugins/bb-plugin-usage-pro`) и пересборка `dist/server.js` через `scripts/build.mjs` — бандл и серверный артефакт уезжают в коммит вместе.
   - Сборщик квот опрашивает аккаунт бинарником той установки, которая указана в `accounts[label].install` (фолбэк на `default`), — дополнение к §6 п. 2.
   - Если установка аккаунта недоступна на этой машине (нет в локальном реестре, бинарь отсутствует или не исполняем, реестр битый), аккаунт **не опрашивается** — как фоновым прогревом, так и по кнопке обновления; на карточке ставится пометка по образцу существующих `Out of rotation` / `Parked: <reason>` (например, `Install unavailable: <имя>`), поверх данных из кэша, если они есть.
   - В карточке аккаунта на табе провайдера выводится метка используемой установки (например, чип или подпись `install: secondary`) — дополнение к §6.

## 10. Вне рамок v1 (Non-goals)

1. **Автоматическое скачивание и обновление бинарников плагином:** установка, скачивание и обновление файлов `agy` производятся оператором хоста.
2. **Квоты и лимиты одновременных сессий на установку:** распределение параллелизма балансируется пулом аккаунтов, жесткие семафоры на процесс бинарника не вводятся.
3. **Раздельные провайдеры в BB:** все установки обслуживаются единым плагином `provider-agy`.
4. **Маскировка перед внешними сервисами:** разделение установок изолирует бинарники, версии и локальное состояние ОС, но **не скрывает от Google принадлежность аккаунтов одной машине/IP**. Для сетевой изоляции по-прежнему используется индивидуальный файл `proxy` для каждого аккаунта.

## 11. Тест-план

Проверка выполняется автоматизированным харнессом с использованием двух поддельных бинарников (`fake-agy-main` и `fake-agy-secondary`), каждый из которых записывает свое имя и параметры в транскрипт (`AGY_FAKE_TRANSCRIPT`). Для каждого правила указана мутация, которую тест обязан поймать.

1. **Строгое разделение запусков по всем точкам §6:**
   - Аккаунт установки `main` при `thread/start`, `thread/resume`, восстановлении неизвестного треда (`restoreUnknownSession`), компакции (`runCompactSeed`, `compactRestore`), пробе моделей (`runModelProbe`), страховке окружения шима (`completeShimLaunchEnv` — восстановленный `AGY_SHIM_REAL_BIN` указывает на бинарник аккаунта, а не `default`), сводных пробах (`queryAgyModels`, `queryAcpSessionModels` через `maintenanceEnvAndArgs`), опросе моста (`listAgyModels`) и legacy-запуске (`startChild`) вызывает исключительно `fake-agy-main`.
   - Аккаунт установки `secondary` во всех аналогичных точках вызывает исключительно `fake-agy-secondary`.
   - В транскрипте отсутствуют вызовы чужого бинарника.
   - *Мутация:* подстановка `resolveAgyCommand` или `default`-бинарника в любой из точек — тест падает по записи чужого имени в транскрипте.
2. **Режимы без аккаунта:**
   - `direct` и `relay` сессии запускаются строго бинарником `default`-установки.
   - *Мутация:* выбор бинарника «первого аккаунта пула» или `secondary` для direct — тест падает.
3. **Отсутствие реестра:**
   - При удалении `agy-installs.json` все операции работают через `resolveAgyCommand` в штатном режиме.
   - Аккаунт с заданным `install` при отсутствующем реестре недоступен и не выбирается.
   - *Мутация:* игнорирование поля `install` при отсутствующем реестре (аккаунт запускается неявным бинарником `resolveAgyCommand`) — тест падает: аккаунт обязан быть недоступен.
4. **Битый реестр — громкая ошибка:**
   - `agy-installs.json` с битым JSON, нарушением схемы или `default`, указывающим на несуществующую запись: ни один аккаунт пула не выбирается, `direct`/`relay` не стартуют, `thread/start` возвращает ошибку с причиной.
   - *Мутация:* тихий откат к `resolveAgyCommand` при битом реестре — тест падает (ожидается честная ошибка, а не успешный запуск).
4a. **Запретный ключ `env` в реестре — ошибка схемы:**
   - `agy-installs.json`, у записи которого в `env` присутствует любой запретный ключ (`HOME`, `ELECTRON_RUN_AS_NODE`, `GEMINI_API_KEY`, `GOOGLE_GEMINI_BASE_URL`, `HTTP_PROXY`/`HTTPS_PROXY`/`ALL_PROXY`/`NO_PROXY` в обоих регистрах, любой ключ префикса `AGY_*` — включая `AGY_SHIM_*`, `AGY_DISABLE_*` и процессные `AGY_PATH`, `AGY_TRANSPORT`, `AGY_ACCOUNTS`, `AGY_CLIPROXY*`), — битый реестр по §2 п. 4: ни один аккаунт не выбирается, `direct`/`relay` и все запуски §6 не выполняются, `thread/start` падает с причиной.
   - *Мутация:* трактовка запретного ключа как игнорируемого с предупреждением (реестр считается валидным, ключ выкидывается из `env`, запуски идут) — тест падает: ожидается отказ схемы, а не запуск с выкинутым ключом.
5. **Неизвестная или сломанная установка (No Substitution):**
   - Аккаунт с `install: "broken"` (имени нет в реестре, бинарник удален или не исполняем, либо значение `install` не проходит шаблон имени) игнорируется при вызове `pickAccount`.
   - Попытка явного `thread/resume` на этом аккаунте переходит на сиблинга либо завершается честной ошибкой без попытки подставить `main`.
   - *Мутация:* трактовка непроходящего шаблон значения как «основная установка» — тест падает.
6. **Сквозная ротация `main` → `secondary`:**
   - Эмуляция ошибки квоты на аккаунте `main` переключает сессию на аккаунт `secondary`. Следующий ход выполняется процессом `fake-agy-secondary`.
   - *Мутация:* ротация, ограниченная аккаунтами той же установки, — тест падает отсутствием перехода.
7. **Чередование в LRU:**
   - Несколько аккаунтов с одинаковым приоритетом из разных установок равномерно чередуются по LRU.
   - *Мутация:* группировка LRU внутри установки — тест падает по нарушению порядка чередования.
8. **Изменение реестра на лету:**
   - Правка `agy-installs.json` (смена mtime) во время работы плагина применяется к следующим запускам без перезагрузки: новый путь бинарника используется при следующем `pickAccount`/запуске.
   - *Мутация:* кэш реестра без проверки mtime — тест падает: измененный реестр не подхватывается.
9. **Сохранение поля `install` при мутациях:**
   - Циклы `markAccountUse`, `markAccountCooldown` и сохранение леджера сохраняют значение `install` на диске и не переносят его в оверлей.
   - `saveLedger` переносит в общий файл дисковые записи меток, которых нет в памяти: метка и `install`, записанные `add-account.mjs` между `loadLedger` и `saveLedger`, переживают чужое сохранение (§3 п. 1).
   - *Мутация 1:* потеря `install` при `saveLedger` или утечка поля в `accounts-overlay.json` — тест падает.
   - *Мутация 2:* запись общего файла строго из памяти без переноса дисковых меток — тест падает: конкурентно добавленная метка исчезает из файла.
9a. **Lock-файл `accounts-state.lock` (§3 п. 1):**
   - (а) Харнесс держит `accounts-state.lock` живым процессом: параллельные `saveLedger` и `add-account.mjs --install` / `--rebind` ждут захвата и не пишут общий файл, пока lock удерживается (`saveLedger` — в пределах границы ожидания §3 п. 1, затем пропускает запись до следующего сохранения); после освобождения lock'а команда записывает `install`, и он остаётся на диске после следующего `saveLedger`.
   - (б) Зависший lock мёртвого держателя (записанный pid не существует либо файл старше границы §3 п. 1) снимается автоматически под сериализующим `accounts-state.lock.break` с перечитыванием файла и сверкой `pid`/`atMs` — захват проходит; при lock'е, удерживаемом живым процессом дольше таймаута, действует поведение §3 п. 1: `saveLedger` пропускает запись с троттлированным предупреждением в `acp-wrapper.log`, команды §4 отказывают, ничего не записывая.
   - (в) Гонки снятия зависшего lock'а — детерминированно, по хукам харнесса: без хуков окно «перечитывание → `unlink`» занимает микросекунды, и мутация тестом не ловится. Харнесс ставит в снимающих управляемые точки остановки: **хук сверки** — между перечитыванием `accounts-state.lock` под break'ом и его `unlink`; **хук захвата** — между `unlink` зависшего lock'а и собственным `O_EXCL`-захватом снимающего (оформление — по образцу хука Мутации 1 п. 9). Порядок шагов зафиксирован:
     1. Мёртвый держатель оставил зависший lock (pid не существует). Снимающие С1 и С2 одновременно признали lock зависшим; процесс З — обычный `O_EXCL`-захватчик.
     2. С1 занимает break, перечитывает lock и останавливается на хуке сверки; С2 ждёт break.
     3. С1 удаляет lock и останавливается на хуке захвата; З занимает lock `O_EXCL` и пишет; С2 занимает освободившийся break, перечитывает lock — `pid`/`atMs` не совпали со слепком зависшего (lock свежий, принадлежит З): С2 отпускает break и уходит в обычный цикл захвата.
     4. З освобождает lock; С1 и С2 проходят по очереди. Проверки: общий файл пишет ровно один писатель за раз, каждая успешная запись видна на диске после прохода (потерянных обновлений нет), свежий lock З не снят чужой рукой.
     5. Отдельный кейс — снятие собственного lock'а в `finally` во время удержания break'а и lock'а другим процессом: файл удаляется только при совпадении `pid`+`atMs`+`nonce` с собственными — чужой свежий lock под тем же именем доживает до конца владельца.
   - (г) Штатное завершение после пропущенной по таймауту записи — проверяется для каждого из хуков `onClose`, `onSigterm`, `onSigint` моста: харнесс держит lock живым процессом на время пропущенной записи и **отпускает его до вызова хука** — обёртка выполняет одну итоговую попытку `saveLedger` под тем же lock'ом, и парковка, не дошедшая до общего файла при живом lock'е, оказывается на диске. Отдельный кейс — lock всё ещё удерживается живым процессом в момент завершения: итоговая попытка исчерпывает тот же таймаут §3 п. 1, в `acp-wrapper.log` пишется предупреждение, обёртка завершается без зависания.
   - *Мутация 1:* запись общего файла без захвата lock'а — тест падает: общий файл оказывается изменён, пока харнесс держит lock (проверка (а) фиксирует это по файлу под удерживаемым lock'ом); потерю `install` детерминированно проверяет хук харнесса между чтением дисковой записи и записью — `saveLedger` перечитывает `install` с диска при каждой записи (`accounts.ts`), и без хука окно «чтение → запись» тесту неподконтрольно.
   - *Мутация 2:* бесконечное ожидание захвата либо молчаливая запись поверх живого lock'а — тест падает.
   - *Мутация 3:* снятие зависшего lock'а без захвата `accounts-state.lock.break` — тест (в) падает: без сериализации break'ом С2 проходит хук сверки параллельно с С1 и на шаге 3 удаляет уже свежий lock З — следующий писатель идёт без взаимоисключения либо общий файл получает потерянное обновление; хуки сверки и захвата делают это окно детерминированным.
   - *Мутация 4:* удаление lock-файла в `finally` без проверки владельца (`pid`+`atMs`+`nonce`) — тест (в) падает: завершившийся бывший держатель стирает чужой свежий lock, и следующий писатель идёт без взаимоисключения.
   - *Мутация 5:* штатное завершение без итоговой попытки `saveLedger` — тест (г) падает: пропущенная парковка не оказывается на диске после срабатывания хука завершения.
10. **Команда добавления `add-account.mjs`:**
    - С флагом `--install secondary` создает каталог аккаунта, запускает вход бинарником `secondary` и пишет `install: "secondary"`; без флага — вход бинарником `default`, поле не пишется.
    - `--install` при отсутствующем реестре или неизвестном имени — отказ, ничего не пишется (ни каталог, ни запись).
    - На спутнике (есть маркер `<dataDir>/pool-satellite`) — отказ, ничего не пишется: записи общего файла на спутнике стираются keeper-синком.
    - Аккаунт невидим для пула без привязки — инвариант проверяется по контрольным точкам, а не непрерывным опросом:
      - (а) в штатном пути (первая проверка после rename прошла) метки в `accounts/` без `install` на диске нет ни в одной контрольной точке — до, во время и после команды;
      - (б) в пути провала метка без `install` видна **только** внутри окна «rename → повторная проверка» одной попытки — во время повторов записи каталог находится в staging (метки в `accounts/` нет), а после выхода команды при исчерпании попыток каталог удалён, и метки в `accounts/` тоже нет;
      - (в) харнесс проверяет инвариант **детерминированно по контрольным точкам** (перед rename, внутри окна «rename → проверка», между попытками, после завершения команды): окно «rename → проверка» существует по построению на каждой попытке, и непрерывный опрос сделал бы тест случайно падающим.
    - Исчерпание попыток записи привязки (перезапись общего файла писателем вне блокировки §3 п. 1) — отказ с откатом: `accounts/<метка>` уже убран обратно в staging на первом провале проверки, по исчерпании staging удаляется; аккаунт не остаётся видимым пулу как привязанный к основной установке.
    - *Мутация 1:* запись привязки до проверки имени по реестру — тест падает.
    - *Мутация 2:* вход сразу в `accounts/<метка>` с записью `install` после входа — тест падает: харнесс видит аккаунт без привязки в окне между появлением токена и записью поля.
    - *Мутация 3:* при провале проверки после rename каталог остаётся в `accounts/` (повторы идут с видимым аккаунтом) либо при исчерпании попыток не убирается — тест падает: `listAccounts` находит аккаунт без `install`, и следующий запуск идёт бинарником `default`.
11. **Импорт и перепривязка:**
    - `import-accounts.mjs --install <имя>` при неизвестном имени — отказ, файл не меняется.
    - Перепривязка `--rebind` меняет `install` атомарно и действует только на новые запуски: уже поднятая сессия не перезапускается.
    - Импорт с `--install` и `--rebind` на спутнике (маркер `<dataDir>/pool-satellite`) — отказ, файл не меняется.
    - *Мутация 1:* перезапуск живой сессии при перепривязке — тест падает.
    - *Мутация 2:* запись привязки без проверки маркера спутника — тест падает: следующая «синхронизация keeper» (перезапись общего файла версией владельца) стирает привязку, и аккаунт возвращается в основную установку.
12. **Usage Pro:**
    - Аккаунт установки `secondary` опрашивается `fake-agy-secondary`; аккаунт с недоступной установкой не опрашивается даже по `force` и получает пометку недоступности в карточке.
    - *Мутация:* опрос всех аккаунтов единым бинарником `default` — тест падает по записи чужого имени в транскрипте.

## 12. Порядок включения оператором

Для настройки и активации второй установки оператор выполняет следующие шаги:

1. **Размещение второго бинарника:**
   Установить или скопировать второй бинарник в отдельный каталог на машине (например, `/opt/agy-secondary/bin/agy`) и выставить права на исполнение (`chmod +x`).
2. **Создание реестра установок:**
   Создать файл `<dataDir>/agy-installs.json`:
   ```json
   {
     "installs": {
       "main": {
         "bin": "/opt/agy-main/bin/agy"
       },
       "secondary": {
         "bin": "/opt/agy-secondary/bin/agy"
       }
     },
     "default": "main"
   }
   ```
   На каждом спутнике пула создается собственный реестр **с теми же именами**; на спутнике оба имени могут указывать и на один и тот же бинарник. На спутнике дополнительно создается пустой файл-маркер `<dataDir>/pool-satellite` — по нему команды записи привязки отказывают (п. 3).
3. **Привязка аккаунтов** — все команды ниже выполняются **только на инстансе-владельце пула**: keeper синкает `accounts-state.json` односторонне владелец→спутник, и запись привязки на спутнике стирается за ~30 с (аккаунт молча уходит в основную установку и запускается чужим бинарником). На спутнике команды отказывают по маркеру `<dataDir>/pool-satellite` (п. 2):
   - Для новых аккаунтов: единая команда добавления
     `node scripts/add-account.mjs --label <метка>` — в основную установку,
     `node scripts/add-account.mjs --label <метка> --install secondary` — в дополнительную.
   - Для существующих аккаунтов: выполнить перепривязку:
     `node scripts/import-accounts.mjs --rebind --label <метка> --install secondary`
4. **Применение реестра:**
   Реестр перечитывается при смене mtime файла — перезапускать плагин **не нужно**. Если плагин всё же перезагружают — только при отсутствии активных тредов на agy.
5. **Проверка по журналу:**
   Убедиться в наличии строки `installs registry loaded: …` в `acp-wrapper.log` (а при использовании stream-json моста — и в `bridge.log`, §9 п. 1) и отсутствии предупреждений о недоступности бинарников.

## 13. Проверить вживую до включения

Следующие аспекты поведения бинарника `agy` не зафиксированы в коде плагина и требуют проверки на живом стенде перед включением функционала в продакшн:

1. **Флаг версии CLI:**
   - Проверить наличие флагов `agy --version`, `agy -v` или подкоманды `agy version`.
   - Уточнить формат вывода (stdout vs stderr, парсинг семантической версии), чтобы обёртка могла безошибочно извлекать строку версии при старте.
   - До подтверждения способа в журнал пишутся только имя установки и путь (§9 п. 1).
2. **Механизм встроенного самообновления:**
   - Проверить, обновляет ли фоновое самообновление бинарник по пути его фактического запуска (`argv[0]` / `readlink(/proc/self/exe)`), либо жестко пытается перезаписать стандартный путь `$HOME/.local/bin/agy`.
   - Если самообновление жестко привязано к `$HOME/.local/bin/agy`, вторая копия бинарника не будет обновляться автоматически и потребует ручной синхронизации оператором — версии установок при этом разойдутся сами.
3. **Блокировка автообновления:**
   - Выяснить, существует ли флаг или переменная окружения для отключения автообновления `agy`, чтобы предотвратить рассинхронизацию версий на лету.
   - Если найденная переменная окружения попадает под запретный префикс `AGY_*` (§2 п. 3), задать её через `env` установки (§8 п. 1) нельзя — потребуется ревизия спеки с явным списком разрешённых ключей; до такой ревизии префиксный запрет §2 п. 3 остаётся в силе.
4. **Разделяемые системные каталоги:**
   - Проверить через `strace` или анализ открытых дескрипторов, пишет ли `agy` во время работы в общие пути вне `--gemini-dir` (`~/.local/share/antigravity`, `/tmp/agy-*`), и изолируются ли они переменными `XDG_*` и `TMPDIR`.
