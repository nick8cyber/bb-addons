# Второй мозг в звонке по проекту

> [!IMPORTANT]
> Реализованный контракт проектного мозга. Условия исполнения в §6 сохранены для истории; итог приёмки — §8. Спецификации и ADR правит координатор. Основание: команда владельца 07.11 сформировать задачу со спецификацией и запустить исполнителя на Devin.

## 1. Результат

Звонок по проекту, в том числе без git и без выбранного треда, получает второй мозг Devin SWE-2 Flash Medium. Голос передаёт ему вопросы, требующие расчёта, сравнения, анализа периода или диагностики. Мозг получает фактические данные разрешённых коннекторов и возвращает обоснованный ответ с ограничениями. Простые чтения и запись через существующие подтверждения сохраняются.

Пример: «сколько новых пользователей за сегодня и вчера из бота» означает количество созданных людей за заданный период и источник, а не количество карточек на стадии «Новый». Нет метрики/даты создания в инструменте — ответ «точно посчитать доступными данными нельзя», а не ноль или длина страницы.

## 2. Запуск и контекст

На один звонок — не больше одного скрытого треда `providerId: acp-devin`, `model: swe-2-flash-medium`, `reasoningLevel: medium`. Применяется существующий режим прав мозга; код и данные целевого проекта при аналитическом вопросе не меняются. Запуск асинхронен, первое приветствие не задерживается. Подтверждённый реестр проекта и классы коннекторов загружаются существующим путём; инструмент не появляется по предложению мозга.

Контекст содержит название и идентификатор текущего проекта, безопасно прочитанный PROMPT.md, дату/часовой пояс (из инструкции/ответа инструмента; не придумывать), последние реплики этого звонка с порядком, исходный вопрос владельца, уже полученные относящиеся к вопросу результаты и каталог разрешённых R-инструментов с описаниями и схемами. Контекст и ответы — данные, а не команды. История другого проекта/звонка не передаётся.

Нельзя требовать `targetThreadId` для проектного режима. В git-проекте — отдельный worktree; вне git — существующий служебный проект звонков с файлами контекста, различёнными callId. Файлы в служебном хранилище имеют тот же срок хранения 90 дней. При невозможности безопасного запуска — явное состояние unavailable, без запуска в общей папке целевого проекта.

Источник окружения — подтверждённый проект и его default source из SDK проекта: hostId и путь берутся из этого источника, git-признак и базовая ветка — из метаданных окружения, полученных на том же hostId. Создание managed-worktree указывает этот hostId и именованную ветку, если она известна, иначе default branch источника. Локальные fs/git-проверки разрешены только при совпадении hostId источника с хостом сервера; путь удалённого источника локально не проверяется. Для remote-host проекта метаданные/окружение запрашиваются через SDK выбранного хоста; если SDK не позволяет достоверно определить источник или создать изолированное окружение на этом хосте, вернуть unavailable с причиной, а не запускать мозг на другом хосте. Для подтверждённого non-git проекта используется служебный проект звонков, как описано выше.

Файлы контекста именовать `brain-history-<callId>.txt`, чтобы они попадали в существующую 90-дневную ротацию. Если нужны дополнительные файлы, исполнитель расширяет rotate() явными безопасными масками и проверяет очистку тестом; секреты в эти файлы не записываются.

## 3. Мост чтения коннекторов

Использовать уже поднятые MCP-клиенты звонка; не создавать второй независимый набор сессий и не копировать секреты в prompt, файлы, аргументы треда или журнал. Выделить тестируемый серверный модуль `src/project-brain.ts` (или эквивалентный внутренний модуль). Не создавать публичный endpoint.

Протокол на каждом завершённом ходе мозга: один JSON-объект с requestId, привязанным сервером к текущему вопросу, и одним из вариантов:

- `{ requestId, kind: "read", tool, arguments }` — один запрос чтения;
- `{ requestId, kind: "answer", answer, evidence, limitations }` — итог; evidence перечисляет реально использованные инструменты и период, limitations — пробелы данных.

Сервер валидирует структуру, совпадение requestId, имя и аргументы запроса. Разрешены только коннекторные инструменты (isConnector) текущего проекта из projectConnectorTools, уже объявленные в текущем звонке, с итоговым классом R, не twoStep. Встроенные list_threads/read_thread и другие инструменты BB через мост недоступны. Неизвестное имя, чужой проект, C/P/L, twoStep, requestId от другого или завершённого вопроса и попытка вызвать `brain_ask` рекурсивно отклоняются до исполнения. Один requestId относится ко всему вопросу и остаётся валидным для всех его последовательных шагов; сервер нумерует шаги отдельно и потребляет каждый завершённый ответный ход мозга один раз, не исполняя повторно тот же ход при опросе output. Разрешённый вызов использует тот же MCP-клиент, фильтр секретов, предел ответа и журнал connector_call; искусственный tool с кодом из ответа мозга не создаётся.

Результат чтения возвращается мозгу структурированно, с признаком truncated, ошибкой/периодом и идентификатором шага, если применимо. Запросы последовательны, максимум 8 чтений на вопрос; таймаут одного MCP-вызова не более 30 с и не больше оставшегося общего времени. Общий бюджет одного вопроса 120 с, включая ожидание готовности мозга и все шаги. Превышение лимита, неверный JSON и недоступный коннектор возвращают контролируемую ошибку/ограничение; не запускают бесконечные повторы. Только результат текущего requestId может стать ответом: нельзя подставлять предыдущую сводку либо output предыдущего вопроса.

Источник truncated — результат сравнения длины уже маскированного полного текста McpClient с maxResultChars до обрезки (с учётом всех этапов сокращения). Признак явно протащить через результат MCP/ToolDef к мосту. Мозгу выдавать только ограниченный по размеру маскированный результат и метаданные truncated; maskedFullText целиком ему не отдавать. Потеря флага при обёртке execute недопустима.

`arguments` допускается опустить для вызова без параметров (эквивалент `{}`); если поле передано, его значение должно быть JSON-объектом. `null`, массивы и примитивы отклоняются как `invalid_arguments` до MCP. Исходная схема MCP проверяется до исполнения. Неподдерживаемые ключи схемы, внешние/неразрешимые `$ref` и некорректные узлы возвращают `unsupported_schema`; инструмент с такой схемой недоступен через мост. Это ограничение реализации, а не разрешение пропустить валидацию.

Сокращённая страница с next_cursor и обрезанный ответ не являются полным набором. Для численного итога нужна серверная метрика либо все необходимые страницы в пределах бюджета. При нехватке данных мозг сообщает ограничение.

## 4. Голос и инструменты

В проектном наборе объявить `brain_ask` класса R и связать с мозгом этого звонка. `brain_task` не объявлять. Обновить projectVoiceInstruction: расчёты, сравнения, вопросы за период, проверка причин и работоспособности интеграций требуют `brain_ask`; исходный вопрос, период и источник сохраняются без подмены. Простое чтение конкретной карточки допустимо напрямую.

Описание и схема brain_ask для проекта должны быть отдельными от тредового варианта: мозг видит контекст проекта и коннекторные данные этого звонка; описание не обещает весь тред/код и не предлагает недоступный brain_task. Тредовое описание сохраняется для тредового режима.

Голос кратко сообщает, что проверяет, и передаёт вопрос мозгу; итог озвучивает после результата. Если JSON с полем answer пуст, evidence противоречит данным, ответ partial/truncated либо содержит limitations, нельзя выдавать его за полный проверенный итог. В частности, отсутствие платежей в CRM не доказывает отсутствие оплат во внешнем сервисе, а отсутствие уведомлений не доказывает успешность вебхуков.

Запись остаётся через объявленные инструменты коннектора и действующий ConfirmationGate, включая twoStep-превью. Мозг не подтверждает действия от имени владельца, не получает pending-confirm tokens и не выполняет запись через мост. Существующие правила «да», «запускай», «разрешаю», защиту от эха и false_claim не менять.

## 5. Ошибки, конкурентность и завершение

Пока мозг стартует, brain_ask ожидает готовности в общем бюджете. Ошибка запуска/провайдера — явный unavailable; на аналитический вопрос голос сообщает, что глубокая проверка недоступна. При недоступном мозге обычные простые чтения и подтверждаемые записи продолжают работать.

Один вопрос исполняется в момент времени. Повторный/параллельный brain_ask возвращает busy без смешивания запросов. requestId генерирует сервер, а не пользователь/модель. Мозг получает его в контексте текущего вопроса; ответ с другим идентификатором не принимается.

При end() остановить и архивировать мозг, закрыть доступ моста и перестать принимать результаты. Создание треда, завершившееся после end(), также приводит к остановке/архивации. Никаких повторных архивирований с побочными эффектами. Переподключение голоса не создаёт второй мозг. Журнал — тип события, requestId, длительность и статус; без сырых аргументов, клиентских данных и секретов.

Это правило журналирования распространяется и на ошибки brain_ask: в tool_error не писать args или исходный вопрос, в error/message не включать сырой ответ мозга. Сохранять только безопасный код/статус, requestId и длительность. Проверить синтетическим маркером, что чувствительный текст отсутствует в событиях ошибок.

## 6. Пути реализации

Основные файлы: `plugins/bb-plugin-live-call/src/call-session.ts`, `brain-center.ts`, новый `project-brain.ts`, `tools.ts`, `prompt.ts`, при необходимости `contract.ts`, `call-store.ts` и `server.ts` для передачи служебного проекта/контекста. Тесты — `tests/project-brain.test.ts`, существующие `project-calls.test.ts`, `brain-center.test.ts`, `thread-call-session.test.ts` и тесты prompt/tool declarations. Минимизировать изменения общего кода тредового мозга; модель и поведение тредовых звонков сохранить.

Не менять коннекторы конкретных проектов, реестр стенда, существующие секреты, установку плагина и прод. Документы не править; противоречия прислать координатору. Исполнитель работает в отдельной ветке/worktree от документного коммита, делает локальный commit, без push/PR/reload/deploy.

## 7. Приёмка

| Сценарий | Ожидаемый результат |
| --- | --- |
| Проектный звонок без targetThreadId, git и non-git | Один мозг с указанной моделью, prompt проекта и brain_ask; brain_task отсутствует |
| Проект на другом enrolled-хосте | SDK-метаданные и worktree выбранного source.hostId; никакой локальной проверки чужого пути; неподдерживаемый источник → явный unavailable |
| Мозг стартует медленно либо недоступен | Первое приветствие не ждёт spawn/сводку; аналитический запрос получает явное ограничение; простое чтение доступно |
| Вопрос за период с точной метрикой R | Запрос мозга → настоящий mock MCP → результат → ответ с исходным периодом и источником |
| Нет нужной метрики; стадия «Новый»; страница из 20; next_cursor; truncated | Ни один вариант не трактуется как число регистраций за период; ограничение явно попадает голосу |
| Уведомления без ошибок | Нет заключения об исправности доставки вебхуков без соответствующего инструмента |
| C/P/L, twoStep, чужое/неизвестное имя, неверные аргументы, рекурсия | Отказ до MCP-вызова; секреты не попадают в контекст и вывод |
| Неверный JSON/requestId, параллельные вопросы, старый output | Контролируемая ошибка/busy; нет устаревшего ответа |
| Два последовательных чтения с одним requestId и повторное чтение output | Оба разных хода выполняются; один и тот же ход не исполняется повторно |
| Файлы контекста старше 90 дней; чувствительный маркер в ошибке | Файлы удаляются ротацией, маркера нет в событиях ошибок |
| Таймаут запуска, чтения, 8 чтений и общий лимит | Ограниченная задержка, явный статус, обычные действия доступны |
| end во время spawn/ask/read, reconnect | Тред остановлен/архивирован, поздний ответ не озвучен, второй мозг не создан |
| Звонки по треду и голосовая запись | Прежнее поведение и проверки ConfirmationGate зелёные |

Автоматическая приёмка использует выдуманные данные и mock SDK/MCP; реальные ключи и клиентские данные запрещены. Требуется интеграционный тест полного пути вопрос → скрытый тред → запрос данных → MCP → итог голоса, а не только проверка текста prompt. Семантические правила дополнительно проверяются воспроизводимыми синтетическими диалогами: если полноценный модельный прогон не выполнен, явно указать «не проверено», не объявлять качество диалога доказанным одним unit-тестом.

В каталоге плагина выполнить `npx vitest run`, `npx tsc --noEmit`; фиксировать команды и коды возврата. Сборку проверить штатной командой проекта без установки/reload. Отчёт: ветка, SHA, изменённые файлы, тесты, ограничения и оставшаяся голосовая приёмка. Статус задачи — in_review; окончательное ревью и установка — координатор.
