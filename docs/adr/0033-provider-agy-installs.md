# provider-agy — параллельные установки agy и привязка аккаунтов

## Контекст

1. В текущей архитектуре `provider-agy` все аккаунты пула запускаются через один и тот же исполняемый файл `agy`, путь к которому определяется глобально (`resolveAgyCommand`: `AGY_PATH` → `~/.local/bin/agy` → `PATH`). Хотя каждый тред работает в отдельном процессе, они делят общий бинарник на диске, единый цикл автообновлений и общие системные каталоги вне папки аккаунта.
2. Появилась необходимость разнести нагрузку между как минимум двумя независимыми установками бинарника `agy` на одной машине (например, основная и дополнительная установки из разных каталогов), привязав определенные аккаунты пула к конкретным установкам.
3. Уточнение владельца 18.11: цель — разнесение нагрузки по двум бинарникам, а не версионирование. По умолчанию версии установок совпадают; разные версии допустимы, но не являются основным сценарием. При этом логика пула (ранжирование `priority`, LRU, пригодность по моделям §2.3, ротация по квоте) должна оставаться полностью единой: аккаунты одного тарифа в разных установках взаимозаменяемы.

## Решение

1. **Реестр установок (`agy-installs.json`):**
   - Вводится локальный файл конфигурации инстанса `<dataDir>/agy-installs.json`.
   - Файл содержит словарь `installs` с именами (`[a-z0-9-]{1,32}`), абсолютными путями к бинарникам `bin` и опциональными переменными окружения `env` для изоляции кэша и путей обновления.
   - Поле `default` задает имя **основной установки**; остальные записи являются **дополнительными**.
   - Файл локален для машины (keeper его не синхронизирует).
2. **Обратная совместимость без реестра:**
   - При отсутствии `agy-installs.json` поведение байт в байт совпадает с прежним: действует единственная неявная установка `default`, использующая `resolveAgyCommand(process.env)`.
3. **Привязка аккаунта (`accounts-state.json`):**
   - Привязка хранится в общем файле `accounts-state.json` в поле `accounts[label].install`.
   - Поле подчиняется тем же правилам, что `priority` (§2.2): общее (shared-owned), редактируется оператором, при записи `saveLedger` перечитывается с диска, в `accounts-overlay.json` не попадает.
   - Отсутствие поля `install` означает привязку к установке `default` (новый аккаунт по умолчанию привязывается к основной установке без записи поля).
   - Спутник получает имя установки через синк `accounts-state.json`, а путь к бинарнику берет из своего локального реестра `agy-installs.json`.
4. **Строгий запуск без подмены:**
   - Каждый процесс от имени аккаунта запускается строго бинарником назначенной ему установки во всех точках кодовой базы (сессия ACP, ротация, resume, восстановление неизвестного треда, пробы моделей, usage-pro).
   - Сессии прямого режима без аккаунта (`direct`, `relay`) используют установку `default`.
   - Если установка аккаунта не найдена в реестре или бинарник недоступен: аккаунт исключается из кандидатов на этапе `pickAccount`. Возобновление закрепленного треда переходит на сиблинга либо завершается честной ошибкой. Неявная подмена другим бинарником категорически запрещена.
5. **Единый пул и ротация:**
   - Выбор аккаунта в `pickAccount` установку не учитывает: ранжирование тиров по `priority` и LRU внутри тира работают сквозным образом по всем установкам.
   - Ротация между установками разрешена: при исчерпании квоты на аккаунте одной установки тред переходит на свободного сиблинга другой установки и продолжается её бинарником.

Контракт спецификации — [docs/specs/provider-agy-installs.md](../specs/provider-agy-installs.md).

## Последствия

- Нагрузка процессов и дискового ввода-вывода распределяется между независимыми бинарными файлами.
- Пользователь и демон BB видят единый пул моделей и аккаунтов без дробления интерфейса.
- Служебное окружение (`env`) каждой установки позволяет изолировать временные каталоги и кэши (`XDG_CACHE_HOME`, `TMPDIR`), устраняя взаимное влияние параллельных процессов.
- При старте плагина регистрируются и логируются версии всех установок; при расхождении версий в лог пишется информационное предупреждение.
- Вторая установка разводит бинарники, обновления и локальное состояние ОС, но не скрывает от Google принадлежность аккаунтов одной машине/IP (сетевая изоляция решается файлами `proxy` у каждого аккаунта).

## Отклонённые варианты

1. **Второй экземпляр плагина или отдельный BB-провайдер (`provider-agy-alt`):**
   - Отклонено: разрывает единый пул аккаунтов. Потребовало бы дублирования настроек, раздельных очередей ротации, ручного выбора провайдера пользователем в UI и разрушило бы единую прозрачную ротацию при исчерпании квот.
2. **Отдельные пользователи ОС или контейнеры:**
   - Отклонено: чрезмерная эксплуатационная сложность на выделенном сервере. Ломает прямой доступ к файлам рабочей копии проекта, локальные хуки, права доступа к ssh/git и требует сложной межпроцессной авторизации.
3. **Переключение активного бинарника через симлинк в файловой системе:**
   - Отклонено: глобальная мутация симлинка несовместима с параллельно работающими тредами разных аккаунтов, приводит к race condition и нарушает требование строгой изоляции процессов.
