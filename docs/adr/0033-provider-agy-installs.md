# provider-agy — параллельные установки agy и привязка аккаунтов

## Контекст

1. В текущей архитектуре `provider-agy` все аккаунты пула запускаются через один и тот же исполняемый файл `agy`, путь к которому определяется глобально (`resolveAgyCommand`: `AGY_PATH` → `~/.local/bin/agy` → `PATH`). Хотя каждый тред работает в отдельном процессе, они делят общий бинарник на диске, единый цикл автообновлений и общие системные каталоги вне папки аккаунта.
2. Появилась необходимость разнести нагрузку между как минимум двумя независимыми установками бинарника `agy` на одной машине (например, основная и дополнительная установки из разных каталогов), привязав определенные аккаунты пула к конкретным установкам.
3. Уточнение владельца 18.11: цель — разнесение нагрузки по двум бинарникам, а не версионирование. По умолчанию версии установок совпадают; разные версии допустимы, но не являются основным сценарием. При этом логика пула (ранжирование `priority`, LRU, пригодность по моделям §2.3, ротация по квоте) должна оставаться полностью единой: аккаунты одного тарифа в разных установках взаимозаменяемы.

## Решение

1. **Реестр установок (`agy-installs.json`):**
   - Вводится локальный файл конфигурации инстанса `<dataDir>/agy-installs.json`.
   - Файл содержит словарь `installs` с именами (`[a-z0-9-]{1,32}`), абсолютными путями к бинарникам `bin` и опциональными переменными окружения `env` для изоляции кэша и путей обновления. `env` установки кладётся первым слоем окружения запуска, ключи плагина, шима и аккаунта — поверх него. Ключи, управляемые плагином, шимом и аккаунтом (`HOME`, `ELECTRON_RUN_AS_NODE`, `GEMINI_API_KEY`, `GOOGLE_GEMINI_BASE_URL`, прокси-ключи `HTTP(S)_PROXY`/`ALL_PROXY`/`NO_PROXY` в обоих регистрах и весь префикс `AGY_*` — включая `AGY_SHIM_*`, `AGY_DISABLE_*` и процессные `AGY_PATH`/`AGY_TRANSPORT`/`AGY_ACCOUNTS`/`AGY_CLIPROXY*`), в `env` запрещены: их присутствие делает реестр невалидным — ошибка схемы, запуски не выполняются.
   - Поле `default` задает имя **основной установки**; остальные записи являются **дополнительными**.
   - Файл локален для машины (keeper его не синхронизирует).
2. **Обратная совместимость без реестра:**
   - При отсутствии `agy-installs.json` поведение байт в байт совпадает с прежним: действует единственная неявная установка `default`, использующая `resolveAgyCommand(process.env)`. Единственное отличие — аккаунт с заданным `install` (приехал синком) на машине без реестра недоступен локально (см. Последствия).
3. **Привязка аккаунта (`accounts-state.json`):**
   - Привязка хранится в общем файле `accounts-state.json` в поле `accounts[label].install`.
   - Поле подчиняется тем же правилам, что `priority` (§2.2): общее (shared-owned), редактируется оператором, при записи `saveLedger` перечитывается с диска, в `accounts-overlay.json` не попадает.
   - Отсутствие поля `install` означает привязку к установке `default` (новый аккаунт по умолчанию привязывается к основной установке без записи поля).
   - Спутник получает имя установки через синк `accounts-state.json`, а путь к бинарнику берет из своего локального реестра `agy-installs.json`.
   - Путь добавления аккаунта один для обеих установок — единая команда оператора `scripts/add-account.mjs --label <метка> [--install <имя>]`: берет бинарник установки из реестра (без флага — основная) и запускает родной вход (`HOME=<staging> <бинарник установки>`) в интерактивном терминале во **временный каталог вне `accounts/`**; после успешного входа записывает привязку и проверяет её чтением с диска ещё в staging, затем атомарным `rename` делает аккаунт видимым пулу и перепроверяет привязку; при провале проверки каталог немедленно возвращается в staging и цикл «запись → проверка → rename» повторяется; при исчерпании попыток записи — отказ с откатом: каталог уже убран из `accounts/` в staging, staging удаляется, иначе аккаунт без `install` был бы виден пулу как привязанный к основной установке и запустился бы чужим бинарником. Тот же откат действует и при импорте токенов (`import-accounts.mjs --install`). Гонки записи общего файла закрывает advisory lock-файл `<dataDir>/accounts-state.lock` (захват созданием файла с `O_EXCL`, в файле — pid держателя, время захвата `atMs` и случайный `nonce`; lock покрывает всю операцию `saveLedger` — чтения дискового состояния для слияния и записи `conversations-state.json`, `accounts-overlay.json` и `accounts-state.json`; зависший lock — pid не существует или возраст >60 с по `atMs`, при нечитаемом файле по mtime — снимается под отдельным сериализующим файлом `accounts-state.lock.break`, захватываемым `O_EXCL` (зависший break — pid держателя не существует **и** mtime старше 30 с — снимается прямым `unlink` после повторного stat, вложенный сериализатор не вводится): под ним lock перечитывается и удаляется только при совпадении `pid`/`atMs` с прочитанными до захвата break'а, при несовпадении break отпускается и цикл захвата повторяется — ни параллельный `O_EXCL`-захват третьего процесса, ни второй снимающий не могут унести чужой свежий lock при соблюдении протокола (остаточное окно — в Последствиях); снятие своего lock'а в `finally` удаляет файл только при совпадении `pid`+`atMs`+`nonce` со своими; ожидание `saveLedger` ограничено десятками миллисекунд — event-loop обёртки не блокируется, по таймауту вся запись пропускается до следующего сохранения, а при штатном завершении (хуки `onClose`/`onSigterm`/`onSigint` моста — новый код, попытка идёт до передачи в `shutdown` моста) обёртка выполняет одну попытку сохранения под тем же lock'ом; команды по таймауту отказывают): все записи `accounts-state.json` — `saveLedger` обёртки и команды оператора — проходят через него, и слепок, снятый до записи `install`, не может быть записан поверх неё; дополнительно при записи общего файла записи меток, которых нет в памяти, переносятся с диска целиком — слепок пула не роняет новую метку вместе с `install`. `import-accounts.mjs --install` и перепривязка `--rebind` остаются вторичными путями; при неизвестном имени установки обе команды отказывают, ничего не записывая.
   - Все команды записи общего файла (`add-account.mjs`, `import-accounts.mjs --install`, `--rebind`) выполняются **только на инстансе-владельце пула**: keeper синкает `accounts-state.json` односторонне владелец→спутник, и запись спутника стирается за ~30 с — аккаунт молча ушёл бы в основную установку и запускался бы чужим бинарником. На спутнике команды отказывают по пустому маркеру `<dataDir>/pool-satellite`, который выставляет оператор.
4. **Строгий запуск без подмены:**
   - Каждый процесс от имени аккаунта запускается строго бинарником назначенной ему установки во всех точках кодовой базы (сессия ACP, ротация, resume, восстановление неизвестного треда, пробы моделей, usage-pro).
   - Сессии прямого режима без аккаунта (`direct`, `relay`) используют установку `default`.
   - Если установка аккаунта не найдена в реестре или бинарник недоступен: аккаунт исключается из кандидатов на этапе `pickAccount`. Возобновление закрепленного треда переходит на сиблинга либо завершается честной ошибкой. Неявная подмена другим бинарником категорически запрещена.
5. **Единый пул и ротация:**
   - Выбор аккаунта в `pickAccount` установку не учитывает: ранжирование тиров по `priority` и LRU внутри тира работают сквозным образом по всем установкам.
   - Ротация между установками разрешена: при исчерпании квоты на аккаунте одной установки тред переходит на свободного сиблинга другой установки и продолжается её бинарником.

Контракт спецификации — [docs/specs/provider-agy-installs.md](../specs/provider-agy-installs.md).

## Последствия

- Нагрузка процессов и дискового ввода-вывода распределяется между независимыми бинарными файлами.
- Пользователь и демон BB видят единый пул моделей и аккаунтов без дробления интерфейса.
- Служебное окружение (`env`) каждой установки позволяет изолировать временные каталоги и кэши (`XDG_CACHE_HOME`, `TMPDIR`), устраняя взаимное влияние параллельных процессов.
- При старте плагина регистрируются установки из реестра; версии кэшируются по (путь, mtime, размер) файла бинарника, при расхождении версий в лог пишется информационное предупреждение.
- Битый реестр (`agy-installs.json` не разбирается, не проходит схему или `default` не указывает на запись) — громкая ошибка: не запускаются ни аккаунты пула, ни сессии direct/relay, `thread/start` падает с указанием причины; тихого отката к неявной установке нет.
- Отсутствующий или неисполняемый бинарник — не «битый реестр», а локальная недоступность конкретной установки (проверяется перед каждым запуском, а не при загрузке реестра): недоступны только аккаунты этой установки, а у `default` — ещё и `direct`/`relay`; остальной пул работает.
- Аккаунт с заданным `install` на машине без реестра (или без записи с таким именем) недоступен локально: привязка приезжает синком, а применить её не к чему — такой аккаунт исключается из выбора до появления реестра с тем же именем.
- Запись привязки возможна только на владельце пула: команды на спутнике отказывают по маркеру `<dataDir>/pool-satellite`, потому что keeper-синк стёр бы её за ~30 с и аккаунт молча ушёл бы в основную установку. Спутник, у которого оператор не выставил маркер, этой защиты не имеет — маркер входит в порядок включения (§12 спеки).
- Записи общего файла упорядочены advisory lock-файлом `<dataDir>/accounts-state.lock`, покрывающим всю операцию `saveLedger` (чтения дискового состояния для слияния и записи `conversations-state.json`, `accounts-overlay.json`, `accounts-state.json`): блокировку обязаны брать все писатели (`saveLedger` и команды оператора), читателей она не замедляет; `saveLedger` ждёт захвата не дольше десятков миллисекунд и по таймауту пропускает запись целиком (изменения остаются в памяти до следующего сохранения, а при штатном завершении обёртки — до одной итоговой попытки сохранения под тем же lock'ом), команды по таймауту отказывают; зависший lock снимается под сериализующим `accounts-state.lock.break` с перечитыванием и сверкой `pid`/`atMs` (зависший break — только мёртвый pid держателя и mtime >30 с), а `finally` удаляет lock только по совпадению `pid`+`atMs`+`nonce` со своими — при соблюдении протокола ни гонка трёх захватчиков, ни позднее снятие бывшего держателя не травмируют чужой свежий lock. Писатель вне блокировки её не уважает — на владельце, где выполняются команды, это ручная правка оператора и сторонний процесс (keeper синкает общий файл только на спутник, на владельце не пишет), — поэтому у команды добавления остаются повторная проверка привязки и откат.
- Остаточное окно advisory-протокола — известное ограничение v1 (ядерная блокировка `flock` сознательно не вводится — нативная зависимость вне объёма): чужой свежий lock может быть снят, если держатель break'а умер внутри break-секции и два снимающих пришли одновременно, либо если живой держатель lock'а удерживает его дольше 60 с (SIGSTOP, своп) — тогда возможны два писателя на микроокно. Ущерб ограничен: `saveLedger` перечитывает `install`/`priority` с диска при каждой записи, у `add-account.mjs` есть повторная проверка и откат; у `--rebind` потерянное обновление теоретически возможно при микроскопической вероятности окна.
- Вторая установка разводит бинарники, обновления и локальное состояние ОС, но не скрывает от Google принадлежность аккаунтов одной машине/IP (сетевая изоляция решается файлами `proxy` у каждого аккаунта).

## Отклонённые варианты

1. **Второй экземпляр плагина или отдельный BB-провайдер (`provider-agy-alt`):**
   - Отклонено: разрывает единый пул аккаунтов. Потребовало бы дублирования настроек, раздельных очередей ротации, ручного выбора провайдера пользователем в UI и разрушило бы единую прозрачную ротацию при исчерпании квот.
2. **Отдельные пользователи ОС или контейнеры:**
   - Отклонено: чрезмерная эксплуатационная сложность на выделенном сервере. Ломает прямой доступ к файлам рабочей копии проекта, локальные хуки, права доступа к ssh/git и требует сложной межпроцессной авторизации.
3. **Переключение активного бинарника через симлинк в файловой системе:**
   - Отклонено: глобальная мутация симлинка несовместима с параллельно работающими тредами разных аккаунтов, приводит к race condition и нарушает требование строгой изоляции процессов.
