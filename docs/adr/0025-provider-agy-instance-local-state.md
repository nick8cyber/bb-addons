# provider-agy — локальное состояние инстанса

## Контекст

На одном хосте живут два bb-инстанса на одном пуле Google-аккаунтов (владелец и орнелла). Инфраструктурный keeper `bb-token-keeper` синкает `accounts-state.json` односторонне владелец→спутник (~30 с + inotify) — так спутник видит метки пула. Но в файле смешаны два вида данных с разной природой синка: общие метки аккаунтов и то, что каждый инстанс пишет сам — пины `providerThreadId→account` и метки от собственных ошибок (429-cooldown, lastUsed, парковки). Любая запись спутника стирается следующей синхронизацией.

Инцидент 11.11 (тред `thr_vff52cr5vy`, «встреча идёт», инстанс orn): сессия создана 09:22Z на `djelsotv.ru`, пин записан в её файл и стёрт синком. Resume в 12:28Z не нашёл владельца → запуск на дефолтном HOME → `not_found: trajectory not found` — хотя траектория жива в копии HOME нужного аккаунта на том же инстансе. Подтверждено системно: все свежие пины спутника в общем файле отсутствуют.

## Решение

Состояние разделено по природе синка:

- `accounts-state.json` — только `accounts` (метки пула; синкается как раньше).
- `conversations-state.json` — пины бесед, per-instance; resume всегда происходит на инстансе-создателе, поэтому пин локален по построению. Миграция — union при чтении с legacy-полем общего файла; общий файл поле теряет при первой записи.
- `accounts-overlay.json` — тень меток, выставленных этим инстансом. Эффективная метка = merge: числовые поля — max обеих сторон, метки — со свежей стороны; overlay применяется, пока `writtenMs >= shared.lastUsedMs` по аккаунту (свежая общая активность снимает тень целиком — снятие парковки владельцем доезжает).

API `accounts.ts` для вызывающих не меняется — слитое состояние собирается в `loadLedger`/`saveLedger`; stream-json мост получает то же поведение без правок вызовов.

## Отвергнуто

- **Слияние внутри keeper** (двусторонняя сводка `accounts-state`): keeper — рутовый защищённый скрипт с валидацией JSON и атомарной записью; логика «чей кулдаун/парковка побеждает» расширяет его поверхность, а ошибка слияния портит состояние обоих инстансов разом. К тому же freshness-правила для снятия тени — это ровно та же логика overlay, только внутри инфраструктурного скрипта.
- **Симлинк `accounts-state` на файл владельца**: `saveLedger` атомарен через temp+rename — rename подменяет сам симлинк при первой же записи спутника, связь рвётся; плюс меж-uid права и гонки load-modify-save без лока.
- **Пины в общем файле как есть**: каждый resume спутника после простоя >30 с падает — подтверждено инцидентом.

## Следствия

Resume спутника снова находит владельца беседы — `trajectory not found` по этой причине исчезает. Метки спутника (429-cooldown, auth-dead/eligibility-парковки) работают до истечения, а не ~30 с. Владелец по-прежнему не видит меток спутника — принято: реальную квоту режет Google, метка владельца о том же аккаунте приедет к спутнику через общий файл. Handoff треда на другой инстанс теряет пин — поведение как при промахе сегодня (запуск на дефолтном HOME, честный `trajectory not found`), регрессии нет.

## Границы (принято осознанно, аудит 11.11)

- **Тень снимается любой свежей shared-активностью**, не только «настоящим» снятием парковки: `markAccountUse` владельца на той же метке поднимает `shared.lastUsedMs` и гасит живой кулдаун спутника до `untilMs`. Спутник-специфичные причины (свой proxy/egress) поэтому могут мигать 429→метка→снятие. Альтернативы хуже: у общего файла нет метки «когда сторона писала», а «не снимать пока жив кулдаун» ломает протокол ручной разпарковки, который как раз построен на бампе `lastUsedMs`. Самозаживление остаётся честным для реальной квоты Google — она сгорит и у владельца.
- **Merge-on-save по полям, а не целиком по `writtenMs`**: первая редакция перезаписывала запись overlay целиком — свежий штамп со stale-содержимым стирал кулдаун соседнего враппера (блокер аудита). Числовые поля — max с дисковой записью, метки — с более свежей; локально метки только растут, поэтому max безопасен. Пины пишутся по `dirtyPins` (только изменённые ключи) — stale-слепок не вернёт чужой перепин. Две поправки по финальному аудиту: снятая тень (`writtenMs < shared.lastUsedMs`) в merge не участвует вообще — считается отсутствующей, иначе `max()` воскрешал мёртвый кулдаун; свежесть строк (`parkedReason`/`lastError`) считается per-record по `overlayStamp` — мутация одной строки бампит обе, окно равно латентности save, принято как тот же LWW-класс.
- **«Призраки» вычищаются**: overlay-запись на метку, которой нет ни в общем файле, ни в `accounts/`, удаляется при save — иначе мусор утекал бы в общий файл и оттуда синком на все инстансы.
- **Откат версии теряет пины**: общий файл `conversations` больше не несёт; откат происходит вместе с локальными файлами или с честной потерей пинов (resume промахивается как раньше).
- Окно read→rename в merge-on-save и `*.pid.tmp` при креше — тот же класс, что был у temp+rename общего файла; без локов и GC.
- **Torn-read**: тень, живая на `load`, но снятая между `load` и `save` (keeper-синк попал внутрь ~мс-окна синхронного load→mutate→save), кратко воскрешает свои числа — in-memory entry уже смержен и гейт на диске её не отсечёт. Отличить унаследованные поля от своих без per-field provenance нельзя — не делаем: окно микросекундное, а следующая активность владельца по метке снова поднимет `lastUsedMs` и снимет тень сама.
