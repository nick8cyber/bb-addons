# Voice STT — захват микрофона: выбор устройства, тёплый микрофон, запасной режим

## Контекст

Живой ввод `voice-stt` захватывает звук в браузере (`getUserMedia` + Web Audio worklet → PCM16 16 кГц → WebSocket → Gemini Live). При реальном использовании 07.11 вскрылись проблемы, которых не было видно в эмуляции:

- **Мак брал микрофон iPhone.** macOS через Continuity делает микрофон соседнего iPhone входом по умолчанию. `getUserMedia` без `deviceId` открывал его: запись шла, звука не было. Нативные приложения берут встроенный микрофон.
- **Задержка старта.** От нажатия до первого звука проходило 780–945 мс на iPhone и 680–875 мс на Mac. Это включение микрофона ОС. Пока оно шло, начало фразы терялось.
- **Зависание на iPhone.** После прерывания аудиосессии (звонок, Siri, чужой звук, блокировка) iOS WebKit оставляет `AudioContext` в состоянии `running`, но граф не рендерит ни кадра до перезапуска приложения. Плашка висела на «Включаю микрофон…», на сервер уходило 0 КБ. Нативный микрофон bb при этом работает. Предположительно он пишет через `MediaRecorder` — это не проверено.
- **Перенос кнопки на iOS.** Старт `getUserMedia` на касании подвешивал отрисовку: кнопка не ехала за пальцем.

## Решение

1. **Выбор входа.**
   - На десктопе вход выбирается явно. Исключаются iPhone, iPad, Continuity и виртуальные входы. Порядок: запомненное рабочее устройство → `default`, если это не iPhone → встроенный → первый оставшийся.
   - Ручной выбор — раздел настроек плагина «Микрофон». Хранится в `localStorage`, свой на каждом устройстве. Ищется по id, затем по метке.
   - На самом iPhone берётся системный вход по умолчанию.
2. **Тёплый микрофон** (`micWarmSeconds`, по умолчанию 30 с).
   - После записи цепочка паркуется: звук идёт только в кольцевой буфер ~0,5 с в памяти. Следующая запись подхватывает живой микрофон без `getUserMedia` и начинается с буфера.
   - ~0,5 с звука до касания уходят на распознавание. Индикатор микрофона ОС горит всё окно.
   - Гасится сразу: при 0 в настройке, смене микрофона, уходе в фон и выключении живого ввода.
3. **Предзахват на касании (touch).**
   - На касании будится только `AudioContext` (в жесте, требование iOS).
   - Если палец 120 мс не сдвинулся, поднимается микрофон, и звук копится. Перенос начинается раньше 120 мс и микрофон не трогает.
   - Мышь и трекпад стартуют запись сразу на нажатии.
4. **Самовосстановление.**
   - Сторож следит за захватом: нет кадров 1,5 с, одни нули с начала, дорожка `ended`.
   - Перезапуск — всегда новый поток и новый `AudioContext`.
   - Touch: после одного неудачного перезапуска — **запасной захват `MediaRecorder`**. Web Audio помечается мёртвым до перезагрузки страницы, следующие записи сразу идут запасным захватом.
   - **Потоковый вариант (0.1.25, основной).** MediaRecorder режет запись кусками по 400 мс. Весь накопленный файл раскодируется `decodeAudioData` в `OfflineAudioContext` 16 кГц: звуковой вывод для этого не нужен, а именно он отказал у Web Audio. Новые сэмплы уходят в ту же живую сессию Gemini, поэтому интеримы и финал остаются. Хвост ~64 мс держится до следующего куска из-за перекрытия кадров AAC/Opus и досылается перед `end`.
   - **Файловый вариант** — если раскодировать кусками не вышло 3 раза подряд. Живая сессия отменяется, по концу записи файл уходит в файловую цепочку (gemini → codex → groq) через RPC `liveFallback` с `mimeType`.
   - Десктоп: до трёх смен устройства, потом запасной режим.
   - Плашка показывает каждый шаг: «микрофон пропал — перезапускаю…», «микрофон перезапущен — жду звук…», «живого текста не будет — распознаю после записи».
5. **Диагностика.** Клиент шлёт кадры `diag`, сервер их логирует:
   - устройство и почему оно выбрано, частоты, путь захвата;
   - задержку «касание → первый звук», тёплый старт;
   - сбои, перезапуски, запасной режим;
   - объём звука каждой записи и причину каждой отмены.

## Отвергнутые варианты

| Вариант | Почему нет |
|---|---|
| `getUserMedia` без `deviceId` на маке | Continuity подставляет iPhone. |
| Выбор микрофона в серверной настройке | `deviceId` свои у каждого браузера и устройства. |
| Старт микрофона на касании без задержки | Подвисание переноса на iOS, индикатор при каждом переносе. |
| Переиспользовать `AudioContext` при перезапуске на iOS | После прерывания он «running», но молчит. |
| Сразу `MediaRecorder` всегда | Нет живого текста по ходу речи; Web Audio здоров в большинстве сессий. |
| Тёплый микрофон без звука до касания | Первое слово обрезается, если говорить вместе с тапом. |

## Последствия

- Последующие записи в окне тёплого микрофона стартуют мгновенно: на реальном iPhone первый звук через 7–8 мс после касания, против ~600–700 мс у холодного старта.
- Индикатор микрофона горит до 30 с после диктовки. ~0,5 с до касания попадают в запись: может захватиться хвост чужой фразы.
- Вероятная причина «мёртвого» Web Audio на iPhone — гипотеза, не подтверждена: аудиосессию занимает другое приложение (например, диктовка OmniFlow), iOS ставит звуковой вывод страницы на паузу, а захват `MediaRecorder` продолжает работать. По логу сбой временный, основной путь сам оживает через 20–40 с.
- В потоковом запасном режиме первый звук приходит на ~0,4–1 с позже обычного. Файловый вариант идёт без промежуточного текста и на 1–3 с дольше.
- 07.11 реальный сбой на iPhone подтвердил файловый запасной путь: `MediaRecorder` писал звук, файл распознался.
- Потоковый вариант, проверка в Chromium с имитацией iPhone:
  - звук уходит на сервер во время записи (78–170 КБ);
  - 08.11, повторный прогон на синтетической речи (espeak-ng): интеримы по ходу речи пришли («Нет, это проверка» → «Привет. Это проверка живого»), финал — от `gemini-live`, без файлового запасного пути;
  - отправленный звук (8 с) сохранён и сверен с исходником через `ffmpeg silencedetect`: паузы на тех же местах со сдвигом 0,06 с, провалов и повторов нет;
  - распознаётся только начало фразы, но так же распознаётся и сам исходный файл без захвата (`bb voice-stt transcribe`). Значит, дело в синтетическом голосе, а не в потоковом раскодировании;
  - на настоящем iPhone ждать в логе `client mic recorder stream:` и затем `live-session: finished with N` без `fallback`.
- Если раскодирование кусками отказывает 3 раза подряд в любой момент, в том числе после уже отправленных кусков, запись уходит файлом целиком (0.1.26).
- Диагностика доставки: сервер пишет итог `liveFallback`, клиент — итог вставки через RPC `clientLog`.
