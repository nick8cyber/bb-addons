# ADR-0041: Наблюдатель-сверка графа задач (PLUG-398)

## Контекст

Режим `shadow` (§32.1, ADR-0032, ADR-0039) должен был показать на живом потоке, совпадает ли ручная работа координаторов с графом, прежде чем включать `strict`. Журнал за 20.11 19:11 – 23.11 21:00 UTC (510 строк `task_transitions`) ответа не дал:

- 491 строка (96%) — `task-not-enqueued`. Спека запрещала неявную запись в очередь, а координаторы раздают напрямую. Графу не с чем сравнивать.
- 19 зеркал по 7 задачам очереди — 19/19 `would_reject`. Зеркало оценивает действие, но не продвигает узел. Каждая задача навсегда на `start`, любой следующий шаг — «не тот узел».
- `shadow_eval` для `run-queue` взял бы заново со `start` пять задач, уже закрытых в трекере, потому что статусы очереди не синхронизируются.
- Тот же день: гейт §31.9 по-разному работал на пути очереди и на прямом пути (GH-684, PLUG-397). Тесты проверяли только путь очереди.
- Обход `workGraphProjects = off` для growthhack держится бессрочно, пока его не снимут руками.

## Решение

Спека §32.5:

1. В `shadow` первый ручной `delegate` принимает задачу в очередь (`shadow-adopt`) сразу в фактическом узле. `run-queue` такие задачи в `shadow` не берёт.
2. После оценки зеркало следует в фактический узел (`shadow-follow`) по фиксированной таблице «действие → узел». Счётчики кругов ведутся так же, как в §28.1.
3. Каждое действие получает класс: `match`, `repeat`, `skip`, `graph-only`, `unmapped`. Класс считается по событию графа (переход матрицы §28.1 с учётом машинных узлов и шлюза владельца, первая раздача в узле), а не по равенству узлов. Зеркало не входит в `owner_gate`: вид одобрения определяется маршрутом и текущим узлом. `release-audit` не принимается и не зеркалируется.
4. Конечные статусы очереди синхронизируются с трекером (`shadow-sync`). Закрытая задача не может быть взята заново.
5. `bb orchestrator shadow-report` даёт числа по классам. Проект готов к `strict` при окне ≥ 48 ч, ≥ 3 полных циклах, `unmapped = 0`, `task-not-enqueued` ≤ 5%, `(match + repeat) / (match + repeat + skip + unmapped)` ≥ 90% (`graph-only` — отдельный счётчик) и разборе каждого `skip`. Переключение — слово владельца.
6. Переопределения `workGraphProjects` допускают срок (`until`). `off` — не дольше 24 ч. По истечении срока — автовозврат с событием и сообщением координатору.
7. Гейт §31.9 вызывается с одинаковыми входами на обоих путях. Тест параметризован по путям.

## Последствия

- Очередь `shadow`-проектов перестаёт быть «чистой»: в ней появляются принятые задачи с `payload.origin = 'shadow-adopt'`. Это осознанная замена прежнего правила §32.1.
- `strict` становится решением по числам, а не по ощущению. Пилот — `proj_at84bcu8q7` (`SMK`, `PLUG`).
- Узлы `checks` и `design_check` в ручном потоке не выполняются. Они учитываются как `graph-only` и включаются автоматически только в `strict`.
- Обход гейта больше не может «забыться»: срок обязателен для `off` по объектной записи, строковая бессрочная запись остаётся для совместимости и видна в отчёте.

## Отклонённые варианты

- **Включить `strict` сразу.** Граф заново начал бы закрытые задачи и остановил бы потоки, которые он не видел.
- **Оставить пассивное зеркало и разбирать журнал вручную.** 96% действий вне очереди — разбирать нечего.
- **Реконструировать историю задач задним числом.** Нарушает урок 8 (§5.6). Сверка начинается с момента выкладки.
