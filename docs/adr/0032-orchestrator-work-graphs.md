# ADR-0032: Граф работы задачи кодом (ревизия 34)

## Контекст

Аудит координатора за 16–18.11 (материалы аудита координатора в KB `projects/bb-orchestrator-work-graphs-plan.md`) показал: координатор, ведущий задачу «в голове», теряет поручения владельца (четыре пункта без спеки и задач), простаивает часами (6 часов 17.11, повторно 18.11), а спека растёт под уже написанный код (PLUG-293 — 17 отказов аудита, §26 вырос с 6,7 КБ до 18 КБ в ходе исполнения). Плагин был построен как набор инструментов, которые агент вызывает, когда вспомнит: порядок шагов держался на памяти модели, а не на коде.

Ошибка проектирования — та же, что описана в проекте жёсткого графа (KB `projects/bb-orchestrator-graph-architecture.md`): «задачу ведёт модель, а не код». Исправление — перевернуть управление: **задачу ведёт код, агент выполняет работу внутри узла и сдаёт результат**. Принципы взяты из открытой заметки agent-work-graphs (конспект — KB `projects/bb-orchestrator-work-graphs-plan.md`); семь уроков под конкретные провалы трёх дней — раздел 7 аудита координатора.

## Решения (ревизия 34, спека §27–§32)

1. **Узел задачи — запись в базе, а не текст хендоффа.** Таблица `task_queue` (очередь: `task_key`, `project_id`, `coordinator_thread_id`, `route`, `level`, `node`, `status`, `priority`, `depends_on`, `confirmation_mode`, `spec_sha`, `acceptance_sha`, `release_note`, `review_rounds`, `entered_at`, `deadline_at`, `deferred_by`, `deferred_reason`) и неизменяемый журнал `task_transitions` (`task_key`, `from_node`, `to_node`, `from_status`, `to_status`, `actor`, `reason`, `payload`, `created_at`). Узел вычисляется из журнала; `task_queue.node` — денормализованная копия. Отложить пункт очереди можно только явной командой/записью `bb orchestrator defer <KEY> --reason "<причина>"` от владельца.
2. **Детерминированный граф задачи:**
   `start → design → spec → spec_review → code → review → design_check → release → done`.
   Переход делает только код и только по доказательству: коммит, вердикт ревью, решение владельца, итог выкладки, таймаут будильника. На маршрутах `fix`, `docs`, `simple` узлы архитектора (`design`, `design_check`) автоматически пропускаются.
3. **Конвейер `run-queue` (сервис и CLI `bb orchestrator run-queue`):**
   - Фоновый сервис плагина, действующий от лица координатора задачи (`coordinator_thread_id`, роль `orchestrator`).
   - Автопереходы по событиям: сдача `spec` → автозапуск `spec_review` (web-gemini) → при OK → автозапуск `code` → сдача исполнителя (`done`) → автозапуск ревью по `reviewByLevel` → при `{"verdict":"OK","blockers":0}` → автозапуск `design_check` (для `feature`) → при OK → автозапуск `release` (с автоподстановкой `--kb "<заметка>"`) → `published` → автоочистка копий `taskCleanup` → взятие следующей задачи из `task_queue`.
   - Замечания ревью — возврат на доработку новым заходом; потолок — **3 круга**, дальше эскалация к архитектору или владельцу.
4. **Будильник на каждом узле, включая координатора.** У каждого узла — ответственный и срок из `policy.timing`; молчание и зависание — события с нарастающими напоминаниями N/3N/7N и эскалацией (склеено со сторожем координатора §5.6). Ход агента без вызова инструмента при незакрытом узле — не исход: «вопрос агента — не сдача», сторож возвращает узел в работу.
5. **Режимы одобрения `approvalMode`:**
   - Настройка проекта `approvalMode: "auto" | "manual"` (по умолчанию `manual` для `feature`, `auto` для `fix`/`docs`/`simple`) и колонка `task_queue.confirmation_mode`.
   - В режиме `manual` — ровно **одно** подтверждение владельца на задачу: шлюз перед выкладкой (переход `review / design_check → release`). Внутренние узлы проходят автоматически.
   - Одобрение даёт только владелец: команда `bb orchestrator approve <KEY>` (вызов из треда с ролью плагина отклоняется как `approval-owner-only`).
6. **Роль и уровень `architect` (слово владельца 18.11):**
   - Сильная модель (у владельца: Opus 5.5 / Gemini 3.8 Pro). Два узла: `design` (проектирование до кода, формирование договора приёмки) и `design_check` (проверка соответствия архитектуре перед выкладкой).
   - Архитектор не имеет операционных команд раздачи и выкладки — исключён риск «второго координатора».
7. **Уровни `spec` и `research` в политике:**
   - `spec` — отдельный писатель спек (у владельца: Gemini 3.8 High, agy);
   - `research` — исследования (Gemini 3.8 / web-gemini).
   - Тест связи «роль → уровень → маршрут → живая раздача» на каждое соединение при валидации политики.
8. **Договор приёмки до кода (узел `design`):**
   - Формирует архитектор на старте: проверяемые критерии с явными командами верификации и ожидаемым результатом.
   - Код конвейера фиксирует договор в файле `docs/specs/acceptance/<KEY>.md` (путь внутри `docs/`, разрешён в `leaks.allow`), делает коммит и сохраняет `acceptance_sha` в `task_queue`.
   - Закон трёх исходов каждого пункта: прошло, упало, не запускалось; «не запускалось» не считается проходом («неизвестное — не ноль»).
9. **Команды управления очередью (§6):**
   - `bb orchestrator enqueue <KEY> [--priority N] [--mode auto|manual] [--route feature|fix|docs|simple]`
   - `bb orchestrator defer <KEY> --reason "<причина>"` (только владелец)
   - `bb orchestrator reject <KEY> --reason "<причина>"` (возврат на доработку текущего узла)
   - `bb orchestrator resume <KEY>` (возобновление отложенной задачи)
   - `bb orchestrator approve <KEY>` (одобрение перехода в `manual`)
   - `bb orchestrator run-queue [--once] [--json]`
10. **Порядок реализации срезами (за флагом `workGraph`):**
    - Флаг проекта `workGraph`: `off` (по умолчанию), `shadow` (пассивный режим: журнал и БД пишутся, команды работают без блокировок), `strict` (строгий режим переходов).
    - Срезы 5а (таблицы, transitions, CLI run-queue в `shadow`), 5б (репетиция с подставными агентами), 5в (автопереходы и будильник за флагом), 5г (`approvalMode`, архитектор, договор приёмки).

## Последствия

- Поручения владельца не теряются после сжатия контекста: дорожная карта и очередь — записи базы, а не текст хендоффа.
- Простой становится событием: будильник узла будит ответственного и эскалирует владельцу; зависание координатора видно и по простою задачи.
- «Готово» — по договору приёмки, а не по слову агента; плавающий критерий исключён.
- Конвейер выкладки защищён: запуск `release` от `run-queue` валидируется через `coordinator_thread_id`, заметка формируется автоматически.
- Цена: два вызова сильной модели на задачу полного маршрута (`design` + `design_check`) и ревью по цепочке; для простых задач — легковесные маршруты без архитектора.
