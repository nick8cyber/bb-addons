# ADR-0032: Граф работы задачи кодом (ревизия 34, уточнения r34.1)

## Контекст

Аудит координатора за 16–18.11 (материалы аудита координатора в KB `projects/bb-orchestrator-work-graphs-plan.md`) показал: координатор, ведущий задачу «в голове», теряет поручения владельца (четыре пункта без спеки и задач), простаивает часами (6 часов 17.11, повторно 18.11), а спека растёт под уже написанный код (PLUG-293 — 17 отказов аудита, §26 вырос с 6,7 КБ до 18 КБ в ходе исполнения). Плагин был построен как набор инструментов, которые агент вызывает, когда вспомнит: порядок шагов держался на памяти модели, а не на коде.

Ошибка проектирования — та же, что описана в проекте жёсткого графа (KB `projects/bb-orchestrator-graph-architecture.md`): «задачу ведёт модель, а не код». Исправление — перевернуть управление: **задачу ведёт код, агент выполняет работу внутри узла и сдаёт результат**. Принципы взяты из открытой заметки agent-work-graphs (конспект — KB `projects/bb-orchestrator-work-graphs-plan.md`); семь уроков под конкретные провалы трёх дней — раздел 7 аудита координатора. В ревизии r34.1 устранены замечания архитектора (Б1–Б4, Б6, Б7): добавлены ворота владельца перед release в режиме «сам», тумблер ✅/👤 и кнопки в чате, машинный контроль границ маршрутов при сдаче кода, определение режима shadow, со 2-го круга ревью проверяет только прошлые блокеры с авто-исполнением рекомендации архитектора при 1-й блокировке в auto, машинная сверка спеки до ревью и строгое соблюдение универсальности без зашитых имён провайдеров.

## Решения (ревизия 34, спека §27–§32, уточнения r34.1)

1. **Узел задачи — запись в базе, а не текст хендоффа.** Таблица `task_queue` (очередь: `task_key`, `project_id`, `coordinator_thread_id`, `route`, `level`, `node`, `status`, `priority`, `depends_on`, `confirmation_mode`, `branch`, `interaction_id`, `spec_sha`, `acceptance_sha`, `result_sha`, `release_note`, `payload`, 7 изолированных счётчиков: `spec_attempts`, `spec_review_rounds`, `code_attempts`, `check_attempts`, `code_review_rounds`, `design_check_rounds`, `release_attempts`, `entered_at`, `deadline_at`, `node_alarm_at`, `deferred_by`, `deferred_reason`) и неизменяемый журнал `task_transitions` (`task_key`, `from_node`, `to_node`, `from_status`, `to_status`, `actor`, `reason`, `payload`, `created_at`). Единая модель: узел — рабочий этап (`node`), операционное состояние — статус (`status`, включая `cancelled`). Отложить или отменить пункт очереди можно только явным решением владельца.
2. **Детерминированный граф задачи:**
   `start → design → spec → spec_review → [owner_gate] → code → checks → review → design_check → [owner_gate] → release → done`.
   Переход делает только код и только по доказательству: коммит, вердикт ревью, машинные тесты, решение владельца, итог выкладки, таймаут будильника. Маршруты:
   - `feature`: полный путь со всеми узлами (в `manual` со шлюзом `owner_gate` перед кодом и шлюзом `owner_gate` перед выкладкой `release`, Б1; в `auto` — без `owner_gate`);
   - `fix`: в `manual` (Б1) — `start → owner_gate (договор) → code → checks → review → owner_gate (выкладка) → release → done`; в `auto` (Б3) — `start → code → checks → review → release → done` (автономно на старте, с машинной проверкой соблюдения рамок маршрута при сдаче кода по §31.7);
   - `docs`: в `manual` (Б1) — `start → spec → spec_review → owner_gate (выкладка) → release → done`; в `auto` — `start → spec → spec_review → release → done` (с машинной сверкой ссылок на кодовую базу по §31.6, Б7);
   - `simple`: в `manual` (Б1) — `start → owner_gate (договор) → code → checks → review → owner_gate (выкладка) → release → done`; в `auto` (Б3) — `start → code → checks → review → release → done` (с машинной проверкой рамок маршрута при сдаче кода);
   - `research`: `start → research → done` (без кода и выкладки).
3. **Конвейер `run-queue` (фоновая служба плагина и CLI `bb orchestrator run-queue`):**
   - Фоновый процесс плагина, действующий от лица координатора задачи (`coordinator_thread_id`, роль `orchestrator`). CLI выполняет один такт (`--once`).
   - Автопереходы по событиям: сдача `design` → коммит договора плагином (`acceptance_sha`) → раздача `spec` с `--from <acceptance_sha>` → сдача `spec` (`spec_sha`) со статической сверкой ссылок (§31.6) → автозапуск `spec_review` (по `reviewByLevel["spec"]`) → при OK в `auto` сразу раздача `code` (с `--from <spec_sha>` для feature, с `--from <acceptance_sha>` для fix/simple; спека и договор не теряются!), в `manual` — переход в `owner_gate` → сдача кода (с проверкой границ маршрута для fix/simple по §31.7) → машинный узел `checks` (запуск безопасных тестов и проверок договора из `acceptance_sha` в копии задачи) → при успехе автозапуск ревью по `reviewByLevel` → при `{"verdict":"OK","blockers":0}` → автозапуск `design_check` (для `feature`) → при OK в `auto` → автозапуск `release` (в `manual` — шлюз `owner_gate` перед выкладкой, Б1) → `published` → автоочистка копий `taskCleanup` → взятие следующей задачи из `task_queue`. Для PR-режима: статус `pr_open` до события слияния `on: merged`.
   - Замечания ревью, проверок и выкладки — возврат на доработку новым заходом; потолок — **3 круга**:
     - **Со 2-го круга ревью (Б6):** аудитор проверяет СТРОГО только блокеры прошлого круга; запрещено предъявлять новые блокеры к неизменявшимся частям.
     - **Авто-исполнение рекомендации архитектора при 1-й блокировке (Б6):** при первом достижении порога 3 сервис автоматически запрашивает консультацию архитектора (`tools: []`). В режиме `auto` при наличии конкретной рекомендации (`target: code|spec|design|release` из допустимого подмножества узла и маршрута; при неприменимой цели → `blocked`) она автоматически исполняется один раз кодом конвейера (`payload.architect_auto_applied = true`, сброс счётчиков, перевод в целевой узел со статусом `running`). В статус `blocked` с эскалацией владельцу задача переходит только при повторном тупике (второй раз достигнут порог 3), неприменимой цели либо в режиме `manual`.
4. **Будильник на каждом рабочем узле, включая координатора.** У каждого активного рабочего узла (`design`, `spec`, `spec_review`, `code`, `checks`, `review`, `design_check`, `release`, `research`) — детерминированный срок (`node_policy`). Пассивные состояния ожидания (`owner_gate`, `waiting_release_note`, `pr_open`, `deferred`, `blocked`, `stalled`, `done`, `cancelled`) будильник не взводят. При живом исполнителе в ходе будильник задачу не останавливает до истечения предельного времени хода. Сброс будильника происходит **строго по доказательствам текущего узла этой задачи** (коммит, вердикт, переход); такты `run-queue` и чужие задачи будильник не сбрасывают. Координатор спит, пока задачи идут штатно, и просыпается только по блокировкам (`blocked`, `stalled`, `waiting_release_note`). В §5.6 задачи из `task_queue` при `workGraph ≠ "off"` исключены из автонапоминаний простоя.
5. **Режимы одобрения (`approvalMode`, Б1, Б2, Б3):**
   - `auto`: полная автономность по цепочке до завершения задачи (`done`);
   - `manual` (режим «сам», решение владельца 15.11, Б1): владелец одобряет ТОЛЬКО спецификацию/договор и выкладку на всех маршрутах: шлюз `owner_gate` различается дискриминатором `payload.gate_stage` (`pre_code` перед кодом, `pre_release` перед выкладкой).
   - **Интерфейс (Б2, r34.2):** интерактивный тумблер `[ ✅ Авто ] / [ 👤 Сам ]` в окне чата у тредов с ролью `orchestrator` и `executor`. Область применения: в окне задачи тумблер меняет `confirmation_mode` ТОЛЬКО этой задачи; проектный режим `orchestrator.approvalMode` меняется исключительно тумблером в окне координатора. Переключение тумблера мгновенно меняет режим подтверждения без флагов CLI и правок файлов. Нативные кнопки действий владельца в карточке задачи и панели очереди (`approve`, `reject`, `defer`, `resume`, `dequeue`), исключающие необходимость ручной работы в терминале при штатном взаимодействии.
   - Единое строгое правило «только владелец» (согласованно с §23 п.3): любой вызов команд `approve`, `defer`, `resume` (из `blocked`/`deferred`), `reject` на `owner_gate` и передача флага `--mode` в `enqueue` при наличии переменной окружения `BB_THREAD_ID` (независимо от роли) СТРОГО ОТКЛОНЯЕТСЯ с ошибкой `permission-denied: owner-only`. Доступ разрешён только человеку: CLI без `BB_THREAD_ID` или UI (честная граница по §23.3: tools: [] для всех агентских ролей, проверка BB_THREAD_ID, игнорирование ответов карточки, сквозной аудит в task_transitions).
   - Защита от занижения маршрута без ломки автономности (Б3): задачи агента на `fix`, `simple`, `docs`, получающие режим `auto` по умолчанию маршрута или из настройки `orchestrator.approvalMode`, выполняются полностью автономно до завершения (`done`) без блокировки на старте; защита обеспечивается машинной проверкой маршрута при сдаче кода (§31.7).
6. **Роль и уровень `architect` (§30):**
   - Роль `architect` (сильная модель проектирует на старте и валидирует в конце).
   - Архитектор код не пишет и не коммитит (`tools: []`), сдаёт результаты текстом — исключён риск «второго координатора».
7. **Уровни `spec` и `research` в политике:**
   - `spec` — отдельный писатель спек конвейера;
   - `research` — исследования.
   - При `workGraph: "off"` отсутствие уровней даёт предупреждение, не ломая действующую политику r33; при `workGraph ≠ "off"` — валидируется тестом связи (§27.3).
8. **Договор приёмки до кода, машинные сверки спеки и проверки (`checks`):**
   - Архитектор формирует проверяемые критерии с командами верификации в отчёте; процесс плагина коммитит их через git plumbing в `docs/specs/acceptance/<KEY>.md` в функциональной ветке задачи под автором из git-конфига репозитория (`acceptance_sha`). На `fix`/`simple` плагин коммитит договор при `start` (`acceptance_sha`), и код раздаётся с `--from <acceptance_sha>`.
   - **Машинная сверка спецификации перед ревью (§31.6, Б7, r34.2):** до раздачи ревьюеру плагин автоматически проверяет упоминаемые в спеке пути файлов и имена функций/типов против репозитория. Новые сущности явно помечаются в спеке (`[new]` или раздел `## Новые сущности / New Entities`); всё непомеченное обязано физически существовать в базовом коммите (текстовый поиск в файле без AST и package.json). Невозможность запуска — исход «не запускалось» (не проход). При некорректных ссылках — отказ сдачи `spec-refused: invalid-codebase-reference`. Исполнитель всегда читает из git и коммитит в git (никакой сдачи текстом в оркестраторе).
   - **Машинная проверка границ маршрута при сдаче кода (§31.7, Б3, r34.2):** при сдаче кода на `fix`/`simple` проверяется отсутствие изменений в путях спек, миграций и публичных API (настройки `orchestrator.routeLimits`), а также лимиты диффа (настройки `maxFiles` и `maxLines`, по умолчанию 3 файла и 150 строк). Тестовые файлы (`tests/**`, `**/tests/**`, `**/*.test.*`, `**/*.spec.*`, `**/*_test.*`, `**/__tests__/**` по диалекту §18.5) в объём не считаются. При нарушении — автоматический перевод задачи на маршрут `feature` в узел `design` (перепроектирование архитектором).
   - Защита договора приёмки: писателю спеки и исполнителю кода изменение договора запрещено (проверка diff `acceptance_sha..result_sha`).
   - Машинный узел `checks` перед ревью: считывает договор строго из блоба `acceptance_sha` и запускает в рабочей копии задачи исполнителя `wt/<KEY>-<round>` (сокращённо `wt/<KEY>`) команды из настроенного списка безопасных раннеров (`checks.allowedRunners`) и одобренные владельцем команды договора (`shell: false`, без утилит скачивания пакетов `npx`, `go run` и без шелл-метасимволов). Честная граница (§23.3): запуск в рабочей копии захода `wt/<KEY>-<round>`, очистка секретов окружения, таймаут 300 с с SIGKILL.
   - Закон трёх исходов: прошло, упало, не запускалось; «не запускалось» не считается проходом.
9. **Команды управления очередью (§6):**
   - `bb orchestrator release-note <KEY> "<заметка>"` (передача заметки для waiting_release_note)
   - `bb orchestrator defer <KEY> --reason "<причина>"` (только владелец)
   - `bb orchestrator dequeue <KEY> [--reason "<причина>"]` (снятие задачи с очереди владельцем, архивация ветки в теги refs/tags/archive/<KEY>-cancelled-<ts> и удаление локально и в origin при наличии ветки, статус cancelled)
   - `bb orchestrator enqueue <KEY> [--priority N] [--mode auto|manual] [--route ...] [--level ...] [--acceptance <файл|текст>] [--release-note <текст>] [--depends-on ...] [--force-reset-branch]` (постановка и повторный запуск задачи; сохранение договора в payload.acceptance_text и заметки в release_note; флаг --acceptance и смена договора — только владелец; синхронная проверка невлитой ветки task_queue.branch в enqueue: отказ unmerged-branch-exists без изменения записи, либо синхронная архивация в тег refs/tags/archive/<KEY>-force-reset-<ts> и удаление старой ветки при --force-reset-branch)
   - `bb orchestrator reject <KEY> [--target spec|design|code] --reason "<причина>"` (возврат на доработку со сбросом последующих счётчиков: на `pre_code` для feature дефолт `spec`, для fix/simple строго без `--target` в `deferred`; на `pre_release` дефолт `code`/`spec`; при `blocked`/`deferred` запрещён; недопустимая цель — отказ `target-invalid`)
   - `bb orchestrator resume <KEY> [--target spec|design|code|release] [--reopen]` (возобновление задачи из deferred/blocked/stalled; blocked/deferred — только владелец, с допустимыми целями строго по маршруту)
   - `bb orchestrator approve <KEY> [--comment <текст>]` (одобрение перехода owner_gate владельцем)
   - `bb orchestrator run-queue [--once] [--json]`
10. **Порядок реализации срезами (за флагом `workGraph`):**
    - Режимы `workGraph`: `off` (по умолчанию, совместимость r33), `shadow` (пассивный режим: аудит, БД и зеркалирование действий человека с записью «сделал бы / отклонил бы» в `shadow_eval` для задач очереди и служебной записью аудита с маркерами `'none'` в `task_transitions` для внеочередных вызовов, Б4), `strict` (строгий режим: блокировка прямых delegate/merge/release вне run-queue для любых задач вне очереди (graph-required) и внутри очереди (graph-managed), выкладка строго при node=release, status=running).
    - Срезы: 5а (таблицы, transitions, CLI enqueue/dequeue/run-queue в `shadow`, `PLUG-309`, статус done), 5б (run-queue: автопереходы и матрица §28.1 с чистой функцией переходов Б5, `PLUG-312`, статус done), Спека r34.1 (закрытие блокеров архитектора Б1–Б4, Б6, Б7), 5в (репетиция сквозного пути с подставными агентами перед strict), 5г (автопереходы и будильник за strict), 5д (уровень spec, роль architect, узлы design/design_check), 5е (режим одобрения, тумблер ✅/👤, кнопки в UI).

### Дополнение · обязательная проверка документации

Проверка «спека до кода» размещается на общей границе запуска исполнителя кода. Прямые команды и переходы графа используют один договор и один источник подтверждения. Так режим наблюдения может сохранять ручной путь координатора, а правило документации остаётся обязательным для проекта. При выкладке сохранённый договор проверяется на точном целевом коммите. [Гейт до кода](../specs/orchestrator-graph.md#319-единая-проверка-спецификации-до-запуска-кода) · [Гейт выкладки](../specs/orchestrator-release.md#проверка-принятых-документов)

## Последствия

- Поручения владельца не теряются после сжатия контекста: дорожная карта и очередь — записи базы, а не текст хендоффа.
- Спека не теряется: `code` раздаётся от коммита `spec_sha`, выкладка публикует и спеку, и код.
- Простой становится событием: будильник узла будит ответственного и эскалирует владельцу; пассивные состояния ожидания человека будильник не взводят; сторож §5.6 не спамит при штатной работе очереди.
- «Готово» — по договору приёмки, а не по слову агента; договор защищён от подмены; машинный узел `checks` отсекает сломанный код до ревьюера.
- Одобрение владельца стоит в правильных точках (перед кодом и перед выкладкой в режиме «сам», Б1) и управляется прямо из интерфейса чата (Б2).
- Задачи агента на простых маршрутах не блокируют автономность (Б3), сохраняя надёжный машинный контроль соблюдения рамок.
- Режим `shadow` даёт полную прозрачность и доказательную базу готовности к переходу в `strict` (Б4).
- Конвейер выкладки защищён: запуск `release` от `run-queue` валидируется через `coordinator_thread_id`, пустая заметка при `requireNote: true` переводит задачу в `waiting_release_note` с возможностью передачи заметки через команду `release-note`.

## Решения от 20.11 (PLUG-359, PLUG-360, PLUG-361)

1. **Компактное меню роли и режима одобрения в композере (PLUG-359):**
   Вместо отдельного тумблера и переключателя ролей реализован компактный объединённый селектор `RoleApprovalMenu` в строке действий композера. Единая кнопка-меню отображает текущую роль и статус одобрения (`✅` авто / `👤` сам). Меню содержит две секции: выбор роли треда и выбор режима одобрения (отображается при активном графе для orchestrator и executor).
2. **Проектный режим графа задач (PLUG-361, ADR-0039):**
   Введена настройка `workGraphProjects: { [projectId: string]: "off" | "shadow" | "strict" }`. Проекты вне графа (`off`) полностью изолированы: наблюдатель абсолютно молчит (0 записей в `task_transitions`), прямые действия не блокируются. Режим `strict` в одном проекте не затрагивает другие проекты стенда.
3. **Защита критических настроек от агентов (PLUG-360, ADR-0039):**
   Любое изменение `workGraph`, `workGraphProjects`, `approvalMode` фиксируется в `events` и `command_runs`. Изменения вне меню (`source: 'outside_menu'`) создают карточку владельцу `PluginInteractionRequest` с кнопками `[ Оставить ]` и `[ Вернуть прежнее значение ]`. Прямой вызов из тредов агента (`BB_THREAD_ID`) отклоняется с `permission-denied: owner-only`.
