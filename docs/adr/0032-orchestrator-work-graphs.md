# ADR-0032: Граф работы задачи кодом (ревизия 34)

## Контекст

Аудит координатора за 16–18.11 (`audit-coordinator-2026-11-18.md`, материалы аудита координатора) показал: координатор, ведущий задачу «в голове», теряет поручения владельца (четыре пункта без спеки и задач), простаивает часами (6 часов 17.11, повторно 18.11), а спека растёт под уже написанный код (PLUG-293 — 17 отказов аудита, §26 вырос с 6,7 КБ до 18 КБ в ходе исполнения). Плагин построен как набор инструментов, которые агент вызывает, когда вспомнит: порядок шагов держится на памяти модели, а не на коде.

Ошибка проектирования — та же, что описана в проекте жёсткого графа (KB `projects/bb-orchestrator-graph-architecture.md`): «задачу ведёт модель, а не код». Исправление — перевернуть управление: **задачу ведёт код, агент выполняет работу внутри узла и сдаёт результат**. Принципы взяты из открытой заметки `matveymaslov/agent-work-graphs` (конспект — KB `projects/bb-orchestrator-work-graphs-plan.md`); семь уроков под конкретные провалы трёх дней — раздел 7 аудита координатора.

## Решения (ревизия 34, спека §27–§32)

1. **Узел задачи — запись в базе, а не текст хендоффа.** Таблица `task_queue` (очередь: узел, статус, приоритет, зависимости, политика переходов) и неизменяемый журнал `task_transitions` (`task_key`, `from_node`, `to_node`, `actor`, `reason`, `payload`, `created_at`). Узел вычисляется из журнала; `task_queue.node` — денормализованная копия. Отложить пункт очереди можно только явной записью «отложено владельцем».
2. **Детерминированный граф** `start → design → spec → code → review → release → done`. Переход делает только код и только по доказательству: коммит, вердикт ревью, решение владельца, итог выкладки, таймаут будильника. Одна функция перехода отвечает каждой команде плагина «можно» или отказом со списком допустимого.
3. **Конвейер `run-queue`** (сервис и CLI `bb orchestrator run-queue`): сдача исполнителя (`done`) → автозапуск ревью по `reviewByLevel` → при `{"verdict":"OK","blockers":0}` → автозапуск `release` → `published` → взятие следующей задачи из `task_queue`. Замечания ревью — возврат на `code` новым заходом; потолок — **3 круга**, дальше эскалация к архитектору или владельцу.
4. **Будильник на каждом узле, включая координатора.** У узла — ответственный и срок; молчание и зависание — события с нарастающими напоминаниями и эскалацией (механика сторожа координатора §5.6). Ход агента без вызова инструмента при незакрытом узле — не исход: «вопрос агента — не сдача», узел возвращается в работу.
5. **Режимы одобрения `approvalMode`:** `auto` — полная автономность по цепочке; `self` — явное одобрение владельца перед переходом к следующему узлу. Одобрение привязано к доказательству узла (sha) и принимается только от владельца — вызов из треда с ролью плагина отклоняется.
6. **Роль и уровень `architect`** (слово владельца 18.11): сильная модель (Opus 5.5 / Gemini 3.8 Pro) проектирует на узле `design` и перепроверяет на `design_check` перед выкладкой. Инструментов раздачи и выкладки у архитектора нет — два входа, ноль операционных команд, иначе «второй координатор». На маршрутах `simple`/`fix`/`docs` узлы архитектора пропускаются.
7. **Уровни `spec` и `research` в политике:** `spec` — отдельный писатель спек (по умолчанию Gemini 3.8 High); `research` — фиксация в политике стенда (web-gemini → Gemini 3.8). Тест связи «роль → уровень → маршрут → живая раздача» на каждое соединение: «вычислено, но не подключено» не выпускается.
8. **Договор приёмки до кода** (узел `design`, формирует архитектор): проверяемые пункты с явными командами верификации и ожидаемым результатом. Исполнитель и аудиторы сверяются с договором; три исхода каждого пункта — прошло, упало, не запускалось; «не запускалось» не считается проходом («неизвестное — не ноль»).
9. **Порядок реализации** (по конспекту agent-work-graphs): сначала журнал и очередь в базе, затем репетиция всего пути с подставными агентами, и только затем живые прогоны — код срезами 5а–5г за выключенным флагом `workGraph` (по умолчанию `off`, включение `strict` по проектам).

## Последствия

- Поручения владельца не теряются после сжатия контекста: дорожная карта и очередь — записи базы, а не текст хендоффа.
- Простой становится событием: будильник узла будит ответственного и эскалирует владельцу; зависание координатора видно не только по простою треда, но и по простою задачи.
- «Готово» — по договору приёмки, а не по слову агента; плавающий критерий исключён, ревьюер проверяет покрытие договора.
- Цена: два вызова сильной модели на задачу полного маршрута (`design` + `design_check`) и ревью по цепочке; для мелочей — лёгкие маршруты без узлов архитектора.
- Ограничение: намеренный обход локально не исключить (агент работает под тем же пользователем ОС); жёсткий слой — защита ветки на хостинге и одобрение только от владельца.
