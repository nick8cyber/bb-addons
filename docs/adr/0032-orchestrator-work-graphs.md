# ADR-0032: Граф работы задачи кодом (ревизия 34)

## Контекст

Аудит координатора за 16–18.11 (материалы аудита координатора в KB `projects/bb-orchestrator-work-graphs-plan.md`) показал: координатор, ведущий задачу «в голове», теряет поручения владельца (четыре пункта без спеки и задач), простаивает часами (6 часов 17.11, повторно 18.11), а спека растёт под уже написанный код (PLUG-293 — 17 отказов аудита, §26 вырос с 6,7 КБ до 18 КБ в ходе исполнения). Плагин был построен как набор инструментов, которые агент вызывает, когда вспомнит: порядок шагов держался на памяти модели, а не на коде.

Ошибка проектирования — та же, что описана в проекте жёсткого графа (KB `projects/bb-orchestrator-graph-architecture.md`): «задачу ведёт модель, а не код». Исправление — перевернуть управление: **задачу ведёт код, агент выполняет работу внутри узла и сдаёт результат**. Принципы взяты из открытой заметки agent-work-graphs (конспект — KB `projects/bb-orchestrator-work-graphs-plan.md`); семь уроков под конкретные провалы трёх дней — раздел 7 аудита координатора.

## Решения (ревизия 34, спека §27–§32)

1. **Узел задачи — запись в базе, а не текст хендоффа.** Таблица `task_queue` (очередь: `task_key`, `project_id`, `coordinator_thread_id`, `route`, `level`, `node`, `status`, `priority`, `depends_on`, `confirmation_mode`, `spec_sha`, `acceptance_sha`, `release_note`, `spec_review_rounds`, `check_attempts`, `code_review_rounds`, `design_check_rounds`, `entered_at`, `deadline_at`, `node_alarm_at`, `deferred_by`, `deferred_reason`) и неизменяемый журнал `task_transitions` (`task_key`, `from_node`, `to_node`, `from_status`, `to_status`, `actor`, `reason`, `payload`, `created_at`). Узел вычисляется из журнала; `task_queue.node` — денормализованная копия. Отложить пункт очереди можно только явным решением владельца через пользовательский интерфейс плагина (`PluginInteractionRequest`).
2. **Детерминированный граф задачи:**
   `start → design → spec → spec_review → [owner_gate] → code → checks → review → design_check → release → done`.
   Переход делает только код и только по доказательству: коммит, вердикт ревью, машинные тесты, решение владельца, итог выкладки, таймаут будильника. Маршруты:
   - `feature`: полный путь со всеми узлами;
   - `fix`: `start → code → checks → review → release → done` (без проектирования и спеки);
   - `docs`: `start → spec → spec_review → [owner_gate] → release → done` (без кода и архитектора);
   - `simple`: `start → code → checks → review → release → done`;
   - `research`: `start → research → done` (без кода и выкладки).
3. **Конвейер `run-queue` (сервис и CLI `bb orchestrator run-queue`):**
   - Фоновый сервис плагина, действующий от лица координатора задачи (`coordinator_thread_id`, роль `orchestrator`).
   - Автопереходы по событиям: сдача `spec` → автозапуск `spec_review` (по `reviewByLevel["spec"]`) → при OK в `auto` сразу в `code`, в `manual` — переход в `owner_gate` → сдача кода → машинный узел `checks` (запуск безопасных тестов и проверок договора) → при успехе автозапуск ревью по `reviewByLevel` → при `{"verdict":"OK","blockers":0}` → автозапуск `design_check` (для `feature`) → при OK → автозапуск `release` → `published` → автоочистка копий `taskCleanup` → взятие следующей задачи из `task_queue`. Для PR-режима: переход в `pr_open` до события слияния `on: merged`.
   - Замечания ревью — возврат на доработку новым заходом; потолок — **3 круга**, дальше статус `blocked` и эскалация к архитектору или владельцу.
4. **Будильник на каждом рабочем узле, включая координатора.** У каждого активного рабочего узла (`design`, `spec`, `spec_review`, `code`, `checks`, `review`, `design_check`, `release`, `research`) — детерминированный срок (`node_policy`). Пассивные состояния ожидания (`owner_gate`, `waiting_release_note`, `pr_open`, `deferred`, `blocked`, `done`) будильник не взводят. Сброс будильника происходит **строго по доказательствам текущего узла этой задачи** (коммит, вердикт, переход); такты `run-queue` и чужие задачи будильник не сбрасывают. Координатор спит, пока задачи идут штатно, и просыпается только по блокировкам.
5. **Режимы одобрения (`approvalMode`):**
   - `auto`: полная автономность по цепочке;
   - `manual` (режим «сам»): обязательный шлюз владельца (`owner_gate`) после `spec_review` перед переходом к `code`. Владелец подтверждает коммит спеки и договора приёмки карточкой в интерфейсе (`PluginInteractionRequest`).
   - Защита от обхода: инструменты одобрения исключены из агентских схем (`tools: []`). В CLI серверный контекст не может надёжно гарантировать отсутствие манипуляций субпроцессами агента (§23.3), поэтому в строгом режиме одобрение принимается строго через UI-карточку. Защита от необоснованного занижения маршрута: отклоняется `route-downgrade-refused` и требует подтверждения владельца через UI.
6. **Роль и уровень `architect` (§30):**
   - Роль `architect` (Opus 5.5 / Gemini 3.8 Pro): сильная модель проектирует на старте (узел `design`) и валидирует в конце (узел `design_check`).
   - Архитектор код не пишет и не коммитит (`tools: []`), сдаёт результаты текстом — исключён риск «второго координатора».
7. **Уровни `spec` и `research` в политике:**
   - `spec` — отдельный писатель спек (у владельца: Gemini 3.8 High, agy);
   - `research` — исследования (Gemini 3.8 / web-gemini).
   - При `workGraph: "off"` отсутствие уровней даёт предупреждение, не ломая действующую политику r33; при строгом режиме — валидируется тестом связи (§27.3).
8. **Договор приёмки до кода (узел `design`) и машинные проверки (`checks`):**
   - Архитектор формирует проверяемые критерии с командами верификации в отчёте; сервис `run-queue` коммитит их в `docs/specs/acceptance/<KEY>.md` в функциональной ветке задачи под автором из git-конфига репозитория (`acceptance_sha`).
   - Раздача на узел `code` выполняется с `--from <acceptance_sha>`.
   - Машинный узел `checks` перед ревью: запускает команды из белого списка проекта (`checks.allowedRunners`) и одобренные владельцем команды договора, возвращая ошибки исполнителю без траты токенов аудитора. Произвольные unapproved команды отклоняются.
   - Закон трёх исходов: прошло, упало, не запускалось; «не запускалось» не считается проходом.
9. **Команды управления очередью (§6):**
   - `bb orchestrator enqueue <KEY> [--priority N] [--mode auto|manual] [--route feature|fix|docs|simple|research] [--level complex|medium|simple|spec|research|architect] [--acceptance <файл|текст>] [--release-note "<текст>"]`
   - `bb orchestrator release-note <KEY> "<заметка>"` (передача заметки для waiting_release_note)
   - `bb orchestrator defer <KEY> --reason "<причина>"` (только владелец через UI)
   - `bb orchestrator reject <KEY> --reason "<причина>"` (возврат текущего узла на доработку)
   - `bb orchestrator resume <KEY>` (возобновление отложенной/заблокированной задачи)
   - `bb orchestrator approve <KEY>` (одобрение перехода owner_gate владельцем через UI)
   - `bb orchestrator run-queue [--once] [--daemon] [--json]`
10. **Порядок реализации срезами (за флагом `workGraph`):**
    - Флаг проекта `workGraph`: `off` (по умолчанию), `shadow` (пассивный режим: журнал и БД пишутся, команды работают без блокировок), `strict` (строгий режим переходов).
    - Срезы 5а (таблицы, transitions, CLI run-queue в `shadow`), 5б (репетиция с подставными агентами), 5в (автопереходы и будильник за флагом), 5г (`approvalMode`, архитектор, договор приёмки).

## Последствия

- Поручения владельца не теряются после сжатия контекста: дорожная карта и очередь — записи базы, а не текст хендоффа.
- Простой становится событием: будильник узла будит ответственного и эскалирует владельцу; пассивные состояния ожидания человека будильник не взводят.
- «Готово» — по договору приёмки, а не по слову агента; машинный узел `checks` отсекает сломанный код до ревьюера.
- Одобрение владельца стоит в правильной точке (перед кодом, а не перед выкладкой) и принимается строго через UI плагина.
- Конвейер выкладки защищён: запуск `release` от `run-queue` валидируется через `coordinator_thread_id`, пустая заметка при `requireNote: true` переводит задачу в `waiting_release_note` с возможностью передачи заметки через команду `release-note`.
- Цена: вызовы сильной модели на задачу полного маршрута (`design` + `design_check`) и ревью по цепочке; для простых задач — легковесные маршруты без архитектора.
