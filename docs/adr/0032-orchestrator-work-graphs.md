# ADR-0032: Граф работы задачи кодом (ревизия 34)

## Контекст

Аудит координатора за 16–18.11 (материалы аудита координатора в KB `projects/bb-orchestrator-work-graphs-plan.md`) показал: координатор, ведущий задачу «в голове», теряет поручения владельца (четыре пункта без спеки и задач), простаивает часами (6 часов 17.11, повторно 18.11), а спека растёт под уже написанный код (PLUG-293 — 17 отказов аудита, §26 вырос с 6,7 КБ до 18 КБ в ходе исполнения). Плагин был построен как набор инструментов, которые агент вызывает, когда вспомнит: порядок шагов держался на памяти модели, а не на коде.

Ошибка проектирования — та же, что описана в проекте жёсткого графа (KB `projects/bb-orchestrator-graph-architecture.md`): «задачу ведёт модель, а не код». Исправление — перевернуть управление: **задачу ведёт код, агент выполняет работу внутри узла и сдаёт результат**. Принципы взяты из открытой заметки agent-work-graphs (конспект — KB `projects/bb-orchestrator-work-graphs-plan.md`); семь уроков под конкретные провалы трёх дней — раздел 7 аудита координатора.

## Решения (ревизия 34, спека §27–§32)

1. **Узел задачи — запись в базе, а не текст хендоффа.** Таблица `task_queue` (очередь: `task_key`, `project_id`, `coordinator_thread_id`, `route`, `level`, `node`, `status`, `priority`, `depends_on`, `confirmation_mode`, `approval_token`, `spec_sha`, `acceptance_sha`, `release_note`, `spec_review_rounds`, `check_attempts`, `code_review_rounds`, `design_check_rounds`, `entered_at`, `deadline_at`, `node_alarm_at`, `deferred_by`, `deferred_reason`) и неизменяемый журнал `task_transitions` (`task_key`, `from_node`, `to_node`, `from_status`, `to_status`, `actor`, `reason`, `payload`, `created_at`). Узел вычисляется из журнала; `task_queue.node` — денормализованная копия. Отложить пункт очереди можно только явной командой `bb orchestrator defer <KEY> --reason "<причина>"` от владельца.
2. **Детерминированный граф задачи:**
   `start → design → spec → spec_review → [owner_gate] → code → checks → review → design_check → release → done`.
   Переход делает только код и только по доказательству: коммит, вердикт ревью, машинные тесты, решение владельца, итог выкладки, таймаут будильника. Маршруты:
   - `feature`: полный путь со всеми узлами;
   - `fix`: `start → code → checks → review → release → done` (без проектирования и спеки);
   - `docs`: `start → spec → spec_review → [owner_gate] → release → done` (без кода и архитектора);
   - `simple`: `start → code → checks → review → release → done`;
   - `research`: `start → research → report → done` (без кода и выкладки).
3. **Конвейер `run-queue` (сервис и CLI `bb orchestrator run-queue`):**
   - Фоновый сервис плагина, действующий от лица координатора задачи (`coordinator_thread_id`, роль `orchestrator`).
   - Автопереходы по событиям: сдача `spec` → автозапуск `spec_review` (по `reviewByLevel["spec"]`) → при OK в `auto` сразу в `code`, в `manual` — переход в `owner_gate` → сдача кода → машинный узел `checks` (запуск тестов и команд договора) → при успехе автозапуск ревью по `reviewByLevel` → при `{"verdict":"OK","blockers":0}` → автозапуск `design_check` (для `feature`) → при OK → автозапуск `release` → `published` → автоочистка копий `taskCleanup` → взятие следующей задачи из `task_queue`. Для PR-режима: переход в `pr_open` до события слияния `on: merged`.
   - Замечания ревью — возврат на доработку новым заходом; потолок — **3 круга**, дальше статус `blocked` и эскалация к архитектору или владельцу.
4. **Будильник на каждом узле, включая координатора.** У каждого активного узла — детерминированный срок (`node_policy`). Сброс будильника происходит **строго по доказательствам текущего узла этой задачи** (коммит, вердикт, переход); такты `run-queue` и чужие задачи будильник не сбрасывают. При истечении срока — эскалация. Координатор спит, пока задачи идут штатно, и просыпается только по блокировкам.
5. **Режимы одобрения (`approvalMode`):**
   - `auto`: полная автономность по цепочке;
   - `manual` (режим «сам»): обязательный шлюз владельца (`owner_gate`) после `spec_review` перед переходом к `code`. Владелец подтверждает коммит спеки и договора приёмки карточкой в интерфейсе или через CLI с `--token`.
   - Защита от обхода: инструменты одобрения исключены из агентских схем; вызов `approve`/`defer` доступен только владельцу. Защита от необоснованного занижения маршрута: `--force-route <причина>` либо подтверждение владельца.
6. **Роль и уровень `architect` (§30):**
   - Роль `architect` (Opus 5.5 / Gemini 3.8 Pro): сильная модель проектирует на старте (узел `design`) и валидирует в конце (узел `design_check`).
   - У архитектора нет инструментов изменения кода и раздачи — исключён риск «второго координатора».
7. **Уровни `spec` и `research` в политике:**
   - `spec` — отдельный писатель спек (у владельца: Gemini 3.8 High, agy);
   - `research` — исследования (Gemini 3.8 / web-gemini). При `workGraph: "off"` отсутствие уровня `research` даёт предупреждение, не ломая действующую политику; при строгом режиме — валидируется тестом связи.
8. **Договор приёмки до кода (узел `design`) и машинные проверки (`checks`):**
   - Архитектор формирует проверяемые критерии с командами верификации и коммитит их в `docs/specs/acceptance/<KEY>.md` в функциональной ветке задачи (`acceptance_sha`).
   - Машинный узел `checks` перед ревью: запускает команды верификации договора и тесты проекта машиной, возвращая ошибки исполнителю без траты токенов аудитора.
   - Закон трёх исходов: прошло, упало, не запускалось; «не запускалось» не считается проходом.
9. **Команды управления очередью (§6):**
   - `bb orchestrator enqueue <KEY> [--priority N] [--mode auto|manual] [--route feature|fix|docs|simple|research] [--level complex|medium|simple|spec|research] [--acceptance <файл|текст>] [--force-route <причина>]`
   - `bb orchestrator defer <KEY> --reason "<причина>"` (только владелец)
   - `bb orchestrator reject <KEY> --reason "<причина>"` (возврат текущего узла на доработку)
   - `bb orchestrator resume <KEY>` (возобновление отложенной задачи)
   - `bb orchestrator approve <KEY> [--token <approval_token>]` (одобрение перехода на `owner_gate` владельцем)
   - `bb orchestrator run-queue [--once] [--daemon] [--json]`
10. **Порядок реализации срезами (за флагом `workGraph`):**
    - Флаг проекта `workGraph`: `off` (по умолчанию), `shadow` (пассивный режим: журнал и БД пишутся, команды работают без блокировок), `strict` (строгий режим переходов).
    - Срезы 5а (таблицы, transitions, CLI run-queue в `shadow`), 5б (репетиция с подставными агентами), 5в (автопереходы и будильник за флагом), 5г (`approvalMode`, архитектор, договор приёмки).

## Последствия

- Поручения владельца не теряются после сжатия контекста: дорожная карта и очередь — записи базы, а не текст хендоффа.
- Простой становится событием: будильник узла будит ответственного и эскалирует владельцу; зависание координатора видно и по простою задачи.
- «Готово» — по договору приёмки, а не по слову агента; машинный узел `checks` отсекает сломанный код до ревьюера.
- Одобрение владельца стоит в правильной точке (перед кодом, а не перед выкладкой) и надёжно защищено от подделки агентами.
- Конвейер выкладки защищён: запуск `release` от `run-queue` валидируется через `coordinator_thread_id`, пустая заметка при `requireNote: true` переводит задачу в `waiting_release_note`.
- Цена: вызовы сильной модели на задачу полного маршрута (`design` + `design_check`) и ревью по цепочке; для простых задач — легковесные маршруты без архитектора.
