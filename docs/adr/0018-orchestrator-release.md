# Выкладка через release

Контракт — [спека release](../specs/orchestrator-release.md); связь с политикой и ролями — [спека оркестратора](../specs/orchestrator.md) §2, §13.

## Контекст

Правила выкладки жили в текстах для агентов: координаторы забывали актуализировать спеки, ADR и документы, в коммиты попадали личная почта, пути машины и чувствительные данные, подписи коммитов расходились. Владелец каждый раз перечислял шаги вручную.

## Решения

1. **Единственный путь выкладки — команда плагина `release`.** Конвейер с фиксированным порядком шагов: приёмка → синхронизация ветки → проверки проекта → машинный скан утечек → аудит проверяющим агентом → целевое действие → пост-проверка. Любой провал останавливает выкладку.
2. **Документы правит координатор**, конвейер проверяет, что он это сделал: проверяющий агент сверяет изменения кода со спеками, ADR и документацией; явный отказ — трейлер `Docs-not-needed:` с причиной.
3. **Проверяющий агент — отдельный уровень политики `release-audit` с цепочкой резерва**: модель выбирает пользователь; недоступность одной модели переводит аудит на следующую.
4. **Обычный `git push` отклоняется общим хуком** (глобальный `core.hooksPath` пользователя разработки) без одноразового токена `release`, привязанного к SHA. Локальные хуки репозитория вызываются; репозитории со своим `core.hooksPath` не затрагиваются; служебные репозитории с автопушем исключаются.
5. **Без переписывания истории**: свежая цель вносится слиянием (по умолчанию), force-push запрещён, отказ CI чинится новыми коммитами.
6. **Целевое действие — настройка проекта** (push в ветку или PR в ветку); проекты со своим CI/CD проходят те же проверки и заканчивают PR со строкой `Источник: bb тред …`.

## Последствия

- Выложить без проверок и документов нельзя; правила проверяет машина, а не память модели.
- Плагин зависит от `gitleaks` и `git` на машине; без них `release` отказывает.
- Хук на машине — точка отказа для всех push пользователя: установщик делает опись репозиториев и исключения, есть отключение.

## Исход (12.11)

`release` включён решением владельца: growthhack-social — PR в `dev` с настройкой, согласованной с куратором CI/CD проекта (проверки — хук проекта `scripts/hooks/pre-push` и проверка спек; полный pytest оставлен CI; `allowedTrailers: Co-Authored-By: Claude` убран вечером 12.11 по слову владельца — подписываться Клодом нельзя нигде); остальные проекты с репозиторием — push в основную ветку с их быстрыми проверками и автором из конфига репозитория (без автора — отказ, никого не подставлять). bb-addons — после скрипта проверок изменённых плагинов (включено 12.11: `checks` = `scripts/check-changed-plugins.sh`, `public`, `leaks.allow` = `docs/` + файл фикстур утечек; первые выкладки PLUG-225, 230, 231 прошли через `release`). sales-agent — исключён (слово владельца: там не коммитим). Общий git-хук не установлен.

## Дополнение (r7, 12.11): проект настройки — по репозиторию

Первая настоящая выкладка (bb-addons) отказала `release-excluded`: задача раздана из родительского bb-проекта, чей каталог лежит над репозиторием плагинов, и `release` взял его настройку, а не настройку репозитория. Решение — [спека release §6](../specs/orchestrator-release.md): проект настройки — bb-проект с путём основного каталога репозитория копии исполнителя, иначе проект делегирования. Отвергнуто: продублировать настройку bb-addons в родительский проект — в его каталоге есть и свой репозиторий, и чужие задачи получили бы чужие правила.

## Дополнение (r8, 12.11): проект настройки падает закрыто

Ревью правил r7 нашло: определение проекта настройки при любой ошибке молча брало проект делегирования и искало его заново на публикации — сбой `bb project list` мог снять `excluded`, ослабить утечки до `warn` или сменить цель выкладки. Решение — [спека release §6 r8](../specs/orchestrator-release.md): ошибка — отказ; проект определяется один раз на шаге 1 и хранится в записи выкладки; основной каталог — первая запись `git worktree list`, запасное совпадение — `origin`; неоднозначность — отказ. Фикстуры путей в тестах: отрицательные — префиксы `/home/example/`, `/Users/example/`; положительные — только в файлах фикстур, перечисленных поштучно в `leaks.allow`; сборка строки из частей запрещена (r7 отменено: машиной не отличить выдуманный путь от настоящего). По ревью спеки: ошибка `realpath` чужого пути проекта — не отказ; второстепенные пути не учитываются; совпадение по `origin` — только при явной записи в `projects`.

**Дополнение r10 (12.11, слово владельца).** Выкладка PLUG-237 #9 получила APPROVE, но публикация упала non-fast-forward (координатор запушил документы во время аудита), а после успешной #10 координатор 20 минут ждал сообщения, которого плагин при успехе не шлёт, и перезагрузил плагин из необновлённой копии. Черновик «пересинхронизация без нового аудита» отклонён: ревью спеки нашло обход гейта через переименование в цели и потерю проверки «код ↔ спека», сложность не окупается — non-ff остаётся обычным отказом, координатор не пушит в цель во время своей выкладки. Принято: исход выкладки детерминирован — ровно одна строка координатору на конечный исход; шаги после публикации (ff копии плагинов, перезагрузка изменённых; самоперезагрузка orchestrator передаётся разовой скриптовой автоматизации BB, которая и шлёт итоговую строку) делает конвейер; PR отслеживается сторожем до влития или закрытия без модели; тред аудитора без уведомлений BB, чтобы не было дублей. Обновление плагинов второго пользователя стенда — на хосте по изменению копии владельца (path-юнит), вне плагина.
