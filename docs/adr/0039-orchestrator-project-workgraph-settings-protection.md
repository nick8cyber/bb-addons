# ADR-0039: Режим графа задач на уровне проекта (PLUG-361) и защита настроек от агентов (PLUG-360)

## Контекст

В ходе опытной эксплуатации конвейера графа задач оркестратора (ревизия r34) и анализа работы стенда в режиме аудита `shadow` были выявлены два взаимосвязанных блокера перехода в строгий режим (`strict`):

1. **Блокер перехода в strict — глобальность настройки `workGraph` (PLUG-361):**
   В текущей реализации (`plugins/bb-plugin-orchestrator/server.ts:632-659`, функция `getWorkGraphMode()`) настройка `workGraph` задаётся как единое скалярное поле плагина, общее для всего экземпляра BB. При переключении режима в `strict` функция контроля `assertGraphAllowsDirectAction` (`src/workgraph.ts:294-335`) блокирует любую прямую раздачу (`delegate`), слияние (`merge`) и выкладку (`release`) по любым задачам, отсутствующим в `task_queue`.
   В режиме `shadow` наблюдатель уже зафиксировал коллизию: задача `NET-41` из инфраструктурного проекта `proj_eshr98jkqq` (ведущаяся классическим координатором без очереди) получила отметку `would_reject: graph-required`. В режиме `strict` это приведёт к немедленной остановке работы всех координаторов других проектов стенда, не переведённых на граф задач.

2. **Уязвимость конфигурации — неконтролируемое изменение настроек агентами (PLUG-360):**
   По спецификации §23 настройки плагина оркестратора имеет право изменять исключительно владелец (человек). Однако платформа BB предоставляет доступ к CLI `bb plugin config` любому локальному процессу под тем же пользователем ОС. 20.11 в 16:51 UTC агент исполнительского треда выполнил команду `bb plugin config orchestrator set workGraph shadow` в терминале. Плагин применил изменение на `settings.onChange` без проверки контекста инициатора, без фиксации машинного события в аудите и без уведомления владельца.

## Решения

### 1. Гранулярный режим графа задач по проектам (PLUG-361)

Управление графом задач переводится с монолитного глобального режима на двухуровневую иерархическую схему:

- **Глобальный режим плагина по умолчанию (`workGraph`):**
  Сохраняется в настройках плагина (`'off' | 'shadow' | 'strict'`, значение по умолчанию `'off'`). Служит общесистемным дефолтом для любых проектов стенда, не имеющих индивидуальной настройки.
- **Проектные переопределения (`workGraphProjects`):**
  Вводится словарь сопоставления идентификаторов проектов BB с режимами:
  `workGraphProjects: { [projectId: string]: "off" | "shadow" | "strict" }`
  (настраиваемый в конфигурации плагина). Это **единственный источник режима проекта** (вариант с хранением в `.bb/policy.json` исключён, так как файл репозитория доступен агентам для коммита и позволил бы агенту самостоятельно переключать режим).
- **Алгоритм разрешения (`resolveWorkGraphMode(projectId?: string | null)`):**
  1. Если передан валидный `projectId`, проверяется наличие переопределения в `workGraphProjects[projectId]`. При наличии валидного значения (`'off'`, `'shadow'`, `'strict'`) возвращается оно.
  2. Если переопределение отсутствует — возвращается глобальное значение настройки `workGraph` плагина (по умолчанию `'off'`).
  3. Если `projectId` не передан или задача не привязана к проекту — возвращается глобальное значение `workGraph` плагина (по умолчанию `'off'`).

### 2. Порядок определения проекта задачи (Task Project Resolution) (PLUG-361)

Для определения `projectId` задачи проверка выполняется строго по порядку:
1. **Очередь графа (`task_queue`):** колонка `project_id` (или поле в `payload.project_id`), если задача зарегистрирована в очереди;
2. **Делегирование (`delegations`):** колонка `project_id` из таблицы `delegations` по активному или последнему завершённому делегированию задачи;
3. **Трекер задач (`tracker`):** запрос метаданных задачи через API трекера задач BB (`bb tasks` / `tracker.getTask(key)`), возвращающий `task.projectId`.

Если `projectId` не удалось определить ни по одному из источников 1–3:
- Применяется глобальный режим `workGraph` плагина (по умолчанию `'off'`);
- В журнал плагина логируется предупреждение: `orchestrator: task <KEY> project undetermined; falling back to global workGraph mode (<mode>)`.

### 3. Правило абсолютного молчания наблюдателя при `workGraph: 'off'` (PLUG-361)

Для любого проекта, эффективный режим которого равен `'off'`, наблюдатель **НЕ ПИШЕТ НИЧЕГО** (полная тишина):
- В таблицы `task_transitions` и `task_queue` не добавляется никаких строк;
- Не создаются записи о внеочередных действиях (маркеры `'none'` и `reason: 'task-not-enqueued'`, как было для `NET-41`);
- Вызов конвейера теневой оценки `shadow_eval` не производится;
- Накладные расходы на аудит для проектов вне графа строго равны нулю. Наблюдатель зеркалирует действия (`recordShadowAction`) ТОЛЬКО для проектов, находящихся в режиме `shadow`.

### 4. Изоляция проектов в `strict` (PLUG-361)

Нахождение проекта `A` (например, `proj_at84bcu8q7`) в режиме `strict` **СТРОГО НЕ ВЛИЯЕТ** на работу координаторов и агентов других проектов стенда:
- Контрольная функция `assertGraphAllowsDirectAction` перед проверкой вычисляет `projectId` задачи (по порядку раздела 2) и запрашивает эффективный режим проекта через `resolveWorkGraphMode(projectId)`.
- Если проект задачи находится в `'off'`: прямые вызовы `delegate`, `merge`, `release` выполняются штатно без проверки очереди графа и без ошибки `graph-required`.
- Если проект задачи находится в `'shadow'`: прямые вызовы выполняются штатно и зеркалируются в аудит `task_transitions`.
- Блокирующий отказ `graph-required` (или `graph-managed`) генерируется **ИСКЛЮЧИТЕЛЬНО** для задач тех проектов, чей режим разрешён в `'strict'`.

### 5. Защита критических настроек (PLUG-360)

Настройки `workGraph`, `workGraphProjects` и `approvalMode` относятся к критическим параметрам безопасности конвейера.

1. **Разграничение прав (owner-only):** изменение настроек разрешено **исключительно владельцу** (человеку) из интерактивного интерфейса чата (селектор в композере, карточки `PluginInteractionRequest`) либо из терминала при отсутствии активного треда агента (переменная `BB_THREAD_ID` отсутствует).
2. **Разрешение меню владельца в окне треда:** выбор режима одобрения и режима графа в меню плагина из окна треда разрешён (интерфейсный вызов из окна чата владельца). Команды смены режимов (`setProjectApprovalMode`, `setTaskConfirmationMode`) отсутствуют в наборе инструментов агентов, поэтому меню владельца работает беспрепятственно.
3. **Детекция смены настроек (своя смена vs смена вне меню):**
   - При `settings.onChange` платформа BB не передаёт `threadId` и не различает инициатора (терминал, агент, UI). Плагин не делает ложных утверждений об агенте в аудите;
   - «Своей» плагин считает только смену, пришедшую из его собственного интерактивного меню: перед записью настройки меню выставляет короткоживущую метку/токен намерения (TTL 5–10 с);
   - Любая другая смена критических настроек (`workGraph`, `workGraphProjects`, `approvalMode`) классифицируется как изменение вне меню: порождается машинное событие `settings_changed_outside_menu`.
4. **Машинная запись и карточка владельцу (без терминальных команд):**
   - При возникновении события `settings_changed_outside_menu`:
     1) **Машинный аудит:** плагин фиксирует структурированное машинное событие в таблице `events` с типом `settings_changed_outside_menu`: `{ setting, oldValue, newValue, timestamp }` и логирует в `command_runs`;
     2) **Интерактивная карточка владельцу:** плагин создаёт карточку `PluginInteractionRequest` с текстом «⚠️ Настройка <setting> оркестратора изменена вне меню плагина (было: <oldValue>, стало: <newValue>)» и ровно двумя интерактивными кнопками:
        - `[ Оставить ]` — подтверждает новое значение настройки и закрывает карточку;
        - `[ Вернуть прежнее значение ]` — возвращает значение `oldValue` в настройки плагина и закрывает карточку.
     Никаких команд в терминале для владельца не требуется.

## Требования к верификации и тестам

1. **Тест молчания наблюдателя при `off`:** прямой вызов `delegate` / `merge` / `release` по задаче проекта с `workGraph: 'off'` (при наличии другого проекта в `shadow`/`strict`) оставляет таблицу `task_transitions` неизменной (0 новых записей).
2. **Тест невлияния проекта в `strict` на другие проекты:** стенд сконфигурирован с проектом `A` (`strict`) и проектом `B` (`off`). Прямой вызов `bb orchestrator delegate` по задаче проекта `B` без постановки в очередь проходит успешно; вызов по задаче проекта `A` блокируется с отказом `graph-required`.
3. **Тест задачи с неопределённым проектом:** задача, чей проект не определён ни в очереди, ни в делегированиях, ни в трекере, разрешает режим из глобального `workGraph` плагина и записывает предупреждающую строку в журнал.
4. **Тест меню владельца:** настоящий интерфейсный вызов из меню окна треда (`setProjectApprovalMode`, `setTaskConfirmationMode`) успешно изменяет режим проекта (`orchestrator.approvalMode`) и режим задачи (`confirmation_mode` в `task_queue`).
5. **Тест смены вне меню:** изменение настройки без метки меню генерирует событие `settings_changed_outside_menu` в `events` и создаёт карточку с двумя кнопками.
6. **Тест кнопки возврата:** нажатие кнопки `[ Вернуть прежнее значение ]` восстанавливает `oldValue` в настройках плагина.
7. **Тест кнопки подтверждения:** нажатие кнопки `[ Оставить ]` сохраняет новое значение настройки.
8. **Тест CLI-защиты:** попытка прямого вызова команды смены настроек из процесса с `BB_THREAD_ID` отклоняется с ошибкой `permission-denied: owner-only`.
