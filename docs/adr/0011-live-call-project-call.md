# ADR-0011. Звонок по проекту

## Контекст

Владелец хочет голосом работать внутри проекта: соцсети, CRM (клиенты, оплаты), инфраструктура (только чтение) и другие. У каждого такого проекта будет свой MCP-коннектор. Грузить в один звонок ручки всех проектов нельзя: контекст разбухнет, модель начнёт путать проекты.

Проверено 03.11 на ключах AI Studio, `gemini-3.8-live` (`research/probes/context-update.mjs`, `resume-swap-tools.mjs`):
- `contextUpdate` — замена инструментов посреди сессии: `v1beta` — 3 прогона, `v1alpha` — 1 прогон; новый инструмент модели не виден, старый вызывается;
- переподключение с тем же handle и новым `setup`: память разговора сохраняется, инструменты остаются прежними;
- новые инструменты появляются только в новой сессии без handle.

Значит, на AI Studio набор инструментов задаётся при старте сессии и до конца не меняется.

## Решение

1. **Звонок по проекту** — отдельный вид звонка, как звонок по треду (ADR-0009). Одна сессия `gemini-3.8-live` (ADR-0006, пересмотр 2). Инструменты и инструкция проекта задаются при старте и не меняются.
2. **Реестр проектов со звонком хранится в плагине звонка** (настройки плагина). Агенты на хосте технически могут менять настройки через `bb plugin config`, поэтому любое изменение реестра действует только после подтверждения владельцем кнопкой в настройках и со следующего звонка (контракт §15.2; голосом — нет: реестр меняется редко). Для каждого проекта:
   - коннекторы: команда или адрес MCP, имена секретов, для каждой ручки **предельный класс** (R / C / P / L);
   - класс по умолчанию для ручки, которой нет в реестре: C или P, не R.
3. **Из репо проекта берётся только текст**: `.bb/live-call/PROMPT.md` — инструкция по проекту и, по желанию, `tools.json` с предложенными классами. Сервер применяет **более строгий** из классов реестра и репо. Команды запуска, адреса и секреты из репо не читаются никогда. Иначе агент проекта мог бы снять подтверждение с ручки записи или подсунуть свою команду.
4. **Только чтение** (например, инфра) обеспечивает реестр: разрешены только ручки класса R, остальные не объявляются модели.
5. **Входы в звонок — универсальные, без зависимости от других плагинов:**
   - действие «Позвонить по проекту» в панели нового треда (`experimental_newThreadPanelAction`): её открывает и родной «+» проекта BB, а контекст действия содержит `projectId`;
   - команда «Live Call: позвонить по проекту» с выбором проекта.
   
   Иконка телефона слева от «+» в строке проекта — **необязательная** добавка в `bb-plugin-sidebar-collapse`. Он рисует её, только если плагин звонка установлен и проект есть в реестре. Без него ничего не ломается, просто нет этой иконки.
6. **Звонок по треду в проекте из реестра** получает те же ручки проекта по тому же реестру и классам (контракт §15.4 п. 7).
7. **Переключение проекта посреди звонка** — пока не делаем. В TODO: новая сессия с инструментами другого проекта плюс выжимка разговора от сервера, пауза ~1 с.

## Последствия

- В каждом звонке только ручки одного проекта: точнее выбор, меньше контекст.
- Безопасность в одном месте: реестр, `ConfirmationGate`, секреты — на стороне плагина.
- Вопрос «что во всех проектах» остаётся за обычным звонком координатору.
- ADR-0010 (коннекторы, PLUG-100) — коннекторы подключаются к звонку по проекту по этому реестру, а не ко всем звонкам сразу.

## Отвергнуто

- **Все коннекторы в одном звонке** — контекст разбухает.
- **Подгрузка ручек на лету** (`contextUpdate`, переподключение) — на AI Studio не работает (проверено). Вернуться, если Google включит.
- **Диспетчер `project_open` / `project_call`** — работает, но ручки проекта модель видит как аргументы одного общего вызова, а не как настоящие инструменты; точность ниже. Запасной вариант.
- **Описание коннекторов и классов в репо проекта** — его правят агенты проекта; граница доверия должна быть у владельца.

## Пересмотр 04.11

- Подтверждение изменений реестра — только кнопкой, со следующего звонка; голосом — нет (реестр меняется редко).
- Ревью сервера (PLUG-109) — НЕ ОК; до исправлений §16.7 (PLUG-112) реальные проекты в реестр не вписывать.
- Секреты коннекторов — одной секретной настройкой `projectSecrets`; модули — `src/mcp-client.ts`, `src/project-registry.ts`.
- Граница защиты подтверждения реестра (проверено 04.11): RPC `projectCallsApprove` доступен и через `bb plugin rpc call` из shell, поэтому агент на хосте подтверждает реестр сам. Кнопка защищает только канал звонка. Варианты и решение — контракт §15.2 п. 4, на решение владельца.
- Делегирование подтверждения (слово владельца 04.11 «сам делай»): реестр первого реального проекта вписывает и подтверждает куратор звонка — кнопкой в окне настроек, не командой RPC. Исполнители проектов реестр не трогают (контракт §15.2 п. 4).
- Первый реальный коннектор (04.11): MCP-сервер проекта уже был (stdio, ручки с двухшаговыми записями). Для звонка: отдельный токен агента, классы ручек в реестре, `PROMPT.md`/`tools.json` в репо проекта; сеть хост BB → прод проекта — решение владельца. Схемы со скалярным объединением со строкой переводятся в `string` (§14.4). Двухшаговые ручки (§14.10) — в работе, до них они в реестре не объявляются.
