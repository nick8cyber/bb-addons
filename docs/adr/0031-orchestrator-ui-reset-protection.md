# ADR-0031: Защита от сброса UI при параллельной выкладке

## Контекст

При параллельной разработке и выкладке нескольких задач одного плагина, затрагивающих пользовательский интерфейс (UI: фронтенд-скрипты, стили, разметку), возникает риск затирания незамерженных изменений. Если задача B выкладывается в целевую ветку `origin/<target>`, не включив в себя коммиты параллельной задачи A того же плагина (находящейся на этапе `in_review`), публикация ветки задачи B сбрасывает интерфейс на стенде к состоянию без изменений задачи A.

Ручной контроль со стороны координатора ненадёжен (особенно при автономной ночной работе). Требуется строгая программная защита на уровне конвейера оркестратора.

## Решения (ревизии 33.5, 33.6; задача PLUG-279, спека §24.2)

1. **Таблица `plugin_staged_features` в SQLite плагина (§7, §24.2):**
   - Поля: `task_key` (PK), `project_id`, `plugin_name`, `branch_name`, `result_sha`, `ui_touched` (1/0), `ui_files` (JSON-список изменённых путей интерфейса), `status` (`in_review | merged | dropped`), `dropped_reason`, `created_at`, `updated_at`.
   - При завершении захода исполнителя (`status = 'done'`) плагин проверяет диф захода. Если затронуты файлы интерфейса (шаблоны, CSS, TSX/JSX, каталоги `ui/`, `static/`, `public/`), выставляется `ui_touched = 1`, а список файлов фиксируется в `ui_files`. Запись создаётся со статусом `in_review`.

2. **Гейт выкладки `unmerged-ui` (release §2 шаг 0.1, r33.5/r33.6):**
   - На самом раннем этапе выкладки (шаг 0.1, до дорогостоящего запуска платного аудитора) оркестратор определяет затрагиваемые плагины выкладываемой ветки.
   - Выполняется запрос к `plugin_staged_features` по каждому из затронутых плагинов для всех записей в статусе `in_review` с `ui_touched = 1`.
   - Запись задачи A не блокирует выкладку задачи B, только если:
     а) `result_sha` задачи A покрыт опубликованным релизом (`git merge-base --is-ancestor <result_sha> <published_sha>` = 0);
     б) `result_sha` задачи A является предком публикуемого HEAD (`git merge-base --is-ancestor <result_sha> HEAD` = 0) — то есть задача B подтянула изменения задачи A;
     в) `result_sha` задачи A уже присутствует в целевой ветке назначения `origin/<target>` (`git merge-base --is-ancestor <result_sha> origin/<target>` = 0) — синк выкладки подтянет её автоматически.
   - Если ни одно из условий не выполнено, выкладка останавливается с отказом:
     `release-refused: unmerged-ui: в плагине <plugin> есть незамерженные UI-фичи (<tasks>), файлы: <files>`
     с подсказкой влить изменения или использовать `--force-drop-unmerged`.

3. **Снятие блокировки через `--force-drop-unmerged`:**
   - Если незамерженная задача признана неактуальной или заброшенной, владелец/координатор передаёт флаг `--force-drop-unmerged <причина>`.
   - Причина логируется в аудит-пакете релиза и сохраняется в таблице `releases` (колонка `dropped_unmerged_reason`).
   - После успешной публикации релиза статус сброшенных записей в `plugin_staged_features` переводится в `dropped` с сохранением `dropped_reason`.

4. **Фиксация вливания (`merged`):**
   - При успешном слиянии через `bb orchestrator merge` или выкладке через `bb orchestrator release` статус записи задачи в `plugin_staged_features` переводится в `merged`.

## Последствия

- Исключён риск случайного затирания чужого UI при независимой параллельной разработке задач одного плагина.
- Блокировка точечная: проверяются только задачи того же плагина с `ui_touched = 1`. Бэкенд-задачи и задачи других плагинов не задерживают конвейер.
- Дедлоки исключены наличием явного механизма сброса через `--force-drop-unmerged`.
- Гейт срабатывает на шаге 0.1 до запуска проверок и аудита релиза, экономя время и ресурсы.
