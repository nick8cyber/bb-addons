# orchestrator — встроенная база знаний (KB), команды CLI, MCP-инструменты и интеграция с release

## Контекст

1. **Разрозненность и забывчивость (инцидент 16.11):** База знаний стенда жила в отдельном bash-скрипте `~/.local/bin/kb`, управляющем git-репозиторием KB (`~/.bb/kb` / `~/kb`). Агенты в инциденте 16.11 правили файлы в KB обычными файловыми инструментами (`edit_file`, `write_file`) в обход утилиты `kb`. В результате правки оставались незакоммиченными в локальном дереве, а `kb sync` не отправлял их в GitHub-зеркало (второй хост не видел обновлений).
2. **Флаг `--kb` в `orchestrator release` не писал в KB:** В конвейере выкладки параметр `--kb <note>` сохранял строку только в локальную SQLite-таблицу `releases` и передавал в чат, но физически в репозиторий KB ничего не записывал и не вызывал синхронизацию.
3. **Отсутствие на других установках:** При развёртывании плагина `orchestrator` на новых машинах (у других пользователей, в контейнерах) утилиты `kb` нет — её требовалось настраивать вручную в `~/.local/bin/kb`.

## Решение

Встроить управление базой знаний (KB) непосредственно в плагин `bb-plugin-orchestrator` как универсальную подсистему (`src/kb.ts`):

1. **Настройка `kb` в плагине оркестратора:**
   ```json
   {
     "kb": {
       "enabled": true,
       "path": "~/.bb/kb",
       "autoSync": true,
       "requireCleanOnRelease": true
     }
   }
   ```
   По умолчанию `path`: `~/kb` (если каталог существует на диске) либо `~/.bb/kb`.

2. **Единое сервисное ядро (`src/kb.ts`):**
   Все операции CLI и MCP выполняются через единый сервис с обязательными инвариантами безопасности:
   - **Изоляция путей (Path Traversal):** канонический путь вычисляется внутри `<kb.path>`, запрещены `..`, внешние симлинки и любые обращения к каталогу `.git/` (отказ `kb-refused: forbidden-path`).
   - **Скан секретов:** записываемый контент проверяется шаблонами утечек оркестратора (§22) до записи на диск и коммита (отказ `kb-refused: secret-leak`).
   - **Точечный git add:** строго `git add -- <относительный_путь>`, исключающий случайный захват чужих файлов.
   - **Автоинициализация репозитория (Auto-init):** для операций изменения (`write`, `append`, `sync`, `recordReleaseNote`) при отсутствии каталога `<kb.path>` или отсутствии в нём git-репозитория плагин автоматически создаёт директорию (`mkdir -p`) и инициализирует репозиторий (`git init`), обеспечивая работу на свежих установках. При сбое создания директории или `git init` возвращается ошибка `kb-refused: init-failed`. Операции чтения (`list`, `search`, `read`) и `status` репозиторий не инициализируют; `status` при отсутствии репозитория возвращает отказ `kb-refused: not-a-repo`.
   - **Блокировка (File Lock):** эксклюзивный замок `<kb.path>/.git/orchestrator-kb.lock` на время мутаций (`write`, `append`, `sync`, `recordReleaseNote`) предотвращает гонки между параллельными тредами. По истечении таймаута 30 с операция завершается отказом `kb-refused: lock-timeout`.
   - **Чистота коммитов:** авторство из git-конфига репозитория KB (`user.name`/`user.email`; при отсутствии identity в git коммит завершается ошибкой `kb-refused: commit-failed`), без `--no-verify` и без трейлеров `Co-Authored-By`. При наличии трейлера `Co-Authored-By` в сообщении коммита (`--message` или заметка `--kb`) операция отклоняется отказом `kb-refused: forbidden-trailer` до создания коммита, до записи файла на диск и до `git add` (дерево и индекс остаются чистыми).
   - **Отказы git-операций:** сбой любой git-команды при выполнении операций базы знаний завершается детерминированным отказом `kb-refused: <операция>-failed` (или `sync-conflict` при конфликтах rebase): `add-failed` (`git add`), `status-failed` (`git status`), `commit-failed` (`git commit`), `rev-parse-failed` (`git rev-parse`), `log-failed` (`git log`), `remote-failed` (`git remote`), `sync-conflict` (rebase conflict), `sync-failed` (`git push` или сбой сети/авторизации).

3. **Команды CLI (`bb orchestrator kb`):**
   При отключённой базе (`kb.enabled: false`) любая команда CLI завершается отказом `kb-refused: kb-disabled: база знаний отключена в настройках` (код 1, в `--json` поле `error.code: "kb-disabled"`).
   - `bb orchestrator kb list [--json]` — список документов базы знаний (исключая `.git/`). При отсутствии каталога возвращает пустой список.
   - `bb orchestrator kb search <текст> [--query <текст>] [--limit N] [--json]` — полнотекстовый поиск по `.md` файлам (аргумент или флаг `--query`; по умолчанию лимит 50 совпадений). При отсутствии каталога возвращает пустой список.
   - `bb orchestrator kb read <путь> [--json]` — вывод содержимого документа (при отсутствии каталога или файла — отказ `kb-refused: file-not-found`).
   - `bb orchestrator kb write <путь> [--message <msg>] [--file <input>] [--content <text>] [--json]` — атомарная запись файла из пути или флага (ввод через `--content` или `--file`, ввод из stdin не поддерживается; при ошибке чтения `--file` — отказ `invalid-arguments: не удалось прочитать файл --file <file>: <error>`) с созданием каталогов и инициализацией репозитория (`ensureKbRepo`; при сбое — отказ `kb-refused: init-failed`), точечным `git add -- <путь>`, коммитом `kb(<task|thread|cli>): <путь>` (используется `taskKey` задачи вызывающего треда при его наличии, либо `threadId`, либо `kb(cli): <путь>`) и вызовом `sync` при `autoSync: true` (при отсутствии remote `synced: false`; при сбоях git — отказы `add-failed`, `status-failed`, `commit-failed`, `rev-parse-failed`).
   - `bb orchestrator kb append <путь> [--message <msg>] [--file <input>] [--content <text>] [--json]` — добавление в конец документа (ввод через `--content` или `--file`, ввод из stdin не поддерживается; при ошибке чтения `--file` — отказ `invalid-arguments`) с созданием каталога/репозитория (`ensureKbRepo`) и коммитом `kb(<task|thread|cli>): <путь>` (используется `taskKey` задачи вызывающего треда при его наличии, либо `threadId`, либо `kb(cli): <путь>`).
   - `bb orchestrator kb sync [--json]` — `git pull --rebase` + `git push` в upstream с блокировкой и разбором ошибок (при отсутствии каталога инициализирует пустой репозиторий; при отсутствии remote выводит сообщение об отсутствии upstream с кодом 1, в `--json` поле `synced: false`; при сбоях git — `remote-failed`, `sync-conflict`, `sync-failed`).
   - `bb orchestrator kb status [--json]` — статус репозитория KB (`git status --porcelain` и сверка с upstream; при отсутствии каталога или `.git` — отказ `kb-refused: not-a-repo`, автоинициализация не выполняется; при сбое `git status` — `status-failed`).

4. **Инструмент MCP (`orchestrator_kb`):**
   - Единый инструмент MCP с параметрами: `action` (`list` | `search` | `read` | `write` | `append` | `sync` | `status`), `path`, `content`, `query`, `message`, `limit` (по умолчанию 50).
   - **Матрица ролей (RBAC):** роли `executor` и `orchestrator` имеют полный доступ ко всем операциям базы знаний. Для любых других ролей (включая `auditor`, `release-auditor`, `none`, `helper`, `researcher`) вызовы `write`, `append`, `sync` отклоняются с ошибкой `permission-denied: роль <роль> не может изменять базу знаний`. Операции чтения (`list`, `search`, `read`, `status`) разрешены тем ролям, которым выдан инструмент (в базовой схеме ролей — `orchestrator` и `executor`; ролям без инструментов плагина инструмент не выдаётся).
   - При отключённой базе (`kb.enabled: false`) любой вызов инструмента отклоняется с кодом ошибки `"kb-disabled"`.

5. **Интеграция с конвейером `release`:**
   - **Шаг 1 (Приёмка):** при `kb.enabled: true` и `requireCleanOnRelease: true` (по умолчанию) проверяется `git -C <kb.path> status --porcelain`. При наличии незакоммиченных изменений — отказ `release-refused: uncommitted-kb: в базе знаний незакоммиченные файлы (<файлы>)` (при сбое команды `git status` — отказ `release-refused: uncommitted-kb: сбой проверки базы знаний (<ошибка>)`).
   - **Шаг 7 (`postPublish`):** при наличии параметра `--kb "<заметка>"` оркестратор автоматически (независимо от наличия, триггера `on` или пропуска шагов настройки `postPublish` в проекте):
     - при отсутствии каталога KB автоматически выполняет создание директории и `git init` (`ensureKbRepo`; при сбое — `pp.kbWriteFailed` с ошибкой `init-failed`);
     - формирует детерминированный файл `<kb.path>/releases/<YYYY-MM-DD>-<KEY>.md` (дата UTC, шаблон с метаданными задачи, коммита и заметкой);
     - соблюдает идемпотентность: если файл уже закоммичен с идентичным содержимым (в репозитории присутствует коммит `rel(<KEY>): ...` и `git status --porcelain -- <relFile>` пуст), повторный коммит пропускается; при расхождении содержимого (изменённая заметка) или наличии незакоммиченных изменений выполняется коммит `rel(<KEY>): <заметка>`;
     - коммитит: `git commit -m "rel(<KEY>): <заметка>"`;
     - выполняет `kb sync` в upstream KB; при сетевой ошибке синхронизации релиз кода не откатывается, а строка координатору рапортует `KB: записан локально, ошибка синхронизации: <ошибка>` (`pp.kbSyncFailed`); при успехе — `KB: записан релиз releases/<YYYY-MM-DD>-<KEY>.md (синхронизировано)` (`pp.kbSuccess`); при ошибке локальной записи/коммита — `KB: не записано, ошибка: <ошибка>` (`pp.kbWriteFailed`) (при `kb.enabled: false` с параметром `--kb` — `KB: не записано, ошибка: kb-disabled`);
     - строка KB в `postPublish` всегда предшествует хвосту перезагрузки интерфейса «обнови страницу BB…».

6. **Обратная совместимость хоста:**
   - Скрипт `~/.local/bin/kb` заменяется на враппер `exec bb orchestrator kb "$@"`.

## Следствия

- Агенты не могут обойти коммит и синхронизацию базы знаний.
- Заметки выкладки фиксируются детерминированно в UTC-файлы `releases/<YYYY-MM-DD>-<KEY>.md` без риска потери кода при сетевых сбоях пуша KB.
- Полная изоляция от path traversal, утечек секретов и гонок параллельных тредов.
- Контракт: [спека orchestrator](../specs/orchestrator.md) §26 (r33.8), [спека release](../specs/orchestrator-release.md) §2 (r11.7).
