# Orchestrator

Контракт — [спека](../specs/orchestrator.md).

## Контекст

Координатор сегодня раздаёт работу тремя командами (`bb tasks dispatch`, `bb thread update --parent-thread … --visibility hidden`, при необходимости `bb thread options --set mode=bypass`), правило маршрутизации живёт текстом в инструкциях агентов, а за зависшими исполнителями следит внешний скрипт в терминале. Каждый шаг агент может забыть; правила по-разному доходят до разных провайдеров. Плагин bb-orchestra (сторонний, без лицензии — берём только идеи) делегирует через собственные треды с явными провайдером и моделью, но не знает про задачи и пресеты.

## Решения

1. **Раздача через `bb tasks dispatch`, а не собственный `threads.spawn`.** Работа у нас идёт задачами: спека в описании, комментарии, статусы, ревью, `bb tasks threads`. У плагина `tasks` нет API привязки треда к задаче — только его CLI. Поэтому `delegate` вызывает `bb tasks dispatch --json` и сразу дописывает родителя и скрытость через `threads.update`, а уведомления родителю — через `bb thread update --parent-notifications auto` (поля нет в типах SDK 0.4.87, сервер его принимает). Цена — окно в доли секунды, когда тред ещё не скрыт; сверка §7 закрывает сбой между шагами. Если `tasks` получит API — переходим на `threads.spawn` с `parentThreadId` и `visibility` при рождении.
2. **Маршрут = пресет.** Модель, провайдер, усилие, права и рабочая копия уже живут в пресетах и проверены; политика ссылается на пресеты и добавляет только то, чего в пресете нет (провайдер для шаблонов квоты, группа квоты, автоперевыпуск). Так нет двух источников правды. Явный `executionInputSources` не нужен: значения приходят из пресета.
3. **Политика — JSON в настройке плагина, значения по умолчанию нет.** Пустая политика — плагин просит настройку через навык `orchestrator-setup`. Частная политика пользователя хранится только в его настройках, в репозиторий не попадает.
4. **Сторож — фоновый сервис плагина на событиях треда**, а не опрос CLI: подписка `experimental_thread.events` + `threads.events.list` по номеру события. Состояние — в SQLite плагина, сверка каждые 60 с, поэтому перезагрузка плагина ничего не теряет.
5. **Автоперевыпуск — свойство уровня, а не провайдера.** Для уровней, где сложное нельзя молча отдавать слабее (complex, review), сторож только снимает и сообщает; перевыпуск решает координатор.
6. **Отчёт исполнителя доставляет BB**, плагин его не пересылает: исполнитель — дочерний тред с `parentNotifications=auto`. Блокирующего ожидания нет.
7. **Плагин — единственный источник правил раздачи** (ревизия 4, решение владельца 08.11): встроенный навык координатора + короткое правило из политики, подача тредам-координаторам включена по умолчанию. На установке с ручными инструкциями раздачи они отключаются после приёмки.
8. **Режим `bypass` для Devin чинится в провайдере**, а не в оркестраторе: это свойство моста ACP, оно нужно и при ручной раздаче. Оркестратор выставляет режим только как страховку.
9. **Старые механизмы — страховка до приёмки**: внешний сторож и автоскрытие работают рядом; плагин следит только за своими делегированиями. Провайдерные «костыли» раздачи (хуки, дописывающие флаги к spawn и привязку после dispatch) удаляются после перехода на `delegate`.
10. **Плагин несёт логику, модели выбирает пользователь** (решение владельца 08.11): готовых профилей и команды генерации пресетов нет. Настройку делает агент пользователя по навыку `orchestrator-setup`: спрашивает о подписках, проверяет модели машины, предлагает уровни и пишет политику.
11. **В оркестраторе нет логики провайдеров.** Требования к провайдеру (права, доставка инструкций, сообщения посреди хода, сигналы квоты) перечислены в спеке §12; пробелы закрываются в плагинах провайдеров (Devin, agy, прочие ACP), а не обходами в оркестраторе.

12. **Роли агента** (решение владельца 08.11): в MVP — `orchestrator` (по умолчанию), `executor`, `auditor` и выбор роли в окне нового чата; свои роли и `researcher` — следующий этап. Роль решает хук `message.dispatch` до подготовки окружения (видит, откуда пришёл тред), источник правды — таблица плагина `thread_roles`; `pluginMetadata.role` только для показа, потому что метаданные может переписать агент треда. Подача — через динамические инструкции с общим бюджетом 4096 символов. Встроенные инструменты провайдера плагин не отключает — роль держится на инструкции и правах пресета.

13. **Правила работы с git — отдельная настройка `gitInstructions`** (решение владельца 08.11): текст добавляется отдельным разделом в каждую раздачу и перевыпуск; значение по умолчанию обезличено, пользователь правит под свой репозиторий.

14. **Снятая у провайдера модель — маршрут недоступен** (решение владельца 09.11): исход `unavailable`, маршрут на 15 минут недоступен, перевыпуск по цепочке уровня (спека §5.3, ревизия 19).

15. **Переход выполнен** (решение владельца 09.11): плагин подаёт правила раздачи сам (`injectInstructions = true`), ручные инструкции раздачи отключены, раздача — только через `delegate`; провайдерные хуки привязки тредов после `spawn`/`dispatch` удалены. Внешний сторож и автоскрытие остаются страховкой до отдельного решения.

16. **Выкладка — отдельный конвейер `release`**, см. [ADR-0018](0018-orchestrator-release.md).
17. **Исход хода с ошибкой, заходы, вливание и уборщик** (ревизии 23–26: заходы, merge, уборщик, ревью по сложности, доставка итога, решения двух аудитов и сквозной проверки), см. [ADR-0024](0024-orchestrator-branches-janitor.md).

## Последствия

- Раздача становится одним вызовом с проверкой лимитов и защитой от двойного запуска.
- Плагин зависит от CLI `bb tasks` (формат `--json` у `dispatch`); изменение формата ломает раздачу — тест на разбор ответа и понятная ошибка.
- Шаблоны квоты — эвристика по тексту ошибок; список расширяем в политике.

**Дополнение r32 (12.11, слово владельца).** Плагин должен быть универсальным: люди ставят его на свои стенды. Разбор нашёл пять мест, заточенных под стенд автора: тексты только по-русски, шаги после выкладки только для раскладки `plugins/<dir>` с перезагрузкой плагинов, PR только через GitHub `gh`, сроки в коде, нет своих действий на события. Решение: настройки `language` (по умолчанию en), `postPublish.commands`/`on`, `prProvider` (github | command | none), `timing`, `eventHooks`; прежнее поведение — значениями по умолчанию; команды и хуки — только из настроек владельца установки, без подстановки данных задач в аргументы. Язык делается последним, чтобы собрать строки остальных задач.

**Дополнение r32 после аудита Fable 5.2 (12.11, по слову владельца — аудит этим исполнителем).** Аудит подтвердил решения, но нашёл недописанные контракты: две спеки противоречили, повтор команд после рестарта, неполный контракт команды PR, неверная модель доверия (настройки может менять любой агент с shell) и неочищенный вывод, нет контракта событий, параллельные задачи с миграциями. Принято: release-спека — единственный контракт выкладки; один запускатель с журналом `command_runs` (не больше одного запуска, прерванные не повторяются); события в таблице `events` в одной транзакции с переходом, история событий не порождает; изменения исполняемых настроек журналируются и сообщаются координатору; вывод маскируется; процесс автора (тексты ролей, тело PR, заметка в базу знаний, строгие умолчания скана) — тоже настройки; задачи строго по очереди.
