# bb-plugin-orchestrator

Раздача задач `bb tasks` на треды исполнителей по политике (спека:
`docs/specs/orchestrator.md`, ADR-0015).

## Что делает

- **Политика** (настройка `policy`, многострочный JSON): уровни с
  цепочками маршрутов по пресетам `bb tasks`, лимиты
  `maxActive`/`perLevel`, квотные группы. Пустая или битая — плагин
  сообщает `needs-configuration`, а `delegate` отказывает.
- **`delegate`** (инструмент `orchestrator_delegate` + CLI): один вызов —
  проверка лимитов, запись делегирования `dispatching` (частичный
  уникальный индекс против двойной раздачи), собственный спаун
  исполнителя (`threads.spawn` с родителем-координатором, `hidden`,
  `parentNotifications=auto` и меткой `pluginMetadata.delegationId` при
  создании — без пробуждения `ownership-assigned`; `bb tasks dispatch`
  остаётся только запасным путём на отказ схемы own-spawn полей),
  привязка задачи (`bb tasks attach`), best-effort `mode=bypass` для
  пресетов `permissionMode=full`, отметка `running`, комментарий
  «Раздано» на задаче. `--no-code` (`noCode` у инструмента) помечает
  делегирование без ожидаемых коммитов (§4.1 r28): исполнителю велят
  только отчитаться — требования раздела §2.2 «коммит/ветка/SHA»
  опускаются (r28.1); сторож не пишет «коммитов нет» и помечает
  появившиеся коммиты; метка едет только перевыпусками сторожа (новый
  `delegate` без флага — обычная раздача), видна как `no-code` в
  `status`/`show` и заставляет `merge`/`release` отказывать «задача без
  кода: вливать нечего», когда последний заход не дал коммитов (r28.1).
- **Раздача только координатору**: инструменты `orchestrator_*` и правило
  маршрутизации получают только треды, чья роль может раздавать
  (`delegates`, §13); `delegate` перепроверяет вызывающего при вызове
  (`not-a-coordinator`).
- **Сторож** (фоновый сервис, §5): окно первого ответа
  (`firstResponseSeconds`) → `stalled` + остановка; определение квоты
  (`errorInfo.category`, затем текстовые паттерны) → `quota`, 15-минутный
  `route_holds` на квотную группу; снятая модель (`thread.start failed`
  до первого хода, паттерны `model not found`) → `unavailable`:
  `stalled`, 15-минутный холд на сам маршрут, без остановки — исполнитель
  не запускался; исходы `done`/`cancelled`/`failed`/`approval`/`timeout`;
  автоперевыпуск ниже по цепочке уровня, когда `autoFallback` разрешает
  (одна транзакция, `reissue_of`, переиспользует шаги §4); сообщения
  координатору через `threads.send` `queue-if-active` с префиксом
  `[orchestrator]`, комментарии на задаче повсюду.
- **`merge`** (инструмент `orchestrator_merge` + CLI, §14): вливает
  `result_sha` завершённого захода в копию координатора после проверок
  §14 (чистый итог, чистая копия координатора, незащищённый приёмник,
  свежий HEAD исполнителя по §16.2, одно вливание на копию). Конфликт
  откатывается в чистую копию; при включённом `mergeAutofix` раздаётся
  заход разбора той же задачи и уровня. В защищённые ветки отказ — ими
  владеет `release`.
- **`release`** (CLI `bb orchestrator release <KEY>`, спека
  orchestrator-release §17.3): единственный путь кода на удалёнку —
  приёмка (включая гейт ревью по публикуемым SHA) → синхронизация ветки
  → проверки проекта → машинный скан утечек (патч каждого коммита, §16.6)
  → агент-аудитор → публикация (`push` или `pr`) → досмотр. Влитый заход
  публикует ветку `merged_into` из копии координатора; остальное — ветку
  исполнителя.
  **Гейт ревью (§17.3 Б4):** публикуемая ветка должна быть проверена —
  вершина ветки исполнителя равна проверенному `result_sha`; коммиты
  выше неё отказывают `unreviewed-commits` (собственные коммиты конвейера
  — sync-merge/трейлеры документации, записанные в строке выкладки, не
  считаются). На ветке `merged_into` OK-ревью, привязанное к ВЕРШИНЕ,
  покрывает всё ниже (включая доки координатора); без него каждое влитое
  делегирование, чей `merged_sha` на вершине и не опубликован, требует
  своего OK-ревью, и ни один коммит не должен остаться необъяснённым.
  Перепроверка новой вершины: `bb orchestrator delegate <KEY> --level
  <аудит> --from <sha>` — `--from <merged_sha>` привязывает ревью к
  влитому итогу.
  **Общие хуки (§17.3 Б2):** `hooks/install.mjs` ставит глобальный
  `core.hooksPath` и обёртку под каждым именем `githooks(5)`, КРОМЕ
  `push-to-checkout` — её наличие отключает встроенное обновление
  worktree при `receive.denyCurrentBranch=updateInstead`; установщик
  убирает обёртку, оставленную старой установкой под этим именем. Теневое
  перекрытие работает и в обратную сторону: пока задан глобальный
  `core.hooksPath`, git читает хуки ТОЛЬКО из него — собственный
  `.git/hooks/push-to-checkout` репозитория всё равно не сработает.
  `pre-push` — гейт оркестратора; остальные — копии `chain`, которые
  exec'ят собственный `.git/hooks/<name>` репозитория — только когда он
  исполняемый, как и сам git. Общий `pre-push` — **страховка от
  забывчивости, а не жёсткий гейт**: он останавливает случайный
  `git push` разовым токеном `push-token-*.json` (связка ветка+sha), но
  агент под тем же пользователем может записать токен сам — для жёсткого
  гейта нужна защита ветки на хостинге (обязательные проверки);
  `orchestrator-setup` её предлагает. Установщик берёт каталог токенов
  из `bb orchestrator hooks-dir` (каталог данных плагина) — переопределяется
  флагом `--hooks-dir`; без флага и без рабочего `bb` отказывает с
  подсказкой, а не гадает путь. Чужой глобальный `core.hooksPath`
  отказывает ДО копирования файлов. После обновления плагина
  перезапустите `hooks/install.mjs` — `release` откажет `hook-stale`,
  когда обёртка отсутствует, отличается от плагиновой или остался
  снятый `push-to-checkout`. `threadIds` (включено по умолчанию)
  разрешает маркер id треда в теле PR из шаблона `prBody` (по умолчанию
  `BB-Thread: {thread}` / `BB-Task: {task}`) и выводит `thr_…` из
  правила утечек bb-ids; выключено — `prBody` не применяется, тело
  пустое, и каждый `thr_…` — находка `leaks.bbIds` (см. «Тело PR»).
  `allowedTrailers` / `allowedEmails` (§17.3 С6) выводят совпадающие
  трейлеры коммитов (например `Co-Authored-By`) и адреса/домены почты
  из правил `foreign-bot-trailer` / `personal-email` машинного скана.
  Не выведенные чужие ботовые трейлеры идут по `leaks.trailers` (§18.6):
  `block` | `warn`, по умолчанию `warn` — установка автора явно ставит
  `"block"`. Проверка подписи `commitIdentity` (§18.6) имеет четыре
  исхода: ключа нет вовсе → находка подписи только предупреждает и
  `bb orchestrator status` сообщает «автор коммитов не задан»;
  разрешённая подпись (литерал `Имя <email>` или `"repo"`, отвеченный
  конфигом репозитория) блокирует каждый коммит с иной подписью;
  `"repo"` без `user.name`/`user.email` в конфиге репозитория отказывает
  «в конфиге репозитория не задан user.name/user.email», а литерал,
  который не разбирается, отказывает «commitIdentity не удалось
  разобрать». Досмотр (§2 шаг 7) без конфига выкладки держит строгие
  умолчания до §18.6 — там находка подписи тоже блокирует. Секреты
  (категория 1) блокируют всегда. `leaks` проекта сливается с
  `defaults.leaks` по ключам (как `timing`), не заменяя его целиком.
  Проект настроек (спека release §6 r8) — bb-проект репозитория копии
  исполнителя, разрешается один раз на шаге 1 и пишется в строку
  выкладки (`settings_project_id`); любая ошибка разрешения отказывает
  (`release-settings-unknown` / `release-settings-ambiguous`).
  Тестовые образцы утечек — `tests/fixtures/leak-samples.ts` (перечислены
  в `leaks.allow`), негативные — на `/home/example/`.
  **Детерминированный исход (§2 r10):** одна выкладка на
  репозиторий+цель (охраняется `repo_root` строки выкладки), одна
  строка исхода на выкладку — успех, находки досмотра и итог
  postPublish складываются в неё. Строка пишется в запись (`notice_text`)
  до отправки и хранится до доставки (`notified_at`): повтор насоса
  пересылает сохранённый текст — он не перезапускает досмотр,
  postPublish и `automation create`. Пропавший тред координатора — не
  вечный повтор: текст ложится комментарием на задачу, и доставка
  подтверждается. У аудита 30 минут от первой раздачи; ревьюер или
  аудитор, закончивший ход без вердикта, получает ОДНО напоминание,
  второй ход без вердикта завершает заход без OK (выкладка аудитора
  отклоняется «аудит без вердикта»). Для целей `pr` насос проверяет PR
  через `prProvider` (`gh pr view` для `github`, `view` для `command`;
  `none` — без слежения) каждые `timing.prPollMinutes` (5): влит →
  «PR влит» + задача done, закрыт → одна строка +
  `timing.prReopenWatchHours` (72 ч) на переоткрытие-вливание, open
  `timing.prStaleHours` (72 ч) → одна строка «PR висит 72 ч»,
  `timing.prErrorLimit` (3) сбоя провайдера подряд → одна строка
  «слежение невозможно». `postPublish` (`{checkout, branch?,
  reloadPlugins}`) перематывает настроенную копию после push и
  перезагружает изменённые плагины — каталоги с изменённым манифестом
  требуют `npm ci`, провайдеры с идущими ходами откладываются, а плагин
  оркестратора перезагружает себя разовой скриптовой автоматизацией
  (сам себя перезагрузить не может).
- **Сверка** (§7): при старте сервиса и каждые 60 с — перечитывает треды
  и события после `last_seq`, доводит оборванные шаги §4.4–4.6,
  перепривязывает `dispatching` строки по метке
  `pluginMetadata.delegationId` под координатором (`threads.list` +
  запасной поиск по заголовку/createdAt — кандидаты с меткой другого
  делегирования пропускаются; `bb tasks threads` — последнее средство
  для каждой строки: запасные строки и дор30-строки без метки) или
  удаляет их, переживает перезапуски без двойных перевыпусков.
  `bb orchestrator reconcile` запускает проход немедленно.
- **CLI**: `delegate`, `status`, `show`, `cancel`, `merge`, `policy
  show|validate`, `instructions`, `reconcile`, `release`, `janitor`,
  `hooks-dir`.

## Роли

Три встроенные роли (§13.1): `orchestrator` (по умолчанию, единственная
с `delegates: true`), `executor`, `auditor`. Роль — это текст инструкции
плюс инструменты и навыки плагина, доступные треду.

- **Выбор**: окно нового чата получает выпадающий список «Роль»
  (`composer.customize`, область нового треда); выбор хранится по
  проекту в `pending_roles`.
- **Решение**: хук `message.dispatch` решает роль один раз, на первом
  сообщении треда, и пишет её в `thread_roles` — источник истины
  (`pluginMetadata.role` — только отображение). Треды, которых хук не
  видел, откатываются на критерий §3: нет родителя и нет меток
  исполнителя → координатор.
- **Ограничения** (§13.2 п.5, §13.3): плагин выдаёт и удерживает только
  свои инструменты — встроенные провайдера (правка файлов, shell)
  управляются режимом прав пресета. Текст роли доходит до агента,
  только если провайдер доставляет инструкции BB; на провайдере без
  доставки роль идёт без текста (agy на ACP-мосту доставляет её;
  `acp-devin` восстанавливает инструкции после сжатия через
  `provider-devin`).

## Настройка

Готовых наборов моделей нет — настройка это проход, который агент делает
с пользователем через навык `orchestrator-setup` (§2.1): инвентаризация
провайдеров, отображение пресетов на уровни и цепочки запасных, запись
политики, валидация.

- `language` (`en` | `ru`, по умолчанию `en`, §18.1) — язык всех текстов
  для людей и агентов: сообщения координатору, вывод CLI и инструментов,
  инструкции исполнителю («задача без кода», «Заход N»), правило
  маршрутизации, памятка git по умолчанию, отказы хука `pre-push`.
  Строки лежат в каталогах `src/i18n/<язык>.ts`; ключа нет в выбранном
  языке — берётся английский вариант с предупреждением в журнал.
  Машинные контракты не переводятся: JSON вердикта, коды ошибок, имена
  настроек и полей, маркеры `prBody`, метки журналов. Значение
  `gitInstructions`, совпадающее со встроенным текстом любого языка,
  считается значением по умолчанию и выводится на текущем языке; своё
  значение идёт как есть, пустое выключает раздел. Плагин объявляет
  набор навыков текущего языка (`orchestrator-coordinator`/
  `orchestrator-setup` или их `-ru` пары) и переписывает установленный
  хук `pre-push` при смене языка — его тексты версионированы вместе с
  языком. Описания инструментов и справка CLI регистрируются при
  загрузке — после смены `language` обновляются по `bb plugin reload`.
- `policy` (многострочный JSON, §2) — уровни, цепочки маршрутов, лимиты,
  квотные группы. Пустой или битый → `needs-configuration`, `delegate`
  отказывает.
- `gitInstructions` (§2.2, ≤ 1500 символов) — раздел «Работа с git»,
  добавляемый в начало инструкций каждой раздачи («Additional
  instructions» стартового промпта); пустое значение выключает его.
- `injectInstructions` (по умолчанию включено) — выключение глушит все
  порождаемые плагином тексты; инструменты и `orchestrator-setup`
  остаются.
- `roleTexts` (многострочный JSON, §18.6) — `{orchestrator|executor|
  auditor: "…"}`: текст, ДОБАВЛЯЕМЫЙ к встроенной инструкции роли (не
  замена). Обязательные части плагин дописывает сам — запрет
  `sudo`/пакетов/изменений хоста у `orchestrator`/`executor` и строгая
  строка JSON-вердикта у `auditor` — `roleTexts` не может их убрать;
  `release-auditor` не настраивается. Составной текст должен укладываться
  в 2500 символов на роль — проверяется на реальных подстановках
  (`handoffPath`, имя уровня ревью из политики); битый документ или
  переполнение сообщается как needs-configuration и игнорируется целиком.
  Если поздние подстановки (смена политики, `handoffPath`) вырастят текст
  сверх лимита при использовании, дополнение для этой отрисовки
  отбрасывается — обязательный хвост не режется.
- `handoffPath` (§18.6, по умолчанию `$BB_THREAD_STORAGE/HANDOFF.md`) —
  путь файла хендоффа, подставляемый в правило хендоффа текстов ролей и
  напоминание о сжатии §16.5; одна строка до 256 символов — многострочное
  или слишком длинное значение отказывается при записи, сохранённое
  битое игнорируется (действует дефолт) со строкой needs-configuration.
  Запасной `~/.cache/bb-handoff/<тред>.md` для провайдеров без
  `$BB_THREAD_STORAGE` остаётся встроенным.
- `userThreadPlugins` (§17.1, через запятую/пробел) — id плагинов, чьи
  треды продолжают чат человека (хендофф сессии, сжатие чата) и держат
  роль координатора. По умолчанию ПУСТО — тред, рождённый плагином,
  получает роль `none`, если его id не перечислен. На обновлении
  сохраняется только явно ЗАПИСАННОЕ значение — задайте его до
  обновления (`bb plugin config orchestrator set userThreadPlugins
  "handoff external-compact"`), а не полагайтесь на прежний дефолт схемы.
- `release` (многострочный JSON, orchestrator-release §6) — настройка
  выкладки: `commitIdentity`, `defaults` и переопределения по проектам
  (`target`, `sync`, `checks`, `public`, `docsMap`, `leaks`, `excluded`,
  `threadIds`). Пустое — `release` отказывает (конвейер выключен).
- `mergeAutofix` (по умолчанию выключено, §14/§16.6) — при конфликте
  вливания раздаётся заход исправления на ту же задачу и уровень;
  выключено — конфликт только сообщается координатору.
- `maxConcurrentCommands` (§18.2, по умолчанию 4) — потолок
  одновременно идущих команд журнала (postPublish и хуки событий).
- `retentionDays` (§18.2, по умолчанию 30) — записи `command_runs` и
  `events` старше этого срока вычищаются.
- `eventHooks` (многострочный JSON, §18.5) — хуки событий
  `[{name, on, run, projects?, timeoutSec?, notifyOnFail?}]`; подробнее —
  «Хуки событий (`eventHooks`)» ниже. Пустое — хуков нет.
- `janitor` (многострочный JSON, §15–16, по умолчанию
  `{"enabled": false}`) — настройка уборщика: `enabled`, `mode
  apply|report`, `afterMerge`, `abandonedAfter`, `intervalMinutes`,
  `excludeProjects`, `protectedBranches`, `deleteBranches`, `scope
  workers|all`. Битый документ предупреждает в журнале и держит
  уборщик выключенным.
- `needs-configuration` снимается только перезагрузкой плагина (SDK V1):
  после исправления настройки — `bb plugin reload orchestrator`.

## Переход с ручной раздачи

По §8: пока инструкции ручной раздачи на месте, держите
`injectInstructions = false`, чтобы правило плагина их не дублировало.
Сам переход — отдельный шаг координатора после приёмки: своя политика
через `orchestrator-setup`, `injectInstructions = true`, инструкции
ручной раздачи выключены; внешний вотчер может остаться страховкой до
осознанного выключения. Раздачам плагина внешний вотчер не нужен — он
рискует двойным перевыпуском.

## Примечания

- Предупреждения о пропавших пресетах — в журнале, `policy show` и
  `policy validate`; проверка идёт при валидации/первом delegate/в фоне —
  никогда синхронно при загрузке плагина.
- **Навыки координатора**: `orchestrator-coordinator` (полная методика
  координатора, §3) и `orchestrator-setup` (§2.1) лежат в `skills/` —
  setup всегда, coordinator только при включённом `injectInstructions`.

## Уборщик: восстановление

Перед каждым удалением уборщик записывает SHA удаляемого в базу
(`janitor_items.tip_sha`) и строку в журнал плагина
(`removed branch|copy <репозиторий>:<ветка> at <sha>`; для копии — ещё
её HEAD); `bb orchestrator janitor run`/`report --json` выводят их.
Вернуть удалённую ветку:

```
git -C <репозиторий> branch <ветка> <sha>
```

Восстановление работает, пока `git gc` не убрал объекты — ориентировочно
две недели (стандартный `gc.pruneExpire`). После — ни ветку, ни копию
не вернуть.

Незакоммиченное в грязной копии исполнителя спасается снимком
(`refs/orchestrator/rescue/<тред>[-<N>]`) и при архиве треда, и при его
удалении — в окне ~5 минут до уборки среды BB; каждая попытка пишется в
таблицу спасений и видна в `bb orchestrator janitor report` (в т. ч.
когда строка координатору не дошла). Для итога захода (§4.1
`result_dirty`) неотслеживаемый `node_modules` — каталог или ссылка,
на любой глубине — это воспроизводимое состояние зависимостей, а не
незакоммиченная работа: грязной копией он не считается, любая другая
строка статуса — считается.

Две отчётные пометки отмечают брошенные копии, похожие на уже
опубликованные, — ни одна к удалению не ведёт; обе попадают в
`janitor report` и суточное сообщение координатору с маркером
` (squash?)` или ` (content?)`. `squash-suspect` («похоже, влито
squash; проверьте и удалите вручную») срабатывает, когда дерево копии
по `merge-tree` совпадает с целью, а её коммиты проверку
предок/`patch-id` не прошли; `content-on-target` («содержимое
совпадает с целью; проверьте и удалите вручную») проверяется раньше и
срабатывает, когда `git cherry <цель> <вершина>` не выводит строк «+»
или каждый файл, изменённый вершиной против merge-base, в цели
совпадает с версией на вершине (`--no-renames`,
`--literal-pathspecs`).

## Настройка под свой процесс

После выкладки `release` может выполнить шаги `postPublish`: обновить
настроенную копию, запустить команды через общий запускатель (журнал
`command_runs`), перезагрузить плагины. Полная схема —
`docs/specs/orchestrator-release.md` §6 и `docs/specs/orchestrator.md`
§18; здесь — частые примеры.

> Все команды из этой настройки **исполняет сам плагин с правами BB**.
> Каждый запуск пишется в журнал (argv, cwd, вывод до 300 символов с
> маскировкой секретов) и идёт списком аргументов без shell — `sh -c`
> используется только если вы сами так записали команду. Маскировка —
> страховка от типовых утечек (токены, пароли в URL), а не гарантия:
> секрет в нестандартном виде останется в журнале — не печатайте их.
> Изменение исполняемых полей (`eventHooks`, `postPublish.commands`,
> `checks`, `prProvider` с типом `command`) фиксируется снимком
> доверия и сообщается координаторам с незавершённой работой — не
> включайте хуки и postPublish для настроек, которым не доверяете.
> Хуки и команды выполняются от пользователя BB: агент с доступом к
> shell (и к `bb` CLI) может изменить эти настройки — давать агентам
> shell значит доверять им это.

### Плагин в корне репозитория

`checkout` — любой каталог, не обязательно `…/plugins/<id>`:
перезагружаются плагины, чей `rootDir` в реестре лежит внутри копии и у
которых изменились файлы. `checkout` можно опустить — тогда выполняются
только команды.

```json
{
  "projects": {
    "proj_repo": {
      "postPublish": {
        "checkout": "/home/example/bb-addons",
        "branch": "main",
        "reloadPlugins": true
      }
    }
  }
}
```

### Своё действие после выкладки

`commands` — список `{name, run | command, cwd, timeoutSec, when,
stopOnFail, installsDeps}`: `run` — argv-массив без shell (схема §18.2),
`command` — строка `sh -c`, если shell нужен явно. `cwd: "checkout"` —
каталог копии, иначе путь (относительный — от каталога репозитория);
по умолчанию — `checkout`, если он настроен, иначе основной каталог
репозитория. В env уходят
`ORCH_EVENT` (`release.published` | `pr.merged`), `ORCH_TASK`,
`ORCH_SHA`, `ORCH_BRANCH`, `ORCH_TARGET`, `ORCH_REPO_DIR`:

```json
"postPublish": {
  "on": "published",
  "commands": [
    { "name": "deploy", "run": ["/home/example/deploy.sh", "main"],
      "timeoutSec": 600, "stopOnFail": true },
    { "name": "docs", "command": "mkdocs build",
      "when": ["docs/**", "mkdocs.yml"] }
  ]
}
```

`when` — glob (`*`, `?`, `**`), хотя бы один патч против изменённых
выкладкой путей; `stopOnFail` — падение обязательной команды пропускает
все поздние; `installsDeps` — успешная команда снимает с плагинов
пропуск «изменены зависимости — переустанови вручную».

### GitLab и другие PR-провайдеры

`prProvider` задаётся в слоях `defaults`/`projects`; объект проекта
заменяет объект `defaults` целиком, без слияния по ключам — в отличие
от `timing` и `leaks`. Выбирает, чем открывается и досматривается PR
(§18.3):

- `{ "type": "github" }` — по умолчанию; работает через `gh`. На шаге 1
  выкладки, до аудита, проверяется `gh auth status`.
- `{ "type": "command", "create": [...], "view": [...], "find": [...]? }` —
  свои исполняемые файлы (argv без shell). `create` и `view` обязательны и
  проверяются на шаге 1: файла нет или он не исполняемый — выкладка
  отказывает до аудита. `find` необязателен.
- `{ "type": "none" }` — ветка публикуется, PR не открывается и не
  отслеживается: строка «ветка опубликована …; PR открой вручную»,
  задача `in_review`. `postPublish.on: "merged"` при `none` не сработает
  никогда — настройка предупреждает об этом при чтении.

Контракт `command` (каталог запуска — основной каталог репозитория,
таймаут `timing.prCommandTimeoutSec`): команды провайдера идут тем же
запускателем, что `postPublish.commands` — каждая в своей группе
процессов, по таймауту группе шлётся SIGTERM, затем SIGKILL, так что
зависшая обёртка не подвешивает выкладку и слежение. `create` получает
`ORCH_BRANCH`, `ORCH_TARGET`, `ORCH_TITLE` и тело PR в stdin, печатает
URL (`https?://…` — первая такая строка); ненулевой код — отказ, даже
если URL напечатан. URL с учётными данными (`user:pass@`) — отказ
«PR не открыт: URL с учётными данными», в записи и строки он не
попадает. `view` получает `ORCH_PR_URL`, печатает JSON
`{"state":"OPEN"|"MERGED"|"CLOSED","mergeCommit":"<sha>"|null}`.
`find` получает `ORCH_BRANCH`, `ORCH_TARGET`, печатает URL открытого PR
ветки или пусто; без `find` повторная выкладка задачи переиспользует
`pr_url` прошлой выкладки этой задачи и ветки этим же координатором,
если `view` отвечает `OPEN`. Весь вывод провайдера в строках
координатору проходит ту же очистку и маскировку секретов, что вывод
команд.

GitLab через `command` (пример со скриптами-обёртками над `glab`):

```json
"defaults": {
  "target": { "action": "pr", "branch": "main" },
  "prProvider": {
    "type": "command",
    "create": ["/home/example/tools/mr-create.sh"],
    "view": ["/home/example/tools/mr-view.sh"],
    "find": ["/home/example/tools/mr-find.sh"]
  }
}
```

```sh
# /home/example/tools/mr-view.sh — печатает JSON для слежения
glab mr view "$ORCH_PR_URL" -F json | jq '{
  state: (if .state == "merged" then "MERGED"
          elif .state == "closed" then "CLOSED" else "OPEN" end),
  mergeCommit: .merge_commit_sha }'
```

### Тело PR и заметка в базу знаний

`prBody` (слоёно, по умолчанию `BB-Thread: {thread}\n\nBB-Task: {task}`)
— шаблон тела PR с подстановками `{thread}`, `{task}`, `{title}`. При
`threadIds: false` шаблон не применяется — тело пустое (id треда и ключ
задачи не публикуются, §16.6). Разбор «чей PR» при повторной выкладке —
по маркеру в теле; разбираются только два маркера: `BB-Thread: thr_…`
и прежний «Источник: bb тред thr_…». Свой шаблон с `{thread}` в другом
виде («Thread: {thread}») разбираемого маркера не создаёт — тогда, как
и при `threadIds: false`, «свой PR» определяется по своим записям о
прошлых выкладках этой задачи этим координатором; чужой PR не
трогается (§18.3).

`requireNote` (по умолчанию `false`) при `true` делает `--kb <заметка>`
или `--no-kb <причина>` обязательными: шаг 1 выкладки без одного из
флагов отказывает «нужна заметка: --kb … или --no-kb …».

### Хук в чат

```json
"postPublish": {
  "on": "merged",
  "commands": [
    { "name": "chat",
      "command": "curl -sf -X POST https://chat.example.com/hooks/rel -d '{\"text\":\"released\"}'" }
  ]
}
```

### Хуки событий (`eventHooks`)

Хуки — отдельная настройка плагина `eventHooks` (уровня плагина, не
документа `release`; имя `hooks` занято git-хуками): реакция на
события конвейера, не только на выкладку. Каждое событие пишется в
таблицу `events` в той же транзакции, что и породивший его переход, и
там же сопоставляется с действующими хуками — хук, добавленный или
переименованный после события, по нему не запускается. История до
миграции событий не порождает.

```json
[
  {
    "name": "chat",
    "on": ["release.published", "pr.merged"],
    "run": ["/home/example/tools/notify-chat.sh"],
    "timeoutSec": 120,
    "notifyOnFail": true
  },
  {
    "name": "stalled-watch",
    "on": ["delegation.stalled"],
    "run": ["/home/example/tools/stalled.sh"],
    "projects": ["proj_repo"]
  }
]
```

Поля хука: `on` — виды событий; `run` — argv без shell (каталог
запуска — каталог данных плагина; свой каталог задавайте в команде);
`projects` — необязательный фильтр по проекту события; `timeoutSec` —
120 по умолчанию; `notifyOnFail` — по умолчанию `false`, при `true`
плагин шлёт координатору одну строку «хук name на событие упал:
итог» на серию сбоев — следующая только после успешного запуска этого
хука. «Сбой» — исходы `failed` и `timeout`; `interrupted` после
рестарта плагина («прервана перезапуском») — тоже строка, если
включено.

Имена хуков уникальны (пробелы по краям не считаются) и не должны
содержать управляющих символов (`\x00`–`\x1f`) — дубль или
управляющий символ в имени это ошибка разбора. При любой ошибке
разбора `eventHooks` хуки не запускаются вовсе — события в журнал
`events` продолжают писаться, а сверка доверия видит изменения и с
битым документом. Хук, не читающий stdin, — норма: ошибка записи в
него игнорируется и не роняет плагин.

События v1: `delegation.done` (все уровни, включая ревью; кроме
`release-audit` — его исход это события выкладки), `delegation.failed`,
`delegation.stalled` (`reason`: `stalled`/`quota`), `review.verdict`
(делегирование ревью с прочитанным вердиктом — один раз на
делегирование; `verdict`, `blockers`), `release.published`,
`release.rejected`, `release.failed`, `pr.merged`, `pr.closed`.
Оживлённый тред (`done` → `running` → `done`) порождает
`delegation.done` повторно — с новым id события; пишите хуки
идемпотентными по `delegationId`, если это важно.

Хук получает JSON события v1 в stdin — `{ "version": 1, "event",
"at", "task", "project", "coordinatorThreadId", "delegationId"?,
"level"?, "route"?, "threadId"?, "reason"?, "verdict"?, "blockers"?,
"releaseId"?, "sha"?, "branch"?, "target"?, "prUrl"? }` — и окружение
`ORCH_EVENT`, `ORCH_TASK`, `ORCH_PROJECT`. У событий делегирования
`project` — проект делегирования; у событий выкладки и PR — проект
настройки выкладки (`settings_project_id`), с ним же сравнивается
`projects` хука. Запуск — общим запускателем (журнал `command_runs`,
`source: "hook"`), записи `events` и журнала хранятся `retentionDays`
дней (30).

### Тексты ролей, хендофф и userThreadPlugins

`roleTexts` — дополнение к тексту роли (не замена): ключи только
`orchestrator`, `executor`, `auditor`; обязательные части (запрет
`sudo`/пакетов/хоста, JSON-вердикт аудитора) плагин добавляет сам
после вашего текста, `release-auditor` не переопределяется, итог —
не длиннее 2500 символов. `handoffPath` — путь хендоффа в текстах
ролей и напоминании о сжатии (по умолчанию
`$BB_THREAD_STORAGE/HANDOFF.md`). `userThreadPlugins` — id плагинов,
продолжающих чат человека (по умолчанию пусто).

```json
"roleTexts": "{\"orchestrator\": \"- Отчёты владельцу — по-русски.\"}",
"handoffPath": "/home/example/HANDOFF.md",
"userThreadPlugins": "handoff external-compact"
```

Поведение прежней установки автора сохраняется явными значениями:
`userThreadPlugins: "handoff external-compact"`, `leaks.trailers:
"block"` в `defaults` выкладки, `commitIdentity`, `postPublish.
reloadPlugins: true`, `prBody: "Источник: bb тред {thread}\n\nЗадача:
{task}"` — без них умолчания новой установки (пустой список, `warn`,
нейтральный `prBody`) мягче прежних.

### Таймауты

`timing` в слоях `release` (defaults + projects, слияние по ключам):
`auditTimeoutMinutes` (30), `checksMinutes` (10), `prepareMinutes`
(20), `prPollMinutes` (5), `prStaleHours` (72), `prReopenWatchHours`
(72), `prErrorLimit` (3), `prCommandTimeoutSec` (60),
`commandTimeoutSec` (300), `postPublishWaitMinutes` (30 — срок
только на ожидание: замок копии, очередь команд, удержание
перезагрузки; запущенную команду ограничивает её `timeoutSec`).
Таймауты сторожа — `policy.timing`:
`quotaHoldMinutes` (15), `approvalRepeatMinutes` (10),
`postDispatchGraceMinutes` (5), `bbNotifyWaitSeconds` (120). Значения
вне пределов — предупреждение и дефолт, не ошибка конфига.

## Ограничения

- **Платформа — Linux.** Команды запускаются через `sh` (postPublish
  `command`, свои обёртки) каждая в своей группе процессов — по
  таймауту группе шлётся SIGTERM, затем SIGKILL; уборщик читает
  `/proc/<pid>/cwd`. macOS и Windows не поддерживаются.
- **Внешние программы.** Обязательные: `git` ≥ 2.39 (`patch-id
  --verbatim`, `merge-tree --write-tree`) и `gitleaks` — без него шаг
  машинного скана выкладки отказывает. `gh` — только при
  `prProvider: "github"` (на шаге 1 проверяется `gh auth status`);
  `prProvider: "command"`/`"none"` работают без `gh`. Свои программы —
  `postPublish.commands`, `eventHooks`, `prProvider.command` — по
  настройке.
- **Исполнители на другой машине не поддержаны.** Итог захода
  (`result_sha`, `result_commits`, `result_dirty`), `merge` и спасение
  грязной копии читают worktree локальным `git -C` — среда исполнителя
  должна жить на том же хосте, что и сервер bb с плагином.
- **Без `/proc` уборщик ничего не удаляет.** Проверка «в копии нет
  живого процесса» (§15 п.5) читает `/proc/<pid>/cwd`; на системе без
  `/proc` (например macOS) каждая копия остаётся `process-unknown` —
  прогоны работают, но ничего не снимается.
- **Git ≥ 2.39.** Ниже — `patch-id --verbatim` не существует: уборщик
  отказывает прогон, а `merge --dry-run` — с подсказкой обновить git
  (`merge-tree --write-tree` — с 2.38).
