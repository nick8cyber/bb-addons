## Порядок работы (обязателен)

1. **Спека до кода.** Любая смена поведения — сначала правка `docs/specs/*` (и ADR, если это решение), отдельным документным коммитом, ревью спеки, и только потом код. Исполнитель спеку не правит: расхождение кода со спекой — вопрос куратору.
2. **Ветка от `feat/live-call`** (не от `main`): `git fetch origin && git checkout -B <ветка> origin/feat/live-call`. Коммиты — явными путями (`git add <файлы>`): `node_modules` в worktree исполнителя — симлинк.
3. **Тесты на каждый пункт**, лучше схемой «первый коммит — красные тесты, второй — исправление». Пробы ревьюеров переносить в `tests/` (относительные пути, без `/tmp` и абсолютных путей), а не держать во внешних каталогах.
4. **Ревью до вливания**, после исправлений — повторное ревью того же ревьюера. Ревьюер не правит код.
5. **Вливание в `feat/live-call` — только `git merge --squash`** одним коммитом на задачу: в промежуточных коммитах исполнителей бывают реальные id. После вливания:
   ```bash
   git log -p origin/feat/live-call..HEAD | grep -nE 'call_m[a-z0-9]{6}|thr_[a-z0-9]{10}|/home/' | grep -v thr_test
   ```
   — вывод пустой. Если задачи пересекаются, конфликты сводит куратор, после — пост-интеграционное ревью.
6. **PR не открывать** (PR нужны только в другом проекте владельца): ветку после проверок и ревью вливать в `main` напрямую, по слову владельца; перед вливанием предупредить активных агентов проекта.

## Правила стенда

- **Перед `bb plugin reload|install|config|disable|enable live-call`** — `bb call status | grep -q "звонок: нет" &&`. Перезагрузка рвёт идущий звонок владельца.
- Пока идут голосовые прогоны, плагин не перезагружать и код плагина в рабочую копию, из которой он установлен, не коммитить: прогоны пойдут на разных сборках.
- Сборка: `bb plugin build .` в каталоге плагина. Проверка коннекторов без звонка: `bb call connectors [--project <id>]`.
- Прямые пробы к Gemini — только на ключах тестового пула, не на ключах плагина.
- Поведение звонка (таймеры, фильтры, тексты вставок) не менять сверх задачи и спеки.

## Подтверждение действий — что важно помнить

Самая хрупкая часть — `ConfirmationGate` (§7.1). Правила там детерминированные, у каждого — таблица контрольных случаев в спеке, и тесты `plug-119-*`, `plug-120-*`, `confirmation-gate.test.ts` должны оставаться зелёными. Принятые остаточные риски и почему не иначе — [ADR-0012](../../docs/adr/0012-live-call-voice-confirmation-rules.md). Если ревью находит новый пограничный случай эвристики, не латайте её точечно: сначала опишите правило в спеке с контрольными случаями.

## Коннекторы проектов

Код MCP-коннектора проекта живёт в репозитории самого проекта (например, у CRM — `ops/crm-mcp/server.py` с тестами в его бэкенде). Плагин звонка запускает установленную копию по команде из реестра. После правки коннектора: тесты в репо проекта → установка копии → `bb call connectors --project <id>` → живой звонок. Новая ручка коннектора видна голосу только после строки в реестре проекта (класс) и подтверждения кнопкой в настройках. Приватные детали установок — в базе знаний стенда, не здесь.

## Частые ловушки

- `inputTranscription` от Gemini приходит через ~2 с после речи и без гарантии порядка — время прихода текста не доказывает, о каком аудио он.
- Транскрипт речи модели теряет дефисы (`агентукуратору`), STT иногда пишет русскую речь латиницей.
- Эхо глагола вопроса распознаётся как другая форма того же глагола («запусти» из «Запустить…») — поэтому эхо-фильтр по корням и say класса P без корня «разреш».
- `maskSecrets` применяется ко всем каналам; набор точных значений — только допустимые секреты (§14.1), плюс их JSON-формы (§14.6).
- Ревьюеры в конце иногда ждут разрешения на уборку своих временных файлов — проверить `bb thread interactions list <тред>`.
